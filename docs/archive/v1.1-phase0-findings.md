## STOP CONDITIONS

1. **The sing-box v2ray API is not wire-compatible with qui's existing Xray stats client.** The server registers `/v2ray.core.app.stats.command.StatsService/QueryStats` (service name overridden in `experimental/v2rayapi/stats.go:21-23`), while Xray's generated client calls `xray.app.stats.command.StatsService` and sing-box's generated client calls `experimental.v2rayapi.StatsService`. Both fail with `Unimplemented`; only a custom full-method call works. The plan's “reader that mirrors `core/xray/stats.go`” can mirror the data flow, but cannot reuse the generated client or method name; a sing-box-specific call is required.
2. **sing-box ignores the legacy `pattern` field and duplicates results for overlapping `patterns`.** `Pattern` alone returns every counter; `patterns: ["user>>>", "traffic>>>"]` returned 10 entries including duplicate names. qui's reader rejects duplicate names (`internal/agent/core/xray/stats.go:164-165`), so a multi-pattern reader can fail. Use exactly one non-overlapping pattern, or no pattern. **Extended by 6c:** qui's Xray reader issues two sequential legacy-`pattern` queries when an outbound account exists (`internal/agent/core/xray/stats.go:141-151`); each sing-box response contains every counter, so the append yields 12 entries / 6 duplicate names and `readCounters` fails with `invalid or duplicate core statistic`. A legacy `pattern` with `reset=true` also zeroes inbound/outbound counters, not just user counters.
3. **sing-box per-user counters exist only for names listed in `stats.users`.** A user `u3` that authenticated and transferred 1000 bytes was absent because only `u1`/`u2` were listed. Omitted credentials silently have no user counters. **Clarified by 6c:** creation is lazy; `u2` was listed in `stats.users` but had no counters at all because it transferred no bytes.
4. **sing-box counters are not payload bytes.** They include transport/HTTP header overhead. Measured: u1 down 1,235,173 for 1,234,567 payload (+606); u2 down 2,346,409 for 2,345,678 (+731); u1 up 457,064 for 456,789 (+275). Quotas based on these counters over-count. **Changed by 6d:** Xray 26.3.27 over-counted identically (for 1,234,567 payload: up 129, down 1,235,026 on both cores), so this is a proxy-counter property, not a sing-box defect; quota math over-counts on either core.
5. **Xray `AddRule(shouldAppend=false)` is not atomic on failure.** It resets balancers and rules before validation; missing balancer, duplicate ruleTag or duplicate balancer left `ListRule` empty in the probe. A bad gate can remove all routing and let traffic fall through to the default outbound (not fail-closed). The plan's "atomically replaces" wording is wrong.
6. **Xray `AddRule` takes protobuf, not JSON.** The plan's `user`/`source` keys are valid only in Xray's JSON config layer; a raw JSON `TypedMessage` fails with `proto: cannot parse invalid wire-format data`. The Agent must send `SourceGeoip`/`UserEmail` fields or run the JSON loader. **Resolved by 6a for the JSON-loader route:** official `xray api adrules` calls `serial.DecodeJSONConfig`, builds the router config, and accepted `user`, `source`, `geosite:`, `geoip:`, and the balancer. A custom protobuf client still cannot send raw JSON.
7. **Xray online maps have no expiry.** They are refcounted, keyed by IP only (no port), exclude `127.0.0.1` and `[::1]`, update `lastSeen` on each new connection, and delete the IP immediately when the refcount reaches zero. There is no upstream active window; the panel must compute one. Devices behind one NAT IP are indistinguishable.
8. **Our sing-box build is an upstream non-naive build, not an official release asset.** Official linux amd64/arm64 and Windows amd64/arm64 assets use naive tags (and CGO variants/libcronet); ours uses `DEFAULT_BUILD_TAGS_OTHERS` + `with_v2ray_api`, CGO=0, Go 1.26.10. It is reproducible, but not byte-equal to those assets. (Official Windows 386 is the non-naive exception.)
9. **The claim "the build fails on a dirty checkout" is false.** With an untracked file, `go build` exited 0 and recorded `vcs.modified=true`; upstream Makefile/release scripts do not reject dirty trees.
10. **sing-box's log parser currently drops the source line.** `inbound connection from <ip>:<port>` is silently ignored (`singbox.go:224-233`); an overlay test produced `records=0 rejects=0 poisoned=false pending=0`. Adding source tracking needs code (ID-keyed source join), not just a regex.
11. **Clash API `/connections` has no user field.** Gating by user requires the log parser's connection-ID-to-user map; source IP/port are present and `DELETE` closes TCP/UDP sessions, but the user join is mandatory.
12. **The Xray API is unauthenticated on loopback.** Any local process can AddRule/RemoveRule and alter gating; binding to `127.0.0.1` avoids remote access but is not an authorization boundary.
13. **Xray SOCKS UDP has no user attribution, so a (user, source) gate cannot stop UDP.** 6b: a user+source gate returned `block` in `TestRoute`, but both a new and an existing UDP association still passed; a source-only gate blocked a new association while an existing one kept working. The UDP worker builds `session.Inbound` without `User` (`app/proxyman/inbound/worker.go:361-366`), and the dispatcher caches one outbound conn per association (`transport/internet/udp/dispatcher.go:79-85`). If qui needs per-user UDP gating/accounting, this is a blocker; source-only gating plus association teardown is the only partial control.

`adapter/outbound/tuic.go:55-65` (in `TuicOption`):

```go
SkipCertVerify bool     `proxy:"skip-cert-verify,omitempty"`
NameCertVerify string   `proxy:"name-cert-verify,omitempty"`
Fingerprint    string   `proxy:"fingerprint,omitempty"`
Certificate    string   `proxy:"certificate,omitempty"`
PrivateKey     string   `proxy:"private-key,omitempty"`
SNI            string   `proxy:"sni,omitempty"`
```

How they are used (`component/ca/config.go:88-133`, called tls config for both protocols at
`hysteria2.go:170-180` and `tuic.go:136-146`):

- `Fingerprint` → `NewFingerprintVerifier` (`component/ca/fingerprint.go:14-38`). It strips `:`,
  hex-decodes, **requires exactly 32 bytes (SHA-256)**, and matches **any certificate in the
  chain** against `sha256.Sum256(cert.Raw)` (`fingerprint.go:32`). If a non-leaf matches, that
  certificate is used as the trusted root and the chain is verified with the SNI. So
  `fingerprint:` is a real **certificate SHA-256 pin**.
- `Certificate`/`PrivateKey` → **client certificate** (`GetTLSConfig` sets
  `GetClientCertificate`, `config.go:125-133`); it is **not** a CA.
- There is **no per-proxy inline PEM CA field** for hysteria2/tuic (no `ca`/`ca-str` in either
  struct; a repo-wide search for `ca-str` only finds the OpenVPN `ca` field).
- The only inline/global trust addition is top-level `tls.custom-certifactes`
  (`config/config.go:395-402`, note the upstream typo), read into `CustomTrustCert` and fed to
  `ca.AddCertificate` on every apply (`hub/executor/executor.go:93`). `AddCertificate` accepts
  inline PEM or a file path (`component/ca/config.go:27-46`).
- `name-cert-verify` pins by DNS name using the (system/embedded/global) root pool.

Test with `-t` (`hysteria2.yaml`, `tuic-v5.yaml` above) used a 64-hex `fingerprint:` value:
both passed. A malformed non-SHA-256 value is rejected at startup with
``fingerprint string length error,need sha256 fingerprint`` (source, `fingerprint.go:26`).

**Answer: PARTIAL.** Per-proxy certificate **SHA-256 fingerprint pinning: YES** (`fingerprint:`).
Per-proxy **inline PEM CA: NO**. A global inline CA exists only as
`tls.custom-certifactes` (sic), applied to all TLS outbounds.

### 1d) Hostile proxy names through yaml.v3

`work/yamlquote/main.go` marshals a config with `gopkg.in/yaml.v3 v3.0.1` containing names:

```yaml
name: |-
  newline
  inside
name: 'name: with space'

```

`mihomo -t` on the generated file: **PASS**, exit 0, `test is successful`.

**Answer: YES.** yaml.v3 quoting round-trips all required hostile names and mihomo accepts them,

to keep names unique and avoid commas/`>>>`-style grammar collisions in rule strings.

### 4d) RoutingService dependency and operational risk

`infra/conf/api.go:29-41` maps `RoutingService` to the router command service; the
API listener is the only transport. The router feature must exist in the Xray
config (it does in qui's renderer). Our probe enabled StatsService, HandlerService
and RoutingService together for the other tests; the source shows `RoutingService`
alone registers AddRule/RemoveRule/ListRule/TestRoute, and AddRule does not call
stats or handler. Running with only RoutingService was not isolated in the probe,
so that exact minimal combination is **source-verified, not independently executed**.

`api.listen` is on loopback and has no authentication. Any local process that finds
the port can AddRule/RemoveRule, including removing gates. This is an accepted local
trust boundary for the Agent, but it must be documented; do not expose the API port
off-host.

The plan's §7.4 flow is feasible with these caveats: send protobuf (or convert JSON
first), send the full config including balancers and baseline rules, validate before
apply, use unique `qui-gate-*` ruleTags, and remove by ruleTag. The gate blocks new
TCP immediately and leaves established TCP alone; Xray has no per-connection kill,
so existing sessions drain normally (as the plan states). The non-atomic failure
mode and the JSON/protobuf mismatch are the two changes the plan must absorb.
