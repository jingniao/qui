# K3b panel report — multi-core panel side (2026-10-29)

**Status: panel implementation complete locally; native-core CI, Linux/root,
RC and release acceptance remain pending. Nothing was committed, pushed or run
against a real server or `state/panel.db`.**

This phase implements the seven K3b requirements of
[K3a agent report](v1.2-k3a-agent-report.md) on the panel side: negotiation,
`Inbound.Core`, per-component update tasks, Owner remove-core tasks, node-kind
traffic counters, per-core connection observation, and scoped restart/health
plus backup/route/documentation coverage. Section 8 lists the JSON shapes the
frontend needs.

### Behaviour changes an existing installation will notice

1. **Publishing validates inbounds against the reported core.**
   `validateStateCoresTx` runs for every created revision, batch item and
   rollback, so a revision whose inbound protocol is not advertised by the
   assigned core (or whose core is no longer enabled) is refused at publish time
   instead of failing on the node. The `subscription` WireGuard test recorded its
   capability after publishing and was updated accordingly.
2. **The DB no longer enforces "one enabled inbound per port".** 0125 drops
   `inbound_active_port` because uniqueness must hold across cores; it is
   enforced by `validateInboundPorts` and by `desiredstate.Validate` on the node.
   The message is `inbound port <n> is already used by <id> on this node`.
3. **One active core-update task per node became one per (node, component).** A
   second task for another component is now accepted where it used to be
   `ErrNodeBusy`; a duplicate of the same component is still refused.
4. **A report with one named core but no `multi_core_supported` flag is valid.**
   Such an Agent stays a one-core node. Before this fix the panel closed the
   control stream with `invalid multi-core capabilities`, which broke the local
   fake-core flows and would break any Agent that only decorates its scalar
   capabilities.

## 2. Negotiation and persisted per-core state (requirement 1)

- `Hello.multi_core_supported` (11) and `Hello.node_traffic_supported` (12) are
  negotiated independently; `Welcome.multi_core_supported` (20) and
  `Welcome.node_traffic_supported` (21) answer with what the panel actually
  implements. `node_traffic_supported` is only granted when the panel has an
  `AccessRecorder`, i.e. exactly when a node counter can be ingested.
- `nodes.multi_core_supported` / `nodes.node_traffic_supported` persist the
  negotiated outcome, so an old Agent keeps `multi_core_supported=0`, and a
  database restore resets both to "not reported yet".
- `capabilities_json` stores the whole `Capabilities` message, including
  `cores[]` (`name`, `version`, `protocols`, `singbox_user_stats`,
  `forward_inbound_supported`, `device_gate_supported`, optional `healthy`,
  `observation_contract_version`); `heartbeat_json` stores `cores[]` (`name`,
  `healthy`, `error`, `started_at`, `traffic_source_status`).
- `node.EnabledCores` models a legacy report as exactly one core built from the
  scalar fields and never invents a value: an Agent that reported no core gives
  no cores, and a missing per-core health observation stays absent (`healthy` is
  an optional protobuf field, so it is `null`/absent in JSON, never `false`).
  `Repository.scan` fills `Capabilities.Cores` and `Heartbeat.Cores` for a legacy
  record so the view is uniform.
- `node.SelectedCore(caps, "")` resolves the empty core to `capabilities.core_name`
  (the current primary) everywhere: validation, rendering and D5 coverage.
- `validateMultiCapabilities` accepts at most two cores, refuses duplicate or
  unknown names, refuses two cores without `multi_core_supported`, refuses a
  primary missing from the list, and tolerates the one named core without the
  flag that an Agent produces when it only decorates its scalar capabilities
  (that stays a one-core node). A one-core list whose name contradicts
  `core_name` is refused. Each entry is re-validated through the ordinary
  capability validator, so per-core protocol lists keep their existing rules.
- `validateCoreStatuses` refuses duplicate/unknown core names, unknown error
  codes, an invalid start timestamp or traffic-source status, and a status that
  reports a core error while claiming to be healthy. Both validators run inside
  `validateMessage`, so a malformed report fails the stream with
  `InvalidArgument` instead of storing garbage.

## 3. `Inbound.Core` (requirement 2)

- Storage: `migrations/0125_multi_core_panel.sql` adds
  `inbounds.core TEXT NOT NULL DEFAULT '' CHECK(core IN ('','xray','sing-box'))`.
  The empty string means "the node's current primary core" and is never rewritten
  to a concrete name, so a later primary change keeps following the primary
  exactly like the Agent's `desiredstate.Inbound.Core` contract.
- Paths covered: draft save/update (`proxy.SaveInbound` writes `core` in the same
  statement as the rest of the row), rendering (`snapshot.go` copies `record.Core`
  into `desiredstate.Inbound.Core`), automatic quota revisions (rendered from the
  same snapshot, so the value is inherited, never dropped), user-access
  quick-connect (`deployment/user_access.go` re-saves `Core: existing.Core`),
  canvas/published entries (`canvas_publish_apply.go` keeps the entry inbound's
  core), restore (the column travels in the archive and is validated on load) and
  subscriptions (they read the published snapshot, whose inbounds carry the core).
- Validation on save and on publish (`proxy.ValidateInboundCore`):
  - unknown/absent core -> `selected core is not reported enabled`;
  - a non-empty core on an Agent without `multi_core_supported` ->
    `multi-core unsupported`;
  - protocol matrix per core (`proxy.ValidateCoreProtocol`,
    `desiredstate.CoreSupportFor`) plus the reported `protocols[]` inbound flags;
  - `forward` requires `forward_inbound_supported` on the selected core;
  - WireGuard is refused on sing-box, and gate coverage follows
    `device_gate_supported` of the selected core;
  - node-wide port rule of the Agent: any other **enabled** inbound on the same
    node with the same numeric port conflicts, regardless of core, transport or
    `forward` (that is what `desiredstate.Validate` enforces on the node).
- A component whose add/remove task has not settled is not selectable:
  `node.CoreSelectionIsBlocked` (fed by `decorateCoreSelection` on both `Get` and
  `List`) blocks the name during the save and during the render, failing with
  `core_pending`.
- `core` is a normal field of `Inbound`/`InboundInput`; `httpapi.Decode` keeps
  `DisallowUnknownFields`, so an old panel and a new panel refuse each other's
  unknown field instead of silently dropping it.

## 4. Per-component update tasks (requirement 3)

- Migration 0125 adds `core_update_tasks.adding` and replaces the "one active
  task per node" index with
  `core_update_active_component ON core_update_tasks(node_id,component) WHERE
  status IN ('queued','running')`. Existing rows are not rewritten: 0107 already
  backfilled `component`, and `migrations/multi_core_panel_test.go` proves a
  pre-0125 row keeps its component, that the two components get independent
  slots, and that a duplicate of the same component is refused.
- `Adding` is computed at queue time (`node.SelectedCore(...) == nil`), so the
  panel records an install as an addition without trusting a later report, and
  `core_selectionBlocked` can tell an unfinished addition from a removal.
- `sequence` is allocated per `(node, component)`, so an absent component can be
  installed through the same schema-2 `CoreUpdateRequest` while the other
  component keeps its own history.
- `PendingCoreUpdate` dispatches queued work before re-sending a running command,
  so `xray` and `sing-box` never starve each other while a reconnect still
  re-sends the same `command_id` (never a new identity).
- `CoreUpdateResult` routes by the envelope `component`: an empty or different
  component is refused, the same result is accepted idempotently, a changed
  result is refused, and a cleared task keeps its status and still refuses.
- Selection is only reopened by a fresh capability report:
  `core_selectionBlocked` drops the component once no add/remove task is active,
  and `ValidateInboundCore` still requires the component to be reported enabled,
  so a successful task alone can never fabricate capabilities.

## 5. Owner remove-core tasks (requirement 4)

Table `core_remove_tasks` (0125):

```text
id, node_id, component, revision, status(queued|running|success|rejected|unconfirmed),
code, result_json, created_by, created_at, updated_at
UNIQUE(node_id, component) WHERE status IN ('queued','running')
```

Flow: `POST /api/v1/nodes/{id}/cores/{component}/remove` -> `QueueRemoveCore`
(one transaction) -> `RemoveCoreCommand{id,component,revision}` over the existing
connect loop -> `RemoveCoreResult` validated
(`id`/`component`/`revision`, `success == (code == "success")`), stored once,
`Ack`ed by the ordinary message flow, and re-sent with the same identity after a
disconnect. A late replay is still accepted after the node confirmed a later
revision; a changed component or revision is refused.

Refusals (HTTP 409, `error.code`):

| Code | Meaning |
| --- | --- |
| `core_in_use` | an inbound of the current draft **or** of the published revision still uses the component, including disabled inbounds; `error.inboundIds` lists them |
| `core_pending` | the component is being added/removed, or a deployment/update holds the node |
| `last_core` | the component is the only enabled core |
| `revision_mismatch` | the submitted revision is not the node's currently confirmed revision |
| `unsupported` | the Agent did not negotiate multi-core, or the component is not reported |

The component stays in `capabilities.cores` until a capability report removes it,
so the UI never hides a core the Agent is still running. Owner + CSRF + matching
`confirmNodeId` are required and the operation log records `remove_core` with the
task id. `GET /api/v1/nodes/{id}/cores/{component}/removals` returns the newest
100 tasks of that pair. An unanswered task stays `running` and therefore blocks
new operations on that node/component (`core_pending`), exactly like an
unanswered update task: the Owner can see it in that list, and the Agent answers
it again on the next connection. Deleting the node turns it `unconfirmed`.

Removal is not "delete the binary": the Agent only disables installer-owned
files, and a later verified update re-enables them. Rolling back to a revision
that uses the removed component is refused by the panel with
`rollback refused: inbound <id>: core "xray" is unavailable: …`, because the
Agent would refuse it too (and, after a primary change, an empty-core inbound of
an old revision is ambiguous — publish an explicitly assigned copy instead).

## 6. Node-kind traffic counters (requirement 5)

- Accepted only on a negotiated session: the panel inspects every counter of a
  `TrafficBatch` and rejects the whole batch with
  `FailedPrecondition, "node traffic not negotiated"` when a `kind:"node"` counter
  arrives without `Welcome.node_traffic_supported`.
- `access.ingestNodeCounter` validates `kind == "node"`, the core
  (`xray|sing-box`), `credential_id == "node"`, a `core_epoch` ending in `.node`,
  `revision >= 1` and `0 <= bytes <= 1 PiB`. A counter that does not advance and
  is not newer than the stored observation is an idempotent no-op; a regressed
  counter with a newer observation is a conflict (the batch is rejected).
- Deltas are computed per `(node, epoch, credential)` from
  `node_traffic_cursors` and written to `core_traffic_samples`; batch idempotency
  and `Ack` stay on the ordinary `TrafficBatch` path, so a repeated batch adds
  nothing (`k3b_stream_test.go` sends the same batch twice).
- These bytes never touch `user_traffic_cursors`, quotas or
  `account_traffic_samples`. `node_traffic_samples` (0125) unions
  `core_traffic_samples` with `account_traffic_samples` **only for epochs that
  have no node cursor**, so a core that reports node counters is not counted
  twice. Dashboard totals, `GET /api/v1/traffic/summary` without a user/device
  filter and the monthly per-node aggregation read that view; per-user views keep
  reading account samples only.
- Multiple live epochs per node are kept: nothing retires a peer epoch when
  another core reports, and a restart simply starts a new epoch at zero.

## 7. Per-core connection observation, D5 and scoped commands (requirements 6-7)

- `ConnectionStatus.cores[]` is accepted only on a negotiated session; each entry
  is validated (known core name, no duplicate) and stored volatile per
  `(node, core)` with the existing TTL. An entry whose `snapshot_json` is empty
  carries no measurement and is skipped, so a partially measurable node keeps the
  cores that did report; the legacy `snapshot_json` path still works when no
  per-core entry is present.
- `connections.Store.RecordCores` merges the per-core snapshots before admission:
  connections are summed, credential addresses are unioned and deduplicated,
  `DeviceGateSupported` is the OR, the merged epoch joins the sorted constituent
  epochs and the merged observation time is the earliest. Address keys stay in
  memory only (never stored, logged or backed up) and the existing masking/TTL/
  fail-open behaviour is unchanged. `CoreSnapshots` exposes the individual cores
  for the coverage calculation, with the same TTL.
- `DeviceObserver` evaluates every enabled inbound of the published state against
  the capability of *its* core: an inbound on a core without
  `device_gate_supported`, or a core whose snapshot is missing, marks the node as
  partially enforcing (fail-open) instead of silently claiming D5.
- `proxy.Inbound` exposes `userTrafficSupported` (`null` when the core is not
  reported) and `deviceGateSupported`, both derived from the selected core, so
  official sing-box without `with_v2ray_api` shows per-user bytes as unknown while
  its node aggregate still arrives through node counters.
- Scoped restart and health checks keep their additive `core` field
  (`POST/GET /api/v1/nodes/{id}/restart-core`, `POST/GET …/health-checks`); an
  empty `core` is still a whole-node operation and a named core must be reported
  enabled (`409 core_unavailable` for health, `409 restart_conflict` for restart).
  Historical rollback stays whole-node, and a rollback that needs a removed core
  is refused with the reason above.

## 8. JSON shapes used by the frontend

`GET /api/v1/nodes/{id}` (the `Node` view; existing snake_case plus the K3b
additions):

```json
{
  "id": "n1", "name": "tokyo-1", "status": "online", "enabled": true,
  "coreSelectionBlocked": ["sing-box"],
  "capabilities": {
    "core_name": "xray", "core_version": "26.3.27",
    "multi_core_supported": true, "singbox_user_stats": true,
    "forward_inbound_supported": true, "device_gate_supported": true,
    "cores": [
      { "name": "xray", "version": "26.3.27",
        "protocols": [{"protocol":"vless","inbound":true,"outbound":true,"tcp":true,"udp":true}],
        "singbox_user_stats": false, "forward_inbound_supported": true,
        "device_gate_supported": true, "observation_contract_version": 2 }
    ]
  },
  "heartbeat": {
    "core_healthy": true,
    "cores": [
      { "name": "xray", "healthy": true,
        "started_at": {"seconds": 1761696000, "nanos": 0},
        "traffic_source_status": {"status": "covered", "core_epoch": "native", "revision": 12} }
    ]
  }
}
```

`capabilities.cores` uses the protobuf snake_case field names, like every other
capability field. `heartbeat.cores` is always an explicit array (`[]` when the
Agent reported none) with the same snake_case item shape. `healthy` inside a core
capability is absent unless the Agent sent the optional field;
`coreSelectionBlocked` is always an array (`[]` when nothing is blocked).
`multi_core_supported` is the negotiated value, so a legacy Agent shows `false`
and one core.

Inbound (`GET /api/v1/inbounds`, `POST`, `PUT`):

```json
{ "id":"i1","nodeId":"n1","name":"vless-443","core":"sing-box","protocol":"vless",
  "listen":"0.0.0.0","port":443,"enabled":true,"subscriptionVisible":true,
  "internalRelay":false,"defaultOutbound":"direct","allowedUserIds":[],
  "userTrafficSupported":true,"deviceGateSupported":false,
  "settings":{ }, "createdAt":"…", "hasTlsKey":true, "hasWireGuardKey":false }
```

`core` is `""|"xray"|"sing-box"`; requests accept the same field and reject
unknown JSON fields. `userTrafficSupported`/`deviceGateSupported` are `null`
while the selected core is not reported.

Add/upgrade core tasks (`POST /api/v1/core-updates`, `GET /api/v1/core-updates`):

```json
{ "adding":true,"id":"t1","nodeId":"n1","component":"sing-box","version":"1.14.3",
  "url":"https://github.com/SagerNet/sing-box/releases/download/v1.14.3/sing-box-1.14.3-linux-amd64.tar.gz",
  "sha256":"<64 hex>","sequence":1,"revision":12,"status":"queued",
  "commandId":"upd_…","createdBy":"owner","createdAt":"…","updatedAt":"…",
  "result":{"id":"upd_…","node_id":"n1","revision":12,"status":"success",
            "code":"success","target_digest":"<64 hex>",
            "installed_version":"1.14.3","installed_digest":"<64 hex>",
            "installed_sequence":1} }
```

Request body: `{"nodeId","confirmNodeId","revision","component","version","url","sha256"}`;
`component` is required and `confirmNodeId` must equal `nodeId`. `adding` is
`true` when the component was not reported enabled at queue time. `status` is one
of `queued`, `running`, `success`, `failed`, `failed_closed`, `cleared`.

Remove-core tasks (`POST /api/v1/nodes/{id}/cores/{component}/remove`,
`GET /api/v1/nodes/{id}/cores/{component}/removals`):

```json
{ "id":"r1","nodeId":"n1","component":"sing-box","revision":12,
  "status":"queued","code":"","createdBy":"owner","createdAt":"…","updatedAt":"…",
  "result":{"id":"r1","component":"sing-box","revision":12,"success":true,"code":"success"} }
```

The list response is `{"items":[…]}` (newest first, at most 100). Refusal body:

```json
{"error":{"code":"core_in_use","message":"Core removal refused","inboundIds":["i1","i2"]}}
```

Restart and health history items keep their shape and add `core`:

```json
{"commandId":"c1","revision":12,"status":"pending","code":"","createdAt":"…","core":"xray"}
{"id":"h1","nodeId":"n1","revision":12,"core":"sing-box","status":"queued","createdAt":"…","deadline":"…"}
```

### Install command flags

Fresh node with both cores (`deploy/linux/node-install.sh`, also produced by the
register dialog's install command):

```text
… node-install.sh | bash -s -- --version 1.2.0 --panel panel.example.com \
    --grpc-port 9443 --ca-sha256 <hex> --token <enrollment> --core xray --core sing-box
```

`--core xray|sing-box` is repeatable (default `xray`); `--core-source qui|official`
selects the sing-box source (default `qui`, same release as the Agent).
`install.sh` additionally accepts per-core `--core-version`, `--core-url`,
`--core-sha256` after the `--core` they belong to, plus the global
`--qui-version`. Offline installs use `--core-bundle/--core-sums` on `install.sh`
and `--bundle/--sums` on `node-install.sh`. An upgrade without `--core` keeps
every recorded core — omission never removes a core.

## 9. Backups, restore, route coverage

- `backup.validateMultiCore` runs from `inspect.go`: 0125 must be applied exactly
  when the three new tables exist, `inbounds.core` values must be valid, cursor
  core/epoch/byte bounds are checked, `core_remove_tasks` must use the known
  component/status vocabulary, and no `(node, component)` may have both a pending
  removal and a pending update. A stored removal result must match its row
  (id/component/revision/code and `success`), and both timestamps must parse as
  RFC3339Nano.
- `inventory` counts `core_remove_tasks`, `node_traffic_cursors` and
  `core_traffic_samples` next to the existing totals.
- `deployment.PrepareCoreUpdatesRestoreTx` clears `core_remove_tasks`, copies the
  archive rows and turns every queued/running removal into `unconfirmed` (never
  re-sent); `core_update_tasks` is copied including `adding`. `access` restores
  `node_traffic_cursors` with the other traffic cursors so restored bytes are not
  counted twice.
- `internal/platform/server/testdata/portal_route_coverage.txt` lists
  `POST /api/v1/nodes/{id}/cores/{component}/remove` and
  `GET /api/v1/nodes/{id}/cores/{component}/removals`, and
  `internal/platform/server/k3b_stream_test.go` negotiates, ingests node counters
  and checks the idempotent `Ack` end to end, including the "not negotiated"
  refusal.
