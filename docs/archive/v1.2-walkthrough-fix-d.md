# Walkthrough fix D — canvas scheme array normalization

Date: 2026-10-29. Uncommitted changes only.

## Root cause and observed database state

The K4 compatibility code cloned connections with
`append([]CanvasConnection(nil), connections...)`. For an empty input, including
an explicitly supplied `[]`, this produces a nil slice. Both scheme saving and
server-layout hydration used this pattern, so a new empty scheme was persisted
with `connections:null`, and an older server scheme stored with `connections:[]`
could also be returned with `connections:null`. Go's default JSON encoding then
exposed that nil slice as null.

The frontend called `scheme.layout.connections.map(...)` without a null guard.
One failed mapping aborted the whole list assignment. The canvas caught the
error only to show a toast, then displayed its empty overlay because the current
scheme was absent. This made existing schemes appear missing and encouraged
creating more schemes.

A read-only Node SQLite inspection of `state/panel.db` found four rows: two older
layouts with `instances:[]` and `connections:[]`, and the two reported new rows
with `instances:[]` and `connections:null`. All four `client_published_layout`
values were the empty string, the unpublished sentinel. There is no
`published_layout` column. The scheme response contains the typed layout and
publication metadata; shared tunnels are separate resources and ports are
optional scalar properties. No additional null-array field is needed to explain
the earlier failure: the older server scheme's empty connections were already
changed to nil during hydration. The mapping self-test also covers null legacy
publication/tunnel/port metadata and nullable instance ports.

## Changes

- `CanvasLayout.normalized()` establishes non-nil instances and connections.
  Its encoding method guarantees `[]` for every layout JSON write, including
  scheme create/update, tunnel endpoint projections, and future snapshots.
  Decoding remains strict and rejects unknown fields.
- Stored-layout decoding and K4 hydration normalize both collections in memory.
  Connections are cloned into a non-nil empty slice during save, hydration and
  tunnel preview. Existing rows therefore load correctly without rewriting them.
- Reviewed inline tunnel dehydration and legacy adoption/reconciliation: tunnel
  JSON stores a connection object, while scheme layout writes use the shared
  layout encoder. Server publish bookkeeping updates publication metadata, not
  layout JSON. Client publication now encodes the reviewed layout instead of
  copying historical raw JSON. Client recovery normalizes restored draft and
  publication layouts within its transaction, preserving unpublished sentinels.
- Frontend scheme mapping treats missing/null layout collections as empty arrays.
  The canvas tracks loading and load failure explicitly. A failure covers the
  workspace with the error and a **重试** button, including when stale schemes
  remain in the store. Only a successful empty result shows **暂无中转方案 / 新建方案**.
  Scheme creation is guarded during loading/failure. Both the shared creation
  helper (also used by the node list) and local import send `connections: []`.
- Added Go tests for server/client create and update with omitted, null and empty
  collections; raw storage and HTTP responses; historical null rows through list
  and detail GET; read normalization without database repair; strict decoding;
  client snapshot and restore normalization. Added executable frontend mapping
  and reload-failure/retry checks to the canvas library self-test.

The node list already uses the shared mapping/loading helper, so it receives the
compatibility fix without changing its page or other agents' layout work.

No development database rows were edited or deleted. No migrations, `go.mod` or
`go.sum` were edited, and no commit was made. Existing workspace changes belong
to ongoing work and were retained.
