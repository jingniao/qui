# v1.3.1 发布说明

发布日期：（待发布）。v1.3.1 是 v1.3.0 之上的缺陷修复版本，不新增功能、不改数据模型（**没有迁移**）。预发布版：`v1.3.1-rc.1` → `4889cf3`（GitHub 发布 432337602）、`v1.3.1-rc.2` → `ebe8301`（432510161）；rc.2 已在三台主机上运行，最终版候选为 `ebe8301`。门禁、代码审查与实机（RC-F、RC-G）结果见[验收矩阵](v1-acceptance.md) §12。

**平台：** 与 v1.3.0 相同，构建 linux/amd64 与 linux/arm64；只有 amd64 在真实主机上验收，arm64 只在 qemu-user 模拟下验证，**不是真实 arm64 主机**（[验收矩阵](v1-acceptance.md) §12）。GOST 仍只支持 linux/amd64。

## 主要变化

- **移除核心后清理运行目录：** 确认核心退出后，Agent 同时删除该核心的 `runtime/<组件>/`（运行标记、accounting key、访问日志与临时文件），启动时恢复中断的移除也在 `Close()` 成功后清理。退出未确认（`ErrCoreStopUnconfirmed`）时目录、禁用清单与镜像全部保留，因为该目录正是“没有残留进程”的证据；`cores.json.enc`、更新历史与安装器二进制不受影响。这修掉 v1.3.0“移除 GOST 后节点上留下 `runtime/gost`”的限制。
- **画布发布只重启改动过的服务器：** 发布先整体校验捕获到的全部依赖，再丢弃“只为中继依赖而纳入、且已运行相同配置与相同启用意图”的服务器——它们没有修订、没有部署目标、没有回滚项，因此核心不重启。比较时忽略修订号，用户访问集合按集合比较（空集合等于缺失）。裁剪后的批次允许中继目标不在批内，按该目标当前已发布状态校验依赖；显式中继批次接口（`POST /api/v1/deployment-batches/relay`）仍发布全部成员。改 us2↔uk 的隧道不再重启 alpine 上的 Xray（RC-F 已确认）。另外，**画布自己的服务器在发布时总是重新发布**，即使字段没有变化（跳过只用于“仅为依赖而纳入”的服务器），因此隧道两端的核心仍会重启。
- **画布隧道管理的入站不能在入站编辑器里改名：** 判定按 `canvas_tunnel_objects` 的归属行，不按名字前缀；普通保存改了名字会返回“该入站由画布隧道管理，不能在入站编辑器中修改名称。”，画布自身的生成路径仍可改名并由回滚撤销。未归属的入站可以自由改名，即使名字看起来像生成的。这修掉 v1.3.0“改名会让入站脱离画布”的限制。
- **Agent 本地队列的容量设置不再随连接替换丢失：** spool（SQLite）的 `journal_mode`／`journal_size_limit`／`max_page_count` 只在打开时设过一次，而这些 pragma 属于**单条连接**；`database/sql` 在语句被中断后会换一条连接（spool 取样有 1 秒截止时间，负载下可能触发），新连接带着 SQLite 默认页上限，Agent 上报的数据库容量因此变成 17,592,186,036,224 B，面板以 `invalid spool capacity observation` 拒绝**每一次**控制会话，节点一直离线到 Agent 重启，容量上限也没有真正生效。现在 pragma 写进每条连接的 DSN，页上限仍由一次探测打开按页大小算出；回归测试 `TestSpoolDiskCapacitySurvivesConnectionReplacement`。这是既有缺陷（不是 1.3.x 引入）；2026-11-03 在 alpine-node 上出现（约 05:07Z 起离线，06:50Z 重启 Agent 后恢复），处置见[运维手册](operations.md)第 13 节。

## 其他修复

- 代码审查（Codex 3 轮）修掉两项：用户访问集合比较中的凭据顺序，以及 nil 与空集合被当作不同配置的情况；末轮无发现。spool 修复与门禁改动各 1 轮，均无发现。
- 一项审查意见明确不修改：中继依赖检查不比较传输方式。这是既有行为，本次未扩大范围；依赖检查仍按目标节点当前已发布状态判断。
- **门禁变快（`ebe8301`，只影响开发流程）：** 真实核套件只跑 `scripts/real-core-packages.sh` 列出的 8 个包（与全量跑相同的 119 项真实核通过）并用 `-p 4`，511–527 秒（原 1274 秒）；恢复类测试并行（单独约 330 秒，原 1133 秒）；qui sing-box 的构建按构建脚本摘要缓存，每个版本只构建一次；`cores` 只在每周或派发时勾选 `cores=true` 才跑，`check` 按发布提交跑（约 21 分钟）。本地门禁合计 2366 秒（原约 3140 秒）。`check` 部分仍约 31 分钟，`internal/platform/server`（152 个串行测试，`-race` 下约 1580 秒）已是最长的包；把它并行化是可能的后续项，本次没做。见[部署与升级](deployment.md)第 2 节。

## 升级注意

- 面板先升级，再升级 Agent（组合主机用 `qui-update --component panel|agent`）。**没有迁移**，升级不做数据库变更；`qui-update` 仍会在替换前备份面板数据库。
- **升级 Agent 会短暂重启该节点的代理核心**：核心是 Agent 的子进程，Agent 换了二进制就把它们用自己的新版本拉起；修订不变、也没有回滚，但该节点上所有既有连接会瞬断（RC-F 中 uk 与 us2 的 Xray 都换了 PID）。**发布配置仍会重启该节点上的全部核心**（v1.3.0 起的行为没有改变），本次修复只是让更多情况下不再触发发布。
- 升级前已经完成的移除所留下的 `runtime/<组件>/` **不会**被升级自动清理（清理只发生在移除动作或中断移除的恢复里）。需要清掉就重新添加该核心再移除一次，或按[运维手册](operations.md)第 19 节确认没有残留进程后手工处理。
- 主机侧（非代码，Owner 2026-11-03 批准）：uk-node 的 conntrack 表从 7680 提到 131072（buckets 32768），此前负载下 `nf_conntrack: table full` 引起的核心反复重启不再出现。检查与做法见[运维手册](operations.md)第 13 节；这是宿主机设置，不由面板或调优 helper 下发。
- 其余行为与 v1.3.0 相同：GOST 不能作为主核心、一次发布重启该节点全部核心、整机流量从首次采样起累计。

## 已知限制

- arm64 只在 qemu-user（amd64 主机上的 user-mode 模拟）下验证：归档能加载、启动并通过所选取测试，未经真实 arm64 主机验收，时序与架构相关的内核行为不代表真机。
- GOST 会持续对转发目标做健康探测（RC-F 实测约 6 次/秒的零字节连接），选目标时须知。
- LXC 的整机流量只能统计容器自己的网卡，不能统计物理宿主机。
- 面板“添加内核”安装的组件镜像保存在 Agent 状态目录的 `releases/installed/`，**不创建** `/usr/local/lib/proxy-agent/gost`（该固定路径只属于安装器）；这是设计如此，不是缺失。
- 一次发布仍重启该节点的全部核心（含 Xray 与 sing-box），发布窗口内既有连接短暂中断。
- 正式浏览器走查仍未执行。
