# qui 更新实际运行的 Agent

状态：设计待确认；尚未修改产品代码或生产环境。

## 目标与范围

Owner 要求 `qui` 菜单也能更新实际运行的 Agent，适用于 Alpine/OpenRC 和 systemd。保留现有入口：`qui` 的更新菜单继续调用 `qui-update`，`qui-update --component agent --version X.Y.Z` 同样完成更新。无需网页再操作，也不要求输入面板管理员凭据。

受管节点必须更新引导程序及实际 Agent；普通节点沿用现有更新和启用受管流程。只装 Agent 的主机只处理 Agent；组合主机保持既有组件选择与顺序。保留配置、身份、业务修订、核心和队列。菜单分别显示引导程序版本与受管安装版本；服务已停止时不能将磁盘安装版本标成正在运行。

当前实机证据：Alpine shlii 的 `/usr/local/bin/proxy-agent --version` 为 1.5.8，受管子进程 `/var/lib/proxy-agent/releases/agent-installed/proxy-agent-4d1c…bin --managed-worker` 为 1.5.5。现有脚本明确只更新引导程序，故菜单更新成功不代表网页版本变化。

## 方案比较

1. **采用：本机签名升级接入现有受管安装事务。** 更新器取得目标签名清单与程序，验证后在本机执行受管切换，复用健康检查、安装历史、锁和失败回滚。终端完成整条更新链路。
2. 命令行调用面板 API 排队升级：需要额外的管理员认证，并依赖面板在线及目录可达，不采用。
3. 清空受管历史并重新初始化为新版本：会破坏已有安装、恢复和防重放记录，不采用。

## 行为与实施边界

- 下载继续采用更新器已有官方 GitHub Release 来源与指定版本；在线路径不依赖面板 22550 或配置的网页下载目录。
- 受管 Agent 产物必须同时通过官方/已配置签名信任、组件、平台、版本、大小和 SHA256 验证，验证前不执行候选程序。归档摘要通过不能代替 Agent 签名通过。
- 引导程序升级和工作进程升级构成一个对用户可见的操作，但各自实际结果须分别记录。不得在仅引导程序完成时打印“Agent 已更新”。
- 在停止服务前完成可提前完成的下载、校验和兼容性检查。进入切换阶段前检查并发更新、发布和未收尾恢复状态；存在冲突明确退出，不覆盖旧任务。
- 新增固定的本地 Agent 运维入口，复用 `agenthost` / `updater.Installer` / `agentprocess.Driver`，不用 shell 直接修改加密安装历史。入口以现有服务账号访问状态，取得生命周期锁，绑定节点和当前业务修订。
- 停止、启动及最终服务状态验证复用 `deploy/linux/service.sh` 的 systemd/OpenRC 抽象；不增加仅供 Alpine 使用的另一套更新流程。
- 失败时保留原始错误和退出码，按现有安装事务回到上一受管镜像。服务无法恢复时显式报告失败，不输出成功。
- 采用两个有明确结果的阶段：先按既有 shell 事务更新并提交引导程序，再运行受管 Agent 安装事务。第二阶段失败则保留已更新的引导程序，受管安装器恢复旧工作镜像，并以非零退出码显示两个版本及失败原因。第二阶段不得调用第一阶段的 shell 快照回滚来覆盖受管状态。中断后按受管安装历史恢复，重复命令根据实际工作版本继续，不仅检查引导版本。
- 版本相同按实际工作进程/安装历史判断，不能仅凭引导程序已是目标版本跳过更新。对于包含新本地入口的目标版本，引导程序已经达到该版本、工作进程仍旧时，重复同版本命令必须完成工作进程升级。已发布的 1.5.8 没有新入口，不声称它具备该能力。
- 受管更新要求服务已运行，便于确认当前工作版本并完成切换健康检查；服务停止时在任何变更前明确拒绝并提示先启动，不擅自启动用户停下的服务。普通非受管节点保持现有停止状态更新行为。
- 既有离线 `--bundle` / `--sums` 调用保持离线：普通节点保持原义；受管更新另提供 `--agent-manifest FILE` 指定配套官方签名清单，候选程序取已校验归档中的 Agent。清单缺失或版本/平台/摘要不匹配时在变更前明确失败，不偷偷联网或跳过签名。无需增加重复的二进制参数，也不改现有发布归档格式。
- 对旧发布版本和降级遵守现有签名序号及存储格式规则；不绕过防回退限制。旧目标缺少新本地入口时，在操作前说明不支持，不能留下“引导升级成功、工作进程未动”的假成功。

## 相关文件

- `deploy/linux/qui.sh`：准确区分版本，继续使用统一更新入口。
- `deploy/linux/update.sh`、必要的 `service.sh` 部分：目标产物准备、受管升级编排、最终核验和错误传播。
- `cmd/agent/`、`internal/agent/agenthost/`：固定的本地升级和状态查询入口，复用现有受管事务。
- `internal/agent/updater/`：只补本地已签名候选加载等现有流程缺少的入口，不重写安装历史。
- 发布打包脚本、部署/运维文档和说明书：仅在产物格式或命令行为变化时同步所需部分。

不顺带增加菜单启停功能，不改网页下载自动跟随域名，不改代理核心升级，不回滚或重发节点业务配置。

## 现有安装首次迁移

旧 `qui-update` 已将自身流程解析到运行进程，安装新的脚本文件后不会在本次调用中自动执行新逻辑。因此首次迁移到包含本功能的新版本分两步：先通过现有命令升级更新器和引导程序，再运行一次相同目标版本的命令完成实际 Agent 升级。此后 `qui` 更新菜单或 `qui-update --component agent` 一次即可完成。发布说明须明确这次性操作，版本号随后续发布决定，不改写既有 1.5.8 资产。

本次不扩展旧更新器的自交接机制；这属于实现选择，Owner 如要求首次迁移也只能执行一次命令，需要单独调整方案。

## 验证要求

需要针对受管节点“引导已新、工作进程仍旧”的回归检查，以及签名错误/产物缺失在停止前失败、并发拒绝、健康失败回滚、中断恢复、版本核验、普通节点、停止状态和离线调用检查。OpenRC 与 systemd 都需验证。

测试新增与执行遵守 Owner 授权范围，不以改期望、跳过断言或删除测试处理失败。生产 shlii 的实际升级在本地检查和发布流程通过后进行；不能直接将未经验证的开发二进制替换生产 Agent。现有未跟踪 `docs/v1.5.5-production-upgrade.md` 保持不动。
