# 流量回执与核心明细的安全淘汰设计

状态：已通过独立设计审查并获 Owner 批准；本地实现已落地，独立审查发现的三项问题已修正；编译／类型与格式检查见实施记录，测试未运行、未部署。

## 1. 用简单的话说明

流量回执相当于收据。面板与节点共同确认一段连续编号都已处理、节点也已删除待发数据后，用一条进度记录代替旧收据。最近的收据再留 24 小时便于排障。

核心明细相当于每 5 秒记一次电表变化。保留最近 7 天的详细记录，旧记录合并成小时用量；累计电表已经计算到哪里仍然保留，防止重复记账。

已有的旧收据没有连续编号，第一版保留它们，不能承诺升级后立即回收这部分空间。旧版节点继续使用已发布的上报方式，升级到双方支持的新协议后才开始淘汰新回执。

本设计只涉及流量存储及其必要的查询、升级和恢复链路。生产升级、数据库手动清理、VACUUM、发布版本及 Git 提交均不包含在本次授权中。

## 2. 已确认的目标与设计者提出的参数

Owner 要求解决回执和核心明细长期累计造成的数据库增长，并要求不重复计量、不丢记账结果，继续支持断线补传与备份恢复。

以下参数已随设计获 Owner 批准：

| 项目 | 建议行为 |
| --- | --- |
| 核心原始明细 | 保留最近 7×24 小时；只合并已经完整早于保留边界的小时 |
| 核心历史汇总 | 按节点、核心、UTC 小时长期保存，不按 epoch 分行 |
| 新协议已确认回执 | 在双方确认后继续保留 24 小时，再分批淘汰 |
| 旧协议历史回执 | 保留，不推断完成，不自动删除 |
| 历史查询 | 合并区间按小时查询；不能精确回答的半小时或任意秒边界查询明确报错 |
| 累计游标 | 保留，沿用各模块的所有权和一致性校验 |

不改变用户额度规则、整机流量、账户明细现有保留策略、访问域名记录、核心采样频率，也不减少传输可靠性。

## 3. 当前实现与约束

### 3.1 Agent 生成和发送批次

- `internal/agent/control/control.go` 每 5 秒调用核心采样。
- `internal/agent/core/node_traffic.go` 的 `SaveAccountAndNode` 分别保存账户计数和核心总量，可能一次采样生成多个批次。
- `internal/agent/spool/traffic.go` 的 `SaveTraffic` 仅保存有变化的累计计数；生成随机批次 ID，密封后写入本地 SQLite，和本地累计游标一起提交。
- 本地流量队列没有按时间删除。被拒收的批次会隔离，允许后面的批次先发送；序号设计必须允许这种乱序交付。
- `AckTraffic` 校验 ACK 对应的原始批次后删除队列行。当前没有“节点已持久删除批次”的独立确认进度。
- 当前控制连接的 `AgentMessage.sequence` 还包括心跳、发布结果等消息；重连后同一个队列批次可能使用新的消息序号，不能把它直接当作固定批次编号。

### 3.2 面板处理

- `internal/panel/access/traffic_service.go` 先核验节点、批次及其修订归属，保存加密待续输入，再写统计；账户批次继续交给 user 模块记账。
- `internal/panel/access/account_traffic.go` 在统计事务中保存 `traffic_batches(node_id,batch_id,digest,received_at,accounting_completed_at)`。
- `internal/panel/access/node_traffic.go` 依靠 `node_traffic_cursors` 求累计差值，非零差值写入 `core_traffic_samples`。
- `internal/panel/access/traffic_pending.go` 只在正常链路完成后写 `accounting_completed_at`，并删除加密待续输入。
- user 模块用独立累计游标防止重复扣额度。统计提交、用户扣账、完成标记之间存在可恢复的跨模块窗口。
- `internal/panel/access/traffic_completion.go` 将缺失回执报告为未观察到，不能把缺失、游标覆盖或没有 pending 行当作完成证明。

### 3.3 查询与恢复

- 总览、趋势、节点卡片、月统计、访问审计节点汇总读取 `node_traffic_samples`；用户和设备筛选读取账户表。
- `node_traffic_samples` 只在同 epoch 没有 node 游标时使用账户样本，防止账户与核心总量重复相加。
- 当前备份校验和恢复会处理核心样本、回执、完成标记、统计游标和待续输入。新表不能只加入在线查询而遗漏恢复。
- 旧数据库 `auto_vacuum=NONE`。删除后主要先获得可复用页，文件不会因本功能立即缩小。

## 4. 考虑过的路线

| 路线 | 收益 | 问题与选择 |
| --- | --- | --- |
| 直接按日期删除两类数据 | 实现少、短期回收多 | 破坏重放识别和历史统计，不采用 |
| 压缩回执字段与索引，保留所有回执 | 无须新的交付确认协议 | 数量仍持续增长，不能单独达到目标，不作为本轮主方案 |
| 固定批次编号与双方完成检查点；核心明细先汇总后删除 | 新回执可淘汰，核心历史用量可保留 | 需要面板和 Agent 协议、恢复及查询一起变更；采用此方向 |

Owner 已要求推进前述推荐方向。24 小时窗口、历史查询精度及旧回执第一版保留是本文件明确提出的实现边界。

## 5. 核心明细合并

### 5.1 存储与事务

新增 `core_traffic_hourly`，唯一键为 `(node_id,core,bucket)`，字段至少包括上传、下载、原始样本数。`bucket` 为规范化 UTC 整小时。原始表增加适合保留时间扫描的索引，索引是否被现有结构覆盖由实现者核对。

每次最多处理 500 条旧样本，沿用既有清理工作的小事务方式。对本次选中的确切行，按小时汇总差值、累加原始样本数、删除原始行、保存任务进度，在一个数据库事务内提交。失败全部回滚，不能只提交汇总或只提交删除。批次大小是任务调度参数，不截断或丢弃业务数据。

只合并 `observed_at < floorUTC(now-7days, 1hour)` 的数据，允许额外保留不足一小时明细。任务不能删除累计游标，不改变 epoch 关系，也不重置核心计数。

同一运行周期同一时间的多次增量在现有原始行中合并；汇总中的样本数统计被删除的原始行数，不声称它等于采集调用次数。

### 5.2 迟到数据

离线节点补传旧计数仍走现有身份、修订和累计游标校验，先得到真实新增量。为了延用现有同时间合并和样本数口径，第一版始终先写原始表，下一轮再将过期行原子并入对应小时。新旧存储可以暂时同时存在于同一个小时，查询必须各加一次。

补传导致较早小时重新出现原始行是正常状态，任务不能使用单一时间水位跳过这些行。游标判断重复计数，不依赖样本是否仍存在。

### 5.3 查询行为

新增由 access 模块提供的统一节点流量查询能力，供 dashboard 和 access 调用，计算：核心原始增量＋核心小时汇总＋原有符合回退条件的账户原始样本。

不可直接把小时桶起点放进原来的 `node_traffic_samples.observed_at` 然后继续任意时间筛选，这会把跨查询边界的整个小时算错。所有消费者必须明确采用新查询语义。汇总样本计数使用 `sum(samples)`，不能使用汇总行数冒充原始样本数。

- 最近 7 天仍支持原有精确时间边界。
- 对确实与汇总桶重叠的历史范围，UTC 边界整小时才能精确查询；不涉及历史汇总的范围不额外限制。
- 边界切入已有汇总桶时返回固定原因码 `traffic_history_resolution`，带可查询边界和精度，由现有页面提示选择整小时。禁止按时间比例分摊或静默扩大范围。
- 总览今日、近期趋势继续使用原始数据。月统计在 Asia/Shanghai 等整小时偏移时区可精确合并；历史月份的半小时、45 分钟偏移边界若切入汇总桶，也明确返回精度限制。
- 改面板时区后不能假装恢复已经丢弃的秒级分布；遵循同一边界规则，页面单独呈现不可用的历史项，其他可读取的指标正常展示。
- 用户、设备筛选与现有账户保留策略保持一致，不从核心总量推导用户用量。
- 新功能只保住当前数据库实际留有的历史；旧版已经删除的账户回退样本不补造，保留覆盖范围说明。

不另存一份月总量，避免时区切换时出现两份总量不一致；满足边界条件的月总量由长期小时汇总计算。

## 6. 新回执的序号与检查点

### 6.1 协商与身份

Hello/Welcome 新增明确的回执淘汰能力位，只有双方协商成功才启用。已发布的旧 Agent 保持原协议并保留其回执，这是实际部署版本所需的兼容，不按版本号猜能力。

新增独立交付元数据 `(queue_id,delivery_seq)`，与原始 `batch_id`、摘要绑定；它们放在 protobuf 传输信封中，不改旧批次 JSON，不改变已存加密 payload 的摘要。

节点首次创建受支持队列时生成 `queue_id`，在认证的本地状态中持久保存。节点重启、核心换 epoch、重连和 Agent 升级均不更换此 ID。序号在首次持久入队时分配，和批次、本地累计游标、下一序号一起提交；失败不得消耗一个无法解释的序号。

`queue_id`、序号分配、未确认集合与确认进度必须纳入认证状态。沿用并明确升级现有 bound-store/witness 机制，不能只加可被单独替换的明文元数据。现有 v1 摘要不覆盖流量队列，新格式须先验证 v1，再建立受认证的新版本；失败保留原库和错误。迁移不能先更新版本再校验旧材料。

丢失本地状态、换队列或恢复出较旧进度时明确报错，不能自动生成新 ID 绕过保护。需要更换节点身份时沿用现有显式恢复入口，并留下旧队列封存记录；不能冒充旧队列续号。核销恢复码后，若匹配的原 spool 仍在，允许校验连续性后继续原队列；若是新 spool，则登记新队列并保留旧队列封存记录，普通握手不授权换队列。

### 6.2 面板状态

新增节点队列状态表，按 `(node_id,queue_id)` 保留各代队列，每节点仅一条活动队列；恢复核销在同事务写关闭时间与恢复记录 ID，换队列后的旧检查点保留。至少保存：队列身份、连续完成进度 `C`、节点确认删除进度 `A`、已淘汰进度 `R`、各进度更新时间与协议状态。

未淘汰回执保存固定交付序号与原始摘要绑定，对 `(node_id,queue_id,delivery_seq)` 建唯一约束。避免另建一份永久逐批次映射表，把增长搬到别处。

`traffic_pending_batches` 也保存交付身份，和加密原文一起在现有待续输入事务中落盘。校验、统计、用户记账和后台续做的调用参数均携带该身份；不能只在 gRPC 会话内存中保存。首次统计入库时把身份写入回执，pending 与回执之间的同一批次绑定必须完全一致，任何阶段都不能由重试改绑。统计尚未提交时由 pending 保留关联，统计提交后由回执保留关联；pending 完成删除后不留下额外永久映射。

- `C` 仅覆盖每个序号都经过正常统计和账户处理、写完完成标记的连续前缀。
- `A` 是面板已验证并持久保存的节点删除确认；必须满足 `A <= C`，不接受未来确认或其他队列的确认。
- `R <= A <= C`；推进 `R` 前必须确认目标区间没有缺口、未完成行或 pending 引用。
- 隔离批次可以先留下缺口，后面的批次继续处理；缺口阻止检查点跨过它，不阻止后续流量入库。

### 6.3 ACK 与二次确认

面板正常链路完成后返回包含原始批次 ID、队列 ID、交付序号的 ACK，Agent 验证全部身份与当前待发原文。

Agent 在同一个 SQLite 事务中删除已确认队列行，并更新本地确认状态，再通过新的独立确认消息上报“已持久删除的连续前缀”。中间被隔离的行仍在队列，不能用已收到过的最大 ACK 作为连续前缀。

本地连续前缀从本地已分配序号和最小未确认序号计算，依靠受认证状态证明没有人为丢行；若需要暂存乱序 ACK 事实，它们在前缀推进后同事务删除，不长期保留。

面板在验证 `A <= C` 后持久保存 A，再返回确认消息的正常控制 ACK。任意网络中断允许同一进度重复确认，不重复统计，也不依赖单次会话内存。

### 6.4 淘汰事务

旧回执达到以下所有条件才可删除：

1. 双方已协商新协议，身份与固定交付编号完整。
2. 统计、账户记账和完成标记均已持久完成。
3. 序号位于双方确认的连续前缀，且不被 pending 或活动恢复工作引用。
4. 从该批次被持久纳入双方确认前缀起经过至少 24 小时；不能只用采样时间判断。
5. 拟淘汰区间中的更早回执也全部满足条件。

为避免每个批次保留第二张确认收据，记录待淘汰连续区间的持久封存边界与开始时间；同一时刻只保留一个等待满 24 小时的候选边界。新确认的更高进度不延后已有候选的计时，候选淘汰完再冻结下一段。实际保留可能超过 24 小时，不承诺精确一天容量。

分批删除回执和推进 R 在同一事务完成，使用序号范围顺序处理；提交后 R 之前不再依赖逐批次行，候选状态也必须可崩溃恢复。

### 6.5 旧数据再次出现

对 `seq <= R` 的批次在统计及用户记账之前拒绝，返回 `traffic_delivery_retired`。它不等于“摘要已核验”或“这个批次刚刚成功处理”；Agent 保留原数据并报告本地状态冲突，不能收到此错误就删队列。

对尚未淘汰的同序号、同批次、同摘要正常幂等；序号绑定不同 ID/摘要明确冲突。新的交付序号不得用来重新包装已经淘汰的旧批次；正常 Agent 不改序号，面板仍保留累计游标用于重复计量防护，并继续执行原始来源校验。

按旧 `batch_id` 查询且原始收据已不在时，报告“原始回执未保留，不能按批次验证”；检查点只证明序号区间的封存状态，不能代替任意旧 ID 的摘要证明。不能通过保留永久 ID→序号映射恢复这种能力。

## 7. 已发布数据的迁移

### 7.1 现有核心样本

新增迁移表和索引，不修改已应用的 `0152_baseline.sql` 或 0153。迁移只建结构，后台任务分批整理旧样本，避免在启动迁移中一次性重写大表。

### 7.2 旧回执与现有队列

第一版明确保留没有新协议身份的旧回执，包含没有 `accounting_completed_at` 的历史行。不能用游标覆盖、队列为空或 pending 为零补写完成证明。

Agent 升级时在队列锁和一个事务内为所有已有流量队列行分配固定交付编号；保留原 JSON、ID、密封数据和隔离状态。其后新批次接着编号，不能由发送循环临时编号。

面板首次收到带新编号的旧批次时核验原始摘要，通过正常链路处理或续做记账，然后保存固定绑定及完成事实。重复尝试绑定须一致，不能把“旧统计回执存在”直接升级为整条链路完成。迁移前已经收到 ACK 并从节点队列删除的批次没有可补充的编号，继续作为旧回执保留。

协商及固定队列注册成功后，在该节点持久记录协议切换；恢复或降级后的旧程序不能继续发送无编号流量以绕开检查点。未切换的其他节点仍走已发布协议。固定队列丢失或 Agent 降级时明确要求升级或恢复匹配状态，不静默回退。

旧回执的进一步清理是后续有独立证据的任务，本版本不把它描述为已经支持。

## 8. 备份、恢复和一致性

新小时汇总、整理状态、固定队列身份、交付绑定、双方确认和封存检查点全部加入加密备份、清单计数、材料校验和模块恢复。

在线恢复或保有当前冻结库的离线恢复时，流量相关状态作为同一组采用当前冻结库的事实：核心原始表、小时汇总、核心/账户统计游标、账户现有聚合、回执、完成状态、队列状态及待续输入。不能把当前 R 与旧备份的统计拼接，也不能对重叠原始样本和汇总直接相加。

沿用 user 模块对额度和原始记账游标的恢复权威规则，新增检查确保没有保留较新的封存进度却回退关联扣账状态。证据不一致时整个候选恢复失败，不静默丢待续输入。当前冻结库的 pending 与候选中的 pending 按既有规则保留并校验，已在 R 内的冲突待续输入必须阻止安装，不能重放或丢弃。

恢复协调器认证冻结证据后，复制并迁移其工作副本，再只读附加；原始证据和归档不修改。旧备份迁移后，若当前冻结库存在新格式，则保留当前新格式数据和协议切换状态；不会因恢复旧备份复活旧回执或重开旧协议。如果没有任何当前库可用，新安装只能拥有该备份实际携带的证据；较新的 Agent 进度与备份不匹配时拒绝继续，不能宣称找回备份之后已经丢失的统计。

备份材料校验不启动整理任务，不对副本内容推断线上已完成状态。恢复执行期间按现有生命周期停止并等待清理工作，恢复后仅启动一个整理循环。

## 9. 调度、可见性及失败行为

- 整理工作接入现有后台生命周期，以独立持久任务状态运行，不改现有访问保留五阶段的含义。
- 对外展示原始样本数、汇总行数、淘汰回执数、最后成功时间，以及每节点“旧协议保留／等待确认／缺口阻塞／正常淘汰”的状态。
- 日志保存固定原因码、节点与队列身份、进度及原始数据库错误，不输出原始流量 payload 或用户凭据。
- 锁冲突、磁盘满、摘要冲突、溢出或确认倒退均报错，保留原始数据和最后已提交进度。下一次调度从已提交状态继续。
- 游标、pending、队列身份、未完成回执以及检查点不属于按日期删除对象。
- 不自动执行 VACUUM，不因为数据库达到某个大小就删除额外业务数据。

## 10. 实现边界与验收依据

预期涉及 `proto/agent.proto` 及生成代码、Agent spool/control、access 的入库/查询/任务/恢复、dashboard 读取、备份校验/清单、必要的错误和状态展示、新迁移及相关文档。现有核心适配器的计量规则和 5 秒采样频率不变。

按 Owner 当前规则，不新增测试方法、测试实体或 mock，不运行测试任务。以下列出未来获得明确测试授权后需要覆盖的场景，本文件不把它们记为已经通过：

1. 汇总前后节点/核心上传下载相等；同一任务重入、失败回滚及迟到补传不重复。
2. 7 天边界、UTC 小时边界、月份边界、非整小时时区及改时区，不能返回假精确结果。
3. 同一批次重复、相同序号不同摘要、核心换 epoch、Agent 重启、断流重连。
4. 统计已写但用户尚未记账；用户已记账但完成标记未写；完成后 ACK 丢失。
5. 节点收到 ACK 后删除事务失败，或本地提交后确认消息丢失，不能提前淘汰。
6. 隔离旧批次造成序号缺口，较新数据仍可上报，淘汰进度不能跨过缺口。
7. 在 24 小时封存窗口及分批删除中途退出后继续运行，不能提前删除或复活行。
8. 新旧双方组合、现有队列无损编号、旧历史回执保留、切换后旧协议明确拒绝。
9. 旧备份恢复到新库、汇总/原始混合恢复、进度倒退、队列替换、spool 认证材料不匹配。

测试授权前只能记录实际获准的静态检查，不能以“实现了检查”或未执行的场景代替验证结果。正式发布和生产升级需要独立完成项目既有检查流程。

## 11. 空间预期与交付顺序

核心旧样本在持续有流量、按 5 秒采集时通常每小时约 720 条，合并后每节点每核心每小时一条；停核前额外采样等情况会改变条数。这是历史区间的典型条数对比，不等于整个数据库能缩小 99.9%。原始 7 天与长期小时汇总仍占空间。

新回执的体积由流量、缺口和双向确认进度决定；24 小时等待窗口、两阶段候选及新增协议字段都会影响容量，先前约 35～41 MiB 的一天估算不能当作本方案稳定占用承诺。旧回执第一版仍保留。

实施先完成核心汇总、统一查询及恢复，再完成 Agent 固定编号、面板完成与确认状态、回执淘汰和升级路径；最终按两部分共同的材料校验收口。两部分都实现并获得相应检查证据后，才能称本功能完成。代码交付与生产应用分开记录。


### v1.7.0 发布前兼容性修正

受管升级失败会用同一数据目录恢复旧 Agent。新编号队列使用 spool ABI 7（认证头 v2），不能在 OpenBound 时直接迁移：先由监督进程确认原始基线、当前和上一签名镜像都能读取该格式，且没有未完成升级任务，再持久提升存储 floor；worker 只在 floor 已提升后迁移。独立 Agent 同样校验原始认证契约。v1.6.1 回滚镜像仅支持旧格式，因此升级节点保留原流量上报并明确记录“回执淘汰未启用”，不删除旧回执；面板核心明细按小时整理独立生效。新装节点可在证明通过后启用新编号协议。此保护防止升级中断后旧镜像无法读取队列。

发布前扩充既有队列/格式回归断言，先复现无条件迁移再修复；真实镜像启动、恢复与完整套件纳入同 SHA Linux/GitHub 门禁。
