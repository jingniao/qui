# 网页 Agent 升级与终端升级统一设计

状态：Owner 已要求按规划实施并发布 v1.7.5；正在实施与现有测试/发布门禁验证。生产部署不在本轮授权内。

## 需求与结论

Owner 要求网页升级 Agent 的完整行为与终端一致，失败时必须给出具体报错。

网页在节点本机调用已安装的同一个更新器：

```sh
/usr/local/bin/qui-update --component agent --version X.Y.Z --yes
```

`--yes` 对应网页上的确认操作；版本固定为用户确认的目标，执行中不重新选择最新版。节点直接访问现有官方 GitHub 来源，沿用终端的下载、归档 SHA256 校验、实际 Agent 签名校验、预检、安装、服务检查和恢复规则。网页不再为新任务导入或使用面板 Agent 下载目录。GitHub 不可达时直接报出下载错误，不自动切换面板目录。

终端已有的指定版本、离线安装和恢复命令继续可用；本次网页只提供在线升级，不增加上传离线包界面。

## 代码依据

- `deploy/linux/update.sh`：终端完整更新器，要求 root；先更新引导程序和随包文件，再更新受管工作进程，分别提交两阶段结果。
- `deploy/linux/install.sh`、`deploy/linux/service.sh`：安装系统文件及 systemd/OpenRC 服务抽象。
- `internal/agent/agenthost/local_protocol.go`、`local_release.go`：实际 Agent 安装通过私有本地 socket 交给唯一监督进程。
- `internal/panel/deployment/agent_updates.go`：现有网页任务绑定签名目录项，仅更新工作进程。
- `pkg/contracts/release/core_update.go`：现有共享 `UpdateResult` 只有分类码，没有原始错误；不能直接承载完整系统升级结果。
- `deploy/systemd/proxy-agent.service`、`deploy/openrc/proxy-agent`：Agent 使用普通服务账号，没有替换系统程序和服务文件的权限。
- `deploy/linux/panel-update-request.sh`、Agent 的调优 watcher：项目已有“普通进程提交固定请求、独立 root 服务执行”的实现模式。

## 方案选择

采用独立的节点系统更新服务，固定调用现有 `qui-update`。网页只提交任务与读取结果；安装逻辑只有一份。

考虑过扩展监督进程自行安装系统文件：需要改变服务权限、复制安装和恢复逻辑，还会在重启自身时丢失执行者，因此不采用。此前建议的“网页由面板缓存完整安装包”不再采用，因为 Owner 明确要求下载来源也与终端一致。

不新增整包签名体系或修改现有发布附件。归档继续沿用终端当前基于官方 GitHub 与 SHA256SUMS 的信任方式，受管实际 Agent 继续独立验证已有官方签名。

## 更新范围与执行

```text
网页确认目标版本
  → 面板持久化任务，经现有 mTLS 控制连接下发
  → Agent 提交固定的本机系统更新请求
  → 独立 root 更新服务持久化接收记录
  → 调用已安装的 qui-update
  → GitHub 下载、校验、预检
  → 引导程序／系统服务／随包脚本更新及健康检查
  → 实际 Agent 更新及健康检查
  → 保存结果和日志
  → Agent 重连后补传，面板确认收到
```

更新范围精确跟随 `qui-update --component agent`，包括它实际安装的 Agent、引导程序、服务定义、共享运维脚本和安装记录。共享脚本继续按终端既有规则处理。保留终端已有的核心配置规范化行为；不额外触发代理核心版本升级、节点配置发布或面板程序升级。

执行服务独立于 `proxy-agent` 的进程树及服务生命周期。停止或重启 Agent 不得终止更新器。systemd 和 OpenRC 同时设计、实现和验收。安装器替换更新服务自身的文件时，当前执行使用固定副本；不得重启或停止正在执行该任务的 runner/watcher。

不把完整升级请求先放入旧 `agentjobs` 工作进程升级队列。否则终端更新器会把自己识别为“已有网页任务”，拒绝取得本地安装锁。完整升级的外层接收记录独立保存，实际安装仍由原更新器取得现有全局更新锁、监督进程锁和生命周期锁。

## 首次启用与已发布数据

现有节点没有新的 root 更新服务，需要在发布后先通过终端安装一次包含本功能的版本，再依据实际安装及运行状态确认是否启用。旧更新器若只完成了引导程序更新，继续遵循已有的同版本重跑要求，不能承诺所有旧节点只需一条命令。

新能力必须由本机 root 更新服务的固定探测请求及对应回执确认，不能仅凭 Agent 版本或文件存在推断。缺少能力时，网页明确显示所缺组件和终端迁移命令，不退回只更新工作进程。

已发布版本存在旧任务、旧结果和升级历史，因此保留它们的读取、补传及原恢复路径；不为缺少新能力的节点创建旧式网页升级任务。这是对真实已发布数据的兼容，不增加假想调用方兼容层。

## 失败信息合同

终端 stdout/stderr 与系统更新器的结构化阶段事件同时保留。网页详情至少包含：

- 节点、任务和尝试编号，目标版本，开始与结束时间。
- 失败阶段：请求检查、下载、校验、预检、引导安装、引导健康检查、实际 Agent 安装、实际健康检查、恢复或结果保存。
- 原始错误文本；更新器退出码，以及已明确取得的失败子命令退出码或终止信号。未知值保持未知。
- 引导程序版本、实际安装版本、实际运行版本及服务状态，分别记录；读取失败必须附具体错误。
- 恢复是否执行、是否成功及恢复错误；恢复成功仍保留最初失败原因。
- 本次任务完整输出的查看、复制和下载入口；日志缺段、保存或补传失败必须明示。

更新器增加可选的结构化报告通道，仅供 root wrapper 取得阶段与命令错误；普通终端输出和执行分支保持一致。阶段来自执行位置，不通过匹配中文输出猜测。更新器退出码与 `curl` 等子命令退出码分别呈现。

同时审查实际安装调用链中把底层错误压成分类码的分支。当前 `agenthost` 部分本地失败通过内存中的 `localError` 回到终端，并非所有拒绝分支都保留原因；因此需要在共同安装路径补全原始错误传递，再由 root wrapper 持久保存。只给现有 `download_failed`、`preflight_failed` 添加中文标签，无法满足本需求。错误传递改善同时作用于终端和网页，不增加另一套安装分支。

日志按任务、尝试、递增序号分块上传，面板持久化后 ACK。节点只在收到 ACK 后清理相应待传数据；重连重复块必须验证内容一致。日志不塞进现有有固定大小和字段校验的 `UpdateResult`。传输分块不截断原始错误，已有日志容量和保留策略的衔接须明确记录，不能静默丢弃。

日志只包含本次更新器输出，不读取任意系统日志或配置文件。仅 Owner 可读。涉及身份材料的输出须在产生处避免泄露，不能直接开放 root 日志目录；不以笼统错误替换正常的原始报错。

以下仅为目标展示示例，不是本次实际运行结果：

```text
升级失败 · 下载发布归档
原始错误：curl: (22) The requested URL returned error: 404
更新器退出码：1；下载命令退出码：22
引导程序：1.7.4；实际 Agent：1.7.4
恢复：未执行，尚未开始替换
[查看本次完整输出] [复制错误] [下载日志]
```

## 结果与恢复语义

- 任务已提交、下载成功、服务进程存活都不能单独算升级成功。沿用终端最终版本和健康检查结论。
- 第一阶段失败按原 shell 快照恢复；第二阶段失败按受管安装记录恢复工作进程，保留已提交的新引导程序，网页如实显示两个版本。
- 断开浏览器、重启 Agent 或重启面板不取消节点任务。
- 更新进程或主机中断且未取得最终回执时显示“结果待确认”，保留最后阶段；不得据超时改成成功或编造失败原因。
- 中断恢复交给现有更新器和开机恢复机制。外层服务在核实原执行者已经终止后核对其恢复结果；不以版本相同代替完整结果，也不自动重复执行未知状态的任务。
- 人工重试建立新尝试，绑定原任务并保留原失败与日志；版本继续固定，恢复及继续安装按终端规则执行。
- 原始失败与恢复失败同时存在时，分别展示，不能互相覆盖。

## 权限与持久化

root 服务只接收固定 schema 的探测或 Agent 在线升级请求。升级请求仅含任务/尝试 ID、节点身份、期望修订和正式版本，不接收 URL、脚本、命令、环境变量或文件路径。root 侧独立检查请求文件类型、属主、内容与运行身份，把请求复制到 root 私有持久目录后再启动；命令参数逐项传递，不使用 eval。

root 接收记录、阶段、最终结果和任务输出均保存在独立 root 目录；Agent 只能读取发布出来的该节点任务状态和日志。按任务 ID 去重，重复请求内容不同时明确拒绝。两种入口继续竞争同一个更新锁，冲突须报告具体占用事实。

新增迁移（预计 0157，以实施时实际迁移头为准），新增完整升级任务、尝试、日志表及节点能力字段，不改写历史迁移或旧任务含义。任务清理、节点删除/接替阻塞、备份校验及恢复均须纳入新任务；历史记录不能只保存在浏览器。

## 验收边界

同一版本、同类初始节点，网页执行与终端上述命令的安装文件、版本、服务、健康检查、失败恢复和业务修订应一致；网页额外增加任务授权、确认和结果展示。

Owner 后续已授权完成实现并发布 v1.7.5，只允许运行现有测试与发布门禁，不新增测试方法、实体、mock 或独立隔离验证场景；生产不部署。现有测试/构建通过不能记作新桥接完整升级和回滚实机通过。

## v1.7.5 实施裁定

- 新迁移固定0157，协议/root路径与设计一致。旧任务API保持，POST新任务仅接受targetVersion，不进入agentjobs。
- root阶段收据决定终态；Agent本机投递错误独立保存与ACK，通过dispatchError展示，后续真正root结果不会被投递错误锁死。
- 原执行结束但终态/恢复材料不足时，root保留interrupted阶段，面板为unconfirmed；相同请求只核对原执行与恢复事实，不重复安装。
- 第二阶段在执行前把原local request ID、候选SHA及完整signed清单fsync到root事件。重启先确认原进程终止，再由当前监督进程只读核对原job和InstallationRequest，完整材料、节点、修订和目标一致才采用真实终态；不以最新安装记录或版本相同替代。原cause回滚前、outcome在结束前加密持久保存于既有local-candidates目录，不修改jobs/spool ABI。原CLI退出收据缺失时整任务保持中断失败、退出码为空；真实受管commit单独显示阶段成功，未伪造整套成功。
- 完整输出另存root专用任务目录并分块补传，不纳入普通100MiB Agent日志轮转；未获后续清理授权前保留，保存失败明确暴露。完整下载拒绝缺段和日志错误。
- 首轮现有测试保留失败记录：节点手工scan漏新能力列、Agent会话探测无服务时等待过久均已修复并窄复验通过。新Linux桥接未获独立场景实机验证授权。
