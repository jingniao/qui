# 订阅按整条线路的维护与离线状态过滤

状态：v1.7.5 已实施，发布门禁由发布批次统一记录；未部署生产。Owner 后续授权实施及现有测试/发布门禁，未授权新增测试方法、实体或 mock。实现记录见[实施计划](../plans/2026-11-20-subscription-route-availability.md#实施记录)。

## 已确认需求

- 入口、中间、出口任意一台受管机器处于维护模式，相关中转线路不出现在订阅里。
- 离线机器采用相同规则：线路经过的任意受管机器被确认离线，整条线路不进入订阅。
- 直连自建节点按自身机器过滤；同一机器上的独立线路按各自真实依赖判断，不牵连不经过故障机器的线路。
- 恢复后重新生成订阅可见；原用户授权、分组、已发布凭据、协议、订阅可见性等条件继续有效。

离线语义沿用前面已确认的规则：以最后有效心跳及 `node_offline.duration_minutes` 判断，规则勾选只控制通知。短暂断开处于“连接中断，等待恢复”时保留订阅，达到持续时间才移除。此次把同一状态语义扩展到订阅；不改变控制操作的连接有效期。

## 已读代码与遗漏原因

- `internal/panel/node/groups.go` 的 `ExpandedNodes` 排除了维护中的目标服务器，没有按离线状态过滤。
- `internal/panel/node/inbound_access.go` 的入站/中转授权检查维护目标服务器，没有完整检查入口和中间机器。
- `internal/panel/subscription/source/published/relays.go` 读取入口的地址与名称，没有过滤入口维护/离线，也没有完整路径信息。
- `internal/panel/subscription/importer/import_relays.go` 的导入出口中转路径存在同样遗漏。
- `internal/panel/subscription/source/published/Relay` 的现有快照只有入口、目标入站/导入及地址等信息，缺少完整依赖机器列表。
- `internal/panel/proxy/tunnels_publish.go`、`tunnels_finalize.go` 已掌握发布涉及的机器及成功收尾时机，可在成功提交时记录依赖。
- `internal/panel/subscription/importer/chains.go` 已按成功发布的客户端画布生成链路；需要确保基础端点过滤后整条链被排除，而不输出残缺链。

## 方案

采用后端统一的订阅可用性读取，加上成功发布的线路依赖索引。所有格式从过滤后的同一端点集合生成。

只在当前 SQL 增加入口条件无法覆盖中间机器；直接读取 `tunnel_hops` 或当前画布会误用草稿，并可能遗漏自建目标后续的固定代理链。因此依赖来源必须绑定实际成功发布内容，状态则在每次生成订阅时读取当前值。

### 线路依赖

1. 每个订阅端点有稳定引用：自建 `inbound:<id>`，中转 `relay:<id>`。记录其实际经过的受管机器 ID、成功发布标识及来源摘要。
2. 普通直连端点只依赖所属服务器。固定服务器中转、隧道及画布方案按实际发布路径收集入口、所有中间跳和最终出口，去重后保存。
3. 目标入站本身还有固定后续链路时，一并合并；不能只记录规则入口与目标服务器。
4. 依赖仅包含该端点实际经过的机器，不能把整个发布批次涉及的所有服务器都算作每条线路的依赖。
5. `pending_delete` 和草稿修改仍读取上一次成功发布路径；失败发布不能覆盖现有依赖。成功撤除时才随已发布端点移除索引。
6. 客户端执行的链式方案继续按成功发布布局组合，任一组成端点不可用则省略整条链；不偷偷删除坏的一跳后输出剩余链路。
7. 纯外部导入节点没有受管机器心跳，不通过域名/IP 猜测它属于哪台服务器，也不虚构离线判定。通向导入出口的线路仍检查所有已知受管跳。

### 维护和离线

- 维护开关保存后，下一次生成订阅立即排除相关线路，无需重新发布运行配置。
- 离线判定由后端统一计算，复用展示状态的输入和优先级；不以 `nodes.status='offline'` 单独判断，否则 gRPC 短断线仍会过早移除订阅。
- 每次生成订阅固定一个服务端当前时间，批量读取节点状态和离线持续时间；在同一次读取中按相同口径过滤所有线路。
- 持续时间为 0 时，沿用现有“连接中断或心跳过期被确认后立即离线”的语义，不能让仍正常上报的机器因为阈值为 0 被过滤。
- 待登记或没有可用历史心跳的机器不虚构等待期；沿用展示和既有授权规则处理。
- 通知关闭不影响订阅离线过滤；修改持续时间后，下次订阅按新值重新计算，不能只靠状态事件使缓存失效。
- 维护解除或机器恢复有效心跳后，下次拉取订阅重新包含合格线路；客户端尚未更新的旧配置仍在客户端保存。

### 数据错误与旧记录

旧版真实已发布的线路没有依赖索引。新增索引时从成功发布快照、原发布记录和已确认配置重建，核对来源标识和摘要；不能拿当前草稿补齐缺失路径。

无法证明完整路径时报告具体线路和缺失材料，阻止将“不知道”当作“可用”或“正常过滤”。数据库、规则或状态读取失败沿用主订阅源错误路径，不能返回伪造的成功空订阅。真实维护/离线导致过滤属于正常结果，预览可解释被排除的机器和原因。

新增依赖索引属于支持已发布状态的必要数据演进；同步校验、备份和恢复。不得修改旧迁移、丢弃历史发布记录或要求所有线路盲目重发。

## 范围与边界

- 覆盖直接自建、关联自建出口的中转、导入出口中转、固定服务器画布/代理链、客户端执行链及其支持的订阅格式。
- 仅影响订阅端点生成与预览，不自动删除对象、不停止核心、不关闭已有连接、不重新发布配置。
- 订阅可用性不能混入凭据渲染和操作准入。特别是离线过滤不得触发自动回收凭据或配置发布，否则短暂展示变化会改变节点业务状态。
- 原本禁用、删除、授权和订阅可见性条件保留，不把本次维护/离线判断扩展成任意核心异常、延迟高或端口探测失败就移除订阅。
- 不修改节点配置页的中转折叠和卡片布局；本轮需求针对订阅。

## 验收例子

线路 `A → B → C`，另有独立直连 `A`、`C`：

| 状态 | 中转 A → B → C | 直连 A | 直连 C |
| --- | --- | --- | --- |
| 全部正常 | 保留 | 保留 | 保留 |
| B 维护 | 移除 | 保留 | 保留 |
| A 维护或确认离线 | 移除 | 移除 | 保留 |
| C 维护或确认离线 | 移除 | 保留 | 移除 |
| B 短暂断线，仍在等待恢复 | 保留 | 保留 | 保留 |
| B 超过离线持续时间 | 移除 | 保留 | 保留 |
| B 恢复有效心跳 | 重新包含 | 保留 | 保留 |

所有“保留”仍以用户原授权、成功发布及订阅可见等条件满足为前提。行为已实施；受 Owner 限制只运行相关现有检查，表中组合未逐项新增实测，不能记作逐项通过。

成功回执和成功回滚只保存本机成功修订与来源证明，完整跨节点线路证明在订阅读取时执行，避免各机器修订暂时不一致阻断反向回滚。默认出口的出站、出口组和固定链包含按类型声明的已发布备用路径；任一相关受管备用节点维护或确认离线，整入口排除。Direct/Block 不增加受管依赖；域名策略路径保持原范围。
