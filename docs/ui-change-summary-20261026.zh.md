# qui 前后台界面与业务交互更改说明

**整理日期：** 2026-10-26  
**代码基线：** `be63347`（v1.0.9 文档提交）及当前未提交的前端改动  
**依据：** 本次对话确认的产品方向、用户说明的修改范围，以及当前路由、页面和数据处理代码的静态核对。

## 1. 本次改动概述

本轮调整将平台从偏配置管理的界面，逐步整理为“前台使用、后台管理”的结构：

- 前台围绕个人用量、授权节点和订阅接入。
- 后台围绕用户、服务器、接入节点、中转方案和分流管理。
- 服务器负责机器与程序运维；代理节点负责用户连接入口。
- 新增无限画布式中转搭建，将线路设计与节点列表联动。
- 客户端策略与节点策略分别配置，共享域名和 IP 规则集。
- 配置版本管理逐步融入节点创建、修改和中转发布流程。

**本文区分“界面已调整”“部分对接”“目标规划”。按钮、表单和状态标签已经出现，不代表后端、Agent 或客户端已具备相应能力。** 本文不是完整代码审计或功能验收报告。

## 2. 改动范围与导航

按用户说明，本轮覆盖前台整体界面；后台覆盖系统总览、用户管理、服务器一级页面、节点配置一级和二级页面，以及分流控制和系统管理的部分内容。

当前主要导航结构如下：

```text
前台使用
├─ 概览（包含个人用量与订阅接入）
└─ 节点（授权接入点与线路）

后台管理
├─ 系统总览
├─ 用户管理
├─ 服务器
│  ├─ 服务器列表
│  ├─ Agent 管理
│  └─ 代理核心
├─ 节点配置
│  ├─ 节点列表
│  └─ 中转搭建
├─ 分流控制
│  ├─ 客户端策略
│  ├─ 节点策略
│  ├─ 规则集
│  └─ 策略模拟
├─ 访问审计
└─ 系统管理
   ├─ 备份恢复
   ├─ 操作日志
   └─ 系统设置
```

访问审计、备份恢复、操作日志等继续保留入口，本文不将其认定为本轮已经完整重做或验收的页面。前台整体修改也不代表登录、首次初始化、错误页均重新设计。

### 主要入口调整

| 原入口 / 组织方式 | 当前调整 |
| --- | --- |
| 用户、设备、订阅分散管理 | 收敛为“用户管理”；`/devices`、`/subscriptions` 重定向到 `/users` |
| 节点同时承载服务器运维与接入含义 | `/nodes` 在后台作为“服务器”，接入点统一到 `/proxy/nodes` |
| 独立入站、出站、出口组、代理链菜单 | 主入口收敛到“节点列表”和“中转搭建”，旧路径重定向 |
| 分流规则、服务规则、网站控制 | 客户端策略、节点策略、规则集、策略模拟；网站控制并入节点策略 |
| 系统中的 Agent、核心版本 | 入口迁入服务器区域；旧路径重定向到对应页签 |
| 独立配置版本页面 | 菜单退出主流程，旧 `/system/revisions` 重定向到服务器 |
| 独立客户端接入入口 | 当前 `/portal/client` 重定向到总览，个人接入内容向前台总览集中 |

依据：[路由](../web/src/app/router.ts)、[侧边栏](../web/src/components/AppSidebar.vue)。重定向不等于旧组件、接口或后端机制已删除。

## 3. 前台整体调整

### 3.1 个人概览与订阅接入

方向是让用户登录后直接看到自身用量、额度、到期和接入信息，减少理解设备凭据、后台入站和配置版本的成本。

主要内容包括：

- 个人额度与用量摘要，区分上传、下载和统计周期。
- 用户接入状态、到期及需要关注的事项。
- 订阅链接复制、二维码和客户端导入入口。
- 可用节点与使用入口。

对话最终收敛到“每用户一个账号、一条共享订阅”，不再以手动创建设备为使用前提。此前“我的设备”的讨论属于早期方案，不应据此承诺共享凭据下的准确物理设备识别。

### 3.2 前台节点

- 展示用户有权限使用的接入点。
- 展示名称、地区或用途、协议、地址及真实状态。
- 提供连接方式、二维码、订阅或客户端导入入口。
- 对同一落地的多条中转线路，采用有意义的线路名称区分。
- 草稿方案、未登记服务器以及未生效线路，不能作为已可用节点展示。

### 3.3 前后台视觉边界

顶部增加前后台模式切换，侧边栏按模式提供不同内容。两侧可共用基础按钮、表格和弹窗，但页面布局与专属样式应控制影响范围，避免改后台时连带改变前台。

**当前仍需衔接：** 模式切换使用 `viewMode`；这不是普通用户的独立认证体系。总览仍存在通过管理接口读取用户并按用户名匹配、失败取第一条的逻辑。真正的个人前台应由后端会话确定数据归属，不能依赖这种临时匹配。

依据：[总览页面](../web/src/modules/dashboard/pages/DashboardPage.vue)、[节点页面](../web/src/modules/nodes/pages/NodeListPage.vue)、[模式状态](../web/src/app/viewMode.ts)、[导航守卫](../web/src/app/guards.ts)。

## 4. 后台系统总览

总览重心调整为“看运行状态、发现问题、进入处理页面”。当前布局包括：

- 核心指标：节点状态、代理核心、有效用户、今日流量。
- 待处理问题与节点运行列表。
- 节点流量摘要、上传下载分布及排行。
- 用户用量与到期情况。
- Owner 可见的近期访问审计。

数据卡片、列表和辅助信息重新组织，注重信息层级与对齐。流量需标明统计范围；没有测量的连接数、资源或用量，不应为了补满页面显示为零。

当前使用了已有总览、节点、用户和账户流量接口；本文未验证所有聚合值的统计口径和运行正确性。

## 5. 用户管理

### 5.1 产品方向

“用户与凭证”收敛为“用户管理”，以用户为单位管理账号、节点组、额度和有效期。凭据由系统维护，隐藏手动创建设备的流程。

用户管理界面规划并已开展的调整包括：

- 新增、编辑、启用、禁用和删除用户。
- 用户名、显示名称、备注及状态。
- 分配节点组、限制允许使用的协议。
- 流量额度、已用量、清零、到期与续期。
- 订阅查看、复制、二维码与重置。
- 密码相关操作、上传下载限速和流量重置周期。
- 用户详情展示权限、用量与订阅相关内容。

当前用户管理中还包含管理员操作相关代码。普通代理用户与 Owner/Viewer 管理员仍需明确区分，不能因为共用页面而混淆账号与权限。

### 5.2 当前接口衔接情况

| 能力 | 当前静态核对结果 |
| --- | --- |
| 用户资料、节点组、额度、有效期 | 已有用户管理接口可复用；仍需按具体交互验收 |
| 手动清零流量、续期 | 页面调用相应已有接口 |
| 用户级订阅体验 | 界面已向用户级收敛，但仍通过默认设备等旧模型衔接 |
| 普通用户登录密码重置 | 当前详情中的重置实现调用代理凭据轮换，不等于修改登录密码 |
| 上传/下载限速、自动流量重置周期 | 当前前端编码到备注字段；不代表节点限速或定时重置已执行 |
| 独立用户登录、共享订阅反复查看 | 属于 v1.1 后端与认证改造范围，不能仅凭界面宣称完成 |

登录密码、订阅 Token、代理接入凭据必须明确区分。只修改登录密码或订阅链接，不应暗示旧代理配置已被撤销。

依据：[用户列表](../web/src/modules/users/pages/UserListPage.vue)、[用户详情](../web/src/modules/users/pages/UserDetailPage.vue)、[用户 API 与扩展字段](../web/src/modules/users/api.ts)。

## 6. 服务器

### 6.1 本轮已调整的页面范围

服务器一级页面以“列表看状态、详情做管理”为原则，调整卡片/列表、筛选、信息层级和管理入口；Agent 与代理核心入口并入服务器区域。服务器详情仅见局部改动，不视为下面所有页签已完成。

### 6.2 对话确认的完整内容方向

| 分类 | 目标内容 |
| --- | --- |
| 基础信息 | 名称、地址、IPv4/IPv6、地区/用途、备注 |
| 状态 | Agent 状态、核心健康、最后心跳、配置同步 |
| 资源 | CPU、内存、磁盘使用率与可取得的容量 |

| 版本 | Agent 版本、核心类型/版本、当前配置与更新结果 |

服务器在线、核心健康、代理可连接是不同维度；测速结果也不能替代当前网速或用户实际延迟。

## 7. 节点配置：节点列表与中转搭建

### 7.1 统一节点列表

将资源分为服务器自建节点、机场订阅导入节点、单独导入节点。统一搜索、筛选和展示名称、来源、地址、协议及状态。

自建节点提供入站配置编辑入口；导入资源在同一列表中呈现，避免与服务器机器混为一谈。

同一落地节点关联多条方案时：

- 在节点下面展示可折叠的“中转线路（数量）”。
- 每条线路显示路径、执行位置、草稿/发布状态与编辑入口。
- 编辑跳转到画布，打开方案并定位线路。
- 添加中转时以当前节点作为落地目标。
- “仅经中转”与可直连分别表达。

### 7.2 无限画布

布局采用左侧资源库、中央无限画布、右侧属性栏和顶部方案工具栏。

```text
资源库
├─ 我的服务器
└─ 代理节点
   ├─ 自建节点（按服务器分组）
   ├─ 机场订阅（按来源分组）
   └─ 单独导入
```

支持拖入资源、移动、缩放、平移、定向连线、属性编辑、方案保存/打开，以及从列表跳转定位。画布实例与原始资源分离：从画布移除实例不应删除原始节点。

### 7.3 执行方式与隧道

| 方式 | 示例 | 目标执行流程 |
| --- | --- | --- |
| 客户端代理链 | 用户客户端 → 导入节点 A → 导入节点 B → 网站 | 编译为目标客户端支持的完整配置订阅 |
| 服务器中转 | 用户客户端 → 自有服务器 → 导入节点 A → 网站 | 生成配置并通过 Agent 发布 |
| 服务器间隧道 | 自有服务器 A → 自有服务器 B | 在可管理服务器上部署对应隧道能力 |

连线按对象能力提供隧道转发、端口转发、代理链连接。导入节点可作为代理链中间跳或出口，但不能要求其安装 Agent、创建服务器监听或接收部署。

隧道通过画布连线创建，点击连线编辑参数；“隧道列表”提供集中查看与定位入口。

### 7.4 当前实现边界

节点来源和画布方案目前由 `proxyNodes.ts` 管理，含本地缓存和预置演示资源。机场订阅拉取、导入解析、探测、链路编译等不能据此认定为完整后端能力。

尤其是当前 `handleConfirmPublish()` 只修改本地 `published` 标记并显示成功提示，没有完成真实 Agent 部署或客户端订阅生成。这部分应记录为“前端交互原型”，待接通后端后再显示实际生效结果。

自建入站保存会调用现有接口并尝试创建版本，但创建版本不等于部署成功，仍需补齐发布及结果确认。

依据：[节点列表](../web/src/modules/proxy/pages/ProxyNodeListPage.vue)、[中转画布](../web/src/modules/proxy/pages/RelayCanvasPage.vue)、[资源与方案数据](../web/src/modules/proxy/proxyNodes.ts)。

## 8. 分流控制

原来的分流规则和网站控制共用策略能力，现收敛为“节点策略”；“服务规则”扩展命名为“规则集”，避免限制为域名。

| 页面 | 职责 |
| --- | --- |
| 客户端策略 | 管理 Clash/Mihomo 的匹配、顺序、直连、阻断、节点/策略组选择 |
| 节点策略 | 管理服务器侧用户/节点范围、匹配条件及出站、出口组、代理链等动作 |
| 规则集 | 统一维护域名、后缀、IP、CIDR；定义匹配目标，不定义转发动作 |
| 策略模拟 | 分客户端与节点端，查看匹配规则、执行动作与原因 |

客户端和节点策略独立配置，共用规则集内容。客户端直连从用户设备发起，节点直连从服务器发起，两者含义不同。

客户端策略计划通过完整配置订阅下发；规则集通过兼容 Clash/Mihomo `rule-providers` 的资源提供。只加载 `proxy-providers` 节点列表不等于加载了分流策略。

**当前边界：** 客户端策略仍在 `localStorage` 保存。规则集页面生成的 provider 片段指向现有服务集 API，不能据此认定该 URL 已具备客户端可直接获取的格式、权限和更新机制。服务集管理接口、策略管理接口与实际订阅导出能力还需分别接通和验证。

依据：[分流 API 与客户端本地配置](../web/src/modules/routing/api.ts)、[客户端策略](../web/src/modules/routing/pages/ClientPolicyPage.vue)、[节点策略](../web/src/modules/routing/pages/RoutingRulePage.vue)、[规则集](../web/src/modules/routing/pages/ServiceRulePage.vue)、[策略模拟](../web/src/modules/routing/pages/PolicySimulatorPage.vue)。

## 9. 系统管理与配置发布流程

### 9.1 系统管理调整

- Agent 管理与代理核心入口迁到服务器区域。
- 保留备份恢复、操作日志、系统设置。
- 原系统设置中的客户端规则入口向分流控制集中。
- 平台基础信息、时区和记录保留等既有设置继续使用原有能力。

### 9.2 发布交互的最终方向

用户确认不再要求到独立“配置版本”页面重复创建和发布：

```text
新建/修改自建节点 → 创建或保存并发布 → 查看结果
中转画布 → 校验方案 → 发布 → 查看各节点结果
客户端方案 → 生成完整订阅 → 客户端更新后生效
```

版本快照、依赖顺序、发布批次和回滚继续由后台处理；节点详情或画布承载进度、失败原因、重试与历史回滚。

当前已调整菜单与旧路径重定向，但发布流程尚不能视为整体完成。不能把隐藏版本页面理解为删除底层版本机制，也不能在新入口未接通时丢失原发布能力。

依据：[系统设置](../web/src/modules/system/pages/SettingsPage.vue)、[路由](../web/src/app/router.ts)。

## 11. 模块化架构与本轮改造边界

### 11.1 当前架构是什么

项目采用**模块化单体**：中央面板按业务模块组织，但以一个 Go 服务运行，使用 SQLite；前端构建后嵌入面板。Agent 是部署在各服务器上的独立程序，管理官方代理核心或计划中允许的构建，并通过 gRPC/mTLS 连接面板。

业务数据不需要为了前后台分离而拆成微服务。浏览器向面板调用 API；面板模块在进程内通过接口和应用服务协作；服务器上的实际执行由 Agent 完成。

### 11.2 现有模块职责

| 层级 | 模块位置 | 主要职责 |
| --- | --- | --- |
| 前端应用层 | `web/src/app/` | 路由、会话、权限导航、统一请求、SSE、时间展示 |
| 前端业务页面 | `web/src/modules/` | 用户、服务器、代理、分流、系统和前台页面及交互 |
| 前端共享组件 | `web/src/components/` | 表格、弹窗、抽屉、状态、分页等通用展示 |
| 面板认证 | `internal/panel/auth` | 当前管理员认证、会话和权限；普通用户认证按 v1.1 计划扩展 |
| 用户 | `internal/panel/user` | 用户、授权、凭据、额度与访问状态，兼容现有设备身份 |
| 服务器与节点组 | `internal/panel/node` | 登记、身份、心跳、能力、状态、节点组与删除 |
| 订阅 | `internal/panel/subscription` | 订阅身份、可访问端点筛选和客户端格式输出 |
| 代理配置 | `internal/panel/proxy` | 入站、出站、出口组、代理链和配置快照构建 |
| 分流 | `internal/panel/policy` | 节点策略、服务集及模拟；新增客户端策略/规则集输出需明确归属 |
| 发布 | `internal/panel/deployment` | 配置版本、任务、依赖批次、执行结果、回滚和更新任务 |
| 记录与总览 | `internal/panel/access`、`connections`、`dashboard` | 访问和流量记录、连接观测、只读汇总 |
| 系统 | `internal/panel/system` | 系统设置、备份、保留策略等 |
| 面板装配与编排 | `internal/platform/server` | HTTP/gRPC 装配、跨模块流程协调，包括自动额度发布 |
| 基础设施 | `internal/platform/` 其他目录 | 数据库、配置、加密、证书、进程锁及恢复等公共能力 |
| Agent | `internal/agent/` | 控制连接、核心适配、配置应用、健康恢复、采集缓存、网络与更新执行 |
| 跨端契约 | `pkg/contracts/` | 面板与 Agent 使用的期望状态、消息、流量和发布等结构 |

模块目录并不表示全部边界已经完善；本轮新功能仍需按职责接入。数据库写入应由所属模块负责，跨模块流程复用接口或应用服务；总览负责汇总读取，不能成为业务配置的写入入口。

### 11.3 新增功能如何接入

| 功能 | 前端负责 | 面板负责 | Agent / 客户端负责 |
| --- | --- | --- | --- |
| 用户级订阅 | 用户表单、个人视图、复制和导入 | 身份归属、授权、凭据与订阅生成 | 客户端按配置接入；Agent 应用用户访问配置并采集 |
| 中转画布 | 对象、位置、连线、属性与草稿交互 | 资源解析、权限、方案保存、权威校验、转换为已有配置与发布任务 | Agent 编译和执行服务器方案；客户端运行支持的代理链配置 |
| 节点直接发布 | 创建/修改入口、进度与错误 | 保存业务配置，构建快照，交由发布模块协调 | Agent 校验、应用、反馈结果和必要的回滚 |
| 共用规则集 | 内容编辑、引用、格式说明 | 持久化、版本、授权及目标格式输出 | 客户端按支持方式更新；服务器通过配置发布使用 |
| 客户端策略 | 匹配、顺序、策略组和预览 | 维护全局模板并整合进完整订阅 | Clash/Mihomo 等客户端实际执行 |
| 服务器监控/调优 | 数据和执行结果展示 | 保存元数据、管理请求、汇总结果 | Agent 采集或执行；没有执行能力的功能不宣称生效 |

界面可做即时输入检查，但不能取代后端对权限和配置的最终校验。画布的图形布局可与运行配置分开保存；前端本地 `published` 字段不能作为真实部署结果。

### 11.4 两条清楚的执行流程

```text
服务器方案：
页面/画布编辑 → 面板业务模块校验与保存 → 构建配置快照
→ 发布模块协调 → Agent 渲染、校验、应用 → 结果回传 → 页面展示

客户端方案：
策略/规则集/链路编辑 → 面板保存与验证 → 订阅模块输出完整客户端配置
→ 用户更新订阅 → 客户端执行
```

移除“配置版本”菜单只简化操作入口，不改变这些模块的职责。客户端配置已经生成，也不代表所有客户端已经更新或连接成功。

### 11.5 前后台隔离与轻量实现原则

- 前后台可共用 API 封装和基础组件，专属页面和布局分别维护；修改共享默认样式前检查两侧影响。
- 长期可将当前按模式分支的大页面拆成清楚的前后台组件；按实际改动逐步拆分，不进行无关重构。
- `viewMode` 只控制显示方式，不能代替后端权限；普通用户数据由会话身份决定。
- `localStorage` 适合布局偏好或明确标注的本地草稿，不作为正式共享业务数据、授权或部署成功的依据。
- 复用现有代理、发布、订阅和 Agent 能力；只有确认现有模块无法合理承载时才新增模块，不为画布建立第二套发布系统。
- 采用直接、可读的逻辑和明确契约，避免通用引擎、重复校验、猜测性兼容和层层兜底。测试针对真实行为变化，纯布局调整不增加大量自动化用例。
