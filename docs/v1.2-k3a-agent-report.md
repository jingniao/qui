## YAML and loading

```yaml
cores:
  - name: xray
    path: /usr/local/bin/xray
  - name: sing-box
    path: /usr/local/bin/sing-box
```

The top-level key is exactly `cores`; item keys are exactly `name` and `path`.
The first item is the compatibility primary. One or two unique entries are
accepted; names are `xray` or `sing-box`, paths must be nonempty. Unknown keys,
duplicates, an empty list and multiple YAML documents are rejected. Legacy
`core_name`/`core_path` maps to one runtime, with an empty name meaning Xray.
When both representations are present, `cores` takes priority. Executable paths
retain the old executable-path semantics (they are not made relative to YAML).
Data and TLS paths retain config-relative resolution.

Because platform files were excluded, `internal/agent/configuration` owns the
strict YAML loader. It returns the existing `config.Agent` with primary scalar
fields and keeps an immutable copy of the parsed list keyed by absolute data
directory. CLI and Agent host loaders use it; worker subprocesses reload the
original config file. `internal/platform/config.LoadAgent` is unchanged and does
not understand `cores`. A future shared-config refactor should remove this
process-local compatibility bridge when platform edits are in scope.

## Runtime, revisions and recovery

- MultiRuntime implements core.Runtime over adapters, in configuration
  order. Production uses it for one or two enabled cores; the primary flat
  runtime migrates into runtime/<core>/ before restore.
- Dual runtimes use `runtime/xray/` and `runtime/sing-box/`, separating the core
  run marker, accounting key, access log and validation/gate temp files. Legacy
  primary runtime files migrate by restartable, conflict-refusing renames, with
  directory synchronization on Unix. Existing per-adapter lifetime checks still
  require proof of the exact old child's exit before replacement.
- `State.ForCore` retains assigned inbounds and the transitive routing closure,
  including group members, chain hops/final outbounds and backup edges. It
  preserves ordering, filters users/credentials/policies, and leaves the source
  state unchanged. `group:` / `chain:` references are normalized for reachability;
  implicit Direct/Block targets remain available. Outbounds are duplicated where
  both cores need them.
- One encrypted revision contains native configs as `{ "xray": {...},
  "sing-box": {...} }`. `DecodeCoreConfigs` also accepts legacy native JSON.
  Reconciler restore, as before, reconstructs metadata by rendering the
  authenticated desired snapshot rather than trusting cached native JSON.
- All active cores validate before any switch. Switching follows config order;
  failure compensates in reverse order, including the failing adapter. An
  independent bounded context permits compensation after request cancellation.
  Empty cores are stopped. In-memory runtime rollback and persisted Reconciler
  rollback are both supported; the latter verifies the retained desired state
  and original success receipt.
- Health is per core, with aggregate scalar health AND. Idle cores are healthy
  without being started. Supervisor tracks independent retry schedules, restores
  only failed cores, and skips only the held component for targeted recovery,
  gate expiry and probes. Normal publication/refresh remains serialized and
  blocked by any unresolved release hold.
- A shared allocator reserves every node inbound and all generated private
  ports. Dual render runs twice so both core configs guard all private stats and
  probe listeners, including ports allocated by the later core. The allocator
  prevents intra-Agent collisions; another local process can still win the
  bind race, handled through native validation/start failure and rollback. A
  targeted restore/update that discovers a new private listener is refused while
  a peer has an older guard set; publish an all-core revision to install the
  expanded guard set before retrying the targeted activation.
- Every adapter receives the same durable traffic/access sinks. Each retains
  its own accounting key and process epoch. Sampling attempts every active
  capable core even if a peer fails. Official sing-box without account stats
  remains unknown for its own inbounds and does not suppress Xray sampling.
- Connection snapshots merge counts by credential and deduplicate address keys;
  the merged epoch hashes the sorted constituent epochs. Failed measurements
  remain unknown. Negotiated multi-core peers additionally receive per-core
  snapshots, including measured peers while another core is down; address keys
  are removed unless device-gate observation was negotiated.
- Device gates fan out by the credentials bound to each core's enabled inbounds,
  independently of user byte-stat capability. Each adapter retains its existing
  volatile TTL, observation-failure revocation and fail-open logic.

Legacy scalar capabilities describe the primary. Scalar startup time and
traffic-source status use the primary; aggregate health uses AND. An old panel
can continue publishing empty-Core states to the primary. Additional connection
payloads are only sent after Welcome.multi_core_supported. Single-core production Agents also use MultiRuntime and advertise multi_core_supported.

## Per-component updates and disk compatibility

Configured cores have separate workers, pending results, component staging,
authenticated release holds and installation selection. The primary preserves
the original `release-history` / `identity/release-checkpoint.enc`. A secondary
uses `core-release-history/<component>` and
`identity/core-release-<component>.enc`. Verified executable images remain under
`releases/installed`, with component/digest-derived names. Activation holds the
Reconciler lock and restores only that component from the committed revision;
it does not restart a healthy peer. An idle component is version-verified but
not started. Startup repairs every configured component's interrupted update.
Results retain existing reconnect resend and permanent-rejection handling.

Storage format guards and retained-image prerequisites are detailed below.

## Persistent inventory, additions and removals (completed follow-up)

- `cores.json.enc` in the Agent data directory is an AES-GCM authenticated,
  node-bound overlay using the original configuration.key. Publication is a
  0600 temp-file write, file sync, atomic rename, then directory sync (Unix).
  Partial temporary files are ignored; wrong-node/tampered inventory fails
  closed. YAML ordering is retained, disabled entries override YAML, and new
  enabled names append deterministically. At least one core must remain. The
  active primary is persisted too; re-adding the original YAML primary cannot
  steal empty-Core assignments on restart.
- Production uses MultiRuntime for a single enabled core too. Runtime layout
  remains `runtime/<core>/` after removals; reducing to one core never returns
  to the flat layout. Initial flat primary files use the existing restartable
  migration before restore. The original YAML primary continues to identify
  its old release-history namespace even when another core becomes primary.
- Both supported components have workers, including absent components. An
  update for an absent component uses the same CoreSource URL/redirect allowlist,
  TLS, SHA-256, bounded archive extraction and executable-image verification as
  ordinary updates. Its own reported version and capabilities are checked before
  enabling it. No inbound can reference an absent core, so additions are idle:
  they are not started for an artificial health test, matching the ordinary idle
  update policy. The first real publication validates/starts it normally.
- Verified images live under `releases/installed/NAME-DIGEST.bin[.exe]`.
  Membership changes hold the Reconciler lock shared with apply, rollback,
  refresh and component updates. Inventory publication is the addition commit
  point; a failure before it keeps the old enabled set and revision. Startup
  removes uncommitted staging/unreachable images and revalidates a committed
  added image's recorded executable digest, size and executable format.
- Add receipts record the exact request identity, archive digest, URL, version,
  sequence and executable digest. Replays of the same request are idempotent;
  changed content under that ID is refused. Re-addition gets a new authenticated
  update-history namespace using its validated request ID. Previous histories
  stay as evidence; re-add sequence checks include the old history high-water
  when present, so removal cannot reset the component's anti-rollback check.
- RemoveCoreCommand is implemented. Current revision/identity and original
  success receipt are checked. Any inbound assignment, including disabled
  inbounds and empty-Core primary assignments, refuses removal (`core_in_use`).
  Interrupted staged revisions with authenticated desired snapshots are checked
  as well (`core_pending`). In-progress Apply shares the lock: removal waits
  for it to resolve and checks its resulting current revision. Last-core,
  stale-revision, unknown-component and unconfirmed-child-exit cases refuse.
- Removal stops/reaps the exact runtime before committing its disabled overlay;
  then detaches the idle adapter and deletes only digest-derived images inside
  the checked Agent-managed image directory. Interrupted cleanup is retried at
  startup, and cannot delete an image before a disabled runtime's marker owner
  confirms exit. Cleanup is idempotent; symlink image entries are unlinked, never
  followed. A symlink image directory is rejected.
- **K3c ownership:** installer YAML, v1/v2 install records and all external
  executables (including `/usr/local/lib/proxy-agent/NAME`) are untouched.
  An installer-owned core is disabled in inventory; uninstall/qui-update still
  own its file and recorded digest. qui-update can carry all recorded files and
  YAML forward without reviving a disabled core because the data overlay wins.
  Omitting installer flags remains non-removal. Explicit installation alone
  does not clear a disabled overlay: re-enable through the verified core update.
  No deploy changes are needed for this ownership policy.
- Successful removal receipts persist in inventory until the stream Ack is
  received, are replayed after reconnect/restart, and have idempotent task ID /
  component / revision semantics. Refusal replies do not mutate inventory.
  Capabilities are refreshed after operations and sent after removal results.

## Mixed-core byte accounting (completed follow-up)

Account counters keep their existing JSON shape and per-process epochs. Xray
and sing-box with with_v2ray_api write both cumulative user counters and a
separate per-core node aggregate (sum of the known account counters). Official
sing-box writes its upstream Clash cumulative node totals with its process epoch;
its user counters remain unavailable. Thus official sing-box only makes its own
assigned inbounds unknown for per-user D5 coverage. These are proxy observations,
not host NIC byte counters; Xray/qui sing-box aggregates cover configured observed
accounts, rather than claiming unaccounted core-internal traffic.

The additive traffic.Counter fields are `kind:"node"` and `core:"xray"` or
`"sing-box"`; node counters use credential/user/device sentinels `node`, empty
protocol, and `<process epoch>.node`. They are never user quota deltas. Node
batches are persisted separately from account batches through the same encrypted
spool/cursor, capacity, retry, quarantine and exact-payload Ack machinery. Each
(epoch, credential) cursor is independent; unchanged samples after restart do
not duplicate batches, and a new process can restart below an old total.

**Additional additive proto numbers:** Hello.node_traffic_supported=12 and
Welcome.node_traffic_supported=21. No existing numbers changed. Node batches are
sent only after Welcome.node_traffic_supported; multi_core_supported alone is
insufficient. Older peers skip these retained batches while compatible account
batches behind them drain. The backlog remains bounded by the normal spool cap;
full storage reports a persistence failure rather than discarding node totals.
Dynamic-descriptor tests include both new fields and unknown-field round trips.

New readers declare Configuration read maximum **4** (inventory semantics) and
Spool read maximum **6** (node-counter semantics); DesiredState/ReleaseHold stay
at 3 and CoreAccounting at 4. Production activation raises Configuration=4,
Spool=6, DesiredState=3, ReleaseHold=3 only after the existing retained-image
readability proof. Defaults retain old writes until activation. A retained
checkpoint-only Agent cannot be used as a fallback after this raise; upgrade the
retained images first. There is no panel migration or dependency change.

   node_traffic_supported. Set node_traffic_supported only after implementing
   the node-counter ingestion below. Persist per-core capabilities, versions,
   flags, heartbeat health/start and traffic-source status. Old Agents remain
   modeled as one core; missing observations must stay unknown.
2. Persist Inbound.Core in draft/desired/automatic/restore/subscription paths.
   Empty assigns to the currently reported primary. Validate protocol, forward,
   WireGuard, gate support and node-wide port uniqueness against the selected
   core. Preserve existing access and authorization rules.
3. Keep one update task per (node, component). An absent xray/sing-box can be
   installed by the existing schema-2 CoreUpdateRequest with its new component;
   route matching envelope component and validate idempotent results per task.
   Wait for success plus refreshed capabilities before offering that component
   in inbound selection. Idle enabled cores are healthy without a process.
4. Implement Owner remove tasks using RemoveCoreCommand(id, component, current
   revision); match and idempotently store/Ack RemoveCoreResult. Retry the same
   identity after disconnect; accept its replay after later revisions. Remove
   all inbound assignments first, including disabled ones, publish and confirm
   that revision, then remove. Never remove the last enabled core. Display
   core_in_use/core_pending/last_core/revision_mismatch refusals and keep the
   component visible until capabilities confirm removal. Installer-owned files
   remain installed but disabled; a verified update re-enables them.
5. Accept traffic.Counter kind=node only on negotiated node-traffic sessions.
   Validate its core, sentinels, empty protocol, revision, epoch and bounds;
   compute cumulative deltas independently by (node, epoch, credential).
   Persist batch idempotency and Ack using the ordinary TrafficBatch mechanism.
   Route these bytes solely into per-core/node totals; NEVER add them to quotas
   or add them again to the account-derived node totals. Account batches keep
   their original attribution/tombstone checks. Permit multiple live epochs per
   node; one core reporting must not retire a peer's epoch.
6. Consume ConnectionStatus.cores per (node, core) and aggregate active addresses
   across cores before admission; Agent fans gates out by assigned credentials.
   Legacy snapshot_json may be empty on a partially measurable node. Preserve
   source masking, volatile-only storage, TTL and fail-open behavior. Show D5
   coverage from each inbound's assigned CoreCapability, with official sing-box
   per-user bytes unknown even when its node aggregate is available.
7. Scoped restart/health checks keep existing additive core fields. Historical
   rollback remains node-wide; a removed core must be reinstalled before rolling
   back to an explicit-core revision that uses it. After a primary change, the
   Agent refuses historical revisions at/before that change containing empty-Core
   inbounds: their original primary is ambiguous. Publish an explicitly assigned
   copy as a new revision instead. GOST remains outside this phase.
