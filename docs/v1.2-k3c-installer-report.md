Implemented locally; not released. No commit, push, deployment, enrollment or

## Files and behavior

- `deploy/linux/install.sh`: repeatable core selection, per-core option state,
  pinned defaults, separate staging and binary destinations, complete record
  carry-forward and v2 writing. Every requested core is downloaded, verified and
  staged before the normal program/core publication starts. Existing core entries
  are merged by name; explicitly selected cores replace their own binary/digest,
  while omitted cores remain owned. Duplicate and unknown names are refused.
- `deploy/linux/node-install.sh`: repeatable selection with a single Xray default;
  passes all selected cores and their own versions/digests to one install.sh call.
  Official sing-box still selects the architecture/libc digest, including musl on
  Alpine. Qui sing-box retains same-release SHA256SUMS and offline sidecar support.
- `deploy/linux/service.sh`: shared, non-executable record parser/writer and Agent
  core-config writer. Records are parsed as data; never sourced or evaluated.
- `deploy/linux/update.sh`: reads v1/v2, snapshots and restores both supported
  core paths and Agent config in addition to the existing component files. Its
  recovery copy and service library already travel inside the durable snapshot.
  Agent updates from a v2 record refuse targets without the v2 writer before
  stopping the service, preventing older installers from dropping ownership.
- `deploy/linux/uninstall.sh`: validates every recorded core's ownership/digest
  before removing anything, then removes every recorded core binary. Existing
  identity, config, revision/spool/release state retention remains in effect.
- `deploy/linux/enroll.sh`, `renew-certificate.sh`, `node-ca.sh`, `panel-ca.sh`:
  accept the shared v1/v2 record contract, so fresh v2 installs can enroll and
  use certificate/CA maintenance commands.
- Tests: extended `core-asset-test.sh`, `release-version-test.sh`,
  `update-test.sh`; added `multi-core-test.sh`.
- Documentation: deployment guide, operations installation/update section and
  AGENTS.md §30. No new edits to systemd/OpenRC definitions were necessary.

## CLI and frontend handoff

The exact new selection syntax is **one `--core NAME` per selected core**:

```sh
--core xray --core sing-box
```

For `web/src/modules/nodes/api.ts:installCommand`, preserve its existing package
bootstrap prefix, URL, version, host, ports, certificate fingerprint and token
handling. Replace its scalar core suffix with the repeated flags from a
deduplicated, allowlisted selection. The default selection remains `["xray"]`.
The command after the existing bootstrap prefix should have this shape:

```sh
curl --no-insecure -fsSL https://github.com/jingniao/qui/releases/download/v<VERSION>/node-install.sh |
  bash -s -- --version <VERSION> --panel <HOST> --http-port <HTTP_PORT> \
    --grpc-port <GRPC_PORT> --ca-sha256 <SHA256> --token <TOKEN> \
    --core xray --core sing-box
```

Continue omitting `--http-port` for 443. Optional `--core-source official` selects
official sing-box; the default is qui. It never changes Xray's official source.
The frontend was read for this handoff but **not edited**; its scalar input and
checkbox UI still need their owning phase's change.

Manual installer example, run only from an already verified release directory:

```sh
deploy/linux/install.sh --node --binary bin/proxy-agent --sha256 <AGENT_SHA256> \
  --core xray --core-version 26.3.27 \
  --core sing-box --qui-version <QUI_VERSION>
```

`--core-version`, `--core-url`, and `--core-sha256` apply to the preceding
`--core`; source/release/qui sidecar options apply to sing-box globally. Defaults:
Xray 26.3.27, official sing-box 1.14.3, qui sing-box 1.14.4-qui.1. Existing Xray
`.dgst` validation, official sing-box's four pinned digests, and qui's unique
SHA256SUMS entry validation remain in use. Neither wrapper nor installer
downloads a second copy of the same selected core; duplicate selections fail.

New installs without flags install only Xray. An upgrade without flags does not
download cores: it carries the recorded set and digests into v2 and retains the
existing config verbatim. Explicit flags replace/add cores; omission is not core
removal. Offline Agent bundles do not make upstream Xray/official sing-box
downloads offline; qui sing-box still accepts its separate local archive/sums.

## Agent configuration and rollback compatibility

Fresh installs and explicit core selections write canonical absolute paths:

```yaml
core_name: xray
core_path: /usr/local/lib/proxy-agent/xray
cores:
  - name: xray
    path: /usr/local/lib/proxy-agent/xray
  - name: sing-box
    path: /usr/local/lib/proxy-agent/sing-box
```

The list is authoritative for K3a. Retaining the scalar pair for the first core
provides a compatibility fallback for older Agent binaries. It does not make an
older Agent multi-core capable. The updater additionally restores the original
config during a failed upgrade, so rollback does not depend solely on unknown-key
handling in an old binary. A plain upgrade can retain legacy-only config because
K3a accepts that as a one-core list.

Only the three top-level core settings are rewritten when cores are explicitly
installed; other YAML blocks are retained. Explicit core installation normalizes
custom core paths to installer-owned paths; review such configs before choosing
cores. Existing config is left byte-for-byte intact on upgrades without core
flags. Manual install.sh still requires a stopped main service and does not offer
the automatic transaction protection of qui-update.

## Record v2

The format has twelve metadata lines, including empty slots, followed by zero or
more core rows. All new installs and successful upgrades write v2, including panel
installs, which have no core rows.

| Line | Meaning |
| --- | --- |
| 1 | `proxycontrol-install-v2` |
| 2 | `panel` or `agent` |
| 3 | Program SHA256 |
| 4 | Main service-definition SHA256 |
| 5–6 | Reserved, empty |
| 7 | `installed` |
| 8–9 | Enforced-source service and trigger/watcher SHA256, or empty |
| 10 | `systemd` or `openrc`, always explicit in v2 |
| 11–12 | K2a tuning service and trigger/watcher SHA256, or empty |
| 13 onward | `core NAME /usr/local/lib/proxy-agent/NAME SHA256` |

V1 reading retains the core/digest on lines 5/6, completion on line 7, init on
line 10 and K2a tuning metadata on lines 11/12. Older short records remain
readable; missing v1 init means systemd in uninstall. V2 rejects duplicate or
unknown cores, noncanonical paths, malformed digests and truncated metadata.
Record entries authorize only the fixed installer-owned binary paths.

Recovery deliberately enumerates both supported binary paths, rather than
reading the live manifest while it is being replaced. This preserves all old
cores and removes newly created files absent from the snapshot. Journal format
stays `proxycontrol-update-journal-v1`: its component plus the updater copy
already determine the complete file set. Signal recovery, boot recovery,
idempotence, panel DB backup/rollback and component isolation keep their existing
protocols. The K2a tuning pair/watcher remains in snapshots and uninstall still
clears tuning before deleting its units or the Agent binary.

## Remaining acceptance and boundaries

- Run the complete Linux/root update suite, then actual systemd/OpenRC install,
  upgrade, failure and boot-recovery acceptance. K2a helper/root behavior and
  architecture/libc execution still need their existing Linux acceptance.
- Bootstrap the first migration with the **new updater from a verified release
  archive**, using the deployment guide's §5.0 method and `--component agent`.
  A previously installed updater cannot retroactively protect the extra files.
- Deliberate Agent downgrade from v2 to an installer without v2 support is
  refused. Failed upgrades can still restore the original v1 record/config.
- Frontend checkbox/command generation and K3a runtime compatibility are owned
  by their concurrent phases; this task does not certify their implementation.
- Only Xray and sing-box are supported by this contract. A future GOST installer
  must extend record validation, snapshot destinations, CLI and asset tests.
- Core removal is currently uninstall-all; omitting a flag never removes an
  installed core. Runtime state/config/identity retention follows §30.
