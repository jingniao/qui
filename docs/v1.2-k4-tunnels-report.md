# K4 — shared server tunnels and explicit object ownership

Date: 2026-10-29. Status: backend implemented locally; not released and not tested on real servers. The previous migration safety gate was resolved by the reviewer's explicit ownership/adoption decision. F4 can use the contracts below. Client execution remains self-contained.

## Storage and migration

`0124_canvas_tunnels.sql` is new. Migrations 0001–0123 are unchanged by K4.

- `canvas_tunnels`: `id`, unique `name`, strictly typed `connection_json`, `source_ref`, `target_ref`, compatibility `inline_scheme_id`, immutable display `object_prefix`, creation/update stamps, `published_version`, and nullable `allocated_port` (1–65535). The JSON contains the existing connection fields, not arbitrary transport settings. The API exposes those fields directly, not as nested JSON. Endpoints are refs such as `server:NODE_A`, not a drawing's instance IDs.
- `canvas_tunnel_objects`: `(object_kind, object_id)` is the primary key; `tunnel_id` references the tunnel with DELETE RESTRICT. Kinds are `inbound|outbound|chain`. A generated object has at most one owner. Ordinary object-deletion triggers remove its ownership row. Tunnel deletion first uses the existing reference/blocker/removal checks; it cannot cascade-delete unknown objects.
- `canvas_tunnel_publications`: records the tunnels in the last publication of each drawing, including a tunnel dropped from its current layout until cleanup is published. Scheme deletion cascades only these associations.
- `canvas_tunnel_reconcile`: one transactional, idempotent legacy reconciliation marker.

SQL creates **one tunnel per existing server connection** and adds `tunnelId` to its layout connection. IDs/names for these migrated resources are `SCHEME_ID.CONNECTION_ARRAY_INDEX`. It never merges two schemes' connections. Forwarding ports retain connection values or the old instance-port fallback. Client layouts and client published snapshots are not rewritten.

Go reconciliation runs at panel startup, before canvas mutations, and in a restore candidate immediately after migration. Automatic adoption requires an existing published server scheme (`publishedAt` nonempty), exact object names generated from its **current** scheme/node names and connection, compatible generated object shape, and a unique claim. Previously allocated implicit listeners are matched by their exact generated name and actual port; ambiguous matches remain unowned. The transaction records object IDs and the allocated port, then marks reconciliation complete. Subsequent name changes never repeat the adoption scan.

There is no attempt to infer deleted or renamed historical owners. Schemes renamed **before** migration, deleted drawings, deleted-name reuse, conflicting claims and unresolved historical chain ownership remain unadopted. Legacy two-hop chain objects are intentionally not automatically assigned to one of their two edge tunnels; the Owner can explicitly assign a compatible chain to its first-hop tunnel. Edge objects can still be adopted when their individual exact-name claims are unique. This means ambiguous legacy publications require reconciliation before publishing, rather than being advertised as migration-complete.

Production planning, lookup, port reuse, publication and removal use `canvas_tunnel_objects`. Prefix inventory helpers are test-only. The old name pattern is used solely for migration matching and the Owner's unowned-legacy inventory. Unadopted objects remain ordinary objects and are never pruned by a tunnel publication.

## Scheme compatibility and sharing

A server write can send a reference-only connection:

```json
{
  "name":"relay-b",
  "execution":"server",
  "layout":{
    "instances":[
      {"instanceId":"a","ref":"server:NODE_A","x":40,"y":120,"role":"entry"},
      {"instanceId":"b","ref":"server:NODE_B","x":320,"y":120,"role":"exit"}
    ],
    "connections":[{"id":"edge","source":"a","target":"b","tunnelId":"TUNNEL_ID"}]
  }
}
```

For `PUT /api/v1/canvas-schemes/SCHEME_ID`, also send the scheme's `updatedAt`. Unknown fields remain rejected. A reference's endpoints must match the resource endpoints. The server hydrates `type`, protocol, ports and transport flags from the tunnel on every GET/list/plan/publish; inline values supplied alongside `tunnelId` do not override the resource.

GET responses retain the existing scheme envelope and return hydrated connections, for example:

```json
{
  "id":"SCHEME_ID","name":"relay-b","execution":"server",
  "layout":{
    "instances":[
      {"instanceId":"a","ref":"server:NODE_A","x":40,"y":120,"role":"entry"},
      {"instanceId":"b","ref":"server:NODE_B","x":320,"y":120,"role":"exit"}
    ],
    "connections":[{
      "id":"edge","source":"a","target":"b","tunnelId":"TUNNEL_ID",
      "type":"tunnel","tunnelProtocol":"tls","tunnelPort":8443,
      "supportTcp":true,"supportUdp":true
    }]
  },
  "createdAt":"TIMESTAMP","updatedAt":"TIMESTAMP",
  "publishedAt":"TIMESTAMP","publishedBatchId":"BATCH_ID"
}
```

Old inline requests without `tunnelId` remain supported transactionally. A new `(scheme ID, connection ID)` creates a tunnel whose initial name is its generated ID. Reusing that connection ID updates its previous tunnel **only if that tunnel was originally created inline for this scheme**. If the previous connection referenced somebody else's tunnel, omitting `tunnelId` creates a separate inline tunnel. Scheme save, resource changes and layout references commit or roll back together, including a stale-scheme failure. Explicit references never implicitly edit a shared resource; F4 should use tunnel PUT for that.

A resource edit is visible in every referencing scheme. Endpoint edits atomically retarget all referring drawings and advance their scheme tokens. A matching server box is reused; otherwise a box is cloned from the previous endpoint with a new instance ID and a 40-pixel offset, preserving unrelated connections. Layout limits still apply and failure rolls back the whole edit. Inline endpoint updates also retarget other referencing drawings.

Two drawings referencing one tunnel generate one object set. Publishing unchanged, already-published tunnel dependencies is a no-op and returns `{"nodes":[],"warnings":[]}` with no deployment call. Publication still records the new drawing's publication association. Shared-hop chain/entry dependencies are included when a tunnel edit requires them; disconnected edits in other drawings are not included. Chains retain owned identity across port/name changes by their sequence of tunnel owners. Two server schemes routing the same entry inbound through different tunnel-ID paths fail plan/publish with `entry_routing_conflict` in the message.

Allocated implicit ports are persisted per tunnel and survive node range edits. A different tunnel cannot automatically take over an owned listener. The old cross-connection listener takeover test now asserts a conflict; resolving that conflict requires the Owner to keep the same tunnel, remove the other resource, or explicitly reconcile unowned legacy objects.

Dropping a reference saves only a draft. On the next publish of the last scheme that dropped it, an unreferenced tunnel's objects are removed in chain/outbound/inbound order, using the existing outside-reference blockers and undo behavior. A tunnel still referenced by another drawing retains its objects. Deleting a drawing retains objects; an orphan whose last drawing was deleted can be explicitly deleted through tunnel DELETE. Unadopted legacy objects are never included in this cleanup.

Client schemes reject `tunnelId`, keep inline connections, retain their existing client publication path, and still return `ok:false` for the server plan endpoint. `tunnel` and `proxy_chain` remain aliases for the same server-hop semantics and the same client mihomo path semantics. Unsupported tunnel implementations are still refused at publication.

## F4 tunnel API

All routes are Owner-only. Writes require the existing administrator CSRF mechanism and record audit actions. GET does not expose credentials. URLs below use the `/api/v1` prefix.

| Method | Path | Result |
| --- | --- | --- |
| GET | `/canvas-tunnels` | `{"items":[<tunnel>],"total":N}`; no pagination |
| POST | `/canvas-tunnels` | 201, one tunnel |
| PUT | `/canvas-tunnels/{id}` | 200, one tunnel; `updatedAt` required |
| DELETE | `/canvas-tunnels/{id}` | 204, or 409 `tunnel_in_use` |
| GET | `/canvas-tunnels/legacy-objects` | `{"items":[<legacy-object>],"total":N}` |
| POST | `/canvas-tunnels/{id}/adopt` | 204 after transactional compatibility/ownership checks |

Create body (PUT uses the same body plus `updatedAt`):

```json
{
  "name":"A to B TLS",
  "type":"tunnel",
  "source":"server:NODE_A","target":"server:NODE_B",
  "tunnelProtocol":"tls","tunnelPort":8443,
  "supportTcp":true,"supportUdp":true
}
```

The complete writable field set is `name`, `source`, `target`, `type`, `tunnelProtocol`, `tunnelPort`, `listenPort`, `targetHost`, `targetPort`, `supportTcp`, `supportUdp`, `updatedAt`. `type` is `tunnel|port_forward|proxy_chain`; protocol vocabulary is `tls|wireguard|gost|brook|nftables`. Optional unset values are omitted; ports are 1–65535. Forward settings require `port_forward`. For a forwarding tunnel, for example, use:

```json
{
  "name":"A to B forward","type":"port_forward",
  "source":"server:NODE_A","target":"server:NODE_B",
  "listenPort":10080,"targetHost":"example.com","targetPort":443,
  "supportTcp":true,"supportUdp":false
}
```

Tunnel response/list-item shape:

```json
{
  "id":"TUNNEL_ID","name":"A to B TLS","type":"tunnel",
  "source":"server:NODE_A","target":"server:NODE_B",
  "tunnelProtocol":"tls","tunnelPort":8443,
  "supportTcp":true,"supportUdp":true,
  "createdAt":"TIMESTAMP","updatedAt":"TIMESTAMP",
  "schemes":[{"id":"SCHEME_A","name":"relay-a"},{"id":"SCHEME_B","name":"relay-b"}],
  "objects":[
    {"kind":"inbound","id":"INBOUND_ID","nodeId":"NODE_B","name":"OBJECT_NAME","port":8443},
    {"kind":"outbound","id":"OUTBOUND_ID","nodeId":"NODE_A","name":"OBJECT_NAME","port":0}
  ],
  "publishStatus":"published"
}
```

`schemes` and `objects` are populated by GET list; mutation responses return these arrays empty, so refresh the list after writes. Status is `draft` (no recorded published version), `modified` (resource stamp differs), or `published` (recorded versions match). It describes panel publication bookkeeping, not Agent health or deployment completion. A failed/in-progress deployment must still be checked through normal deployment results. Outbounds and chains have `port:0`; a chain's `nodeId` is its first node. Empty references/objects are `[]`.

In-use deletion uses the standard nested error envelope:

```json
{"error":{"code":"tunnel_in_use","message":"tunnel_in_use","schemes":[{"id":"SCHEME_A","name":"relay-a"}]}}
```

A stale PUT returns 409 `stale_scheme`. Unknown fields/invalid kinds or incompatible node/port assignments return an invalid-request error. An already-owned adoption object returns 409 `object_owned`; it is never reassigned, even to the same tunnel.

Legacy list item:

```json
{
  "kind":"inbound","id":"LEGACY_INBOUND_ID","nodeId":"NODE_B",
  "name":"[old-name] Node A → Node B (trojan:8443) 中转入口","port":8443,
  "candidateTunnels":["TUNNEL_ID"]
}
```

`candidateTunnels` lists compatible resource IDs, not proof of historical ownership; it is omitted when empty. The list includes only unowned objects with the old canvas-generated shape/name pattern. Explicit adoption body contains only kind and ID:

```json
{"objects":[{"kind":"inbound","id":"LEGACY_INBOUND_ID"},{"kind":"outbound","id":"LEGACY_OUTBOUND_ID"}]}
```

One to 100 entries are accepted; duplicate entries are refused. Existence, kind, source/target node, protocol/listener-port compatibility and ownership assignment are checked in one transaction. No partial adoption occurs when any requested object fails. A compatible chain can be assigned to its first-hop tunnel. This is an explicit Owner decision and is audited.

## Plan contract

`POST /canvas-schemes/{id}/plan` keeps its optional body: empty, `{}`, or `{"layout":<layout>}`. After startup reconciliation it performs no writes. Existing server/connection/warning fields remain, with `tunnels` and optional conflict metadata added:

```json
{
  "ok":true,
  "servers":[{
    "nodeId":"NODE_B","name":"Node B",
    "creates":[{"kind":"inbound","name":"OBJECT_NAME","protocol":"trojan","port":8443}],
    "updates":[],"removes":[]
  }],
  "connections":[{"id":"edge","status":"ok","message":"可发布"}],
  "conflicts":[],"warnings":[],
  "tunnels":[{"tunnelId":"TUNNEL_ID","affectedSchemes":[{"id":"SCHEME_A","name":"relay-a"},{"id":"SCHEME_B","name":"relay-b"}]}]
}
```

`affectedSchemes` lists the current referencing server schemes; a pending last-reference removal also includes the publishing scheme. Routing dependencies can add further tunnels to the plan. This array is available for saved references even when planning fails. Existing objects can remain in `updates` even if a publish can skip an unchanged object set; it is a proposed save, not a claim that each field differs. Top-level `message` is optional.

A colliding unadopted legacy listener/object produces `ok:false`, with a conflict such as:

```json
{"nodeId":"NODE_B","port":8443,"with":"LEGACY_OBJECT_NAME","connectionId":"edge","reason":"legacy_object","objectId":"LEGACY_INBOUND_ID"}
```

Listener conflicts normally identify the connection and node. Name-only outbound/chain conflicts can have `nodeId:""`, `port:0`, `connectionId:""`; `objectId` and `reason` identify the reconciliation problem. Other reasons currently include `listener`, `tunnel_object`, and `object_name`. Publish refuses the same conflicts.

`web/src/modules/proxy/api.ts` provides the resource types, reference-only write-layout type, `CanvasTunnelPlan`, and `canvasTunnelAPI` helpers. Existing conversion helpers retain `tunnelId` in both directions. No F4 page wiring or frontend component edits were made by K4.

## Backup, restore and validation

The portable database includes tunnels, object ownership, publication associations, allocation state and reconciliation marker. Inventory adds `canvasTunnels` and `canvasTunnelObjects`. Archive verification checks schema/migration presence, strict connection JSON, typed layouts, resource references and dangling polymorphic ownership. Ordinary SQLite integrity/foreign-key verification continues to apply. Pre-0124 archives are accepted without these tables; recovery migrates their candidate database and runs the same one-time adoption rule before it can be served. No real `state/panel.db` or server was accessed.
