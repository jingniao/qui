## 1. Findings

### 1.1 Node groups are the only access path

`user_node_group_grants` decides:

- which users' credentials go on a node;
- subscriptions, including `nodeGroup:<id>` labels;
- rule templates (`@nodeGroup`);
- policy entry-group scope;
- portal node lists;
- quota auto-revision targets.

Only the 节点组 page creates groups or sets purpose, enabled and subscription
visibility. With G1, the backend is unchanged and the UI moves.

### 1.2 Node Topology and Administrators

Topology is linked only from the sidebar and points at retired routes, so it is
safe to remove. Moving Administrators is frontend only.

### 1.3 Server pages and the New Node form

This is unchanged from rev 1. In short:

- **Server pages:**
  - hard-coded "—" values, fake 测试点 boxes and "待办" cards;
  - missing AGENTS §11.1/§11.2 fields;
  - duplicated status logic, and `core_error` renders grey;
  - one meta request per node;
  - raw hex colours;
  - 1.3–1.5k-line files with dead code.
- **新建节点 form:**
  - hides options the backend supports;
  - validates by toast only;
  - has no port-conflict or capability check;
  - accepts TLS without a certificate;
  - publishes without review.

### 1.4 How a relay scheme reaches users today

- **Server-executed scheme** (the canvas, `canvas_schemes`):
  - It routes **existing entry inbounds**, rewriting their `DefaultOutbound`.
    Each scheme on a node is reached through its own entry inbound.
  - It also creates hidden relay inbounds, relay outbounds, chains and forwards.
  - Ownership of those objects is tracked **only by a name prefix**
    `"[scheme] "`. There is no `scheme_id` column, and entry inbounds are
    recorded only inside `layout_json`.
- **Per-inbound restriction:** `inbounds.allowed_users_json`. An empty list
  means every node-group-granted user; a non-empty list means
  node-group-granted ∩ the list. The renderer and subscriptions enforce it.
- **Client-executed scheme:** a mihomo `dialer-proxy` chain. It appears in a
  subscription only when the user already receives every hop. There is no
  per-scheme filter.
- **Policies:** scopes have users, devices, nodes and groups, but **no inbound
  scope**. One scheme cannot be restricted by policy.
- **Pre-existing behaviour to decide on:**
  - Quota auto-revisions take each user's inbound binding from the **draft**.
    So an unpublished change to an inbound's allowed users goes live on the
    next automatic revision.
  - This is the documented "accepted exception" (AGENTS §22.1), but it matters
    more once access is managed per scheme.

### 1.5 Single-core assumptions (inventory)

Every layer assumes one core:

- **Agent configuration and runtime:**
  - config `core_name`/`core_path`;
  - one adapter, one Reconciler and one supervisor loop;
  - one `revisions/<rev>/core.json.enc`;
  - one `core-run.json.enc` and `accounting.key` in a shared runtime directory;
  - one access log;
  - independent loopback-port pickers per core.
- **Agent updates and capabilities:**
  - one core-update worker, staging directory and release hold;
  - one capability record.
- **Wire (proto):**
  - `Capabilities` has a scalar `core_name`/`core_version` and one protocol
    list;
  - `Heartbeat` has a scalar `core_healthy`/`core_error`/`core_started_at`;
  - `RollbackCommand.restart_current` assumes one core.
- **Panel:**
  - one `nodes.capabilities_json`;
  - `ValidateCoreProtocol(node core)`;
  - `core_update_tasks` has no component column, with one active task per node;
  - `node_live_connections` stores one row and one epoch;
  - D5 ("sing-box node → no per-user stats") is per node.
- **Installers:** a single `--core`, and an install record with the core at a
  fixed line number.

`desiredstate.Inbound` has **no core field**. Outbounds, groups, chains and
policies are node-global, and each renderer consumes the whole state.

### 1.6 GOST

- **Upstream:** MIT, v3.3.2, `gost_<ver>_linux_{amd64,arm64}.tar.gz` plus
  `checksums.txt`.
- **What it adds** over core `forward` inbounds:
  - multi-target load balancing and failover;
  - port ranges;
  - per-forward bandwidth and connection limits, and byte counters;
  - encrypted forward-only hops (relay over tls/wss/quic, with mTLS);
  - UDP-over-TCP;
  - reverse forwarding.
- **What it cannot do:** it has no user-identity inbounds. It never serves
  subscriptions, quota, device limits or domain access logs, which remain L10
  semantics.
- **Operational constraints:**
  - its Web API, metrics and pprof must stay off or Unix-socket only;
  - certificate changes need a restart, not a reload.

## 2. Design decisions

### 2.1 Group management under 节点配置 (G1)

- New in-page panel **节点配置 › 节点分组**: a tab on the 节点配置 page, not a
  sidebar page. It uses the existing `/api/v1/node-groups` APIs:
  - list with member counts and purpose;
  - create, rename, delete;
  - purpose, enabled, subscription visible, remark;
  - add/remove servers (multi-select).
- Membership can also be edited from Server Details. That save becomes atomic
  via a new `PUT /api/v1/nodes/{id}/groups`.
- **Redirects:**
  - `/node-groups` → the 节点分组 tab;
  - `/topology` → `/proxy/relay`.
- All links that went to `/node-groups` are retargeted: Server Details and the
  empty states of the user grant pickers.

### 2.2 Per-scheme access control (new, decision S)

Recommended model **S1 — scheme grants intersected with node groups**:

- **New table** `relay_scheme_grants(scheme_id, user_id)`, with cascade on both
  sides.
- **New columns:**
  - `canvas_schemes.access_mode`, either `all_granted` (default; today's
    behaviour) or `listed`;
  - `inbounds.scheme_id`, nullable. The scheme records the entry inbounds it
    owns and the hidden objects it creates, which replaces name-prefix
    ownership. A one-time migration backfills it from `layout_json` and the
    existing name prefixes.
- **Effective access** to a scheme =
  `users granted the entry node through node groups ∩ (all | listed users)`.
  Node groups stay the outer boundary, so a scheme can narrow access but never
  widen it.
- **Server schemes:**
  - The renderer applies the scheme filter to the scheme's entry inbounds.
  - An entry inbound belongs to **at most one scheme**. The canvas refuses to
    reuse an inbound another scheme owns, so per-scheme access is unambiguous.
  - The inbound's own `allowed_users` stays for inbounds that no scheme owns.
    For scheme-owned inbounds, the scheme's grants replace it, and the editor
    shows it read-only with a link to the scheme.
- **Client schemes:** `Chains()` receives the viewer's user ID and includes a
  scheme only if the user passes the scheme's grants **and** receives every hop.
- **Subscriptions:** proxies from a scheme get a `scheme:<id>` label. Rule
  templates gain `@scheme:<id>` next to `@nodeGroup:<id>`, so client rules can
  target one scheme.
- **Policies:** add an `inbound_ids` scope (additive), so node policies can
  apply to one scheme's entry. The canvas offers this directly.
- **Portal:** users see the schemes available to them, each with its entry
  nodes.
- **UI:** each scheme on the canvas gets an 访问权限 panel:
  - an `all_granted` / `listed` mode toggle;
  - a user picker limited to node-group-granted users;
  - a preview of the effective users.

  A user's detail page lists the schemes they can use.
- **Publishing:** a grant change is a draft change like any other and takes
  effect when the scheme or node is published.
- **Decision S2** — what quota auto-revisions do with binding changes:
  - **S2a (recommended):** auto-revisions use the **published** grant and
    binding state, so unpublished access edits never go live early. This closes
    the AGENTS §22.1 exception.
  - **S2b:** keep today's ride-along behaviour.
- **Backups and restore:** the new table and columns go into backup validation,
  inventory and the restore merge (the precedent is `user_source_grants`).
  Restore joins grants on existing users.
- **Not chosen:**
  - **S2 (reuse `allowed_users` only):** two writers and no ownership, and it
    can't cover client schemes.
  - **S3 (a node group per scheme):** groups grant whole nodes, so two schemes
    on one node can't be separated.

### 2.3 Multi-core nodes (decision MC)

**Model:**

- **Cores per node:** a node has a **set of enabled cores**, e.g.
  `{xray}`, `{sing-box}`, `{xray, sing-box}` or `{xray, gost}`.
- **Core assignment:** every inbound and forward is assigned to one core
  (`Inbound.Core`, `omitempty`). Empty means the node's legacy single core.
- **Per-core render:** each core gets only its own inbounds, plus the
  transitive closure of the outbounds, groups, chains and policies they
  reference. Outbounds are duplicated per core, not shared, so each core routes
  its own traffic. Users and credentials are rendered into each core that
  serves them.
- **GOST:** a core kind that serves only forwards and relay hops (see §2.4).

**Agent:**

- **Config:** `cores: [{name, path}]`. The legacy `core_name`/`core_path` maps
  to a one-element list.
- **`MultiRuntime`:** implements today's `core.Runtime` over one adapter per
  enabled core. This keeps the Reconciler, supervisor and control loop mostly
  intact. Each core gets its own runtime subdirectory (`runtime/<core>/`), which
  separates run markers, the accounting key, access logs and temp files.
- **Revisions:** one revision covers all cores. `core.json.enc` holds
  `{core: config}`, and legacy single-blob revisions still decode. Apply
  validates every core first, then switches the cores one by one. A failure
  restores the cores already switched (compensating rollback). On startup,
  per-core markers let the Agent finish an interrupted switch.
- **Health:** reported per core. The aggregate `core_healthy` is the AND of all
  cores. The supervisor restores only the unhealthy core, with per-core backoff.
- **Shared resources:**
  - One loopback-port allocator covers every core's inbounds, stats, probe and
    gate ports.
  - Panel validation enforces port uniqueness per node across all cores and
    forwards.
- **Traffic and gates:**
  - Traffic and user stats come from each core into the same spool. Counters
    are already epoch-tagged, and the panel's epoch handling must allow several
    live epochs per node.
  - Connection snapshots are merged.
  - Device gates fan out to the cores serving the device's inbounds; fail-open
    is evaluated per core.
- **D5 becomes per inbound:** a user's traffic on a sing-box inbound without
  `with_v2ray_api` counts as unknown for that inbound only.
- **Core updates:**
  - per component: worker, staging directory and release hold;
  - the panel adds `core_update_tasks.component`, with one active task per
    (node, component);
  - the UI shows and updates each core.
- **Resources:** a core with no inbounds is not started. A single-core setup
  stays the default for small nodes.

**Protocol** (A.4, additive):

- `Capabilities.cores` (repeated `CoreCapability`: name, version, protocols,
  flags);
- `Heartbeat.cores` (repeated `CoreStatus`: health, error, started_at,
  traffic-source status);
- Hello/Welcome `multi_core_supported`;
- an optional `core` field on `RollbackCommand` and the health result.

**Compatibility:**

- An old Agent reports a single core. The panel never publishes an
  `Inbound.Core` that differs from that core, and multi-core is offered only
  when `multi_core_supported` is set.
- A new Agent keeps filling the scalar fields with its primary core and the
  AND-health, so old panels keep working.

**Panel and UI:**

- per-core capabilities, health and versions on the server pages;
- a core selector in the New Node form, limited to cores the node runs;
- a core column in inbound lists;
- the D5 note per inbound;
- `node_live_connections` per (node, core).

**Installers:**

- `--core` may repeat, e.g. `--core xray --core sing-box`.
- A versioned install record v2 lists the cores. `qui-update` carries every
  core forward, and uninstall removes them all.
- The panel's one-click command offers core checkboxes.

**Docs:**

- AGENTS.md: remove the §35 exclusion; rewrite §4.4, §23 and §32.
- `lightweight-refactor-plan.md`: D1 and D5 superseded.
- `deployment.md`: drop "the panel cannot switch a node's core". Cores can now
  be added or removed per node through an Owner action with an install/update
  step.

### 2.4 GOST as a core kind

- **Install and updates:**
  - core kind `gost`, installed only from official GOST releases verified
    against `checksums.txt`;
  - the URL allowlist is the GOST download prefix;
  - same update, health and rollback flow as the other cores.
- **Runs under MultiRuntime** with:
  - its own runtime subdirectory;
  - the config rendered as YAML;
  - Web API, metrics and pprof off (or a Unix socket only);
  - restart-based apply.
- **Objects it serves:**
  - `forward` inbounds assigned to `gost`, extended with multiple targets plus a
    strategy (round/fifo, with maxFails/failTimeout), port ranges, and
    bandwidth/connection limits;
  - encrypted relay hops between qui nodes: a GOST relay over TLS/WSS/QUIC with
    mTLS, using panel-generated node-to-node credentials kept separate from user
    credentials (§9.3), deployed in dependency order like proxy chains.
- **Accounting:** per-forward byte totals via the GOST observer (loopback
  only). These count toward node traffic, with no per-user or domain records
  (L10).
- **Canvas:** the "Gost (TLS 隧道)" connection publishes GOST relay hops.
  Port-forward connections can choose `gost` or a proxy core as the engine.
