## F1 — normal Agent shutdown logged at ERROR

Evidence: uk-node journal, 2026-11-01 10:28 (kernel reboot):
`level=ERROR msg="approved runtime state reconciliation failed" error="context canceled"`.
Code: `internal/agent/supervisor/supervisor.go` logs every `reconciler.Refresh`
error at ERROR, including the cancellation of a normal stop.

Proposed direction: do not log (or log at debug) when the supervisor's own
context is done; keep ERROR for every other failure. One check at the call
site, no new helper.

## F2 — `install.sh` prints its first-install hint during `qui-update`

Evidence: H1 (panel) and H3 (Agent) update output end with
"Next: review /etc/proxy-*/config.yaml, then systemctl enable --now …" right
before qui-update reports the service as running.

Proposed direction: `update.sh` already knows it is updating; have it ask
`install.sh` not to print the first-install hint (an existing mode/flag if
there is one, otherwise one variable), rather than duplicating the message
logic.

## F3 — a user inbound hidden from subscriptions is silently published disabled

Evidence: H7 (uk-node, revisions 136 and 138): an enabled SOCKS5 inbound with
`subscriptionVisible=false`, even as a member of the user's granted node group,
gets `credential_ids=[]` and is rendered `enabled=false`; the inbound API still
returns `enabled: true` and nothing warns the Owner. Cause: user credentials
are assigned only for subscription-visible inbounds
(`internal/panel/user/snapshot.go`, `AND i.subscription_visible=1`), and the
renderer disables an inbound without credentials
(`internal/panel/proxy/snapshot.go`). With the flag set to true the same
inbound served TCP and UDP (revision 139).

Question for Codex: is "hidden" meant to imply "no user access"? AGENTS §12
says internal relay inbounds should be hidden, which suggests hidden =
internal; but the editor lets the Owner create a hidden, non-relay user inbound
and shows it enabled. Options: (a) keep the rule and make it visible — the API
reports the effective state (for example `effectiveEnabled` plus a reason) and
the editor warns when a user inbound is hidden; (b) change the rule so hidden
user inbounds still receive credentials of granted users (subscription
visibility only controls listing). The reviewer leans to (b) if nothing else
depends on the coupling, because the flag's name describes listing, not
access; otherwise (a).

## F5 — the device limit does not reliably observe a second device (P1)

Setting: uk-node on Agent 1.2.0-rc.1 (Xray 26.3.27), active user alice with
deviceLimit 1, public SOCKS5 inbound uk-node:35101. Source A = alpine-node
(113.29.231.0/24), source B = us2-node (23.254.158.0/24). All times UTC,
2026-11-01; devices-online is the panel's admission view (masked addresses).

Run 1 (03:27–03:28): A held a slow download; B made 12 short requests 6 s
apart. All 12 returned 200; devices-online only listed A.

Run 2 (03:36–03:41, after an admission reset):

| Time | Event | devices-online |
| --- | --- | --- |
| 03:36:17–23 | A: one short request, then a slow download (20 kB/s) | |
| 03:37:13 | | A allowed, active; firstSeen 03:36:22, lastSeen 03:36:26 |
| 03:37:23 | B: slow download started | |
| 03:38:14 | (both downloads ended by themselves about 55–60 s after start) | only A, allowed, active=false; **B absent** |
| 03:39:05 | B: slow download re-opened | |
| 03:39:11–40:16 | B: 12 short requests, all 200 | 03:39:36: **no items** |
| 03:40:40 | | B allowed, active; firstSeen 03:40:16 (= request 12) |

So B was not observed while A should still have held the slot (A's 60 s
active + 120 s release ends about 03:39:26), and B's new connections were
never refused. The real-core CI gate tests pass because they apply the gate
directly (`SetDeviceGate`) and do not depend on the observation.

What is known from the code: the Agent samples connections only at each
heartbeat (every 15 s; `internal/agent/control/control.go`,
`connectionReader`); Xray sources come from `GetStatsOnlineIpList`
(`internal/agent/core/xray/online.go`); the existing real-core test
`TestRealOnlineStatisticsTrackAnAuthenticatedClient` expects the user to go
offline right after its connection closes. What is not known: whether Xray
lists an IP for the whole life of a connection or only for a short time after
it starts (A's firstSeen/lastSeen 4 s apart, and B's slow download not seen at
all, point to the latter), and whether the test downloads really stayed open.

Asks for Codex:
1. Settle the Xray online-IP semantics with a controlled experiment on the
   local Linux test machine (`~/.qui-local/r.sh`, Xray 26.3.27 in
   /root/qui-cores, source tree in /root/qui-src): one long-lived connection
   and repeated short ones through a real Xray inbound, polling
   `GetStatsOnlineIpList` every second for a minute. Same for sing-box's Clash
   API connections.
2. Propose the smallest fix that makes "active source" reliable for both cores
   without duplicating the Xray and sing-box paths. Options: sample more often
   and send the union since the last heartbeat; or take sources from the
   access log the Agent already parses every ~100 ms (Xray access lines carry
   the source and the user). No new persistent data; addresses stay in memory.
3. A test that would have caught this: a real-core test that goes through the
   observation (not `SetDeviceGate` directly) with a second source making only
   short connections.

## F6 — a user PUT that changes only deviceLimit also sets trafficResetAnchor (P3)

Evidence: alice had `trafficResetCycle: none`, `trafficResetAnchor: ""`. A PUT
with all fields copied and deviceLimit 1 returned anchor
`2026-11-01T03:19:09.724286340Z`; the restoring PUT with anchor `""` kept it.
Harmless while the cycle is none, but an edit of one field should not change
another. Direction: only default the anchor when a cycle other than none is
set (or keep the stored value when the input is empty and the cycle is none).

## Agreed approach (reviewer decision after discussion with Codex, 2026-11-01)

Codex's experiment on the local test machine (Xray 26.3.27, sing-box 1.14.3,
one 50 s connection plus 1 ms connections every 6 s, polled every second):
Xray lists a source for the whole life of a connection and about 0.75–1.95 s
after it closes; sing-box `/connections` lists only open connections (no
millisecond connection was ever seen). Correction to F5: production samples
every 5 s (`supervisor.Run` → `SampleConnections`) and `observer.Store.Record`
replaces the snapshot, which the 15 s heartbeat then reports — a source caught
in one sample is overwritten by the next empty one. Codex proposed access-log
capture (~200–300 lines); the reviewer chose the smaller fix below, Codex
agreed with 500 ms sampling as its one condition.

## F7 — Agent 1.2 cannot be installed on Alpine/OpenRC: `proxy-agent-tuning` fails to start (P1)

Evidence: H4 on alpine-node (Alpine 3.19 LXC, OpenRC 0.52.1 [LXC], libcap2
present, kernel 6.1.0-54-cloud), two attempts (03:47 and 03:51 UTC,
2026-11-01) of `update.sh --component agent --version 1.2.0-rc.1 … --yes`:

```
 * service proxy-agent-tuning added to runlevel default
 * Caching service dependencies ... [ ok ]
 * ERROR: proxy-agent-tuning failed to start
Installation stopped after it had begun replacing files …
[proxy-agent] install.sh 失败：回滚到 1.0.9 ...
[proxy-agent] 已恢复到 1.0.9，服务运行正常（10 秒内无重启）。
```

Both times the rollback restored 1.0.9 correctly (OpenRC failure path works;
komari-agent, cf-probe, crond stayed started; no tuning process or file left).
syslog has only `daemon.err /etc/init.d/proxy-agent-tuning[…]: ERROR:
proxy-agent-tuning failed to start` and **no** `supervise-daemon … Supervisor
command line` line for the tuning service, while proxy-agent-host-network
(same mechanism, `--capabilities ^cap_net_admin --no-new-privs`) starts
normally. So the start fails before supervise-daemon runs the helper.
Container facts: CapBnd/CapPrm/CapEff = 0x1ffffffffff (capabilities 0..40),
`cap_last_cap` = 40 (so `start_pre` passes), no capsh/setpriv installed.

The init script is `deploy/openrc/proxy-agent-tuning`: supervise-daemon, user
root, `capabilities="^cap_net_admin,^cap_dac_override"` plus `!cap_<x>` for
36 other capabilities (IAB string of 625 characters), `no_new_privs=yes`,
command `/usr/local/lib/proxy-agent/tuning-watch`.

Also: the H4 drill (kill -9 + reboot when the update journal says `started`)
never ran, because `update.sh` writes `started` only after `install.sh`
succeeded (update.sh, `journal_write started`). The plan's trigger has to be a
phase that exists while install.sh is still replacing files (or the drill has
to be defined as "after started"). Docs fix in the host plan.

Asks for Codex:
1. Root cause from the code: openrc-run 0.52's handling of `capabilities` and
   `no_new_privs` for a root `command_user`; install order in
   `deploy/linux/install.sh` (is `tuning-watch` in place before the service is
   started?); anything else in `deploy/openrc/tuning-watch` that can fail in an
   LXC (binaries it needs, inotifyd, flock).
2. A safe diagnostic for Cline to run on alpine-node that captures the real
   error without upgrading the Agent (for example: extract the RC bundle's
   init script and watcher to a temporary service name, start it with
   `rc-service --verbose` or run the equivalent supervise-daemon line in the
   foreground, then remove everything).
3. The fix, and whether `install.sh` should treat a failed tuning helper as
   "tuning unsupported" instead of failing the whole Agent install (tuning is
   an optional feature; the Agent works without it).

### F7 resolved (2026-11-01): the cause is `read` in `start_pre`, not the capability string

Isolated diagnostic on alpine-node (temporary copy of the packaged service with
an inert helper; nothing of the installed Agent touched; all files and the
empty cgroups removed afterwards). Runs 1–4 (original capabilities; numeric
IDs; ambient only; ambient only without no_new_privs) all failed identically in
`start_pre`, before supervise-daemon was ever called:
`+ read -r tuning_last_cap` → `+ return 1`. BusyBox `ash` `read` reads one byte
at a time, and the kernel's integer sysctl files (`proc_dointvec`) return EOF
for a read at a non-zero offset, so `read` sees "4", then EOF without a newline,
and fails; `cat` reads the value in one call (systemd hosts never run this
script, hence only Alpine is affected).

Run 5: the ORIGINAL policy with only `start_pre` changed to
`tuning_last_cap=$(cat /proc/sys/kernel/cap_last_cap) || return 1`: start exit
0, supervise-daemon accepted the full 39-exclusion IAB string, and the helper
ran with `Uid 0`, CapInh/Prm/Eff/Bnd/Amb = `0x1002` (CAP_NET_ADMIN |
CAP_DAC_OVERRIDE only), `NoNewPrivs: 1`.

Decision: F7 fix = that one line in `deploy/openrc/proxy-agent-tuning`
`start_pre` (no change to the capability policy, no degraded mode). Proof on
real Alpine is the H4 rerun with RC2. H4 drill trigger: the plan must kill the
updater while install.sh is still replacing files (the journal phase written
before install.sh), not at `started` (written after it).

## RC2 acceptance findings (2026-11-01)

### F8 — subscriptions drop a second inbound of the same protocol on one node (P2)

Found during H7b on RC2. `published.build` names every self-hosted endpoint
`<node> · <protocol>` (internal/panel/subscription/source/published/published.go),
and `source.Registry.Collect` keeps only the first proxy of each name. A node
with two VLESS (or two SOCKS5) inbounds granted to a user therefore appears
once in every format, with the warning "… was kept; the duplicate was dropped".
1.0.9 emitted both (same display name). Regression for any Owner with two
same-protocol inbounds on one node.

Discussed with Codex, who confirmed the analysis: cross-source first-wins in
`Collect` is tested intent (`TestSourceCollisionKeepsTheFirstSource`); dropping
distinct inbounds of the published source is not. No stored reference uses
published display names (canvas uses `inbound:<id>`, imports use their own
`name|protocol`, sing-box tags use the inbound reference).

Decision (reviewer): `published.Source.Proxies` makes the names unique in one
pass over its built endpoints. A name that occurs once stays `<node> · <protocol>`;
every member of a colliding group becomes `<node> · <protocol> · <port>`. Codex
proposed the full inbound ID as suffix; declined because it puts opaque IDs
into every client, while ports are unique within a node and readable.
Identically named nodes remain covered by `Collect`'s existing warning (the
Owner renames one). `Collect` is unchanged.

### F9 — a fresh node install of 1.2 cannot enroll (P1, release blocker)

Found in H8 (fresh Debian 13 container on us2-node, `node-install.sh
--version 1.2.0-rc.2 … --core xray --core sing-box`). Both cores and the v2
record are installed, then enrollment fails with
`登记目录保留身份、配置、账本或未知材料；…` and node-install.sh aborts; the Agent is
never enabled.

Cause: `install.sh` creates `/var/lib/proxy-agent/tuning` for the K2a tuning
helper before enrollment (deploy/linux/install.sh, next to `host-network`), but
the enrollment directory guard in
internal/agent/identity/enrollment_attempt.go allows only `identity` and
`host-network` at the top level. Proven in the container: with only `tuning`
moved aside, the same token enrolled. Affects every fresh install on systemd
and OpenRC since K2a (rc.1 and rc.2); upgrades never enroll, so H3–H5 and
the unit/CI tests did not see it. The H8 container, node and packages were
removed; us2-node unchanged.

### F10 — unexplained core restores on uk-node under rc.2 (P2, cause open)

uk-node logged `core unhealthy; restoring last successful configuration` nine
times since its rc.2 upgrade (UTC 09:06:38, 09:14:46 during H7b; 10:01:13,
10:01:22, 10:06:22, 10:09:07–22 during H7c), each followed by a core restart
that drops every connection on the node. No other line explains them; no OOM;
listener dials from the node succeeded. Zero such lines under rc.1 on the
same host, and none on us2-node or alpine-node under rc.2.

Codex's analysis: the WARN is reached only when every per-core status was
healthy and the aggregate check a moment later was not; the per-core path
(`RestoreCore`) restarts silently on success, so restarts can exceed the WARN
count. The reason is lost in three places: Xray `Health` discards the exit
error and the failed endpoint, `MultiRuntime.CoreStatuses` replaces every
error with `core_unhealthy` and aggregate `Health` returns nil for ordinary
failures, and the sampler discards the error of clearing the device gate
(which can set `gateRecovery`, a restart request). Candidates: a failed TCP
listener dial within 1 s (stats/probe listeners included), routing recovery
through the sampler (H7b events), or a real core exit. rc.2 runs the sampler
10x as often, which makes timing effects more likely but is not proof.

Decision (reviewer): no change to the restart policy, timeouts or retries
until the cause is known. RC3 carries diagnostics only: the health branch and
its error are kept through MultiRuntime and logged with core and revision on
both restore paths, and a failed gate clear in the sampler is logged. Then
reproduce on uk-node with RC3 and decide the fix from the logged reason.

### F11 — port-forward bytes are missing from Xray node traffic (P3, documented)

H7c on uk-node (Xray only): a TCP forward served 20 HTTPS fetches and a UDP
forward answered DNS, yet the node's traffic did not change. Xray node totals
are the sum of the account counters (internal/agent/core/node_traffic.go
`SaveAccountAndNode`), and a forward has no account; sing-box node totals come
from the core's own total and include forwards
(`TestRealClashApiNodeTrafficTotalsCountForwardedBytes`). No user was charged,
as intended (L10). Decision: document it (AGENTS.md §21, release notes L10);
counting Xray forwards needs inbound statistics, a feature for a later
release. The rest of H7c passed (TCP + UDP forward, valid certificate, not
MPTCP, restored).
