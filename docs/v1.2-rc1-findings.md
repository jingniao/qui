## F1 — normal Agent shutdown logged at ERROR

Evidence: uk-node journal, 2026-11-01 10:28 (kernel reboot):
`level=ERROR msg="approved runtime state reconciliation failed" error="context canceled"`.
Code: `internal/agent/supervisor/supervisor.go` logs every `reconciler.Refresh`
error at ERROR, including the cancellation of a normal stop.

Proposed direction: do not log (or log at debug) when the supervisor's own
context is done; keep ERROR for every other failure. One check at the call
site, no new helper.

## F2 — `install.sh` prints its first-install hint during `qui-update`

Evidence: H1 (panel) and H3 (Agent) update output end with
"Next: review /etc/proxy-*/config.yaml, then systemctl enable --now …" right
before qui-update reports the service as running.

Proposed direction: `update.sh` already knows it is updating; have it ask
`install.sh` not to print the first-install hint (an existing mode/flag if
there is one, otherwise one variable), rather than duplicating the message
logic.

## F3 — a user inbound hidden from subscriptions is silently published disabled

Evidence: H7 (uk-node, revisions 136 and 138): an enabled SOCKS5 inbound with
`subscriptionVisible=false`, even as a member of the user's granted node group,
gets `credential_ids=[]` and is rendered `enabled=false`; the inbound API still
returns `enabled: true` and nothing warns the Owner. Cause: user credentials
are assigned only for subscription-visible inbounds
(`internal/panel/user/snapshot.go`, `AND i.subscription_visible=1`), and the
renderer disables an inbound without credentials
(`internal/panel/proxy/snapshot.go`). With the flag set to true the same
inbound served TCP and UDP (revision 139).

Question for Codex: is "hidden" meant to imply "no user access"? AGENTS §12
says internal relay inbounds should be hidden, which suggests hidden =
internal; but the editor lets the Owner create a hidden, non-relay user inbound
and shows it enabled. Options: (a) keep the rule and make it visible — the API
reports the effective state (for example `effectiveEnabled` plus a reason) and
the editor warns when a user inbound is hidden; (b) change the rule so hidden
user inbounds still receive credentials of granted users (subscription
visibility only controls listing). The reviewer leans to (b) if nothing else
depends on the coupling, because the flag's name describes listing, not
access; otherwise (a).

## F5 — the device limit does not reliably observe a second device (P1)

Setting: uk-node on Agent 1.2.0-rc.1 (Xray 26.3.27), active user alice with
deviceLimit 1, public SOCKS5 inbound uk-node:35101. Source A = alpine-node
(113.29.231.0/24), source B = us2-node (23.254.158.0/24). All times UTC,
2026-11-01; devices-online is the panel's admission view (masked addresses).

Run 1 (03:27–03:28): A held a slow download; B made 12 short requests 6 s
apart. All 12 returned 200; devices-online only listed A.

Run 2 (03:36–03:41, after an admission reset):

| Time | Event | devices-online |
| --- | --- | --- |
| 03:36:17–23 | A: one short request, then a slow download (20 kB/s) | |
| 03:37:13 | | A allowed, active; firstSeen 03:36:22, lastSeen 03:36:26 |
| 03:37:23 | B: slow download started | |
| 03:38:14 | (both downloads ended by themselves about 55–60 s after start) | only A, allowed, active=false; **B absent** |
| 03:39:05 | B: slow download re-opened | |
| 03:39:11–40:16 | B: 12 short requests, all 200 | 03:39:36: **no items** |
| 03:40:40 | | B allowed, active; firstSeen 03:40:16 (= request 12) |

So B was not observed while A should still have held the slot (A's 60 s
active + 120 s release ends about 03:39:26), and B's new connections were
never refused. The real-core CI gate tests pass because they apply the gate
directly (`SetDeviceGate`) and do not depend on the observation.

What is known from the code: the Agent samples connections only at each
heartbeat (every 15 s; `internal/agent/control/control.go`,
`connectionReader`); Xray sources come from `GetStatsOnlineIpList`
(`internal/agent/core/xray/online.go`); the existing real-core test
`TestRealOnlineStatisticsTrackAnAuthenticatedClient` expects the user to go
offline right after its connection closes. What is not known: whether Xray
lists an IP for the whole life of a connection or only for a short time after
it starts (A's firstSeen/lastSeen 4 s apart, and B's slow download not seen at
all, point to the latter), and whether the test downloads really stayed open.

Asks for Codex:
1. Settle the Xray online-IP semantics with a controlled experiment on the
   local Linux test machine (`~/.qui-local/r.sh`, Xray 26.3.27 in
   /root/qui-cores, source tree in /root/qui-src): one long-lived connection
   and repeated short ones through a real Xray inbound, polling
   `GetStatsOnlineIpList` every second for a minute. Same for sing-box's Clash
   API connections.
2. Propose the smallest fix that makes "active source" reliable for both cores
   without duplicating the Xray and sing-box paths. Options: sample more often
   and send the union since the last heartbeat; or take sources from the
   access log the Agent already parses every ~100 ms (Xray access lines carry
   the source and the user). No new persistent data; addresses stay in memory.
3. A test that would have caught this: a real-core test that goes through the
   observation (not `SetDeviceGate` directly) with a second source making only
   short connections.

## F6 — a user PUT that changes only deviceLimit also sets trafficResetAnchor (P3)

Evidence: alice had `trafficResetCycle: none`, `trafficResetAnchor: ""`. A PUT
with all fields copied and deviceLimit 1 returned anchor
`2026-11-01T03:19:09.724286340Z`; the restoring PUT with anchor `""` kept it.
Harmless while the cycle is none, but an edit of one field should not change
another. Direction: only default the anchor when a cycle other than none is
set (or keep the stored value when the input is empty and the cycle is none).
