# v1.2 UI structure proposal — pages first, backend later (draft)

Status: **proposal for Owner review**, 2026-10-28. Pages only; no backend
changes. Everything here uses existing APIs. The backend items in
docs/v1.2-plan.md (per-scheme access S1, multi-core MC, GOST G) wait until the
pages are settled.

## 1. Three words, one meaning each

The current UI mixes these. Every page, label and toast will follow this table.

| Word | Means | Example |
| --- | --- | --- |
| **服务器** | A machine running the Agent (table `nodes`) | Tokyo-01, 1.2.3.4 |
| **节点** | Something a user can connect to: an inbound on a server, which shows up in subscriptions | Tokyo-01 · VLESS 443 |
| **线路组** (today 节点组) | A named set of **servers**. Granting a 线路组 to a user lets that user use every user-facing 节点 on those servers | 日本线路 = Tokyo-01 + Osaka-01 |

Why rename 节点组 to 线路组: a group contains servers, not nodes, and its
purpose is access. "线路" is what users and Owners already call a set of
servers. The backend keeps the name `node_groups`; this is a label change only.

## 3. 线路组 page (节点配置 › 线路组)

### 3.1 Two kinds of groups

The backend has four purposes: subscription, relay, egress and mixed. The page
shows two kinds and keeps the rest behind 高级:

- **用户线路组** (purpose subscription): grants users. This is the normal case.
- **内部分组** (relay/egress, hidden from subscriptions): used only by 中转搭建
  and policies. It never grants users.

### 3.4 Where else membership is edited

Every place uses the same chips plus picker:

- **Server list:** bulk action 加入/移出线路组 on selected servers.
- **Server details › 概况:** 所属线路组 chips, with an edit button. Saves all
  changes in one go.
- **User details:** 授权线路组 chips with the picker (already there; restyled).

## 4. Decluttering rules for every page

1. **One job per page:** lists show status, detail pages do management. A list
   never hosts management dialogs that belong to a detail page.
2. **No placeholders:** no "—" walls, fake 测试点 boxes, "待办" cards or demo
   values. A value that doesn't exist is hidden, with one line saying why.
3. **One status vocabulary:** `StatusBadge` everywhere, with every server state
   from AGENTS §11.4 (including core errors).
4. **Progressive disclosure:** forms show only the fields for the chosen
   protocol or kind. Advanced options sit behind 高级, closed by default.
5. **Design system:** tokens and components only, with no raw hex colours or
   arbitrary sizes. A self-test enforces this.
6. **Small files:** pages over ~400 lines are split into components.

## 10. 中转搭建 — creating and editing tunnels (U5, 2026-10-28)

### 10.1 Problems today (from RelayCanvasPage.vue and internal/panel/proxy/canvas*.go)
- A tunnel can only be created by dragging an arrow on the canvas. Editing
  happens in a small side panel; 隧道列表 is a read-only dialog.
- **The three connection types confuse two separate things.** 隧道转发 and
  代理链连接 compile identically for server schemes: both become
  `tunnelProtocol` (tls → internal Trojan, or wireguard) plus an outbound, and
  two consecutive edges form a chain. Only 端口转发 really differs.
- **Port-forward ports live on the server boxes, not on the connection**
  (`CanvasInstance.listenPort/targetPort`). The target address is always the
  target server's public IP.
- Gost, Brook and nftables are listed as disabled options with no explanation
  of when they will work.
- Nothing shows what publishing will create on each server, and nothing checks
  for port conflicts.

### 10.2 New model shown to the Owner
Two kinds of tunnel, in plain words:

| Kind | What it does | User identity | Built from |
| --- | --- | --- | --- |
| **加密中转** | User traffic entering server A continues, encrypted, to server B. Chaining A→B→C makes a multi-hop route | Kept (quota, routing rules and audit still apply) | Today: TLS (internal Trojan) and WireGuard. After the GOST phase: GOST relay over tls/ws/wss/kcp/quic |
| **端口转发** | A port on server A is passed through to host:port | None (no quota or per-user audit, L10) | Today: core forward inbound. After GOST: port ranges, multiple targets with failover/load balancing, rate limits |

The old 代理链连接 type folds into 加密中转. Existing stored connections keep
loading: `proxy_chain` is shown as 加密中转 and saved unchanged until the Owner
edits it.

### 10.3 Page layout
```
中转搭建  [方案: 日本中转 ▾] [+ 新建方案]          [检查] [发布]
┌ 画布（保留） ───────────────────────────┐┌ 隧道 (3)            [+ 新建隧道] ┐
│  Tokyo-01 ──加密中转 TLS:8443──▶ HK-01  ││ Tokyo-01 → HK-01  加密中转 TLS  │
│  HK-01 ──端口转发 :30000──▶ LA-01       ││   :8443 · TCP/UDP · ✓ 可发布     │
└─────────────────────────────────────────┘│ HK-01 → LA-01     端口转发      │
                                           │   :30000→:443 · TCP · ⚠ 端口冲突 │
                                           └──────────────────────────────────┘
```
- The tunnel list replaces the read-only dialog and is always visible. Each
  row shows a status: 可发布, or the reason it can't be published.
- Clicking an arrow on the canvas or a row in the list opens the same drawer.
  Drawing an arrow opens the drawer with source and target filled in.

### 10.4 新建/编辑隧道 drawer
1. **起点与终点:** source server, then target (a server; for port forwarding
   also a custom host). Shows each side's status, public IP and core.
2. **类型:** 加密中转 / 端口转发, as two cards with the one-line explanation
   above.
3. **参数**, depending on the type:
   - **加密中转:** protocol (TLS / WireGuard; GOST options visible but greyed
     with "需要 GOST 核心"); port, with a live conflict check against the
     target server's existing inbounds and other tunnels; TCP/UDP.
   - **端口转发:** listen port on the source; target host (defaults to the
     target server's public IP); target port; TCP/UDP.
4. **高级 (collapsed):** fields that come with GOST later (rate limit, multiple
   targets, failover). Hidden until supported.
5. **确认:** what publishing creates, per server (for example "HK-01: 新增入站
   [方案] trojan :8443; Tokyo-01: 新增出站 → HK-01"), plus warnings.

### 10.5 Backend needed (small)
- Move port-forward ports onto the connection: add `listenPort`,
  `targetHost`, `targetPort` to `CanvasConnection`. Old layouts read the
  instance fields as a fallback. With today's model, two port forwards from
  the same server would share one listen port.
- A dry-run endpoint `POST /canvas-schemes/{id}/plan` that returns the planned
  objects, conflicts and warnings without publishing. It reuses
  `canvasBuildPlan`.
- No new tunnel protocols until the GOST phase (G).

## 11. 服务器详情 › 网络延迟（24 小时）chart (2026-10-28)

**What is measured:** TCP connect time from this server to probe targets
(the existing 探测目标 such as a local carrier IP, 1.1.1.1:443, or another of
your servers). It is not ICMP ping and not UDP (L10); the chart says so in one
line.

**Chart (top of the 监控 tab):** one line per target, up to 5. The y-axis is the
average connect ms. Failed samples show as gaps, with red marks on a loss strip
below. Hovering shows the time, avg/min/max ms and loss %. The range toggle
starts with 24h only. Before any samples exist, the chart shows one line: "尚无
定时检测数据，请在设置中选择检测目标".

**Why backend work is needed:** probes run only on demand today, and only the
last 100 results per server/target are kept (`internal/panel/node/tcp_probes.go`),
so there is no 24-hour series.
- **Scheduler (panel):** every 5 minutes, for each online server with
  `tcp_probe_supported` and up to 5 targets marked 定时检测, queue a probe
  (3 connects, 3 s timeout) using the existing Agent probe command. The Agent
  does not change.
- **Storage:** new migration `node_latency_samples(node_id, target_id, at,
  avg_ms, min_ms, max_ms, sent, failed)`, kept 7 days (288 rows per target per
  day). It is kept apart from `node_tcp_probes` so the manual history and its
  100-row limit stay as they are.
- **API:** `GET /api/v1/nodes/{id}/latency?hours=24` returns per-target series.
  Settings: per-target 定时检测 flag and the interval (default 5 min).
- **Backup:** the samples are telemetry. Exclude them from backups (or allow
  them, documented); update backup inspect/inventory either way.
- **Chart drawing:** a small in-house SVG component, so no new npm dependency.

**L1 backend implementation (2026-10-28):** migration 0120 adds scheduled targets
(default off, global cap 5), a separate 7-day telemetry table (REAL milliseconds),
and queue source/dispatch tracking. Every 300 seconds the serving panel queues
3 connects with a 3000 ms timeout for eligible nodes (enabled, not deleted,
TCP probe supported, heartbeat within 45 seconds). Manual work has dispatch
priority; one command remains in flight per node. Scheduled work never uses
the manual 100-row history. The loop stops and is joined on shutdown/restore.

Owner/Viewer can read `GET /api/v1/nodes/{id}/latency?hours=24` (1-168 hours);
Owner can create/update targets including `scheduled` using POST/PUT. Samples
and scheduled queue rows are removed from portable backup copies and on
restore; target settings remain. Target deletion cascades samples; logically
deleted nodes return 404 and their samples expire through retention.

**Contract limitation / deviation:** the unchanged Agent returns only a median,
not individual timings or avg/min/max. Points therefore include `medianMs`,
with `avgMs/minMs/maxMs` null; full loss has null timings and sent=failed=3.
The chart must label the available statistic as median. Computing true means
and extrema requires a later Agent contract change. The interval is a fixed
constant (300 seconds), not an editable setting.

**U3 frontend delivery:** the fixed header uses U2 serverStatus, node/meta/group
records; overview uses heartbeat/host metrics, panel-timezone accounts since
midnight and monthly node traffic. Events use revisions/results and core errors.
Nodes use paginated inbounds/outbounds/outbound-groups. Monitoring keeps counters,
spool, health tasks and manual TCP history; manual API lacks mean/time, shown —.
Revisions keep diff/publish/rollback confirmations. Settings saves fetch the latest
node and change only the selected group. Creation query uses a small routed entry
and the existing inbound form fields, leaving the U4 list intact. The frontend
retains the approved avgMs chart contract; L1 median-only data cannot draw its
mean curve. No browser test against a real backend was performed.
