# v1.3.0 implementation design: GOST G1, G2 and G3

Design review, 2026-11-01. Target branch: `release/v1.3.0`.
This document specifies implementation work; it does not claim implementation
or host acceptance. G1 precedes G2, and G2 precedes G3. Each phase must pass
`scripts/check.sh` and its native-core tests on the Linux test machine before
the dependent phase begins.

## Reviewer decisions (override the text below where they differ)

The Owner wants a lightweight system; these cuts keep GOST proportionate to
1–10 users. Where a section below describes a removed mechanism, skip it.

1. **No canary/nonce probes** (§3.3, the G3 probe in §5.3, `probe_port`).
   GOST health = the exact child is alive + every production TCP listener
   answers a dial + every production UDP socket is owned by the child (move
   sing-box's `udpEndpointHealthy` into the shared `core` package so both
   adapters call it). Failures wrap `core.ErrListenerUnavailable` and name the
   listener, like the other adapters. Metrics-scrape failure sets the traffic
   source status only. Target reachability is not GOST health; the existing
   TCP probe and host acceptance cover it.
2. **No MultiRuntime "skip unchanged components" change** in v1.3 (§3.2
   "Required MultiRuntime correction"). A publication restarts the node's
   cores as it does today for Xray + sing-box; document that a GOST change
   also restarts the proxy cores on that node and vice versa. Per-core
   supervisor recovery already isolates a GOST crash.
3. **G3 covers GOST forwards only** (§5.1 case 1). Case 2 (bridging Xray /
   sing-box user traffic through GOST, `dial_override`, `payload_port`,
   `bridge_port`, `proxy_bridge` accounting) is dropped: encrypted user-proxy
   hops keep using the existing Trojan tunnels. In the canvas, `tunnelProtocol:
   "gost"` is offered only for `port_forward` connections; it makes the entry
   node's GOST forward dial its targets through the exit node's GOST relay
   (TLS + client CA). Up to the existing two hops.
4. **One credential set per tunnel, no staged rotation.** Migration 0128 adds
   one nullable sealed column (e.g. `canvas_tunnels.gost_material BLOB`,
   sealed with `Repository.Vault`) instead of `canvas_tunnel_credentials`;
   no `0129_deployment_ordered_steps`, no batch-kind changes. CA and leaves
   are valid for 10 years. "Rotate credentials" generates new material and
   marks the tunnel modified; the next normal publish deploys exit first,
   then entry (existing dependency order), with a short interruption in
   between — documented, acceptable for this deployment size. The CA private
   key is not kept after issuing (nothing else is ever signed with it).
5. Keep everything else: Hello flag + contract version, migration 0127 CHECK
   rebuilds, strict 3.3.2 pin, YAML via `gopkg.in/yaml.v3`, two-stage
   validation, metrics over the unix socket into the node counter, G2 pools /
   ranges / limits, handler-level chain assertion, redaction, backup coverage.

Phase split for implementation: G1a (Agent, contracts, installer, update
allowlist), G1b (migration 0127, panel, web), G2, G3.

## 1. Basis, scope and decisions

Read together with [the v1.3 plan](v1.3-plan.md),
[G0 measured findings](v1.3-g0-gost-findings.md), and `AGENTS.md` sections 4.4,
14, 16, 21, 22.2, 23 and 30.2. The G0 findings are authoritative where the
original intent in `docs/archive/v1.2-plan.md` sections 1.6/2.4 differs: use
Prometheus metrics, not an unimplemented observer; ranges are expanded by qui;
restart is a deliberate apply policy, although GOST supports nontransactional
reload. The K3a/K3b/K3c/K4 reports requested for this review live under
`docs/archive/`, not at the former top-level report paths.

Decisions:

- Add core kind `gost`, Linux amd64 only, alongside Xray and sing-box. A node
  can have one, two or three distinct enabled kinds. Preserve configuration
  order and the persisted compatibility primary.
- Pin official GOST **3.3.2**. Archive:
  `https://github.com/go-gost/gost/releases/download/v3.3.2/gost_3.3.2_linux_amd64.tar.gz`.
  Archive SHA-256:
  `162feb43b1c284dbea599cdfe898169931af875233060dedc19432c7a9d18274`.
  This is an archive digest, not the digest written for the installed binary.
- GOST's only advertised inbound protocol is `forward`, TCP and UDP. It has
  no user credentials, subscriptions, quota, device gate, source-address
  observation or domain collector. Internal relay services are an explicitly
  typed, canvas-managed variant of a forward resource, not a new user protocol.
- Use raw TLS with client-certificate authentication for G3. Neither WSS nor
  QUIC nor the misleading `mtls` transport name is exposed in this release.
  Reverse tunnels and GOST Web API/pprof remain out of scope.
- Reuse `gopkg.in/yaml.v3`, already a direct dependency in `go.mod`. Change
  neither `go.mod` nor `go.sum`; add no dependencies. Preserve JSON native
  configuration storage and materialize canonical YAML for the GOST process.
- Preserve the Owner's forward editor and tunnel drawer. Add fields and
  choices within their current steps and layout.
- T1 owns migration 0126 and Heartbeat fields 34/35. GOST starts at 0127,
  adds no Heartbeat fields, and does not change machine-traffic accounting.
  All migration changes below are new files; existing migrations stay immutable.

### 1.1 Existing mechanisms to reuse

| Existing mechanism | GOST use |
| --- | --- |
| Strict Agent configuration loader and `cores.json.enc` overlay | Accept a third kind; preserve disablement, order, primary and node binding |
| `core.Runtime` / `core.BinaryRuntime`, MultiRuntime and Reconciler | Render, switch, retained revisions, scoped supervision, binary updates and rollback |
| `CoreRun`, exact-child lifetime checks and accounting epochs | Confirm exit before replacement; distinguish GOST process counter resets |
| `release.CoreUpdateRequest` schema 2 and `updater.CoreSource` | Same component task, archive extraction, checksum, image activation and recovery |
| `core.NodeCounter`, traffic sink, encrypted spool and Ack/cursors | Node-only forward bytes, independently of account traffic |
| `Repository.Vault` (`internal/platform/vault`) | Encrypt settings and G3 private credential bundles with the existing configuration key |
| K4 tunnel resources, object ownership, optimistic version and shared dependencies | One engine/configuration per shared tunnel, no ownership by name |
| Relay snapshots and Deployment batches | Capture dependencies, publish targets first, compensate sources first |
| Installer v2 records and update recovery | Record, preserve, snapshot, recover and uninstall GOST without a new service manager |

Do not copy an entire proxy adapter, build a second deployment coordinator,
introduce a metrics server in the panel, or create a second traffic ledger.
Small GOST-specific lifecycle methods should call existing process/accounting
helpers. Any helper extracted from an adapter must have a second actual caller;
avoid a general plugin framework or unrelated refactor.

## 2. Contracts and compatibility across phases

### 2.1 Additive protobuf changes

GOST settings travel in the existing `ApplyCommand.desired_state_json`. Core
names/components already travel as strings. No GOST settings need individual
protobuf fields.

| Phase | Message and field | Meaning |
| --- | --- | --- |
| G1 | `Hello.gost_core_supported = 13`, bool | This Agent understands GOST component installation/removal, even when GOST is absent |
| G1 | `CoreCapability.gost_contract_version = 9`, uint32 | 1 = basic forwards, 2 = G2 options, 3 = G3 relay/bridges; zero = unsupported |
| G2/G3 | No new numbers; raise the reported GOST contract version | Explicitly gate new settings against the selected core entry |

The Hello flag gates queuing absent-component GOST installs; multi-core support
alone is insufficient. Persist it in a new `nodes.gost_core_supported` column in
0127 and reset/refresh it by the existing capability/session recovery rules.
Do not infer it from Agent version text. There is no new Welcome flag: existing
multi-core and node-traffic negotiations still govern their payloads. Do not
repurpose CoreCapability fields 1–8, CoreStatus fields 1–5, or Hello field 12.
Heartbeat 34/35 remain exclusively T1's fields; 36 is not needed.

Regenerate `pkg/contracts/agentpb` with `scripts/generate-proto.sh` during G1
implementation, after reconciling T1's proto changes. Extend descriptor and
unknown-field round-trip tests. Old Agents cannot receive GOST assignments;
G2/G3 settings require the corresponding contract version in fresh capabilities.

### 2.2 DesiredState, runtime storage and version guards

`RenderedConfig.Data` is currently embedded as `json.RawMessage` in
`MultiRuntime.Render`, and `DecodeCoreConfigs` accepts a map of native JSON.
Raw YAML here would break revision persistence. Keep `Data` as deterministic
JSON of typed native GOST structs, extend the core-map decoder to recognize
`gost`, and encode those same structs to `runtime/gost/config.yaml` for exec.
Give native structs matching JSON/YAML tags. Lists retain semantic order;
generated services/names are sorted deterministically. Never marshal public
panel input or arbitrary maps directly into GOST configuration.

G0 establishes `-C` and inline JSON support but does not explicitly establish
loading a `.json` file. This design therefore does not depend on the assertion
that JSON is valid YAML or on file-extension autodetection. A real-binary test
may demonstrate `gost -C file.json -O json`; that would permit a later
simplification, but G1 uses the already measured YAML file path.

Extend `desiredstate.State.Validate`, `ForCore`, support tables and runtime
factories together. Validate assigned core support after resolving an empty
Core to the persisted primary. Explicit `gost` is recommended for all new
forward resources; empty Core remains backward compatible, including a
GOST-only primary. GOST rejects unsupported routing/policy features instead
of silently ignoring them. Global user/domain policies must not accidentally
attach to GOST forwards through `ForCore`'s current global-policy inclusion.
Only the forward's explicit direct or G3 route is meaningful to this adapter.

The storage reader compatibility declarations must reflect a new core name
and new DesiredState semantics. Follow the existing retained-image readability
proof before raising write guards; do not blindly reuse the K3 report's old
numeric maxima. Inspect the current storage-version registry at implementation
time and allocate its next value for Configuration/DesiredState and any affected
release-hold readers. Old readers cannot interpret GOST inventory or G3 material.
Keep old snapshots readable. Panel downgrade requires the pre-migration backup;
an Agent fallback unable to understand GOST must be refused before activation.

## 3. G1: core kind and basic forward runtime

### 3.1 Installer, release validation and component operations

Extend repeated `--core` in `deploy/linux/install.sh` and `node-install.sh` to
`xray|sing-box|gost`. Default new install remains Xray; omission on upgrade
preserves the installed set; explicit flags replace/append, never remove.
`--core-source qui|official` still applies only to sing-box. GOST is always
official and uses the same static amd64 archive on glibc and Alpine/musl.
Reject GOST installation on other architectures/platforms; do not claim arm64
support because upstream publishes an archive.

Install the binary at `/usr/local/lib/proxy-agent/gost`, like the existing
core paths. Set the existing executable ownership/mode and retain MIT license
information in deployment documentation. Normalize Agent configuration with
`cores: [{name: gost, path: /usr/local/lib/proxy-agent/gost}]` alongside other
entries, preserving the first entry and compatibility scalars. No standalone
GOST systemd/OpenRC service is installed: the Agent owns its child process.

Download `checksums.txt` from the same pinned release, require exactly one
matching archive entry, compare it with the pinned digest above, and verify
the archive before extracting. Use existing bounded/path-safe extraction;
the only executable candidate is root entry `gost`. Require `gost -V` exit 0,
first line `gost 3.3.2 (...)`, and parse field 2 as `3.3.2`. Never use
`gost version`. Compute the extracted binary digest separately.

The v2 install record line is exactly
`core gost /usr/local/lib/proxy-agent/gost <binary-sha256>`.
Extend every fixed core-name/path set used by `service.sh`, enroll/certificate
scripts, `update.sh`, `update-recovery.sh`, cleanup traps and uninstall. In
particular, recovery cannot discover protected paths from a half-replaced
manifest: its fixed path set must include GOST. Reuse existing locks, journals,
snapshots and automatic restoration. Retain installed-but-disabled files when
the Agent removes a core; only the installer/uninstaller owns those files.

Extend shared `pkg/contracts/release/core_source.go` and `core_update.go`, not
a second panel-specific URL checker. Exact official prefix:
`https://github.com/go-gost/gost/releases/download/`; accepted v1.3 target is
only tag `v3.3.2`, asset `gost_3.3.2_linux_amd64.tar.gz`, version `3.3.2` and
the pinned archive digest. An underscore-specific asset branch is essential:
the current generic platform matcher assumes hyphens. Do not broaden the qui
sing-box archive regex. Reuse exact HTTPS URL parsing, GitHub redirect hosts,
TLS checks, checksum verification and native executable validation. Subsequent
GOST versions require updating this reviewed pin and rerunning G0 regressions;
an arbitrary official URL plus an operator digest is insufficient for GOST.

`POST /api/v1/core-updates` accepts `component: gost` with the existing schema.
Queue only when the fresh Hello flag is set and the host is linux/amd64.
Use the existing per-(node,component) task, sequence, adding flag, staging,
release hold, reconnect result handling and success-plus-capability selection
barrier. Extend workers in `control/core_updates.go` to include absent GOST,
and factories/version validation in `core_installation.go` and Reconciler.
`BinaryRuntime.ValidateExecutable` syntax-checks the captured configuration;
actual listener/settle validation occurs after the locked switch. An idle
new core is version-checked but not started, as with the other components.

`POST /api/v1/nodes/{id}/cores/gost/remove` reuses RemoveCore tasks and receipts.
Current and interrupted retained snapshots, including disabled assignments and
G3 bridge/relay assignments, block removal. Preserve `core_in_use`,
`core_pending`, `last_core`, `revision_mismatch` and exact-child-exit rules.
Do not erase external binaries, installer records or old update evidence.

### 3.2 Adapter, lifecycle and isolation

Add `internal/agent/core/gost/` with typed native config/render, adapter,
capability/version detection, metrics and tests. Implement **Runtime and
BinaryRuntime**, not only the smaller Adapter interface. ConfigureRuntime
uses the existing traffic sink; SupportsAccountTelemetry is false; account
and connection snapshots remain unavailable, never fabricated zeros.
OutboundHealth reports only actual configured probes, otherwise an empty map.

Capabilities include `name=gost`, version 3.3.2, one `forward` protocol row
(`inbound=true`, `outbound=false`, `tcp=true`, `udp=true`),
`forward_inbound_supported=true`, contract version 1. User-stat/device-gate/
observation flags remain false/zero. Do not advertise `relay`, `socks5`,
`trojan`, `direct` or a user-stat edition as public GOST protocol capabilities.

Use `/var/lib/proxy-agent/runtime/gost/` (relative to configured data directory)
for config, run/accounting markers, private material and `metrics.sock`.
Directory 0700; config/private files 0600; socket accessible only through that
private directory, set 0600 where supported. Render
`metrics.addr=unix://<absolute-runtime-directory>/metrics.sock` and
`log={level: warn, format: text}`. No API/pprof, remote metrics, `-R`, SIGHUP,
debug flags or per-connection access logging. Warn logs are bounded using the
existing child-output machinery; redact credential-bearing details.

Validation and apply sequence:

1. Validate typed contracts, generated names, enum values, references and
   ports in Go. Reject unsupported keys/features; no pass-through metadata.
2. Write candidate YAML privately and run `gost -C <candidate> -O json` with
   the existing 10-second validation deadline and bounded captured output.
   Require successful JSON output. This is only a syntax/render gate and must
   not stop the active process. Check that required services, selector/limiter
   references and handler-chain paths survive normalization. `log` is excluded
   from this comparison because G0 found it absent from serialized output.
3. Under the Reconciler/component lock, sample and persist old counters, stop
   and reap the exact GOST child, install the candidate atomically, then start
   `gost -C <live.yaml>`. Reuse CoreRun lifetime/accounting and run-marker rules.
   Do not start a replacement if stop is unconfirmed.
4. For two seconds require process survival, its expected TCP/UDP sockets and
   metrics readiness. At warn level there are no info-level listener lines:
   do not parse such lines as the readiness condition. On Linux, match socket
   inodes owned by the child PID through `/proc/<pid>/fd` and the relevant
   `/proc/net/{tcp,tcp6,udp,udp6}` tables, with address-family/wildcard handling.
   Reuse existing socket-inspection helpers if present; implement this once for
   GOST if not. UDP connect alone and an unrelated listener are not proof.
5. Run the controlled end-to-end health probe below. Return success only after
   these gates. Exit/bind/parse failures restore the previous file, material
   and process with the existing independent bounded rollback context.
   Preserve useful error codes and the failed service/port in the panel.

Empty assigned service sets do not start GOST. On unexpected process exit,
only its supervisor slot recovers, with the existing per-core backoff.

**Required MultiRuntime correction:** current `MultiRuntime.Apply` iterates
all cores and includes every visited adapter in reverse compensation. That
alone cannot guarantee a GOST-only change leaves peers untouched. Compare each
component's rendered native config **and runtime-affecting metadata** with its
current config. Skip process application for an unchanged healthy component;
advance only revision/accounting metadata through a small shared runtime hook.
Do not ignore changed guard/private-port sets, credentials, routing metadata or
failed health. Only switched components enter compensation. Reuse this rule
for all kinds rather than writing a GOST-only exception. Scoped recovery/core
updates already have a component path and must keep using it.

Revision-only advancement must keep run epoch/cumulative counters while binding
future samples to the newly acknowledged revision. Flush the previous revision's
sample before advancing, serialize this with sampling, and preserve spool
payloads already queued under their old revision. A changed native peer config
in a genuinely all-core publication may restart that peer; a GOST failure must
never cause a gratuitous restart of an unchanged Xray/sing-box process.
Verify PID, epoch and an established peer stream, not just final health flags.

### 3.3 Practical health policy

G0 correctly rejects listener dial as proof of forwarding health. Equally, an
Agent must not write probe bytes into an arbitrary database, SSH, UDP or other
configured target. Separate runtime health from external-target reachability.

For an active GOST core, the Agent runs a tiny loopback TCP and UDP echo target
and renders private GOST canary forwards to it. Reserve all private numeric
ports through the existing shared PortAllocator; keep them stable across
renders. A bounded random nonce through each canary must return unchanged.
Exclude canary services from traffic totals and user-visible resources. Use
the same native rendering path as production forwards. This tests accept,
handler, target dial and bidirectional payload, without external traffic.
Health also checks every production socket and the child/metrics endpoint.
Canary sockets must be isolated from user proxy egress using the existing
private-port guard mechanism.

This health means **runtime forwarding works; arbitrary target health is
unknown**. State that meaning beside Owner health results and in operations
docs. Do not label all real targets healthy from the canary. An all-down target
pool is not a reason to restart a working GOST core. Production target tests
are Owner-directed with a known safe echo/HTTP target during host acceptance;
no new generic remote probing API is introduced. Existing TCP probes remain
TCP-connect observations only. G3 adds a managed cross-node nonce probe.

Reuse the supervisor's consecutive listener-failure policy for transient
socket/canary timeouts (`ErrListenerUnavailable`), with a GOST diagnostic cause;
unexpected exit or unconfirmed stop follows existing immediate recovery rules.
Metrics failure reports traffic-source failure separately; it does not invent
zero usage or restart otherwise functioning forwards indefinitely.

### 3.4 Migration 0127 and panel integration

Add `migrations/0127_gost_core.sql`. CHECK constraints in **five** tables need
attention: `inbounds.core` (0125), `core_update_tasks.component` (0107),
`core_remove_tasks.component`, `node_traffic_cursors.core`, and
`core_traffic_samples.core` (0125). A trigger cannot override a failing CHECK.
Do not use `writable_schema` or edit 0125.

For `inbounds`, use SQLite's transactional column replacement, avoiding DROP
TABLE on this heavily referenced parent: add a temporary replacement core
column with default empty and the expanded CHECK, copy all old values, drop
the old core column, rename the replacement to `core`. The old inline CHECK
disappears with its column. No current index/trigger/view refers to this
column; verify that fact in the migration test. This works with the pinned
modernc SQLite's DROP COLUMN support and leaves all IDs, foreign keys, relay
bindings, group memberships and K4 deletion triggers intact. Final CHECK is
`core IN ('','xray','sing-box','gost')`; enforce forward-only in shared
application/DesiredState validation, not a second duplicated SQL protocol rule.

For the four leaf tables, rebuild each transactionally with its existing
columns/constraints plus `gost`, copying by explicit column names. Drop and
recreate `node_traffic_samples` around the cursor/sample replacements; preserve
its account fallback exactly. Preserve task IDs/results/sequences/adding,
all primary keys and indexes, including active-component unique indexes and
`core_traffic_time`. The obsolete `core_update_attempts` referencing table was
removed in 0107; assert no surviving dependent FK before rebuilding tasks.
Do not toggle `foreign_keys` inside the migration transaction: Migrate already
executes all SQL under BEGIN IMMEDIATE with foreign keys enabled. Verify
`foreign_key_check`, integrity and all related trigger/view definitions after

Panel validation resolves the selected enabled core and requires forward
support; reject `core=gost` on every other ordinary inbound, including
disabled drafts. Maintain the no-credentials/no-subscription/no-user-grants
rules for forwards. Protect render/snapshot/automatic-access/backup/rollback
paths, not only HTTP saves. Audit `ValidateCoreProtocol`: its current unknown
core/protocol fallback returns nil, so merely adding a support-table forward
row is insufficient; a known GOST core must explicitly reject all other rows.

Reuse existing inbound APIs, `core_selectionBlocked`, per-core node detail,
scoped restart/health actions and component update/remove UI. Extend web
CoreName types, labels and selectors. Offer GOST only for forward protocols,
and only after capability confirmation. Preserve unknown measurements as null.
Backup validators for core updates/multi-core must accept GOST only in the
new schema and validate the pin/Hello facts; old archive shapes remain accepted.

## 4. G2: multiple targets, ranges, limits and traffic

### 4.1 Typed data and API

Extend `desiredstate.ForwardSettings`; retain legacy `host`, `port`, `network`.
New JSON fields use the existing settings style (snake_case):

| Field | Type/default | Validation and semantics |
| --- | --- | --- |
| `targets` | array of `{host,port}`, omitted | 1–32 unique host/port pairs; preserve order; same host validation as legacy forwards |
| `strategy` | `round` default | Only `round` or `fifo` |
| `max_fails` | integer, default 1 | 1–100; applies to selector failure marking |
| `fail_timeout` | duration string, default `5s` | Whole seconds 1–3600; normalize to `<seconds>s`; reject negatives/fractions/other text |
| `port_end` | integer, omitted | Inclusive end; base remains `Inbound.Port`; base <= end <= 65535; at most 256 ports per inbound |
| `bandwidth_in_bps` | integer, 0 = unlimited | Decimal bytes/second, client to target; 0 or 1024–1,000,000,000,000 |
| `bandwidth_out_bps` | integer, 0 = unlimited | Decimal bytes/second, target to client; same bounds |
| `max_connections` | integer, 0 = unlimited | 0–100000; TCP concurrent connections per expanded service |

The 256-port limit bounds a lightweight node's listener/configuration size;
also cap rendered production services at 1024 per node (count TCP and UDP
separately, exclude the fixed canary overhead). Enforce limits before expansion.
These are implementation bounds, not new Owner choices.

For a legacy GOST forward, absent targets means exactly one legacy host/port.
For a new pool, host must be empty and legacy port zero/omitted; reject ambiguous
requests providing both representations. Preserve the shape when reading old
rows so opening/saving a form does not rewrite it needlessly. `targets: []` is
invalid. Duplicate targets compare canonical host plus port, with case-normalized
DNS and canonical IP text. Hostnames are destinations, not URLs or shell text;
allow authorized private destinations as existing forwards do.

Only a selected GOST core with contract version >=2 accepts the new options.
Reject presence of GOST-only fields on Xray/sing-box forwards, including explicit
zero/default values; do not quietly strip them on save or primary-core changes.
Use optional/pointer fields or strict decoded presence to distinguish omission.
Shared validation belongs in desiredstate helpers; panel adds capability lookup
and transactional conflict checking rather than duplicating option logic.
Agent validates again after resolving the primary and before render.

The request remains the existing inbound POST/PUT with `settings.forward`.
**There is no `inbounds.settings_json` column in this repository**: the typed
ProtocolSettings JSON is sealed by Repository.Vault into `encrypted_settings`.
Keep that storage mechanism, including redaction, snapshots and backup crypto.
No G2 schema migration is required. Do not create 0128 just for JSON fields.
No new proto numbers; report GOST contract version 2.

### 4.2 Node-wide port validation and native rendering

Introduce one shared numeric-port expansion helper returning the inclusive
listen ports. Reuse it from State.Validate, MultiRuntime's initial reservation,
panel validation, canvas preview/allocation, web conflict hints and backup
semantic validation (web mirrors presentation only; the backend is authoritative).
All enabled inbounds on a node compete by number, across listen address,
address family, protocol and core. Disabled inbounds reserve no ports. Exclude
the same object ID when updating. A forward with `tcp,udp` owns each numeric
port once, then renders one native TCP and one UDP service at that number.
It cannot let another inbound occupy the opposite transport.

The current repository query `WHERE node_id=? AND port=?` only checks base
ports. Replace it with a transactionally consistent read of enabled node
inbounds and their decrypted typed settings; expand and intersect intervals.
For 1–10 users this is simpler than maintaining a second port reservation
table. Use the same interval logic in canvas plan/publish; include all pending
planned listeners and retained owned listeners. Port selection cannot query
only `inbounds.port`. Preserve existing conflict object IDs/connection IDs.

Render one native service per (inbound ID, port, network), with stable generated
name `fwd-<stable-id>-<port>-tcp|udp`. IDs must be encoded as safe name components,
never interpolated into paths. Every service gets the **whole** ordered target
pool, named `target-0`, `target-1`, etc., and its own
`forwarder.selector={strategy,maxFails,failTimeout}`. Ports are expanded by qui,
never written as a range/comma list in `addr`, and never mapped positionally
onto different targets. Use `net.JoinHostPort` for IPv6.

from `service.limiter`. Render `$ <in> <out>` from validated numeric bytes/sec,
using decimal integers (and `0` for an unlimited direction); verify the integer
and one-sided-zero syntax with real 3.3.2 before accepting this encoding.
If that precise unit syntax is not honored, encode the same integer as the
upstream-supported byte-unit string established by a native fixture, and fix
one canonical conversion in the renderer. This is a required implementation
measurement, not permission to accept free-form limiter text. Both zero means
omit limiter and reference entirely. Never emit an unresolved limiter name.

Connections: nonzero max_connections creates `climiters[]` with `$ <n>` and
`service.climiter`. Reject this field for UDP-only forwards in v1.3: G0 measured
TCP concurrent connections, not a UDP concurrency contract. For `tcp,udp`, apply
it to TCP services only and label that scope explicitly. Bandwidth limits are
emitted for both protocols; real UDP enforcement remains a required gate.
Limits and selector state are per expanded (port,network) service, not a shared

Validate native references and chain placement in typed output before exec.
Golden tests and GOST normalization tests must catch unknown selector values,

### 4.3 Node-only accounting

Scrape `/metrics` over an `http.Transport` with Unix DialContext to
`runtime/gost/metrics.sock`, on the existing five-second sampling cadence and
immediately before stop. No Prometheus Go dependency is necessary: parse only
`gost_service_transfer_input_bytes_total` and
`gost_service_transfer_output_bytes_total`, honoring Prometheus quoted-label
escaping and scientific notation. Ignore comments, runtime metrics and unknown
families. Bound response/time using existing collector limits; fail the sample
on malformed/negative/nonfinite/overflow data, and surface source unavailable.
Never treat failed scrapes as zero.

Identify configured services by exact generated service name. Aggregate all
client/host label series per service and then across production forward
services. Do not trust those labels for identity (G0 even observed truncated
host labels), retain them, log them, or send them to the panel. Use a small
streaming parser with bounded line size; test escaped quotes/backslashes and
label order rather than assuming comma splitting is safe. GOST itself may
retain high-cardinality series: Agent aggregation bounds qui storage, not
GOST's heap. Check this on the RC soak.

Input maps to UploadBytes; output maps to DownloadBytes. Sum TCP/UDP and all
range ports exactly once. Use `core.NodeCounter("gost", processEpoch,
revision, upload, download)` and the existing TrafficSink: kind `node`, core
`gost`, credential/user/device sentinels `node`, protocol empty, epoch ending
`.node`. Reuse encrypted spool, cumulative cursor, batch idempotency, negotiated
node-traffic support, Ack and capacity failure reporting. Panel's shared
node-counter validation accepts GOST only for a reported enabled core and a
negotiated session. Extend core-name checks in traffic contracts/ingestion,
not just migration 0127. Never invoke user quota or account-counter ingestion.

GOST counters are cumulative from process start. Preserve the CoreRun process
epoch across an Agent-only restart if the exact child is still owned; a new
GOST process always gets a new epoch even for the same revision. Read/persist
before stop; if the traffic sink fails, do not knowingly discard a final sample
for an ordinary apply—use existing accounting failure behavior. A crash can
lose bytes since the last successful scrape; the five-second cadence cannot
eliminate that window. Prometheus floating representation also limits exact
integer precision for very large totals; do not promise billing accuracy.

Per-service totals stay Agent-local and are the source of the single core
aggregate; do not send one node Counter per service with the same epoch/key,
which would overwrite rather than sum. This phase adds no separate per-forward
history table/API. Today/month node views automatically include the core sample
through `node_traffic_samples`, with no account double count. T1 NIC/billing
usage remains separate and is never added to this aggregate.

G3 relay listeners and canaries are excluded from forward totals on their node;
their counters include relay/TLS overhead. Count actual entry/bridge forward
services only, once per node. A user-proxy bridge may overlap bytes counted by
the proxy core on the same node; section 5.3 defines the exclusion needed to
avoid this new source of cross-core double counting.

## 5. G3: encrypted managed-node hops

### 5.1 Engine selection and interoperability

Reuse the existing K4 `tunnelProtocol: "gost"` value to mean **GOST relay over
TLS with client CA** for server `tunnel` and `proxy_chain` connections. Do not
introduce a competing `engine` field for these: `tls` remains the existing
Trojan implementation, `wireguard` keeps its current behavior, `gost` selects
the new implementation. `forwardCore` from G2 is only for `port_forward`.
Keep Brook/nftables disabled. Client schemes cannot publish or receive GOST
node credentials and retain their existing mihomo semantics.

Two execution cases must be supported without making GOST a user proxy:

1. **Native forward entry:** an existing GOST forward's target pool is reached
   through one or two managed GOST hops. Render a GOST chain on the entry node,
   attached to each expanded forward service's `handler.chain`. Targets remain
   the configured final destinations; they must not accidentally become the
   relay address. A two-hop chain has ordered relay connectors/dialers and must
   reach the final destination through both nodes.
2. **Existing Xray/sing-box user entry:** those cores do not have a native
   GOST-relay connector. Reuse K4's existing internal Trojan relay object and
   node-to-node credential flow as the payload protocol. The source core's
   internal Trojan outbound dials a private loopback GOST TCP forward, which
   uses `handler.chain` to the exit's GOST relay, whose final destination is
   the exit's private loopback Trojan inbound. The remote proxy core continues
   to terminate the internal proxy protocol. GOST sees opaque bytes, never a
   qui user identity. Retain the inner Trojan TLS/SNI verification; do not
   weaken it just because the outer hop is encrypted.

The second case is necessary: simply changing K4's `canvasTunnels` map from
`gost` to a protocol string would either be unsupported by proxy adapters or
silently bypass encryption. Reuse the current Trojan binding, proxy-chain
composition, credential separation and final routing instead of implementing
GOST relay in Xray/sing-box. UDP uses the existing inner protocol's UDP-over-TCP
support and is advertised only after a real test with each core; no local raw
SOCKS/HTTP bridge or new user-facing GOST listener is added.

All-GOST native forward paths may have up to the existing two hops. Mixed
engine user-proxy paths reuse K4's hop graph and wrappers per GOST edge. Reject
native GOST-forward paths mixing non-GOST connectors in v1.3 with a precise
plan error; do not fall back to Direct. This is a connector capability boundary,
not a new unlimited chain implementation. Preserve cycle, branch, repeat-node,
TCP/UDP compatibility and entry-routing-conflict checks.
