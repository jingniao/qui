# v1.3.0 implementation designs: T1 and P2

Design review: 2026-11-01. Target: `release/v1.3.0`, Linux amd64.
This document is the implementation contract for Cline. T1 and P2 are independent
and can be implemented in either order. Neither needs GOST or the concurrent P1
and user-page changes. Preserve those changes when implementing.

Only the new migration specified below may be added; never edit an existing
migration, `go.mod`, or `go.sum`. Use existing Go, SQLite, protobuf, and Vue
facilities. Keep the existing pages, cards, permissions, and traffic pipeline.
No alerts, enforcement, billing integration, new daemon, or frontend redesign.
Unknown measurements are `null` in the REST API and `—` on screen; measured zero
is zero. The Chinese strings below are intentional UI copy.

## Reviewer decisions (override the text below where they differ)

1. **No time-zone key.** Drop `timezone` from `node_machine_traffic_daily`
   (primary key `(node_id,interface_name,local_date)`) and from
   `node_machine_traffic_cursors`. Days are bucketed in the panel zone current
   at ingestion time; a zone change is not a cursor discontinuity, it only
   shifts later buckets. Document: "修改面板时区后，之后的流量按新时区分日，
   已记录的日数据不重新分桶。" Remove the zone-equality filter, the
   zone-change baseline and the per-zone history tests.
2. The rest of the design is accepted as written, including replacing the
   card's monthly proxy readout with machine traffic (proxy traffic stays in
   the node detail, labelled as proxy traffic).

## 1. T1: monthly machine traffic per server

### 1.1 Existing implementation and boundaries

- `internal/agent/capability/host_metrics.go` reads cumulative receive/transmit
  bytes for each non-loopback interface from `/proc/net/dev`, plus live rates.
  `readHost(root, h)` already supports fixture proc trees. Keep that seam.
- `Heartbeat.interfaces` is field 20; `InterfaceCounters` already supplies both
  cumulative directions. `Heartbeat` currently ends at field 33. `HostInfo`
  contains relatively static hardware information, not reboot identity.
- `internal/panel/node/repository.go: Record` accepts sequenced messages in a
  transaction, updates the heartbeat, and calls `recordMetricTx`. Duplicate
  sequences exit before sampling. `metrics.go` retains one fresh rate sample
  per UTC minute, and `latency.go` deletes samples older than seven days.
- `node_meta` and GET/PUT `/api/v1/nodes/{id}/meta` hold financial metadata and
  port ranges. Their legacy local-storage import must keep working unchanged.
- `system_settings.timezone`, read through `system.Repository.ReadSetup` /
  `ReadBase`, is the explicit panel IANA time zone (default `Asia/Shanghai`).
  `/api/v1/system/base` changes it. Neither the browser zone nor server OS zone
  is an accounting input.
- `/api/v1/traffic/nodes/monthly` is retained **proxy** traffic, currently using
  `node_traffic_samples`. T1 gets separate names, tables, and endpoints; do not
  change that API's meaning or add machine bytes to user/core traffic.

Store raw daily RX and TX for **all reported non-loopback interfaces**, but
select exactly **one interface** for a summary. This allows the Owner to correct
the interface choice without throwing away already collected history. It also
avoids sending settings to the Agent. At ten interfaces this is 3,650 daily rows
per server per year, plus ten cursors; a minute series would be much larger.
Never sum interfaces, including during automatic selection.

### 1.2 Agent report and wire compatibility

Add these optional fields to `Heartbeat` in `proto/agent.proto`:

| Field | Number | Type | Meaning |
| --- | --- | --- | --- |
| `boot_id` | 34 | optional string | Trimmed contents of `/proc/sys/kernel/random/boot_id` |
| `default_route_interface` | 35 | optional string | Selected IPv4 default-route interface from `/proc/net/route` |

Keep `HostInfo` and `InterfaceCounters` unchanged. Read both fields on each host
heartbeat, before the early return for a failed `/proc/net/dev` read. A read or
parse failure omits just that measurement. Validate the boot ID as the kernel's
canonical UUID text; do not invent one from uptime, PID, hostname, or Agent start.

Parse `/proc/net/route` using whitespace fields, skipping the header. An eligible
row has destination and mask zero, `RTF_UP` set, no `RTF_REJECT`, a non-loopback
interface, and valid hexadecimal flags and decimal metric. Choose the smallest
metric, then lexicographically smallest interface name on ties. A gateway need
not be nonzero. Ignore malformed rows. This is an IPv4 routing-table heuristic,
not an `ip route get` implementation. If no eligible row exists (including an
IPv6-only server), report unknown. The Owner can explicitly select an interface;
do not introduce shell commands, netlink, or an IPv6 parser in T1.

Retain the existing cumulative counter collection and rates. No new capability
negotiation is needed: old panels ignore the added protobuf fields. A new panel
must not account old-Agent counters without `boot_id`; their monthly machine
traffic is unknown. A missing route field affects automatic selection only;
explicit selection can work when boot ID and interface counters are present.

Regenerate the committed Go protobuf outputs with `scripts/generate-proto.sh`.
Use the existing compiler under `C:/Users/luanf/qui/.tools/protoc` and existing
Go plugins/include directory in the build environment; do not change dependency
files or hand-edit generated descriptors. Extend the web heartbeat type with
`bootId` and `defaultRouteInterface` (protobuf JSON names), preserving existing
snake-case compatibility fields elsewhere.

### 1.3 Storage: new `migrations/0126_node_machine_traffic.sql`

Use three new tables. A separate settings table is preferable to more
`node_meta` columns: existing metadata PUTs and `importOnly` requests cannot
accidentally reset traffic settings, and recovery can copy this unit explicitly.

| Table | Columns and constraints |
| --- | --- |
| `node_machine_traffic_settings` | `node_id TEXT PRIMARY KEY REFERENCES nodes(id) ON DELETE CASCADE`; `method TEXT NOT NULL DEFAULT 'sum' CHECK` in `sum,outbound,max`; `interface_name TEXT NOT NULL DEFAULT ''`; nullable `allowance_bytes INTEGER` with integer type and range 1..9007199254740991 when set; `reset_day INTEGER NOT NULL DEFAULT 1 CHECK` integer 1..31 |
| `node_machine_traffic_daily` | `node_id` FK as above; `interface_name TEXT NOT NULL`; `timezone TEXT NOT NULL`; `local_date TEXT NOT NULL` (`YYYY-MM-DD`); `rx_bytes INTEGER NOT NULL DEFAULT 0`; `tx_bytes INTEGER NOT NULL DEFAULT 0`; primary key `(node_id,interface_name,timezone,local_date)`; both byte columns must be nonnegative SQLite integers |
| `node_machine_traffic_cursors` | `node_id` FK as above; `interface_name TEXT NOT NULL`; `boot_id TEXT NOT NULL`; `rx_bytes INTEGER NOT NULL`; `tx_bytes INTEGER NOT NULL`; `observed_at TEXT NOT NULL` (existing fixed-width UTC timestamp format); `timezone TEXT NOT NULL`; primary key `(node_id,interface_name)`; both byte columns nonnegative integers |

Use the same interface-name validation for settings, ingestion, and backup:
1..15 UTF-8 bytes, excluding whitespace, control characters, `/`, `:`, and the
exact name `lo`. Empty is allowed **only** in settings, meaning automatic.
Keep the Linux name length; do not restrict names to `eth`/`en` prefixes.

No initial daily rows or cursors. Settings may be absent: read defaults
`sum`, automatic interface, no allowance, reset day 1. GET must not write them.
Daily data is retained indefinitely, matching long-lived daily traffic data;
it is independent of `HourlyDays` and seven-day resource retention. Cursors are
also retained, including while a server is offline. Node soft deletion retains
all three tables' rows; physical cancellation/deletion follows the FK.
The primary key is sufficient for period reads; no extra index or scheduler.

The timezone key intentionally prevents combining daily buckets produced under
different zone settings. There is no minute-level history to re-bucket later.
Changing the panel zone starts a separate accounting history for that zone;
returning to a previous zone can reuse its retained daily rows. Document this
behavior and advise choosing the provider's zone before collecting traffic.

### 1.4 Transactional ingestion

Add `machine_traffic.go` to the node module. Call its recorder from the heartbeat
branch of `Repository.Record`, after sequence validation, in the **same** SQL
transaction as the heartbeat and accepted-message receipt. Sample every accepted
fresh heartbeat, not just the last heartbeat in a minute.

Reuse the 45-second freshness rule in `recordMetricTx`: factor its timestamp
check into one small helper and call it from both recorders. Use the validated
message timestamp as the counter observation time. A stale/invalid timestamp is
skipped, without advancing machine cursors. A sequence replay changes nothing.

Read the panel timezone in this transaction. Avoid an import cycle:
`system/backup` already imports `node`. Expose a small timezone-only transaction
reader on the system repository, implemented by the existing `readBase`, and
inject a `func(context.Context, *sql.Tx) (string, error)` into the node repository
at composition time. Both summary handlers and ingestion use this reader and
the same period helpers. Do not duplicate the timezone JSON/default logic, open
a second connection while holding the write transaction, or cache the zone at
Agent connection time. Wire it in production and relevant fixtures.

For each unique, valid non-loopback interface counter in a valid-boot heartbeat:

1. Reject that interface sample if either uint64 counter exceeds MaxInt64; do
   not cast it to a negative SQLite value. If a name appears twice, skip that
   name for this heartbeat. Other valid interfaces can still be collected.
2. Load its cursor. Without a cursor, insert the current counters/boot/time/zone
   as a baseline and add **no usage**. The first sample after upgrade is never
   traffic since boot. A newly discovered interface follows the same rule.
3. Ignore observation times at or before this cursor's time. With a changed
   boot ID, changed timezone, or either counter decreasing, replace the whole
   cursor with a new baseline and add no usage for that interval. Do not count
   the new absolute value or retain just the increasing direction. Interface
   recreation and counter resets within a boot are treated like discontinuities.
4. Otherwise compute unsigned differences, now safe within int64. This includes
   an arbitrarily long Agent/panel outage without a reboot: cumulative counters
   recover those bytes, without rate extrapolation or an offline cutoff.
5. Split each direction's delta across local calendar days intersecting
   `[previous observed_at, observed_at)`, in the cursor's (unchanged) panel zone.
   Allocate in proportion to actual elapsed time in each day, floor each share
   except the final share, which receives the exact remainder. Use calendar
   midnights, not fixed 24-hour increments, so DST days work. Use exact integer
   arithmetic (a small standard-library `math/big` multiply/divide helper is
   sufficient) to avoid delta-times-duration overflow. The sum of shares must
   exactly equal the original delta. Do not create the following day's row for
   a sample exactly at midnight unless the interval overlaps that day.
6. Upsert the daily rows, including zero shares for observed intervals, then
   replace the cursor. Check addition against MaxInt64 so SQLite cannot promote
   overflow to REAL. A storage/overflow error rolls back the whole transaction;
   do not acknowledge a heartbeat whose usage was only partly persisted.

Missing boot ID or missing interfaces produces no accounting writes. Do not
delete cursors on missing measurements, disconnection, Agent restart, core
restart, or route changes. A later valid same-boot sample can bridge that gap.
An interface that disappears and reappears with larger counters cannot always
be distinguished from continuity; state this limit rather than adding a new
interface lifecycle protocol.

The day split is an **estimate of when** bytes crossed the interface, especially
over an outage. The same-boot total is recovered; its day/period allocation is
not exact. No sample-level journal or Agent daily aggregation is required.

### 1.5 Billing periods, interface choice, and settings changes

One backend helper computes periods for both APIs. For a requested reset day D,
construct the anchor in each year/month at local midnight on
`min(D, last calendar day of that month)`. Find the latest anchor <= now and the
immediately following monthly anchor. Do not add one month to a previously
clamped date: January 31 -> February 28 -> March 31. Intervals are half-open;
at the anchor instant the new period starts. `periodEnd` and `nextResetAt` are
the same exclusive boundary. Sum daily rows whose dates fall in that interval,
with exact timezone equality.

Resolve a summary's interface once: explicit `interface_name`, otherwise the
latest **fresh** heartbeat's `defaultRouteInterface`. Require the resolved name
to occur in that heartbeat's interfaces and a valid boot ID for current status
`measured`. Never choose the first interface, the busiest interface, or all
interfaces as fallback. Historical summaries may retain an explicit selection
and known totals when offline; mark them `stale`. Automatic mode may use the
last reported route when the heartbeat is stale, also explicitly marked stale;
without any reported route it is unknown.

Use that one resolved interface for the **entire current period**. An explicit
selection change, or a changed automatic route, therefore recomputes the period
from that interface's retained daily history. Do not stitch interfaces or sum
their rows. This is deliberate and must be explained beside the selector:
`切换网卡会按所选网卡重新计算本期；自动模式使用最近上报的默认路由网卡。`

RX is host receive, TX is host transmit. After summing directions over the
period, compute `sum = RX + TX`, `outbound = TX`, or `max = max(RX, TX)`.
In particular, `max` is **not** a sum of daily maxima. Method/reset-day changes
recompute immediately from retained rows; allowance changes only the display.
Never clear usage or reset counters on the billing date or a settings save.

No daily row in the selected interface/zone/period means unknown, not zero.
A baseline alone is unknown; the next successfully differenced interval can
establish measured zero. Existing rows remain useful when offline: show their
last-known total with stale/partial context. T1 does not claim complete provider
billing coverage; every usage display has the collection-limits tooltip.

### 1.6 REST contract and permissions

Add these routes under the existing node handler, authenticated as node meta:

| Route | Permission | Response |
| --- | --- | --- |
| GET `/api/v1/nodes/{id}/machine-traffic/settings` | Owner and Viewer | Settings object below |
| PUT same path | Owner, existing CSRF middleware | Full replacement of the four settings fields; returns settings object |
| GET `/api/v1/nodes/{id}/machine-traffic` | Owner and Viewer | One summary object |
| GET `/api/v1/nodes/machine-traffic` | Owner and Viewer | `{ "items": [summary, ...], "timezone": "Asia/Shanghai" }` for non-deleted nodes |

Use the batch endpoint on the server list. Both summary endpoints call one
repository summary implementation, with the same captured `now` and settings
zone. Batch-load settings, cursors, heartbeat selection, and daily aggregates;
do not issue one HTTP request or one period query per visible card. Do not add
machine summaries to every general-purpose `NodeView` response.

Settings JSON (defaults shown):

```json
{"method":"sum","interfaceName":"","allowanceBytes":null,"resetDay":1}
```

PUT requires all four fields (including explicit nullable allowance), rejects
unknown fields using the existing decoder, and uses this exact shape. Allowance
is an integer JSON number in 1..9007199254740991 bytes, or null to clear. Zero,
negative, fractional, and out-of-range values are invalid. Keeping the allowance
within JavaScript's exact integer range avoids a second string-number convention
for editable UI data. Daily/cursor counters themselves retain int64 range.

Summary example (byte values are decimal strings to preserve exact totals):

```json
{
  "nodeId":"server-id",
  "settings":{"method":"sum","interfaceName":"","allowanceBytes":2199023255552,"resetDay":15},
  "interfaceName":"eth0",
  "timezone":"Asia/Shanghai",
  "periodStart":"2026-10-15T00:00:00+08:00",
  "periodEnd":"2026-11-15T00:00:00+08:00",
  "nextResetAt":"2026-11-15T00:00:00+08:00",
  "rxBytes":"107374182400",
  "txBytes":"227633266688",
  "usedBytes":"335007449088",
  "status":"measured",
  "lastObservedAt":"2026-11-01T12:00:00Z"
}
```

`status` is `measured`, `stale`, or `unknown`. `measured` requires current valid
host measurements and at least one daily row in this period; `stale` means
known rows exist but that current measurement is unavailable/not fresh (45 s).
`unknown` means no period rows or no resolvable interface; all three byte fields
are null. `interfaceName` and `lastObservedAt` are null when unavailable. The
latter is the selected cursor time, not an HTTP fetch time. Period boundaries
and settings remain available for old Agents. If a new boot has just been
baselined but this period already has rows, retain the known sum; the collection
tooltip still explains the lost interval. Do not use status to claim completeness.

Aggregate RX, TX, and `usedBytes` with checked int64 arithmetic; an actual
overflow is a server error, never a wrapped value. Convert strings to Number
only for existing display formatters/progress arithmetic in the web; never use
rounded UI numbers as storage input. A sum can exceed the allowance.

Validate via one settings validator reused by the handler and backup checker.
A syntactically valid interface need not currently exist: allow configuration
for an offline server and show unknown if it has never been measured.
Return 400 `invalid_request` for decoding/settings errors with a specific field
message; existing 401/403 apply to authentication/role/CSRF, 404 `not_found` to
missing/deleted nodes, and the existing server-error response for DB/zone errors.
Use the existing node `fail` mapping for the actual 404 code if it differs.
PUT runs settings upsert and `Audit.RecordTx` together, action `服务器流量设置`,
target node ID, result `成功`, actor/IP as meta. No remote operation, confirmation
dialog, revision deployment, or audit record for GET. Notify the existing node
refresh mechanism after saving. Do not audit per-heartbeat accounting.

### 1.7 Backup, validation, and restore

All three tables stay in the encrypted SQLite backup. Machine daily rows and
cursors are durable traffic data, **not** seven-day telemetry: do not add them
to `stripLatencySnapshot`, `DELETE FROM node_metric_samples`, or rate retention.
Keep the existing archive manifest version and file inventory (the database is
already hashed); no extra JSON/CSV file or manifest file entry is necessary.

Add `backup/machine_traffic.go` and call its validator from database inspection
beside `validateMultiCore` / `validateMetricsTuning`. Follow their migration
presence pattern: pre-0126 with none of the three tables is valid; migration
presence without exactly all three tables, or tables without the migration, is
`ErrArchive`. Read every expected column even on empty tables. Validate settings,
FKs, unique keys, integer storage classes/nonnegative amounts, canonical dates,
valid IANA zones (reject `Local`), boot IDs, interface names, and cursor UTC
timestamps. Do not compare cursor absolute counters with daily usage; they have
different baselines. Reuse node validators, not a second settings ruleset.
Extend backup `Totals`/`ReadInventory` with `machineTrafficSettings`,
`machineTrafficDays`, and `machineTrafficCursors` counts. Preserve compatibility
with pre-0126 inventory and prepared-restore evidence.

In `node.Repository.PrepareRestoreTx`, after ensuring current nodes/tombstones
exist, preserve current machine settings just like current node metadata. The
coordinator's `restore_source` is the frozen **current database**, not the chosen
archive. If it contains 0126, copy each of the three tables wholesale from it
using `db.CopyRecoveryTable`, as access recovery does for traffic tables. Copy
daily rows and cursors as one unit; never add/max overlapping daily totals, or
mix snapshot daily usage with current cursors. This prevents both lost current
usage and duplicate accounting after restoring an older business snapshot.

If the current source predates 0126, leave the migrated candidate's archived
machine tables intact (or empty/default if the archive predates 0126 too).
An empty current table is still authoritative when the current source has
0126; do not interpret emptiness as permission to resurrect archived usage.
Standalone archive examination retains the archived settings/history/cursors,
but installation/recovery must still satisfy the coordinator's existing current
database and node-identity evidence requirements. T1 adds no fresh-install or
foreign-instance recovery bypass. Do not blanket-clear cursors after restore.
A restored same-boot cursor recovers the subsequent
delta; changed boot/zone is baselined under the normal rules. The usual restore
node identity and replay safeguards remain authoritative.

Update old-schema test fixture builders to remove the new migration/tables
before simulating older schemas, where needed; never change old SQL migrations.

## 2. P2 / F11: Xray forward bytes in node totals

### 2.1 Current behavior and minimal change

`xray/stats.go: configureStats` **already** sets
`policy.system.statsInboundUplink` and `statsInboundDownlink` true. It also turns
on outbound counters when needed for WireGuard account attribution. Keep this
configuration; there is no reason to enable another global traffic mechanism.
User inbounds and forward inbounds therefore have native inbound counters, but
the reader currently queries account sources only.

`render.go` uses desired inbound ID as the rendered inbound tag;
`protocols.go` renders protocol `forward` as `dokodemo-door`. Add an explicit
allowlist of those rendered, enabled forward tags. Do not classify every
`dokodemo-door` as a forward (management/internal listeners must not qualify).

Today `core.SaveAccountAndNode` sums account counters into a `kind:"node"`
counter. Xray must instead produce:

`node uplink/downlink = existing account uplink/downlink sum + selected forward inbound uplink/downlink sum`.

The account side intentionally retains its existing coverage and exclusions,
including internal relay accounts. This fix does not make Xray's total a
whole-core or machine meter. No new per-forward panel tables, attribution,
credentials, capabilities, or protocol changes are needed. sing-box's native
node totals and concurrent adapter changes stay untouched.

### 2.2 Rendered metadata and reader

Add `StatsNodeInbounds []string` to `core.RenderedConfig`. Populate it once,
while rendering/configuring stats, with sorted unique tags of **enabled forward
inbounds actually rendered into this core**. It is runtime metadata, not an
extra Xray JSON property. Leave `StatsAccounts` account-only; gate/online code
and account telemetry must never see fake forward users.

Keep `statsInboundUplink/Downlink` true in generated JSON. Keep outbound stats
conditional for WireGuard. Assert this in the forward golden test, and assert
the forward-only allowlist separately (golden JSON alone cannot cover metadata).

Refactor the current reader into one internal sample reader returning account
counters and a node-only `core.StatsBatch` of forward cumulative totals. Preserve
`readCounters` as a thin account-only wrapper for existing tests/callers, and
keep the public `TrafficCounters` account-only. `sampleTrafficLocked` and
`CollectStats` use the full sample reader. There must be only one parser/query
implementation and one sampled set of values per collection operation.

Alongside existing `user>>>` and conditional WireGuard outbound queries, issue
one `QueryStats` for `inbound>>>` when the forward allowlist is nonempty, always
`Reset_: false`. Accept only exact keys
`inbound>>>TAG>>>traffic>>>uplink` and `...>>>downlink` whose TAG is in the
allowlist. Filter before account/node aggregation. The broad query is one RPC,
not one RPC per forward; its results from user/API/other inbounds are ignored.
Never sum all inbound stats, all outbound stats, or both inbound and outbound
for the same forward. That would double count users or forwarded payload.

Extend the existing duplicate/name/direction/nonnegative/overflow checks and
16384-stat response bound to the additional query; no parallel defensive
parser. Accumulate forwards directly into the node-only totals with checked
addition. Do not materialize fake `traffic.Counter` entries for them. Preserve
WireGuard's per-device outbound aggregation and shared HTTP/SOCKS username
deduplication exactly as they are.

Use existing `CounterSources` to track the selected forward prefixes along with
account prefixes; its configured count becomes
`len(StatsAccounts) + len(StatsNodeInbounds)` in Xray `TrafficSourceStatus`.
Unselected inbound sources must not enter its direction map. A never-created
native source is lazy/unobserved, as today; it contributes no bytes yet and
does not fabricate a measured account zero. Once either direction appears,
require a complete pair. A previously observed selected source disappearing
in the same epoch fails sampling under the existing `Observe` rule. Query,
validation, or source-continuity failure produces no persisted node sample;
retain the existing failure status and final-sample failure behavior.

### 2.3 Persistence, totals, and process lifetime

Extend `core.SaveAccountAndNode` with an optional variadic node-only
`StatsBatch` input. Existing callers pass none; Xray passes the single forward
total. Reuse the helper's checked account summation, add these node-only bytes
with the same bounds, and use existing `NodeCounter`. Compute/validate the
complete node total before attempting sinks, then persist the account batch
first and the independent node batch second, preserving current spool batching
semantics. A node sink failure must be retried without advancing any native
counter; a repeated cumulative sample is safe under panel cursors. Do not put
node-only bytes into the account batch or change sing-box's call sites.

`CollectStats` must also return accounts plus forwards using the shared total
calculation, so heartbeat/live node totals agree with persisted samples. Extract
a small total-summing helper in `core/node_traffic.go` and use it in both paths;
do not leave a second account-only summation loop in `xray/adapter.go`.

Keep the current core process `statsEpoch`, revision/run marker, restart and
rollback handling. Node samples remain `Kind="node"`, `Core="xray"`,
`CredentialID/UserID/DeviceID="node"`, `CoreEpoch=statsEpoch+".node"` with current
revision. Reads never reset native counters. Forward/tag changes are applied by
the existing restart path, yielding a new process epoch; final sampling and
failure handling before stop must use the old rendered allowlist. New-epoch
totals begin at zero and the panel counts the first cumulative value, unlike
T1's host-counter upgrade baseline. No migration or historical backfill for P2.

`internal/panel/access/node_traffic.go` already computes node-counter deltas;
`node_traffic_samples` already prefers them over account-derived samples in the
same epoch. Reuse that contract unchanged. Forward traffic therefore enters
core/node daily/monthly summaries, never `used_traffic`, device counters, or
domain byte attribution. Old Agents keep the F11 limitation until upgraded and
restarted with the updated Agent. Missing pre-upgrade bytes stay missing.

## 3. Implementation gates and Owner decisions

For each implemented phase run the applicable focused tests, then the established
Linux `scripts/check.sh` and real-core suite with the official amd64 Xray and
the existing sing-box matrix. Exercise T1 on the three current hosts including

implementation details left by T1: retain all interface daily rows but display
one interface's period, proportional allocation across local days, durable daily
retention, separate histories per panel timezone, current-data-preserving
