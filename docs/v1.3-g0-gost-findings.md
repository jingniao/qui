## 2. Configuration, and how to validate it

### 2.1 There is no validation mode

`gost -h` (exit 0, printed on stderr) shows every flag:

```console
Usage of bin/gost:
  -C value    config file(s), URL(s), or inline JSON
  -D          debug mode
  -DD         trace mode
  -F value    chain node list
  -L value    service list
  -O string   output format, one of yaml|json format
  -R duration auto reload period (e.g. 30s, 1m)
  -V          print version
  -api string api service address
  -metrics string metrics service address
```

There is **no** `--check` / `--validate` / `--dry-run`. Could `-O` serve as one?
It parses and re-prints the config and exits — but it does **not** validate
anything semantic:

| Config | `gost -C cfg -O yaml` | serve mode `gost -C cfg` |
| --- | --- | --- |
| valid | exit 0, 8 ms, prints YAML | runs |
| `handler.type: nosuchhandler` | **exit 0**, prints `type: nosuchhandler` | **exit 1** in 11 ms, `fatal unknown handler: nosuchhandler` |
| `listener.type: nosuchlistener` | **exit 0** | **exit 1** in 7 ms, `fatal unknown listener: nosuchlistener` |
| `addr: ":999999"` | **exit 0** | **exit 1** in 8 ms, `error init: listen tcp: address 999999: invalid port` + `fatal` |
| duplicate service names | **exit 0** | **exit 1** in 16 ms, after binding both ports: `fatal registry: duplicate object` |
| duplicate `addr` | **exit 0** | **exit 1** in 9 ms, `bind: address already in use` + `fatal` |
| unknown top-level key `nosuchkey: 1` | exit 0 (key silently dropped) | runs, no warning |
| malformed YAML | **exit 1**, `While parsing config: yaml: line 1: did not find expected node content` | same |
| missing file | **exit 1**, `open cfg/does-not-exist.yaml: no such file or directory` | same |
| `services: []` | exit 0 | runs with no listener until killed |

So `-O` is a **syntax/render gate only**; every semantic check happens in serve
mode, and the failure mode is always the same: one `{"level":"fatal",...}` line
on stderr and exit status 1, within 7–16 ms of exec (9–16 ms even when a listener
was already bound).

Note also that `-O` is not strict about its own argument: `-O toml` silently
prints YAML.

```console
$ bin/gost -C cfg/bad-handler.yaml; echo "exit=$?"
{"level":"info","msg":"unknown handler: nosuchhandler", ...}   # (single fatal line)
exit=1
$ bin/gost -C cfg/dup-names.yaml; echo "exit=$?"
{"level":"info","msg":"listening on [::]:18084/tcp","service":"svc",...}
{"level":"info","msg":"listening on [::]:18085/tcp","service":"svc",...}
{"level":"fatal","msg":"registry: duplicate object"}
exit=1
```

### 2.2 What is silently ignored (matters more than what fails)

Because decoding is not strict, a typo produces a *running* process with the
wrong behaviour instead of an error. Verified cases:

- unknown top-level key (`nosuchkey: 1`) → ignored.
- `selector.strategy: bogus` → accepted; six requests through a two-target
  forward returned `A B A B A B`, i.e. it behaved like `round` (see §3.4).
- `limiter: no-such-limiter` → accepted; **no limiting at all** and no log line
  (3.4 GB/s through the forward, see §4.3).
- a junk limit string (`limits: ["not a limit"]`) → accepted, no log line.
- `chain: <name>` at **service** level → silently dropped; the service then dials
  its target directly, without the chain (see §6.1). The chain belongs under
  `handler.chain`.

Rendering a config and reading it back with `-O yaml` is a good way to see what
GOST actually kept, e.g. the service-level `chain` disappears:

```console
$ bin/gost -C cfg/a-fwd-via-b.yaml -O yaml
services:
- name: fwd-via-b
  addr: :20050
  handler:
    type: tcp            # <-- chain: chain-b was dropped here
  listener:
    type: tcp
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
chains:
- name: chain-b
  ...
```

### 2.3 Recommended validation approach for the Agent

Two layers, because GOST gives us no single "validate" call:

1. **Renderer + syntax gate.** The Agent renders canonical YAML from the
   `DesiredState` (never pass panel JSON through), then runs
   `gost -C <file> -O json` with a short timeout: non-zero exit or unparsable
   output means "do not touch the running core", and the fatal message can be
   surfaced to the panel as the apply error. This catches YAML/JSON typos and
   nothing else.
2. **Start-and-settle gate.** Treat *the process itself* as the semantic
   validator: start `gost -C <file>`, then require for a settle window of about
   2 s that (a) the process is still alive and (b) every expected listener is
   present (bind check by parsing the `listening on <addr>/tcp` / `/udp` lines,
   or by dialling each address). Any exit inside the window is a failed apply;
   the exit status is 1 and the fatal message is on stderr. Because a GOST
   service only reports "listening" once its listener is bound, duplicate names
   and port clashes also land in this window (§2.1), so the panel sees a
   failure rather than a silently degraded node.
3. **Never rely on GOST to reject bad values.** The Agent adapter must validate
   what GOST ignores: selector strategy names, limiter/climiter references and
   limit strings, `handler.chain` vs service-level `chain`, and that no unknown
   key is emitted. Round-tripping through `-O yaml` in a unit test is a cheap
   way to assert the renderer's output is canonical.
4. Apply is a **restart** (§7): stop, write config, start, settle-check,
   health-check, and roll back to the previous file + restart on failure — the
   same shape as the existing Xray/sing-box adapters.

## 3. Forwards: TCP, UDP, balancing, failover, port ranges

Test targets (both behind the same host): `127.0.0.1:19001` returns `A`,
`127.0.0.1:19002` returns `B` (`python3 -m http.server` with `id.txt`), plus UDP
echo servers on `19101`/`19102` answering `A:ping` / `B:ping`.

### 3.1 TCP forward with a target pool

```yaml
services:
- name: fwd-tcp
  addr: ":20000"
  handler:
    type: tcp
  listener:
    type: tcp
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
    - name: target-b
      addr: 127.0.0.1:19002
    selector:
      strategy: round
```

```console
$ for i in 1 2 3 4 5 6; do curl -s http://127.0.0.1:20000/id.txt; done
A B A B A B
```

### 3.2 UDP forward with a target pool

Same shape with `handler.type: udp`, `listener.type: udp`, targets on UDP:

```yaml
services:
- name: fwd-udp
  addr: ":20100"
  handler:
    type: udp
  listener:
    type: udp
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19101
    - name: target-b

```

```console
$ for i in 1 2 3 4 5 6; do python3 udpping.py 20100; done
A:ping B:ping A:ping B:ping A:ping B:ping
```

### 3.3 Failover with `fifo` + `maxFails`/`failTimeout`

```yaml
services:
- name: fwd-fifo
  addr: ":20095"
  handler:
    type: tcp
  listener:
    type: tcp
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
    - name: target-b
      addr: 127.0.0.1:19002
    selector:
      strategy: fifo
      maxFails: 1
      failTimeout: 5s
```

```console
both up     : A(curl=0) A(curl=0) A(curl=0)
# kill target A
A down      : A(curl=56) B(curl=0) B(curl=0)      # first request fails, then B
# restart target A, wait 6 s (failTimeout 5s)
A back      : A(curl=0) A(curl=0) A(curl=0)       # marked node expires, A is used again
```

Key point for the panel's health view: GOST **accepts** the client connection
before dialling the target, so a dead target looks like "connection accepted,
then closed" (`curl` exit 56 = response read failure, HTTP 000) and not like
`ECONNREFUSED`. A forward-port health check must therefore test end-to-end
responsiveness, not just the listener socket:

```console
{"level":"error","msg":"route(retry=0) dial tcp 127.0.0.1:19001: connect: connection refused",
 "service":"fwd-fifo","sid":"..."}
{"level":"error","msg":"dial tcp 127.0.0.1:19001: connect: connection refused",
 "node":"target-a","dst":"127.0.0.1:19001", ...}
```

`round` also survives a dead node, but only after one failed request per
`failTimeout` window; the failing node is marked and skipped meanwhile:

```console
strategy=round, target A down:
req1 curl_exit=56 http=000       (tried A)
req2 curl_exit=0  http=200 body=B
req3 curl_exit=0  http=200 body=B
req4 curl_exit=0  http=200 body=B
```

### 3.4 Strategy names are not validated

```console
strategy=fifo     6 requests: A A A A A A
strategy=round    6 requests: A B A B A B
strategy=rand     6 requests: B A A A B A
strategy=bogus    6 requests: A B A B A B        # accepted, behaves like round
```

The binary registers `round`, `fifo`, `rand`, `hash`; an unknown name is accepted
at startup and falls back to round-robin behaviour.

### 3.5 Port ranges: not a config feature

Every config-level attempt was rejected at listen time:

| `addr` | result |
| --- | --- |
| `":20000-20003"` | `error init: listen tcp: lookup tcp/20000-20003: unknown port` + `fatal`, exit 1 |
| `":20200,:20201"` | `listen tcp: address :20200,:20201: too many colons in address` |
| `"127.0.0.1:20300-20302"` | `listen tcp4: lookup tcp/20300-20302: unknown port` |
| UDP `":20400-20402"` | `lookup udp/20400-20402: unknown port` |

Only the CLI expands a range, and it expands it into one service per port,
client-side, before anything starts. `-O yaml` shows the expansion:

```console
$ bin/gost -L "tcp://:20500-20502/127.0.0.1:19001" -O yaml
services:
- name: service-0
  addr: :20500
  handler: {type: tcp}
  listener: {type: tcp}
  forwarder: {nodes: [{name: target-0, addr: 127.0.0.1:19001}]}
- name: service-1
  addr: :20501
  ... (same target)
- name: service-2
  addr: :20502
  ... (same target)
```

With two targets listed in the CLI form the mapping is **positional, one target
per port** — not a pool spread over the range:

```console
$ bin/gost -L "tcp://:20500-20501/127.0.0.1:19001,127.0.0.1:19002" -O yaml
services:
- name: service-0
  addr: :20500
  forwarder: {nodes: [{name: target-0, addr: 127.0.0.1:19001}]}
- name: service-1
  addr: :20501
  forwarder: {nodes: [{name: target-1, addr: 127.0.0.1:19002}]}
$ # live behaviour of the same command
port 20500: A A A A
port 20501: B B B B
```

Consequences for G2: the Agent renders **one `services[]` entry per listening
port** (a range of *n* ports is *n* services), each with the full target pool and
its own selector state — round-robin position and failure marks are per service,
so two ports of the same range fail over independently. A comma-separated port
list in `addr` is never valid.

## 4. Limits: bandwidth and connections

### 4.1 Bandwidth limiter (`limiters` + `limiter`)

```yaml
limiters:
- name: rate-in-1mb-out-200kb
  limits:
  - "$ 1MB 200KB"
- name: rate-in-200kb-out-1mb
  limits:
  - "$ 200KB 1MB"
services:
- name: fwd-rate-slow-out
  addr: ":20032"
  handler:
    type: tcp
  listener:
    type: tcp
  limiter: rate-in-1mb-out-200kb
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
- name: fwd-rate-slow-in
  addr: ":20034"
  handler:
    type: tcp
  listener:
    type: tcp
  limiter: rate-in-200kb-out-1mb
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
```

Measured with `curl -w '%{speed_download} %{time_total}'`:

```console
2 MiB download, direct                       : 2042017526 B/s in 0.001 s  (loopback baseline)
2 MiB download via "$ 1MB 200KB"   (:20032)  :     226898 B/s in 9.24 s
2 MiB download via "$ 200KB 1MB"   (:20034)  :    2092306 B/s in 1.00 s
1 MiB upload   direct              (:20035)  :  885621621 B/s in 0.001 s
1 MiB upload   via "$ 200KB 1MB"   (:20036)  :     254409 B/s in 4.12 s
```

Steady state over an 8 MiB download, to rule out a short burst effect:

```console
"$ 1MB 1MB"    (:20042): 1198158 B/s in 7.00 s      # 8 MiB / 7.0 s
"$ 200KB 200KB"(:20043):  209915 B/s in 39.96 s
```

So the first number is the **client→target ("in") rate** and the second the
**target→client ("out") rate**, matching the `input`/`output` naming of the
counters in §5. Rates are honoured within roughly ±20 % over multi-MiB
transfers (there is a small burst allowance), which is fine for a per-forward
cap and not for precise accounting.

### 4.2 Connection limiter (`climiters` + `climiter`)

```yaml
climiters:
- name: conn-2
  limits:
  - "$ 2"
services:
- name: fwd-conns
  addr: ":20033"
  handler:
    type: tcp
  listener:
    type: tcp
  climiter: conn-2
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
```

Two long-lived connections held, then two more attempts through the limited port
and one through an unlimited control service on the same target:

```console
attempt1 curl_exit=56 http=000 body=''      # accepted then closed immediately
attempt2 curl_exit=56 http=000 body=''
control  curl_exit=0  http=200 body='A'     # control port unaffected
held conn1/conn2: connect ok, later recv 187 bytes ok   # held sessions unaffected
```

The rejection is logged at **warn** each time:

```console
{"level":"warn","msg":"accept: connection limit exceeded","service":"fwd-conns","listener":"tcp","handler":"tcp"}
```

As with a dead target, an over-limit connection is accepted and then closed, so
callers see an empty response rather than a refusal.

### 4.3 Limiters are not validated either

```console
$ bin/gost -C cfg/lim-probe.yaml      # limiter: no-such-limiter, limits: ["not a limit"]
{"level":"info","msg":"listening on [::]:20030/tcp", ...}      # no warning at all
$ curl -o /dev/null -w '%{speed_download}\n' http://127.0.0.1:20044/big8.bin
3398949756          # 8 MiB in 2.5 ms: the reference was silently ignored
```

The panel/Agent renderer must own validation of limiter names, climiter names
and `$ <in> <out>` strings; GOST will happily run unlimited.

## 5. Counters: Prometheus metrics over TCP and over a unix socket

### 5.1 Configuration

```yaml
metrics:
  addr: 127.0.0.1:19090
services:
- name: fwd-m
  addr: ":20040"
  handler:
    type: tcp
  listener:
    type: tcp
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
- name: fwd-udp-m
  addr: ":20041"
  handler:
    type: udp
  listener:
    type: udp
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19101
```

The endpoint is an ordinary service named `@metrics` and answers `GET /metrics`
with Prometheus text (123 lines, including the Go runtime collectors):

```console
{"level":"info","msg":"listening on 127.0.0.1:19090","service":"@metrics"}
```

Unix socket — `metrics: {addr: unix:///root/qui-g0/m.sock}` also works:

```console
{"level":"info","msg":"listening on /root/qui-g0/m.sock","service":"@metrics"}
$ ls -l m.sock
srwxr-xr-x 1 root root 0 11月  1 15:14 m.sock
$ curl -s -o m.txt -w '%{http_code}\n' --unix-socket /root/qui-g0/m.sock http://localhost/metrics
200                    # 123 metric lines
```

A bare path (`addr: /root/qui-g0/m2.sock`) is rejected:
`{"level":"fatal","msg":"listen tcp: address /root/qui-g0/m2.sock: missing port in address"}`.

A unix socket is the better target for G2/G3: no TCP port to expose, no
`ss -ltnup` entry for an operator to wonder about, and the Agent reads it with
the same privileges as the core.

### 5.2 What the counters say, and whether they accumulate

Per-service byte counters with labels `client`, `host`, `service`:

```console
# no series at all before traffic
after one 2 MiB download + 3 UDP pings:
gost_service_transfer_input_bytes_total{client="127.0.0.1",host="192",service="fwd-m"} 86
gost_service_transfer_input_bytes_total{client="127.0.0.1",host="192",service="fwd-udp-m"} 12
gost_service_transfer_output_bytes_total{client="127.0.0.1",host="192",service="fwd-m"} 2.097357e+06
gost_service_transfer_output_bytes_total{client="127.0.0.1",host="192",service="fwd-udp-m"} 18
after a second identical 2 MiB download:
gost_service_transfer_input_bytes_total{...service="fwd-m"} 172
gost_service_transfer_output_bytes_total{...service="fwd-m"} 4.194714e+06
```

- **Cumulative since process start**: 86 → 172 bytes in, 2 097 357 → 4 194 714
  bytes out over two identical transfers. They reset only with the process, i.e.
  on every GOST apply restart, so the panel needs a per-(node, epoch) cursor as
  it already has for the other cores.
- **UDP is counted**: `fwd-udp-m` moved 12 bytes in / 18 bytes out for three
  `ping` datagrams (4 bytes payload in, 6 bytes `A:ping` out each) — per datagram,
  not per stream.
- Other families: `gost_service_requests_total`,
  `gost_service_requests_in_flight`, `gost_service_request_duration_seconds`,
  `gost_services` (gauge of running services).

Caveats from the sample above:

- The label set includes `client` (source IP) and `host`, so the series count
  grows with the number of clients; the Agent must aggregate or drop
  `client`/`host` before storing anything.
- `host="192"` is literally what the exporter emitted (a truncated
  `192.168.5.36`), so the `host` label must not be used for anything.

### 5.3 Nothing else listens by default

With only a forward service configured (no `metrics`, no `api`):

```console
$ ss -ltnup | grep gost
tcp   LISTEN 0 4096  *:18081  *:*  users:(("gost",pid=129779,fd=4))
```

Exactly one listener — the service. There is no `api` (Web API) and no pprof
listener: `-api` and an `api:` section are opt-in, and with `metrics` enabled
only the metrics address is added. A service-only start-up log mentions `api`
zero times. This matches the v1.3 plan's "Web API, metrics and pprof stay off, or
loopback-only where counters need them".

## 6. Encrypted relay between two GOST instances, with client certificates

Setup: two GOST processes on the same machine (A = "entry node", B = "exit
node"), a throwaway CA plus a server cert (CN `gost-b`, SAN `IP:127.0.0.1`) and a
client cert (CN `gost-a`):

```console
$ openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 2 \
    -subj '/CN=g0-test-ca'
$ openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj '/CN=gost-b'
$ printf 'subjectAltName=IP:127.0.0.1,DNS:gost-b\n' > san.ext
$ openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 2 \
    -extfile san.ext -out server.crt
$ openssl req -newkey rsa:2048 -nodes -keyout client.key -out client.csr -subj '/CN=gost-a'
$ openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 2 -out client.crt
```

### 6.1 B — relay handler on a TLS listener that requires a client certificate

```yaml
metrics:
  addr: 127.0.0.1:19091
services:
- name: relay-b
  addr: ":18443"
  handler:
    type: relay
  listener:
    type: tls
    tls:
      certFile: /root/qui-g0/pki/server.crt
      keyFile: /root/qui-g0/pki/server.key
      caFile: /root/qui-g0/pki/ca.crt
```

`caFile` on the listener is what makes client certificates **mandatory**.
Confirmed independently of GOST with `openssl s_client` — the server sends a
CertificateRequest, and a client without a cert gets TLS alert 116:

```console
$ openssl s_client -connect 127.0.0.1:18443 -CAfile pki/ca.crt -servername gost-b -state </dev/null
SSL_connect:SSLv3/TLS read server certificate request
...
403762370A7F0000:error:0A00045C:SSL routines:ssl3_read_bytes:tlsv13 alert certificate required:...
```

### 6.2 A — TCP forward whose chain dials B with a client certificate

```yaml
chains:
- name: chain-b
  hops:
  - name: hop-0
    nodes:
    - name: node-b
      addr: 127.0.0.1:18443
      connector:
        type: relay
      dialer:
        type: tls
        tls:
          certFile: /root/qui-g0/pki/client.crt
          keyFile: /root/qui-g0/pki/client.key
          caFile: /root/qui-g0/pki/ca.crt
          serverName: gost-b
services:
- name: fwd-via-b
  addr: ":20060"
  handler:
    type: tcp
    chain: chain-b        # <-- chain belongs to the handler, not the service
  listener:
    type: tcp
  forwarder:
    nodes:
    - name: target-a
      addr: 127.0.0.1:19001
```

This is exactly the shape the CLI produces (`gost -L tcp://:20070/<target> -F
relay+mtls://...` → `handler.chain`), which is why `-O yaml` is a reliable way to
get a canonical config: the chain is attached to the handler, and the hop node
carries `connector.type: relay` + `dialer.type: tls|mtls` with a `tls` block.

### 6.3 Results

```console
# A with the right client cert
good      curl_exit=0  http=200 body=A
# A without any client cert
nocert    curl_exit=52 http=000 body=
# A with a certificate signed by a different CA
rogue     curl_exit=52 http=000 body=

B log for the rejections:
{"level":"error","msg":"tls: client didn't provide a certificate","service":"relay-b","listener":"tls","handler":"relay","sid":"..."}
```

A rejection looks like an empty reply (`curl` exit 52), not a refused connection,
because GOST accepts the TCP connection before the handshake completes.

Proof that the traffic really traversed B (B's own Prometheus counters, service
`relay-b`, one 2 MiB download):

```console
before: gost_service_transfer_output_bytes_total{...service="relay-b"} 7954
after : gost_service_transfer_output_bytes_total{...service="relay-b"} 2.11088e+06
delta : 2102926 bytes for a 2097152-byte payload      # ~0.28 % relay/TLS framing overhead
```

So relay-service counters are usable for coarse "did traffic flow" checks but
include framing overhead; per-forward byte accounting should be taken from the
forward service on the entry node, where the numbers are exact (86 in /
2 097 357 out for the same payload, §5.2).

### 6.4 Other transports

| Transport | YAML | Result |
| --- | --- | --- |
| TLS | `listener: {type: tls, tls: {certFile,keyFile,caFile}}` + `dialer: {type: tls, tls: {...}}` | works, mTLS enforced |
| QUIC | `listener: {type: quic, tls: {certFile,keyFile,caFile}}` + `dialer: {type: quic, tls: {...}}` | works (`UNCONN *:18444`), `http=200 body=A` |
| WebSocket over TLS (wss) | `listener: {type: ws, ws: {path: /relay}, tls: {certFile,keyFile,caFile}}` + `dialer: {type: ws, ws: {path: /relay}, tls: {...}}` | works (`*:18445`), `http=200 body=A` |

```yaml
# wss variant of B (QUIC is the same with type: quic and no ws block)
services:
- name: relay-b-wss
  addr: ":18445"
  handler:
    type: relay
  listener:
    type: ws
    ws:
      path: /relay
    tls:
      certFile: /root/qui-g0/pki/server.crt
      keyFile: /root/qui-g0/pki/server.key
      caFile: /root/qui-g0/pki/ca.crt
```

`mtls` is a trap: the listener type named `mtls` is **multiplexed** TLS, not
mutual TLS. A `mtls` listener with `caFile` accepted a client that presented no
certificate at all (six of six requests returned 200), so mutual authentication
must be expressed as `listener: tls` + `tls.caFile`, as in §6.1.

A certificate from a foreign CA is rejected, but not with a
"bad certificate" message: the Go client does not send a certificate whose issuer
is missing from the server's acceptable-CA list, so B reports the same
`tls: client didn't provide a certificate` as for a client with no cert. When
debugging a G3 credential problem, that message therefore means "wrong or missing
client cert", not specifically "no cert configured".

## 7. Apply, restart, memory

### 7.1 Start-up and listener readiness

```console
$ start=$(date +%s%N); setsid nohup bin/gost -C cfg/live.yaml >log/live.log 2>&1 &
$ while ! ss -ltn | grep -q ':20080 '; do sleep 0.005; done
$ end=$(date +%s%N); echo $(( (end-start)/1000000 )) ms
12 ms
log: {"level":"info","msg":"listening on [::]:20080/tcp","service":"svc-one",...}
```

12 ms from exec to an accepting listener for a one-service config, so a
start-and-settle window of ~2 s costs almost nothing.

### 7.2 SIGHUP and `-R`: reload without restart

SIGHUP **is** handled and reloads the config file in place — the process
survives, unchanged listeners stay, new ones are added:

```console
$ kill -HUP $PID          # after adding a second service (:20081) to cfg/live.yaml
still alive after SIGHUP
listener: *:20080
listener: *:20081
log: {"level":"info","msg":"listening on [::]:20081/tcp","service":"svc-two",...}
log: {"level":"info","msg":"config reloaded"}
```

`-R <duration>` does the same on a timer (needs no signal):

```console
$ bin/gost -C cfg/live2.yaml -R 2s &
before change: 1 listeners
after adding :20081 and waiting 3.5 s: 2 listeners      # reload picked it up
```

G1 can therefore choose between SIGHUP and a full restart. Recommendation: use a
**restart** for apply (deterministic, matches the existing cores, and the settle
gate from §2.3 needs a fresh process anyway), and keep SIGHUP in mind if an
"apply without dropping the other listeners" path is ever wanted. Note that a
reload is *not* transactional: listeners are added/removed one by one and a bad
config leaves the previous one running with a `fatal` in the log, which is harder
to reason about than stop/start with rollback.

### 7.3 SIGTERM: clean exit, but in-flight transfers are cut

```console
$ curl -o /tmp/dl http://127.0.0.1:20082/big8.bin &   # 8 MiB behind a 1 MB/s limiter
$ sleep 2; kill -TERM $PID
gost SIGTERM exit code=0; curl exit=18 downloaded=3112960 bytes of 8388608
```

Exit status 0, no hang, no restart loop — but the transfer was aborted at
3.1 MiB of 8.4 MiB (`curl` exit 18, partial file). GOST does not drain open
connections on SIGTERM. That is the same trade-off the other cores have (a
restart drops connections) and it should be stated for forwards in G2: applying a
GOST change interrupts the forwarded sessions of that node.

No `kill -9` leftovers were observed after SIGTERM in any of the runs; the
listener is released immediately, and a restart on the same port right after
traffic succeeded three times in a row (no `address already in use`, so
`SO_REUSEADDR` behaviour is fine for restart-in-place).

### 7.4 Memory

`/proc/<pid>/status VmRSS`, forward-only config:

```console
idle (2 s after start)          : 44788 kB, threads=8,  fds=7
during one 8 MiB transfer       : 44788 kB (unchanged, six samples)
after that transfer             : 44788 kB, threads=8,  fds=7
50 concurrent 2 MiB downloads   : 49544 kB, threads=15, fds=65
after they finish               : 51592 kB, threads=15, fds=7   (VmHWM 51592 kB)
```

An earlier idle sample of a one-service config was 41 808 kB / 9 threads. So:
**~42–45 MB RSS idle**, roughly 1 MB per ~10 concurrent connections, and the Go
heap does not shrink back after a burst. For comparison the v1.2 nodes run Xray
and sing-box with their own footprints; a third core with ~45 MB baseline is
acceptable on the three existing hosts but should be counted in the node memory
guidance.

## 8. Logging

### 8.1 Defaults: JSON on stderr, level info, one block per connection

```console
$ bin/gost -C cfg/reload.yaml >log/out.txt 2>log/err.txt &
$ kill -TERM $PID
stdout lines=0 stderr lines=1
stderr: {"time":"2026-11-01T15:13:04.909-10:00","level":"info","msg":"listening on [::]:20080/tcp","kind":"service","service":"svc-one","listener":"tcp","handler":"tcp"}
```

Everything goes to **stderr** as JSON (stdout stays empty), level `info` by
default. Per proxied connection at `info`:

```console
{"level":"info","msg":"127.0.0.1:50868 <> 127.0.0.1:20050", ...}                   # accepted
{"level":"info","msg":"127.0.0.1:50868 <-> 127.0.0.1:19001", ...}                   # dialled target
{"level":"info","msg":"127.0.0.1:50868 >-< 127.0.0.1:19001", ...}                   # target closed
{"level":"info","msg":"127.0.0.1:50868 >< 127.0.0.1:20050", "inputBytes":85,
 "outputBytes":187, "duration":5151111, ...}                                        # session closed
```

That is 13 lines for 3 requests (~4–5 per connection), which is far too much for
a node that forwards port ranges; `-D`/`-DD` only add more (13 lines for a single
request with `-D`).

### 8.2 Minimal logging

A `log` section is honoured (it is not part of the serializable config, so
`-O yaml` cannot confirm it — verify behaviourally):

```yaml
log:
  level: warn
  format: text
```

```console
service reachable? body=A
log after one successful request: 0 lines (level=warn hides info)
after exceeding the connection limit:
time=2026-11-01T15:14:13.466-10:00 level=warn msg="accept: connection limit exceeded" kind=service service=svc-one listener=tcp handler=tcp
```

So `log.level: warn` (or `error`) plus `log.format: text` gives a minimal,
greppable journal for a forward-only core, and genuine warnings (over-limit
accepts) still surface. Recommendation for G1: render
`log: {level: warn, format: text}` by default, and let the panel raise it to
`info` only while diagnosing. The Agent must not rely on `info` lines to detect
readiness once the level is raised; parse the settle gate from the socket state
(§2.3) or keep a separate readiness probe.

## Recommendations for G1–G3

### G1 — GOST as a third core kind

1. **Pin v3.3.2** with the digest above; the archive is one static binary, so the
   installer and `qui-update` need no per-distro variant for amd64 and the Alpine
   node needs no musl build. Mirror the Xray handling: verify `SHA256SUMS`, then
   verify `gost -V` parses to the pinned version before the binary becomes the
   active core (field 2 of the first line of `-V`).
2. **Render canonical YAML only.** The panel/Agent renderer must emit exactly the
   keys GOST understands, and validate everything GOST ignores: selector
   strategies, limiter/climiter names and `$ <in> <out>` strings, `handler.chain`
   (never service-level `chain`), and no unknown keys. A unit test that
   round-trips the rendered file through `gost -C -O yaml` and compares it with
   the input catches most of the silent-footgun classes in §2.2.
3. **Validate in two stages**: `-O json` for syntax (fast, opens no sockets), then
   a start-and-settle gate of ~2 s requiring the process to be alive with every
   expected listener. There is no config-check flag; do not assume `-O` validates
   anything semantic.
4. **Apply = restart, roll back like the other cores**: stop, write the new file,
   start, settle-gate, health-check; on failure restore the previous file and
   restart. Do not use SIGHUP for apply even though it exists (§7.2), because
   reload is not transactional and gives no clean failure signal.
5. **Keep the surface minimal**: no `api:` section, no pprof; `metrics` only on
   `127.0.0.1` or a `unix://` socket inside the runtime directory, rendered with
   `log: {level: warn, format: text}`. Confirmed: without those, GOST opens
   exactly the configured service ports (§5.3).
6. **Health must test end-to-end forwarding**, not the listener: GOST accepts
   connections it cannot serve (§3.3, §4.2), so a listener check would report a
   forward whose targets are all down as healthy.
7. **Node memory guidance**: budget ~45 MB RSS per node running GOST, plus ~1 MB
   per 10 concurrent forwarded connections; the heap does not shrink after a
   burst (§7.4).

### G2 — forwards

1. **One service per listening port.** `addr` has no range support; a range is
   *n* services, each with its own selector state (§3.5). The panel's forward
   editor can keep presenting a range, but the renderer must expand it.
2. **Targets**: `forwarder.nodes[]` plus `selector.strategy`, `round` for
   balancing and `fifo` + `maxFails`/`failTimeout` for failover. Failover costs
   exactly one failed request per failure window, and the client sees an
   accepted-then-closed connection, so the panel should say "failover, one failed
   attempt" rather than promising seamless switching.
3. **Per-forward bytes** come from `gost_service_transfer_{input,output}_bytes_total`
   scraped on the Agent side: cumulative per process, reset on every apply, UDP
   included. Keep a per-(node, epoch, service) cursor exactly like the existing
   node-cursor design, and aggregate away the `client`/`host` labels (§5.2).
   Relay-hop overhead is measurable but small (~0.3 %), so do not use relay
   counters for billing-style numbers.
4. **Limits** are per service (`limiter`, `climiter`), and the over-limit
   behaviour (accept, then close) is the same as a target failure — document it,
   and make the forward editor tell the Owner that a connection limit produces
   dropped requests rather than refusals. Rates are `$ <in> <out>`, ±20 %.
5. Do not expose a GOST forward to end users (no quota, no device gate, no domain
   records): nothing in this spike suggests GOST can attribute traffic to a user;
   counters are per service with a client-IP label only.

### G3 — encrypted node-to-node relay

1. **Relay + TLS + client CA is enough**: `handler: {type: relay}` on
   `listener: {type: tls, tls: {certFile, keyFile, caFile}}`, and the dialling side
   as a chain hop with `connector: {type: relay}` and
   `dialer: {type: tls, tls: {certFile, keyFile, caFile, serverName}}`. A client
   without a valid cert is rejected (§6.3). Do **not** use the `mtls` listener
   type for this — it is multiplexed TLS (§6.4).
2. **Certificates the panel can generate**: the spike used a self-signed CA, a
   server cert (SAN `IP:<node address>` / `DNS:<node name>`) and a client cert;
   the same shape works for per-node credentials generated by the panel, with
   `serverName` set to the certificate's CN/DNS name so verification does not
   depend on the IP.
3. **The chain attaches to the handler.** This is the most dangerous
   misrendering: a service-level `chain:` is dropped silently and the forward
   dials its target directly, i.e. traffic leaves the node unencrypted while the
   operator sees a working forward (§6.1). Add an explicit renderer assertion
   that the chain is under `handler`.
4. **Dependency order** is unchanged from the existing relay logic: publish the
   exit node (relay listener) before the entry node's chain, and roll back in
   reverse. Because a failed dial produces an empty reply rather than a refusal,
   the post-publish probe must be end-to-end.
5. **Diagnosis strings** to map into the panel: `tls: client didn't provide a
   certificate` on the exit node covers both "no client cert" and "cert signed by
   the wrong CA", so the panel's hint should name both causes.
6. QUIC and wss both work if a transport other than raw TLS is ever wanted, with
   an identical client-cert setup. Raw TLS is the simplest and came up fastest in
   the spike, so start there.

## Open risks

| # | Risk | Impact | Mitigation |
| --- | --- | --- | --- |
| R1 | GOST silently accepts typos (strategy names, limiter names, `chain` placement, unknown keys) | a forward that runs with the wrong behaviour and no error | renderer-level validation plus an `-O yaml` round-trip test (G1 item 2) |
| R2 | `-O` looks like a validator but is not | an Agent that "validates" and still fails at start | settle gate; never trust `-O` alone |
| R3 | Restart drops forwarded sessions; SIGTERM does not drain | every GOST apply interrupts active connections on that node | state this in the forward UI; keep applies rare (one service set per node) |
| R4 | Counters reset on every apply restart | lost increments if the Agent does not read them before stopping | read metrics before stop and on a fixed interval; keep the per-epoch cursor |
| R5 | Metric cardinality (`client`, `host` labels) | unbounded series on a busy forward | aggregate in the Agent; never store per-client series |
| R6 | Odd label values (`host="192"` for `192.168.5.36`) | wrong attribution if the labels are trusted | treat `client`/`host` as opaque diagnostics only |
| R7 | Port-range semantics are CLI-only and positional | panel users expect a pool spread across a range | renderer expands ranges, round-robin stays inside each service; say so in the editor |
| R8 | `mtls` name collision (multiplexed, not mutual) | a node that believes it authenticates clients does not | use `tls` + `tls.caFile`; assert no `type: mtls` in renderer tests |
| R9 | Default log volume (~4–5 lines per connection at `info`) | journald growth on nodes with port ranges | render `log: {level: warn, format: text}` |
| R10 | RSS ~45 MB baseline, ~1 MB per 10 connections, no shrink after a burst | node memory budget on small VPS instances | include GOST in the node memory guidance; watch VmHWM on alpine-node |
| R11 | Only amd64 was tested, on one host, with loopback targets, in a short spike | no evidence for arm64 or for long-running production behaviour | same policy as v1.2.0 (amd64 only) and a real-host check in the RC phase |
| R12 | GOST behaviour above v3.3.2 is unverified (this spike pins one release) | an upgrade could change YAML shape or metric names | keep the core-update allowlist on the pinned digest; re-run these checks before bumping |
