## GOST (Owner, 2026-11-01: in v1.3.0)

Taken from the deferred G0–G3 of docs/archive/v1.2-plan.md (§1.6, §2.4).
GOST v3 (MIT, official `gost_<ver>_linux_amd64.tar.gz` plus
`checksums.txt`) runs as a third core kind next to Xray and sing-box, under
the existing multi-core runtime and core-update flow.

- It serves only forwards and node-to-node relay hops, never users: no
  subscriptions, quota, device limits or domain records (L10).
- Its Web API, metrics and pprof stay off, or loopback-only where counters
  need them.
- Applying a change restarts GOST; a GOST failure is rolled back and restored
  without touching the proxy cores.
- Not in v1.3.0: GOST as a user-facing proxy, reverse tunnels, Web API
  exposure.

## T1 — monthly machine traffic per server (Owner request, 2026-11-01)

Goal: the Owner sees each server's total network usage for the current
billing month, against an optional allowance, with a reset day of their
choice — for comparing with the hosting provider's bandwidth quota. This is
the whole machine's traffic (all services), not the proxy traffic the cores
count.

Owner decisions:

| Topic | Decision |
| --- | --- |
| Release | v1.3.0, after v1.2.0 |
| Accounting method | Per server. Default **inbound + outbound**; other choices: outbound only, or the larger of inbound and outbound |
| Counted interface | Per server. Default: the interface that carries the default route (usually `eth0`). Interfaces are never summed (double counting, e.g. through `docker0`) |
| Allowance | Optional per server, shown as a progress bar. Display only: no alerts (not requested) and no enforcement |
| Reset day | A separate "traffic reset day" field, independent of the renewal date in the server metadata |

What exists today (v1.2.0): every heartbeat (15 s) the Agent sends each
non-loopback interface's cumulative byte counters from `/proc/net/dev` and
their rates (internal/agent/capability/host_metrics.go). The panel shows the
live rate and keeps one rate sample per minute for 7 days
(internal/panel/node/metrics.go); it keeps no daily or monthly totals.

Proposed design, to be reviewed:

- Agent: add the kernel boot ID (`/proc/sys/kernel/random/boot_id`) so the
  panel can tell a reboot (counters restart at zero) from a normal sample.
  Traffic while the Agent is offline is still counted when the machine did
  not reboot in between.
- Panel: store daily received/sent bytes per server and interface from the
  counter differences, long retention (small rows); sum them over the billing
  month starting on the reset day. Reset day 1–31; in shorter months it falls
  on the last day; dates in the panel time zone.
- New per-server settings (method, interface, allowance, reset day) in a new
  migration; existing migrations unchanged. Settings are configuration and go
  into backups; usage history is kept with the traffic data.
- Display inside the Owner's existing layout (server card and node detail),
  e.g. "本月 312 GB / 2 TB · 11 月 15 日重置"; unknown values show "—".

Known limits to state in the docs: an LXC container (e.g. alpine-node) only
sees its own interfaces, not the physical host; usage before the first
sample after an upgrade, and across a reboot while the Agent was offline, is
not counted.
