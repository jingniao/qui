# v1.4 A1a: real-core completion-path tests

Implemented on `feat/v1.4-tunnels`, starting HEAD `f8acd7e`. No commit,
push, branch switch, host deployment, migration or production-code change.
This report is the only documentation file written by A1a. Concurrent
documentation, AGENTS.md and web changes were left intact.

## Files and coverage

- `internal/panel/deployment/real_v14_paths_test.go`: shared panel fixture,
  publication/no-op checks and real subscription generation/assertions.
- `internal/panel/deployment/real_v14_runtime_test.go`: real Agent adapters,
  mihomo process, HTTP requests and each-node outage/restart checks.
- `docs/v1.4-a1a-report.md`: this report.

The file set lives in the existing deployment package to reuse `newGostHosts`,
`publishScheme`, `publish`, `driveTunnelPublish`, the SQLite/vault repositories
and simulated Agent receipts without exporting or duplicating test fixtures.
It also reuses `internal/testutil.Certificates` for ephemeral TLS certificates.
Panel configuration uses services, publication uses the actual deployment
repository and batches, and snapshots are read back from the successfully
published revisions. No desired-state JSON is substituted for panel-generated
state. The independent external SOCKS5 stand-in is the sole hand-built state.

Each of these six cases runs with Xray and with sing-box as primary core:

| Case | Configured path |
| --- | --- |
| P1 | US VLESS+TLS direct inbound to the HTTP target |
| P2-inbound | Canvas HK VLESS+TLS to a qui US SOCKS5 exit |
| P2-external | Canvas HK VLESS+TLS to an external authenticated SOCKS5 outbound; an independent real core provides the external listener |
| P3 | Canvas HK VLESS+TLS through JP internal relay to a qui US SOCKS5 exit |
| P4 | Tunnel Management HK to JP GOST mTLS tunnel; `CreateNodeRelay` links an HK rule port to US VLESS+TLS |
| P4-three-implicit-SNI | HK to JP to US GOST tunnel, with US VLESS+TLS co-located at the tunnel exit, exercising the loopback target and implicit TLS name |

All panel nodes have PublicIP `127.0.0.1`; listeners have distinct dynamically
chosen ports across simulated hosts and each real node has its own runtime
directory. User inbounds retain the production wildcard listen address because
the published subscription source deliberately excludes loopback-only inbounds.
Client connections, inter-node dials and the HTTP target use loopback.

P1 uses `SnapshotIntent` and the existing deployment publisher's unchanged-state
comparison. Canvas cases use `SaveCanvasScheme`, `PlanCanvasScheme` and
`PublishCanvasScheme`. P4 uses `SaveTunnel`, `CreateNodeRelay` and
`PublishTunnels`, including real queued revisions and simulated successful
receipts. Every case republishes and requires no new deployment work; managed
tunnels additionally require `unchanged` per-server results.

P1's no-op check specifically uses `NodeSnapshot.ExpandedOnly=true`, the shared
publisher's existing comparison mode. The explicit node-page publish HTTP
endpoint creates a revision on each invocation; this test does not claim that
endpoint has gained no-op behavior. No production change was made to that
existing direct-publication behavior. Canvas and Tunnel Management no-op checks
use their ordinary service publication calls without this fixture flag.

The real subscription service issues a user token, collects published endpoints
with `published.Source` and `RelayStore`, and renders the token through the
`mihomo` format. Checks cover exact endpoint counts/names, server, port, user
VLESS UUID, TLS and server name, the retained direct P4 endpoint, and exclusion
of canvas internal and tunnel-generated listeners. Generated/internal inbound
visibility is checked in the repository too. The client profile keeps every
exported proxy intact and narrows its select group's membership to the expected
exported name; MATCH routes all test traffic through that group.

The runtime test passes each published state unchanged through real
`MultiRuntime.Render`, native `Validate` and `Apply` using Xray/sing-box and,
for P4, GOST. It launches real mihomo, fetches the local HTTP server through
its mixed port and checks the response status/body. Then it stops each node
in turn, requires a fresh request to fail, recreates that node from the same
snapshot and requires traffic to recover without republishing. This prevents
a missing relay or direct fallback from passing merely because every simulated
host shares loopback. These are adapter restarts, not full Agent daemon or
supervisor-kill recovery tests.

## TLS and execution boundary

All VLESS entries use TLS. The ordinary and two-server P4 cases preserve an
explicit `localhost` server name while dialing `127.0.0.1`. The three-server
P4 case starts with no explicit name and requires the relayed subscription to
materialize the original destination address, `127.0.0.1`, as `servername`.
Mihomo receives the ephemeral test CA via Linux's `SSL_CERT_FILE` root loader;
the subscription is not weakened with `skip-cert-verify`.

The test requires `XRAY_BINARY`, `SINGBOX_BINARY`, `MIHOMO_BINARY`,
`MIHOMO_HOME` and `GOST_BINARY`; it never searches for a default binary.
Missing values skip at the top-level test with the variable name. This matters
because the existing CI wrapper loses reason association for nested skips
printed after a parent PASS. The top-level skip was verified to make the
wrapper exit 1. Supplied but invalid binaries fail validation/startup.

`scripts/real-core-packages.sh` automatically discovers the deployment package
from the new environment-variable references; no script change is needed.
Its discovery was run successfully under Git Bash on Windows and included
deployment. Native Windows Go reports Windows absolute directory names, so
that invocation's package strings are not suitable as Linux go-test arguments;
run discovery on the Linux test machine for the full suite.

**No real-core traffic execution occurred on this Windows machine.** Linux TLS
trust, native config validation, traffic and restart assertions are implemented
but remain to be measured on the pinned-core machine. This phase does not
claim host/browser acceptance, RC deployment or release readiness.

## Linux run

Use the repository's pinned real-core CI binaries, including GOST 3.3.2, and
the pinned mihomo geodata directory. Supply absolute paths, for example:

```bash
export XRAY_BINARY=/absolute/path/to/xray
export SINGBOX_BINARY=/absolute/path/to/sing-box
export MIHOMO_BINARY=/absolute/path/to/mihomo
export MIHOMO_HOME=/absolute/path/to/pinned-mihomo-data
export GOST_BINARY=/absolute/path/to/gost

bash scripts/ci-real-core-test.sh -p 1 -count=1 -timeout 15m \
  -run 'TestV14PathPanelFixtures|TestRealV14CompletionPaths' \
  ./internal/panel/deployment

# Full real-core gate, discovering packages on Linux:
GOFLAGS=-p=1 bash scripts/ci-real-core-test.sh -p 1 -count=1 -timeout 60m \
  $(GOFLAGS=-p=1 bash scripts/real-core-packages.sh)
```
