## Delivered behavior

- Server canvas entries can connect directly from an `inbound:` box, as the
  U1b editor sends them. An `inbound:` exit selects its managed node, protocol
  and core. Publication creates a dedicated internal listener and a bound
  outbound with independently generated internal credentials. It leaves the
  original user inbound, its port, visibility and credentials unchanged. This
  follows the existing requirement that relay targets have dedicated internal
  credentials rather than reusing user credentials.
- `outbound:` exits reuse existing external SOCKS5/HTTP/Shadowsocks/Trojan/VLESS
  outbounds. Save, plan and publish check existence, enabled state, nondeleted
  owner node, previous-hop ownership, external-proxy type and requested TCP/UDP
  capabilities. An external exit cannot originate a connection or coexist with
  another successor on its previous-hop node.
- A direct entry-to-external path sets the entry default outbound to that
  outbound. A managed relay path ending at an external exit creates a chain
  even with only one managed relay edge, and sets its `FinalOutboundID` to the
  external outbound. Plain server and managed inbound endpoints retain Direct
  as the final action after reaching their last managed hop. Chain transport
  support includes the final connection's requested transports.
- External outbounds remain independently owned. Detaching an external-only
  route restores the entry to Direct without deleting the external outbound.
  Editing an external outbound invalidates its referencing canvas tunnel
  publication stamps inside the outbound save transaction, so a later canvas
  publish deploys the changed endpoint instead of returning a false no-op.
- `relayPortMode` and `relayPort` are accepted on relay/exit server instances.
  These fields take precedence over legacy connection-level `tunnelPort`.
  Explicit listeners use the existing shared-port conflict path, including
  enabled listeners and persistent claims. Automatic allocation skips all
  configured listeners, including disabled listeners and forward ranges.
  Allocations are persisted in `canvas_tunnels.allocated_port` and reused.
  Canvas alone retains TLS 8443 / WireGuard 51820 without a configured range;
  an exhausted configured range still fails. Existing allocation behavior in
  `canvas_ports.go` is reused without a second allocator.
- Server saves reject new or altered `port_forward` / `tunnelProtocol=gost`
  connections with `端口转发与 GOST 隧道已移至隧道管理`. An identical stored
  connection can remain, and deletion is allowed. Checks run before hydration
  as well as after hydration so a `tunnelId` cannot hide a forbidden edit or
  introduce a newly referenced legacy connection. Client scheme behavior is
  unchanged.
- Shared dependency projection and entry route conflict checks recognize the
  new inbound entry/exit shapes. No-op checks include the selected final
  outbound and require generated internal listeners to remain hidden.
- Strict layout decoding, backup inspection and recovery accept the new refs
  and relay port fields through the shared `CanvasLayout` validator. No schema
  change or backup-specific duplicate decoder is needed.

## U1b compatibility observations

The request field names and external-outbound POST shape match U1b. No web
changes were made. Two editor interactions need frontend review:

- `RelayCanvasPage.vue` changes a configured server's role to `entry` and
  immediately saves, while `relaySchemeToCanvasInput` still serializes that
  instance's old `relayPortMode`/`relayPort`. The contract restricts these fields
  to relay/exit server instances, so that request is rejected. The UI should
  clear those fields when changing to entry, or omit them during serialization.
- `CanvasConnectionDialog.vue` initially selects TCP and UDP independently of
  the external outbound's capabilities. HTTP exits require the administrator
  to uncheck UDP; otherwise the backend correctly rejects the connection. This
  is a capability-selection UX issue, not a JSON contract mismatch.
