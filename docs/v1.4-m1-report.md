## Delivered behavior

- Added migration `0131_canvas_forward_migration.sql`; committed migrations
  0129/0130 and all applied migrations are unchanged. The migration creates
  `canvas_forward_reconcile` and `tunnel_migration_report`. The marker records
  completion and migrated IDs. The latter identifies which published owners
  must retain their legacy materialization on an unchanged republish; ordinary
  X1 objects continue through their existing comparison path.
- Startup calls `ReconcileCanvasForwards` after the existing 0124 reconciliation.
  Recovery uses the same method, after schema migration and 0124 reconciliation,
  with the authenticated archive's configuration key. All conversions, layout
  removals, ownership/claim transfers, report rows and completion marker commit
  in one transaction. A failed transaction can be retried; a completed one is
  never retried automatically, including for unresolved cases.
- Published plain canvas forwards become published direct rules with the
  original canvas tunnel ID/name, source node, actual forward listener, manual
  port mode and TCP/UDP network. GOST forwards also create a two-node tunnel,
  retaining the old canvas tunnel ID and exact sealed material bytes, with its
  existing exit listener in manual mode. Rule and tunnel IDs may be identical
  because they occupy separate tables and ownership includes the owner kind.
  Published version equals draft version; timestamps are set at conversion.
  Subscription visibility is always false.
- Targets come from the existing generated forward, with explicit connection
  fields checked for agreement. A linked target requires an exact public-host
  match and a unique enabled user inbound at that port in the target node's
  successfully running revision, also matching the current inbound row. All
  other resolvable host/port targets remain manual. Merely sharing a port with
  a draft inbound does not grant a linked target.
- Generated entry/exit inbound IDs move from `canvas_tunnel_objects` to
  `tunnel_objects`. Numeric claims reserve the same node/port for each new
  owner; an existing matching canvas claim can be transferred. The reconcile
  never writes `inbounds`, deployed revisions, certificates or node settings.
  Migrated edges are removed from server layouts and their stored published
  layout, if any, leaving all boxes and other connections in place. Deleted
  legacy resources cascade their publication associations.
- X1b already accepts single-leg material for two-node tunnels; no credential
  reader change or reissuance was needed. Three-node tunnels still require an
  independent second leg. Unchanged migrated publications reuse their owned
  inbound input, preserving names, core, listen address and the legacy public
  target instead of switching to loopback. A rule edit, tunnel edit/rotation or
  destination invalidation uses normal X1 materialization. Published drawings
  left with no edges and no outstanding cleanup also return a canvas no-op.
- `GET /api/v1/tunnels/migration-report` returns
  `{items:[{tunnelId,name,reason}]}`. It is Owner-only, read-only and contains
  Chinese reasons without credentials. It is a durable record of the one-time
  attempt, rather than a live issue tracker.

## Backup and restore

Inventory now counts the migration marker/report alongside the five v1.4 tables.
The shared validator checks migration/table and 0130 snapshot-column consistency,
marker contents, sealed material, owners, required claims, numeric conflicts,
duplicate canvas/managed ownership and published snapshot JSON/identity/network.
Historical claims retained during pending publication remain valid; they are not
silently reallocated. A pre-0129 archive has no v1.4 tables and is accepted;
candidate preparation migrates it and converts eligible forwards. A v1.4 archive
preserves its tables, original allocation, migrated-ID history, report and sealed
material. Existing recovery behavior then marks published rules/tunnels modified
for explicit Owner publication; no configuration is sent during restoration.

## Cases left for the Owner

The following remain unchanged on the canvas and receive a report row:

- Any referencing scheme is unpublished, has not published that connection,
  or the canvas tunnel has unpublished changes; an unreferenced resource also
  stays in place.
- Missing/deleted nodes, non-server endpoints or identical entry/exit nodes;
  shared references whose actual layout endpoints disagree.
- Missing or incomplete ownership, non-inbound objects, an unexpected generated
  listener role, duplicate managed ownership, disabled/visible/credential-bearing
  forwards, or an altered default outbound.
- Numeric port conflicts, mismatched historical canvas claims, unsupported
  target pools/ranges, inconsistent connection target/network, unusable GOST
  material or a relay/dialer that no longer agrees with its material/public host.
- Names outside the managed-name contract or conflicting managed IDs/names.

Owner review should establish which original objects and endpoint path are
intended, resolve the recorded issue through the normal management workflow,
and explicitly publish any resulting configuration. M1 does not automatically
claim an unowned object, pick a path, resolve a conflict or rotate a certificate.
