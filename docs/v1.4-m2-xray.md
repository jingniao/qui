# M2: self-hosted Xray VLESS Reality and xhttp

Implemented in the protocol integration branch after review. Xray renders Reality TCP (no flow or Vision), Reality gRPC without flow, and Reality/TLS xhttp in auto, packet-up, stream-up and stream-one modes. Actual installed-core native probes authorize each reported combination separately; xhttp probes cover every offered mode. Agent application uses the probed subset. Old Agent and withdrawn-capability commands remain withheld by the M1 dispatch gate.

Reality keys are generated on first Reality save, including conversion of an existing listener. Ordinary redacted edits retain the key; explicit `rotateRealityKey` generates a new pair in the draft. Persistence and revisions remain encrypted. Public subscription mapping takes only public key, the first concrete DNS SNI/Short ID, and typed transport settings from successful revisions. xhttp client output explicitly uses H2; linked relays retain those fields and remain TCP. Private keys never enter the public model. Internal canvas relays retain their existing TLS/TCP path; new server-private settings are refused for internal relays until a client outbound mapping exists.

Windows/amd64 Xray 26.3.27 focused real-core checks passed 11 server combinations with authenticated HTTP and per-user traffic. TCP and Reality xhttp-auto additionally passed new-connection device gating, wrong UUID rejection, key rotation and historical rollback. Native validation failure retained the serving configuration. Public/private mapping and relay field tests, key creation/edit/conversion/rotation tests, and per-cell probe tests passed. These are Windows tests, separate from Linux and production evidence.

The shared client model/codecs come from S3/S4. The final integrated Linux gate and generated Mihomo client checks remain pending. No production hosts or real subscription sources were accessed. xhttp behind a CDN exposes CDN edge addresses to the existing source-address device estimate; it does not identify physical devices.
