# v1.4 M3 — capability-aware Reality / xhttp editor

Status: reviewed M3 phase delivery in `feat/v1.4-selfhost-m3`, based on M1 `3565153`.
This report accompanies the local phase commit; its Linux gate and browser
acceptance remain pending.
The editor requires the M2 backend key lifecycle and renderer to be integrated;
an older Agent's absent report keeps the new combinations unavailable.

## Behavior

The existing node editor's transport/security step now offers VLESS Reality,
xhttp and XTLS Vision according to the selected node core's actual reported
`server_settings_contract_version` and `server_settings_combinations`. The UI
uses the exact protocol, inbound direction, security, transport and flow tuple.
Core version text and a generic VLESS flag never authorize these settings.

The node types and shared `coreSummary` view support both scalar compatibility
reports and `cores[]`. A listed core's report is authoritative; scalar fields
cannot fill missing capabilities on a second core. Unknown settings contracts,
absent combinations and pending add/remove tasks remain unavailable, including
when the editor follows the primary core through the empty core selection.

Unavailable choices remain visible with reasons. An existing unsupported
selection is retained and blocks save. The editor offers an explicit “TCP + None”
recovery action; it never silently downgrades an existing listener. The action
retains the entered Reality/xhttp/TLS fields for later recovery.

Reality fields are an explicit handshake target, DNS server-name/SNI list,
Short ID list and read-only public key. No handshake target is supplied by
default. The UI explains that the subscription uses the first SNI and Short ID.
Names, counts, Short IDs and target syntax have local field checks; the backend
and Agent remain authoritative. A selected sing-box core requires exactly one
Reality server name, matching M4's single `server_name` representation; Xray
retains its bounded list. A rejected multi-name draft is never truncated.
Reality requires no TLS certificate upload.

Key creation happens on the first successful Reality save, including conversion
of an existing VLESS listener. No separate key-generation API is used. The editor
can explicitly request `rotateRealityKey=true` for an existing key and explains
that clients must refresh their subscriptions after successful deployment. An
ordinary save omits this flag. The public key returned in the save response has
a separate readback/copy field; server private keys are neither editable nor
included in request payloads or confirmation summaries.

xhttp exposes host, rooted path and the four bounded modes: `auto`, `packet-up`,
`stream-up`, `stream-one`. Host stays separate from TLS server name. The UI
describes the current TCP/H2 scope, excludes HTTP/3/advanced tuning and explains
the source-address device estimate limitation behind a CDN.

Internal relays explicitly refuse Reality/xhttp. The role selection and draft
remain intact, and the editor explains that this workflow currently needs
TCP + TLS. M2 enforces the same boundary on the backend; this phase does not
convert canvas/internal relay outbounds or copy server-private settings there.

## Draft and request boundaries

Transport/security changes retain inactive field values, and protocol switches
retain per-protocol drafts. Only `buildPayload` removes fields that contradict
the selected combination: ordinary certificate material for Reality, unrelated
protocol settings, inactive xhttp/Reality blocks, and WebSocket/gRPC fields on
another transport. Typed public-field selection prevents a foreign/private
Reality field from entering a request. Building a request never mutates the
editable draft.

Existing save-then-publish behavior is preserved. Local validation and rejected
saves retain all inputs. Once a save succeeds, a later group/publish failure
retains that persisted draft and blocks duplicate creation. Errors distinguish
save failure from a saved draft whose publish failed. The confirmation summary
states whether key generation/rotation is planned and masks private material.

## Verification

Windows local checks passed using the existing root `web/node_modules` through a
worktree junction; the root dependency directory was not changed:

```text
node web/scripts/node-editor-selftest.mjs
node web/scripts/server-detail-selftest.mjs
node web/scripts/u1b-selftest.mjs
node web/scripts/ui-regression-selftest.mjs
npm --prefix web run typecheck
npm --prefix web run build
git diff --check
```

The editor self-test retains all 37 existing wire-payload comparisons and adds
actual helper/save-handler checks for scalar/per-core authorization, wrong or
absent contract reports, pending primary cores, unsupported stored selections,
field bounds, internal-relay rejection, key generation/rotation requests,
private-key exclusion, draft restoration, payload-only cleanup, returned public
key readback, rejected saves and retained drafts after publishing fails.

The initial sandboxed Vite attempt failed because esbuild could not traverse
parent directories (`Access is denied`); the authorized build outside that
sandbox passed. This was a local build environment restriction, not a frontend
type or bundle failure.

No production service, real subscription source, node configuration or remote
gate was touched. No browser layout/walkthrough, Linux gate, live server save,
real handshake or end-to-end deployment is claimed by M3's frontend tests.
Those require the integrated M2/S3/S4/M3 build and the coordinated acceptance
workflow.
