## 1. Goal and completion criteria

Split relaying into three parts:

```text
节点配置 (Node Configuration)
├─ 节点列表 (Node List)               unchanged page; gains "添加中转" (Add Relay)
├─ 隧道管理 (Tunnel Management)
│  ├─ 隧道 (Tunnels)                  entry → [intermediate…] → exit servers + transport, e.g. HK → JP
│  └─ 规则 (Rules)                    entry listen port + tunnel (optional) + final destination,
│                                     e.g. HK :30001 → via JP → US :443
└─ 中转方案 (Relay Schemes, canvas)   proxy relaying only: proxy entry → internal relay → proxy exit,
                                      e.g. HK VLESS → JP internal relay → US SOCKS5
```

**Done when** all four paths can be configured, published and used, and
subscriptions contain the correct address, port and credentials for each:

| # | Path | Built with |
| --- | --- | --- |
| P1 | User → US VLESS → website | Existing direct inbound (must keep working unchanged) |
| P2 | User → HK VLESS → US SOCKS5 → website | Canvas: entry HK, exit US SOCKS5 (qui inbound or external SOCKS5) |
| P3 | User → HK VLESS → JP internal relay → US SOCKS5 → website | Canvas: entry HK, relay JP, exit US SOCKS5 |
| P4 | User → HK–JP tunnel → US VLESS → website | Tunnel HK→JP + rule HK:port → US VLESS inbound; subscription shows US VLESS with HK address and rule port |

## 2. Decisions (defaults; the Owner may override)

- **D1 Engine.** Tunnels (with or without an intermediate hop) use the GOST
  relay that v1.3 already ships: relay handler on a TLS listener, per-tunnel
  mTLS credentials sealed in the vault, TCP and UDP. Every tunnel node therefore
  needs the GOST core (linux/amd64 only). A rule **without** a tunnel is a plain
  port forward on its entry node: it uses GOST if installed, otherwise the
  Xray/sing-box `forward` inbound (existing render paths). No new core.
- **D2 Transport.** v1.4 offers one tunnel transport: `tls` (GOST relay over TLS
  with mutual auth). Unlike flyx, hop listeners never accept unauthenticated
  relays. Other transports (ws, kcp, mux variants) are backlog.
- **D3 Hops.** A tunnel has an entry, 0–1 intermediate servers and an exit
  (at most 3 servers, 2 relay legs), one server per role. Each node only knows
  its next hop (flyx model): entry chain → mid relay service with its own chain
  → exit relay service. Multi-node hops and load-balanced exits are backlog.
- **D4 Ownership and ports.** Every listener a feature creates (tunnel hop
  listeners, rule entry ports, canvas internal relay ports) is recorded with
  its owner and allocated port. Ports come from the server's
  `node_meta.port_range_start/end`, or are typed in. Once allocated, a port is
  stored and reused by every republish. Allocation never silently falls back
  to a default port: no range and no manual port means an error. Exception
  (review, 2026-11-04): canvas encrypted relays keep their old 8443/51820
  default when the server has no range, so existing schemes republish
  unchanged. Manual saves check only enabled inbounds; claims always reserve;
  automatic allocation skips every inbound, including disabled ones.
- **D5 One conflict check.** One panel function decides whether a numeric port
  on a node is taken. It covers inbounds including forward ranges, tunnel hop
  listeners, rule listeners and canvas objects, uses the Agent's node-level
  numeric rule (TCP/UDP not distinguished, `desiredstate.ListenPorts`), and is
  used by the inbound editor, tunnel editor, rule editor, Add Relay dialog,
  canvas plan/publish and backup inspection. The Agent's
  `desiredstate.State.Validate` stays as the final guard. The existing
  duplicates (`canvasListenerConflicts`, `validateInboundPorts`, frontend
  `portConflict`) are replaced by it or call it.
- **D6 Draft and publish.** Save writes a draft only. Publish computes a plan
  (affected servers, ports, routes and ordering), shows it, then deploys
  through the existing deployment batches (exit before middle before entry;
  rollback in reverse) and reports a per-server result. Republishing an
  unchanged object is a no-op.
- **D7 Relayed subscription entries.** A rule may be *linked* to a destination
  inbound (`target_inbound_id`). The subscription then gets an extra endpoint
  that is the destination inbound unchanged (protocol, credentials, transport,
  TLS/Reality parameters, SNI/server name) except `server` = the rule's entry
  node address and `port` = the rule's listen port. When the destination's TLS
  server name was implied by its address, the relayed endpoint sets it
  explicitly to the original value. Its name is
  `<目标节点> · <协议> · 经 <入口节点>`. The direct endpoint stays and keeps its
  own visibility. The relayed endpoint is listed only when the rule is
  published and marked visible to users, and only for users who can see the
  destination inbound.
- **D8 Follow-the-destination.** A linked rule's target host and port are
  derived from the destination node and inbound. If the exit server of the
  rule's tunnel *is* the destination node, the target is loopback. When the
  node address or inbound port changes, the rule's draft is updated and marked
  "needs publish". Unlinked rules keep manual host and port.
- **D9 Canvas scope.** The canvas keeps proxy relaying (`proxy_chain` and
  encrypted `tunnel` connections between proxy servers). It loses the shared
  tunnel library UI, GOST tunnel forwarding and `port_forward` connections.
  Existing `canvas_tunnels` rows that back canvas encrypted relays stay as the
  canvas's internal storage, so running configs do not change. Canvas exits
  gain (a) a qui inbound as exit (e.g. US SOCKS5) and (b) an external proxy
  outbound (SOCKS5/HTTP/Shadowsocks/Trojan/VLESS with address, port and
  credentials). The chain's final outbound is no longer hard-coded `direct`.
- **D10 Known limitations, documented rather than solved in v1.4:**
  - Behind a tunnel or rule, the destination sees the relay's address as the
    client source. Device limits on the destination count all relayed users as
    one source per relay (PROXY protocol is backlog).
  - Account traffic is still counted on the destination node. Rule and tunnel
    bytes go into node totals only, never into user quotas.
  - GOST and therefore tunnels are linux/amd64 only.

## 5. API contract (fixed before U1a; backend must match)

All paths are under `/api/v1`. Reads are allowed for Owner and Viewer; writes
are Owner-only with CSRF and an audit entry. Errors use the existing
`{error:{code,message,...}}` shape. Timestamps are RFC 3339 strings. Ports are
integers. `updatedAt` is the optimistic-concurrency token: a write must send
the value of the last read, otherwise the server returns 409 `stale`.

```ts
type PublishStatus = 'draft' | 'modified' | 'published' | 'needs_publish' | 'pending_delete';
// draft: never published; modified: saved edits not yet published;
// needs_publish: a linked destination changed (D8);
// pending_delete: deleted but still running; the row stays listed (read-only)
// until a publish removes it from the servers, then it disappears.

interface TunnelHop {
  role: 'entry' | 'mid' | 'exit';
  nodeId: string;
  nodeName: string;                 // read-only
  listenPort: number | null;        // null for entry; for mid/exit, the saved port
  portMode: 'auto' | 'manual';
  connectHost: string;              // '' = the node's public address
}
interface Tunnel {
  id: string; name: string;
  transport: 'tls';
  hops: TunnelHop[];                // ordered: entry, [mid], exit
  ruleCount: number;                // read-only
  status: PublishStatus;
  credentials: { generation: number; serverName: string; notAfter: string; fingerprint: string } | null;
  createdAt: string; updatedAt: string; publishedAt: string | null;
}
interface TunnelInput {
  name: string; transport: 'tls';
  hops: { role: 'entry' | 'mid' | 'exit'; nodeId: string; portMode: 'auto' | 'manual'; listenPort?: number; connectHost?: string }[];
  updatedAt?: string;
}

interface TunnelRule {
  id: string; name: string;
  entryNodeId: string; entryNodeName: string;
  listenPort: number; portMode: 'auto' | 'manual';
  network: 'tcp' | 'udp' | 'both';
  tunnelId: string | null;          // null = direct forward on the entry node
  tunnelName: string | null;
  target:
    | { mode: 'linked'; nodeId: string; nodeName: string; inboundId: string; inboundName: string; protocol: string; host: string; port: number }  // host/port derived (D8), read-only
    | { mode: 'manual'; host: string; port: number };
  ownerNodeId: string | null;       // set when created from a node's Add Relay
  subscriptionVisible: boolean;     // only meaningful for linked rules
  enabled: boolean;
  status: PublishStatus;
  createdAt: string; updatedAt: string; publishedAt: string | null;
}
interface TunnelRuleInput {
  name: string;
  entryNodeId: string;              // must equal the tunnel's entry when tunnelId is set
  portMode: 'auto' | 'manual'; listenPort?: number;
  network: 'tcp' | 'udp' | 'both';
  tunnelId: string | null;
  target: { mode: 'linked'; inboundId: string } | { mode: 'manual'; host: string; port: number };
  subscriptionVisible: boolean; enabled: boolean;
  updatedAt?: string;
}

interface PortCheck { nodeId: string; port: number; free: boolean; usedBy?: { kind: 'inbound' | 'tunnel' | 'rule' | 'canvas'; id: string; name: string } }

interface PublishSelection { tunnelIds: string[]; ruleIds: string[] }
interface PublishPlan {
  ok: boolean; message?: string;
  servers: { nodeId: string; nodeName: string; order: number;
             listeners: { port: number; network: 'tcp' | 'udp' | 'both'; purpose: string }[];
             routes: string[];             // human-readable, e.g. "HK :30001 → JP → 203.0.113.5:443"
             changes: { action: 'create' | 'update' | 'remove'; kind: string; name: string }[] }[];
  conflicts: { nodeId: string; port: number; usedBy: string }[];
  warnings: string[];
}
interface PublishResult {
  batchId?: string;
  servers: { nodeId: string; nodeName: string; revision: number | null; status: 'applied' | 'unchanged' | 'failed' | 'rolled_back' | 'skipped'; message?: string }[];
}

interface NodeRelay {               // a linked rule seen from its destination node
  rule: TunnelRule;
  shareLink: string | null;         // relayed URI (null when the format can't express it)
}
```

| `POST /tunnels/plan` | `PublishSelection` | `PublishPlan` |
| `POST /tunnels/publish` | `PublishSelection` | `PublishResult` |
| `GET /nodes/{id}/relays` | — | `{items: NodeRelay[]}` (linked rules whose destination is this node) |
| `POST /nodes/{id}/relays` | `{tunnelId, inboundId, portMode, listenPort?, subscriptionVisible, name?}` | `NodeRelay` (creates a linked rule; entry = the tunnel's entry) |
| `POST /nodes/{id}/recovery-token` | `{expiresInSeconds?, revokeNow?}` (0 or omitted → 900; 300–3600) | 201 `{node, enrollmentToken, expiresAt, install, purpose: "recover"}`; the code is returned once and only its hash is stored. 409 `node_not_enrolled`, or 409 `node_recovery_blocked` with `blockers: {kind,id,name}[]` |
| `GET /nodes/{id}/recovery-status` | — | Latest `Recovery` record (`status` issued/consumed/superseded/expired, `redeployState`, `redeployRevision`, `redeployCode`); 404 when the node never had one |

`portMode: 'auto'` with no `listenPort` means the server allocates a port from the node range when saving, and the saved port then stays fixed; `auto` with a `listenPort` (from `ports/allocate`) keeps that suggestion if it is still free. Port conflicts are checked again at save. A `pending_delete` tunnel still blocks its rules' tunnel choice and still holds its ports until published.

A rule's `entryNodeId` must equal its tunnel's entry hop. Port errors return
409 `port_in_use` with `usedBy`, or 400 `port_out_of_range`, or 409
`no_free_port` (no range or range exhausted, D4).

**Node identity recovery (migration 0134).** A reinstalled host enrolls again as
the same node record instead of a new one. The code is bound to the certificate
fingerprint current at issue time, expires in 300–3600 seconds (default 900), is
returned once and only its SHA-256 is stored. Redemption reuses the existing
`Enroll` RPC with `purpose: 'recover'`, so the agent binary and the install
script are unchanged: the node id, inbounds, outbounds, groups, tunnels, chains
and revision history are kept, the replaced fingerprint is retired permanently
(a backup restore never revives it), and the published configuration is
redeployed once the new agent reports capabilities. `revokeNow` revokes the
current certificate at issue time and closes the live control stream;
permanent retirement of the old fingerprint happens only when the code is
redeemed.

**Canvas layout additions** (U1b builds the UI; C1 builds the backend). This
extends the existing `CanvasSchemeLayout`:

- `CanvasSchemeInstance.ref` additionally accepts `outbound:<id>` (an external
  proxy outbound) for role `exit`. `inbound:<id>` is accepted as an exit.
- `CanvasSchemeInstance.relayPortMode?: 'auto' | 'manual'` and
  `relayPort?: number` on relay and exit server instances (the internal relay
  listen port).
- New server schemes may only use connection type `proxy_chain` or `tunnel`
  with `tunnelProtocol` `tls` or `wireguard`. Existing `port_forward` and gost
  connections are shown read-only with "将迁移到隧道管理" until M1.
- External exit outbounds are created through the existing
  `POST /api/v1/outbounds` (protocol socks5/http/shadowsocks/trojan/vless with
  address, port and credentials) on the node of the hop before the exit.
