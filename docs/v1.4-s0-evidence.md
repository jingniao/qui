## 2. Method

Every probe run:

- creates a **fresh network namespace** (`ip netns add qui-s0-…`) whose only link
  is `lo`; the wrapper aborts if another link appears, so nothing leaves the host
  and no port of the running gate or any shared service is touched;
- serves the HTTP origin in-process on `127.0.0.1:38080` with a per-attempt
  random path (`/nonce-<hex>`) that the origin echoes back;
- starts a **TLS camouflage target** on loopback (`openssl` self-signed cert,
  ALPN `h2,http/1.1`) for Reality `target`/`dest`, regenerated per cell;
- generates **fresh temporary credentials per cell** (SS2022 PSKs from
  `/dev/urandom`, `xray uuid`, `xray x25519`, new shortId, new certificate) and
  writes them only under `/root/s0-import/evidence/<UTC-run>/<cell>/`
  (directory `0700`, files `0600`). Nothing is copied into the repository and no
  credential is printed;
- records **server-side authentication evidence**: the number of
  `inbound connection` lines (sing-box server log) or `accepted` lines (Xray
  access log) that appear **after** a baseline taken immediately before the
  request. Listener readiness is checked with `ss -ltnH`, never by connecting, so
  a readiness probe can never be mistaken for an authenticated connection. In
  Xray cells both processes write `access.log` and `error.log` into the same cell
  directory (their configs use relative log paths), so that count is an **upper
  bound**; the decisive attribution is the server-format `from tcp:<addr>
  accepted` access line plus the server-side `proxy/vless/inbound` and
  `proxy/freedom` lines. Where they disagree, §4 gives the attributed reading;
- retries the HTTP request **at most once** and records `http_attempt_count`.
  The retry exists because mihomo cells failed their *first* dial in the first
  pass; the cause is undetermined (§5). A mihomo cell that needed the retry
  therefore proves success on a later attempt, not on the first one;
- tears down on success and on error (`trap`): children terminated, namespace
  deleted, verified afterwards (`pgrep -af s0probe.py` empty,
  `ip netns list` free of `qui-s0-*`).

Scripts live outside the run directories (`/root/s0-import/probe/`, `0700`/`0600`)
and run as `python3 -I` (isolated mode: no user site-packages, no `PYTHON*`
environment influence). Output is masked before printing: any token of 16+
base64-ish characters in a log tail or native-check message becomes `<redacted>`.

Three result classes are kept apart in every table:

- **native** — the pinned core accepted or rejected the configuration file
  (`xray run -test -c`, `sing-box check -c`, `mihomo -t -f`);
- **authenticated HTTP** — the nonce came back *and* the server logged an accepted
  connection after the baseline;
- **unverified** — everything else, including "native ok but no authenticated
  connection".

Native acceptance is never treated as support: §4 and §6 contain combinations
that the pinned Xray accepts at parse time and refuses at runtime.

The earlier lead claimed "AES two-key chains pass, chacha chains rejected". That
reproduces, with one precision: the chacha rejection is **server-side and
specific to the multi-user (identity) form**. sing-box 1.14.3 refuses to start a

single-key inbound works. So "chacha20" is not one capability; the single-key and
identity forms differ and S2 must model that.

PSK encoding is not free-form. Native checks against the same sing-box build:

| Key material supplied | Result |
| --- | --- |
| 32 B, standard padded Base64 | accepted (`ok`) |
| 32 B, unpadded Base64 | rejected — `decode psk: illegal base64 data at input byte 40` |

(16 B for `2022-blake3-aes-128-gcm`; 32 B for `…-aes-256-gcm` and
`…-chacha20-poly1305`) and preserve identity segments verbatim:
`serverPSK:userPSK` in that order, each segment Base64 on its own.

name the client-side restriction, not "the server rejected it".

not be described as clean.

The sing-box rejection is explicit on the pinned version:

```text

```

That is a **native client-configuration rejection raised before any connection**:
the pinned sing-box refuses to build the outbound, so the harness never sent an

It is therefore **not** one of the three Vision negative cells, which do reach the
transport and are refused later, at request time, by the client's VLESS outbound
(§5).


## 5. First-attempt limitation in the mihomo cells (cause undetermined)

In the first pass, the mihomo Reality cells failed their **first** HTTP request
with `connection reset by peer` / `context deadline exceeded` and **zero**
server-side accepted connections, while the Xray and sing-box clients against the
*same* server authenticated on their first attempt. With one server kept running,
later attempts in the bisect directories (`variant*`) authenticated, including
3/3 on the 2nd and 3rd attempt in `variant9`.

**The cause is undetermined.** Those bisect runs show that subsequent attempts
succeeded; they do not show why the first one failed, and nothing here isolates
the client from the harness (no instrumented rerun, no cold-start control, no
comparison against a different server launch path). Plausible explanations —
mihomo cold start, a server-launch race, harness timing — remain hypotheses. S0
does not attempt to settle it, and the failure must not be attributed to either
side.

What this means for the numbers in this report:

- the harness retries the HTTP request **at most once** and records
  `http_attempt_count`; two mihomo cells carry `2`
  (`vless-reality-tcp-vision-mihomo`, `vless-reality-xhttp-auto-mihomo`);
- a mihomo positive is therefore a **later-attempt positive**. It establishes
  that the combination works with the pinned mihomo build, not that it works on
  the first request after a fresh server start: that first request **failed** in
  this harness and its cause is undetermined;
- the retry can turn a failure into a pass for a positive cell, so no mihomo
  verdict may be presented as "first attempt verified";
- it cannot turn a pass into a failure. The **three Vision cells are the only
  negative cells that involve the retry**: they fail on both attempts, so their
  rejections are independent of it;
- the **sing-box xhttp cell is not a retry case at all**: the pinned sing-box
  rejects the client configuration natively (`unknown transport type: xhttp`), so
  no HTTP request was attempted and no second attempt exists to compare. Its
  rejection is independent of the retry for a different reason — it never reached
  the network;
- the single-key and identity SS2022 mihomo cells authenticated on attempt 1, so
  the limitation is specific to the mihomo Reality cells in this harness, not to
  mihomo in general.

Independent of the retry, a harness that only checked "HTTP 200" would have
reported the Vision cells as supported; the `net-control-direct` cell shows why —
with the proxy bypassed by the rule set, the origin still answers 200 while the
server authenticates nothing.

The inline comment in `http_probe()` states a race hypothesis. It is a comment in
the probe script, not a finding of this report; the measurements above do not
establish it.

otherwise a parameter that matters on another server build is silently dropped.

## 7. `ss://` encoding: plain percent-encoded userinfo is the canonical export

Canonical export for S2/S4, quoted from the public specifications (fetched
2026-11-05; nothing here is remembered wording any more):

- *Shadowsocks SIP002 URL Scheme*
  (<https://shadowsocks.org/doc/sip002.html>) defines
  `SS-URI = "ss://" userinfo "@" hostname ":" port [ "/" ] [ "?" plugin ] [ "#" tag ]`
  and `userinfo = websafe-base64-encode-utf8(method ":" password)` **or**
  `method ":" password`, with this normative sentence: *"Note that encoding
  userinfo with Base64URL is recommended but optional for Stream and AEAD
  (SIP004). But for AEAD-2022 (SIP022), userinfo MUST NOT be encoded with
  Base64URL. When userinfo is not encoded, method and password MUST be percent
  encoded."*
- *SIP022 AEAD-2022 Ciphers* (<https://shadowsocks.org/doc/sip022.html>) §2.1:
  *"The PSK is encoded in base64 for convenience. Practically, it can be
  generated with `openssl rand -base64 <key_size>`"*, with key sizes 16 bytes for
  `2022-blake3-aes-128-gcm` and 32 bytes for `2022-blake3-aes-256-gcm` (and for
  the optional `2022-blake3-chacha20-poly1305`).

Therefore, for every SS2022 entry:

1. the exported URI is `ss://` + **percent-encoded plain** `method:password` +
   `@host:port` (+ optional `#tag`). Base64URL userinfo is **forbidden by the
   specification for AEAD-2022** and must never be produced by an exporter;
2. `password` is the PSK in **standard padded Base64** (SIP022), and that string
   is then percent-encoded for the URI: `+` → `%2B`, `/` → `%2F`, `=` → `%3D`.
   A 32-byte key is 44 Base64 characters ending in `=`; a 16-byte key is 24
   characters ending in `==`;
3. for the multi-user (identity) form the password is `serverPSK:userPSK`, both
   segments standard padded Base64 in that order, each of the cipher's exact
   length. **Decision, not measured:** the exporter percent-encodes the inner
   separator as `%3A`, so the only literal `:` in the userinfo is the one after
   `method`. S2 must confirm this against a URI-consuming client before locking
   it in;
4. the fragment is display-only. SIP002's FAQ says *"White space is not legal in
   URI. It should be escaped"*, so the tag is percent-encoded (`#S0-SS-01`,
   spaces as `%20`);
5. `method` is the exact cipher name (`2022-blake3-aes-256-gcm`), never an alias.

Base64URL userinfo (`websafe-base64-encode-utf8(method ":" password)`) stays an
**input compatibility path**: it is the SIP002 form recommended for Stream/AEAD
(SIP004) entries, so the parser must keep reading it for non-SS2022 legacy
entries and may accept it as tolerated input for SS2022 — but it is an input
form only, never an output form, and an SS2022 entry exported as Base64URL is a
defect, not a variant.

Measurement status: **none of the cells in this report exercises URI text.**
Every client was given decoded credentials in its own configuration format (§3,
§4), so no client was asked to parse `ss://` here. Revision 1 of this document
claimed "the percent-encoded plain form was also accepted by both clients in
this probe"; that sentence is withdrawn — it was not measured. The export rule
above rests on the quoted specification and must be covered by S2's round-trip
and real-client tests.

The earlier lead reported that a **legacy whole-URI Base64** string "passed" an
HTTP check through a client while authenticating zero connections. That artifact
was not reproduced: none of the three pinned clients consumes URI text at all, so
a successful fetch carrying a URI-shaped password can only come from a
direct/failed-proxy path. The `net-control-direct` cell reproduces that failure
mode deliberately: HTTP 200 with zero authenticated server connections.

Declared consequence (a decision, not a measurement): a **panel-side encoding is
not a transport format**. Legacy whole-URI Base64 must be decoded by the panel
into SIP002 form before any exporter runs; it must never be treated as a
client-side capability and must never justify a "supported" claim for a client.

Further notes that stay inside the measured evidence:

- xhttp negotiated HTTP/2 on this build: the client logs `HTTP version 2`, and
  `mode: auto` resolved to `stream-one` (`XHTTP is dialing … mode stream-one,

- The gRPC + Vision note in [v1.4 S0 fixtures](v1.4-s0-fixtures.md) may only cite

Rejected by the panel even though a core's parser accepts the configuration:

- Vision combined with `grpc` or `xhttp` — native validation passes, the client's
  VLESS outbound refuses it at request time;
- SS2022 `chacha20-poly1305` with multi-user identity (the pinned sing-box refuses
  to start the server inbound);
- SS2022 PSKs that are unpadded, Base64URL, or of the wrong decoded length;
- xhttp for sing-box clients (no such transport), and unknown xhttp connectivity
  parameters (the parser accepts them; the panel must not).

- HTTP/3 modes of xhttp; `mode` alone does not classify a transport as H3, and
  only TCP-carried (H2) xhttp was exercised;

## 10. What this does and does not change

  freshly generated server. This document therefore stands on the new

  validation, migrations and the release remain untouched.
