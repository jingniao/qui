# v1.4 S0 fixture manifest: sanitized synthetic entries

Status: planning artifact for S2–S4 and M1. **Review round 1 and round 2
corrections applied (revision 2 of this manifest; S0 revision 3 overall), and the
final review passed on 2026-11-05 for the evidence and manifest scope only — not
full protocol acceptance. The documentation commit is local and its own Linux gate
was still pending when it was created; the manifest is not implemented.** S0
changes no production code;
S1 is now in progress in a separate worktree and no S1 completion is claimed here.
It contains no real subscription, credential, hostname, address or URL: every
credential is a placeholder token and every address is `127.0.0.1` or
`panel.invalid`.

The **16 representative entries** follow plan §11 item 1: **3 SS2022 AES-256**,
**11 Reality+xhttp** and **2 Reality+grpc**. All 16 are **valid** entries; an
invalid, TLS-only, compatibility or duplicate case never occupies a representative
slot. Negative, compatibility and duplicate cases live in §4 with their own names
and are **not** part of the 16 — none of them replaces a representative entry.

Support status per entry comes from [v1.4 S0 evidence](v1.4-s0-evidence.md) and is
given **per client**. `unverified` and `—` mean "not measured"; neither may be
rendered as "supported".

Placeholder tokens used below (they must never be replaced by real values in a
fixture file):

| Token | Meaning |
| --- | --- |
| `<UUID>` | any RFC 4122 v4 UUID, fixed per fixture |
| `<SNI>` | camouflage server name, e.g. `sni.panel.invalid` |
| `<PBK>` | Reality public key, 32-byte X25519 public key in Base64URL without padding |
| `<PVK>` | Reality private key (server side only, never in a client fixture) |
| `<SID>` | Reality short id, even-length lowercase hex, ≤ 16 characters |
| `<PSK32>` / `<PSK16>` | standard padded Base64 of exactly 32 / 16 random bytes |
| `<USERPSK32>` | second 32-byte PSK for the SS2022 identity form |

Rules the fixtures encode and that S2–S4 must preserve:

1. A SS2022 PSK is **standard padded Base64** of the exact key length (SIP022).
   The `ss://` userinfo is then the **percent-encoded plain** `method:password`
   form (SIP002: for AEAD-2022 the userinfo "MUST NOT be encoded with Base64URL";
   "method and password MUST be percent encoded"). Base64URL userinfo is an
   **input** compatibility path only (§4, `S0-COMPAT-SS-B64URL`) and is never an
   export form. These are different encodings of different things.
2. The identity form is `serverPSK:userPSK` in that order, each segment standard
   padded Base64 of the cipher's exact key length.
3. Reality always carries SNI, public key, short id and fingerprint together; a
   client export that drops any of them is invalid, not degraded.
4. An xhttp entry always carries `path` and `mode`; `mode` is one of the four
   bounded values and is never inferred.
5. Vision (`xtls-rprx-vision`) is only valid with `network: tcp`.
6. A client cell is only "supported" when that (combination, client) pair was
   measured; the evidence grid is per client, not per protocol.

Formats are abbreviated: `URI` = `vless://`/`ss://` share link, `Mihomo` =
`proxies:` YAML block, `sing-box` = outbound fragment, `Clash` = legacy Clash
provider. "omit" means the exporter must drop the entry for that format (with the
per-entry omission contract of plan §5 item 5) rather than emit a lossy proxy.

`pct()` below percent-encodes every character outside RFC 3986 `unreserved`, so
`+` → `%2B`, `/` → `%2F`, `=` → `%3D` and `:` → `%3A`. The cipher name itself
(`2022-blake3-aes-256-gcm`) contains no such character and is written literally.

## 1. SS2022 AES-256 (3 entries)

### S0-SS-01 — single key, canonical plain userinfo

- Identity: `method=2022-blake3-aes-256-gcm`, `password=<PSK32>`, `127.0.0.1:20001`.
- `URI`: `ss://2022-blake3-aes-256-gcm:<pct(<PSK32>)>@127.0.0.1:20001#S0-SS-01`.
  A 32-byte key is 44 Base64 characters ending in `=`, so the canonical link ends
  in `%3D` before the `@`. Base64URL must not appear.
- `Mihomo`: `{type: ss, cipher: 2022-blake3-aes-256-gcm, password: "<PSK32>", server: 127.0.0.1, port: 20001, udp: true}`.
- `sing-box`: `{type: shadowsocks, method: 2022-blake3-aes-256-gcm, password: "<PSK32>", server: 127.0.0.1, server_port: 20001}`.
- `Clash`: omit (legacy provider has no SS2022 support verified here).
- Measured: mihomo ✓ and sing-box ✓ (native accept + authenticated connection)
  with the decoded PSK; the URI itself was not exercised by any probe.

### S0-SS-02 — second single-key entry (distinct key and port)

- Identity: `method=2022-blake3-aes-256-gcm`, a different `<PSK32>`, port `20002`.
- `URI` / `Mihomo` / `sing-box` / `Clash`: same shape as `S0-SS-01`, distinct
  key, port and tag. **Same canonical plain form — this entry is not a second
  encoding.**
- Measured: same client cells as `S0-SS-01` (mihomo ✓, sing-box ✓).

### S0-SS-03 — identity form (server PSK + user PSK)

- Identity: `method=2022-blake3-aes-256-gcm`,
  `password=<PSK32>:<USERPSK32>`, port `20003`.
- `URI`: `ss://2022-blake3-aes-256-gcm:<pct(<PSK32>)>%3A<pct(<USERPSK32>)>@127.0.0.1:20003#S0-SS-03`.
  The separator between the two keys is percent-encoded as `%3A`, so the only
  literal `:` in the userinfo is the one after `method`. This is a decision to be
  confirmed by S2 against a URI-consuming client, not a measured result.
- `Mihomo`: `password: "<PSK32>:<USERPSK32>"` (literal colon in YAML).
- `sing-box`: same password value; the server side needs `password: <PSK32>` plus
  `users: [{password: <USERPSK32>}]` (server-side fixture only, never exported).
- `Clash`: omit.
- Measured: mihomo ✓ and sing-box ✓ with the decoded two-segment password.
- Expected S2 behaviour: keep the two segments verbatim and in order; never
  re-encode, split, merge or trim them.

## 2. Reality + xhttp (11 representative entries)

Shared identity for the eleven entries: `type=vless`, `uuid=<UUID>` (different
per entry), `security=reality`, `sni=<SNI>`, `pbk=<PBK>`, `sid=<SID>`,
`fp=chrome`, `flow` absent, `path=/s0`, one port each `127.0.0.1:21001`–`21011`.
This is the shape the measured cells used against Xray 26.3.27.

The distribution across the four bounded modes is a **fixture-design choice**:
the external source's per-entry modes were never recorded, so spreading the 11
entries over all four values covers the bounded set instead of guessing one. All
eleven are valid entries — invalid, TLS-only and duplicate cases are in §4.

| # | Fixture | `mode` | Xray client | mihomo client | sing-box | legacy Clash |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `S0-XH-01` | `auto` | supported | supported (`alpn: [h2]`) | omit (no transport) | omit |
| 2 | `S0-XH-02` | `auto` | supported | supported (`alpn: [h2]`) | omit | omit |
| 3 | `S0-XH-03` | `auto` | supported | supported (`alpn: [h2]`) | omit | omit |
| 4 | `S0-XH-04` | `auto` | supported | supported (`alpn: [h2]`) | omit | omit |
| 5 | `S0-XH-05` | `packet-up` | supported | unverified → omit | omit | omit |
| 6 | `S0-XH-06` | `packet-up` | supported | unverified → omit | omit | omit |
| 7 | `S0-XH-07` | `packet-up` | supported | unverified → omit | omit | omit |

"Close caveat" = the measured `stream-up` cell delivered the response but logged
`failed to transfer response payload > unexpected EOF` on teardown, and its first
byte arrived ≈6 s after dial (evidence §4). The combination is supported; its
close behaviour is not described as clean.

Format mapping (all eleven entries):

- `URI`: `vless://<UUID>@127.0.0.1:<port>?encryption=none&security=reality&sni=<SNI>&fp=chrome&pbk=<PBK>&sid=<SID>&type=xhttp&path=%2Fs0&mode=<mode>#<name>`
- `Mihomo`: `{type: vless, uuid: <UUID>, network: xhttp, tls: true, servername: <SNI>, client-fingerprint: chrome, reality-opts: {public-key: <PBK>, short-id: <SID>}, alpn: [h2], xhttp-opts: {path: /s0, mode: <mode>}}`
- `sing-box`: **omit** — the pinned build has no `xhttp` transport
  (`unknown transport type: xhttp`).
- `Clash`: omit.

Notes the fixtures deliberately encode:

- only the `auto` rows have a measured mihomo cell; the other modes stay
  `unverified` for mihomo, so their Mihomo export is an omission with an
  "unverified for this client/mode" reason until a cell is measured, never an
  implied pass;
- no fixture may rely on `mode` to decide HTTP/3; H3 was never exercised;
- Mihomo was measured with `alpn: [h2]`; a Mihomo export without it is
  unverified;
- typing is still required: the pinned Xray parser accepts unknown `extra` keys
  and `xmux` tuning (§4), so the shared model must reject what it does not model.

## 3. Reality + gRPC (2 representative entries)

Both rows are **valid representative entries**: `flow` is absent in both, so
neither row is the invalid Vision combination. Vision combined with `grpc` stays
exclusively in §4 as `S0-NEG-VISION-GRPC` and is never one of the 16.

Shared shape for the two rows: `type=vless`, `security=reality`, `sni=<SNI>`,
`pbk=<PBK>`, `sid=<SID>`, `fp=chrome`, `flow` absent, transport `grpc`, one port
each. UUID, fixture name, port and `serviceName` are distinct per row.

| # | Fixture | UUID / `serviceName` / port | Xray client | mihomo client | sing-box | Expected exporter behaviour |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `S0-GR-01` | `<UUID>` (distinct), `serviceName=s0`, `127.0.0.1:22001` | measured at shape level (§ below) | unverified → omit until measured | unverified → omit until measured | emit `type=grpc&serviceName=s0` URI; keep Mihomo `network: grpc` + `grpc-opts.grpc-service-name: s0` and sing-box `transport: {type: grpc, service_name: s0}` behind the per-client status above; Clash omit |
| 2 | `S0-GR-02` | `<UUID>` (distinct), `serviceName=s0 grpc` (contains a space, so the URI must escape it), `127.0.0.1:22002` | unverified **for this instance**; same shape as row 1 | unverified → omit until measured | unverified → omit until measured | same shape as row 1, but the name must survive the codec: URI `serviceName=s0%20grpc`, Mihomo `grpc-service-name: "s0 grpc"` and sing-box `transport: {type: grpc, service_name: "s0 grpc"}` as unescaped literals; Clash omit |

`S0-GR-02` is **not** a second encoding of the shape: it is a second valid
instance with its own UUID, name and port, plus a `serviceName` that cannot be
copied through unescaped. Ordinary characters are not enough — the S3/S4 codec
tests need a value that exercises the escape path (see the SS2022 identity
separator, §1 `S0-SS-03`, for the same "decision to be confirmed by S2" status).

What the measured cell proves and what it does not:

- **Shape level, measured — Xray client only.** The evidence cell
  `vless-reality-grpc-empty-xray` (§4 of the evidence) ran one no-flow gRPC
  endpoint with the Xray client: native check passed, transport connected, the
  VLESS request authenticated and the origin was hit once. That supports
  "Reality + gRPC without `flow` works with the pinned Xray client" — the shape
  both rows share.
- **Instance level, not exercised.** Neither `S0-GR-01` nor `S0-GR-02` was
  replayed with its own UUID, SNI, port and `serviceName`. The percent-encoding of
  `serviceName` in a URI is therefore a codec decision for S2/S3 to confirm
  against a URI-consuming client, not a measured result — exactly like the
  percent-encoded inner separator of the SS2022 identity form.
- **No mihomo and no sing-box cell exists for either row.** The earlier "sing-box
  supports gRPC via `type: grpc`" statement was a lead, not a measurement, and
  stays withdrawn until S3 measures it. Both rows export to those two formats only
  behind the per-client status above; today that means omit.
- **The invalid case is only `S0-NEG-VISION-GRPC`.** A validation layer that only
  runs `xray run -test` still accepts Vision + gRPC (evidence §4): the server and
  client configurations pass native validation, the transport connects, and the
  **client's VLESS outbound** then refuses the flow with zero origin hits. Keeping
  that case out of these two rows is what lets the representative set stay valid
  while the false-positive case stays in the test set.

## 4. Negative, compatibility and duplicate fixtures (not part of the 16)

These are fixtures too: each must produce a precise, stable diagnostic and must
never be silently repaired into something else. They are named separately so they
never take the place of a representative entry, and so the duplicate test cannot
hide the validation result of the entry it duplicates.

| Fixture | Condition | Status and required behaviour |
| --- | --- | --- |
| `S0-COMPAT-SS-B64URL` | SS2022 entry whose `ss://` userinfo is Base64URL of `method:password` | **input compatibility only**: the parser may accept it (SIP002 recommends that form for Stream/AEAD), the exporter must never emit it — for AEAD-2022 Base64URL userinfo is forbidden |
| `S0-NEG-CHACHA-IDENTITY` | SS2022 `2022-blake3-chacha20-poly1305` with `users` | unsupported: the pinned sing-box refuses the *server* configuration (`initialize inbound[0]: invalid argument`); report "chacha20 identity not supported", not a generic failure |
| `S0-NEG-PSK-UNPADDED` | SS2022 PSK, unpadded Base64 | invalid: `decode psk: illegal base64 data`; report a key-encoding error naming standard padded Base64 |
| `S0-NEG-PSK-URLSAFE` | SS2022 PSK, Base64URL alphabet | invalid, same class as `S0-NEG-PSK-UNPADDED` |
| `S0-NEG-PSK-LENGTH` | 16 B key with `…-aes-256-gcm` (or 32 B with `…-aes-128-gcm`) | invalid (`bad key`): report the expected key length for the cipher |
| `S0-NEG-WHOLEURI-B64` | legacy **whole-URI** Base64 (`base64("ss://…")`) as the subscription payload item | not a client format: decode panel-side into SIP002 before export; an HTTP 200 observed through a client proves nothing (evidence §7 control cell) |
| `S0-NEG-SINGBOX-XHTTP` | `network: xhttp` for a sing-box client | unsupported client: omit for sing-box with a format-omission diagnostic (`unknown transport type: xhttp`) |
| `S0-NEG-REALITY-INCOMPLETE` | Reality entry missing `sid`, `pbk`, `sni` or `fp` | invalid: Reality requires the full set; never emit a partial client config |
| `S0-NEG-XHTTP-MODE-INVALID` | xhttp `mode` outside the four allowed values | invalid: reject with the four allowed values (`unsupported mode: invalid` from the core, earlier and clearer from the panel) |
| `S0-NEG-XHTTP-EXTRA-UNKNOWN` | xhttp with unknown `extra` connectivity parameters | the core **accepts** them; the panel must reject with a precise reason (the parser is not a validator) |
| `S0-NEG-XHTTP-XMUX` | xhttp with `extra.xmux` tuning | accepted by the core, behaviour unmeasured: out of the first-release subset, reject with an explicit "unsupported tuning" reason, never pass through |
| `S0-NEG-VISION-GRPC` | Vision with `grpc` | invalid: native validation accepts, the **client outbound** refuses at request time; reject with the transport/flow reason |
| `S0-NEG-VISION-XHTTP` | Vision with `xhttp` (any mode; `packet-up` measured) | invalid: same client-side rejection, zero origin hits |
| `S0-NEG-XHTTP-H3` | xhttp advertised as HTTP/3 | unverified: `mode` does not classify a transport as H3; the first release is limited to TCP-carried (H2) xhttp |
| `S0-ALT-TLS-XHTTP` | Reality replaced by ordinary TLS, xhttp `auto` (Xray measured) | valid entry, **outside** the representative set: it must keep certificate/pinning fields and must not be used as a substitute for a Reality fixture; sing-box/mihomo unverified |
| `S0-DUP-01` | two taps of one endpoint: identical `name` and `protocol`, differing only in `flow` (`none` vs `xtls-rprx-vision`) | duplicate-key test: import keeps the first and reports `duplicate_endpoint_key`; the second is **not** validated or exported. Kept separate from the 11 so deduplication cannot mask the Vision rejection of `S0-NEG-VISION-XHTTP` |

## 5. Out of scope for these fixtures

- Legacy Clash / `clash-legacy` output for every entry above (unverified; the
  plan says omit rather than guess).
- Any URI/text-level acceptance claim: no probe fed `ss://` or `vless://` text to
  a client, so exporter encodings rest on the quoted specifications plus S2–S4
  tests (evidence §7).
- Any client cell the evidence marks `—`: those are omissions, not passes.
- Any UDP, metering, device-gate, traffic-accounting or Agent acceptance claim.
  The probe used a TCP HTTP origin only, and none of those subsystems was
  exercised.
- Any real provider ordering, pagination or naming; the fixtures are deliberately
  minimal and use `panel.invalid` names.
