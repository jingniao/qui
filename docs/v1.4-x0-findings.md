# v1.4 X0: GOST middle relay spike and contract

Status: implemented in source, local unit tests and vet passed on Windows
(2026-11-03). **GOST 3.3.2 runtime results remain to be measured on Linux.**
This is X0 only; no panel, database, web, tunnel management or deployment planner
changes are included. D1–D3 remain the selected engine, transport and topology.

## Contract and topology

The Agent now advertises `gost_contract_version=4`. Version 2 still identifies
pool/range/limit support; version 3 still identifies the existing encrypted relay
support. A middle listener uses the existing desired-state representation:

```text
forward.mode = "relay"
forward.relay = {certificate_pem, private_key_pem, client_ca_pem}
forward.gost_hops = [{host, port, server_name, ca_cert_pem,
                      client_cert_pem, client_key_pem}]
```

`relay` authenticates the previous leg. The single `gost_hops` member authenticates
this node to the next leg. An exit has the same representation with no hops.
An entry retains its target pool and supplies one hop to the middle or exit.
The middle relay has no target pool, network selector, port range or pool limits.
Its target arrives in the relay request and is passed through its handler chain.

No higher native hop limit is needed: the existing `GostMaxRelayHops=2` stays for
contract-3 compatibility, while a middle listener may have **at most one** next
hop. New tunnels must use one next hop per node, at most entry → middle → exit
(three distinct servers, two relay legs). The complete topology and distinct
server roles must be checked by X1, since an individual desired state cannot see
other servers' routes or detect a distributed cycle. Legacy entry configurations
with two native hops remain valid.

`ForwardSettings.ValidateGostContract(reportedVersion)` rejects middle settings
for every version below 4 with
`gost middle relay requires Agent gost_contract_version >= 4`.
It accepts legacy relay settings at 3 and rejects them below 3. Render also calls
this guard with the build's own supported contract. **X1 must call it with each
node's reported capability before delivery**; X0 intentionally does not change
the existing panel/canvas publisher, which cannot create middle services today.
Never infer support from the GOST binary version, which remains 3.3.2.

Each material half has its own directory under
`runtime/gost/tls/<inbound>/<half>-<material digest>/`:
`relay-…` for the listener; `hop0-…` for the next-hop dialer.
Directories are 0700 and files 0600 on Linux. Digest names preserve old material
for rollback. The middle server leaf and outgoing client leaf must be distinct;
X1 should issue separate leaves for each role/leg from the tunnel CA.
The runtime suite deliberately uses different test CAs on the two legs to catch
accidental sharing of listener/dialer material. Production may use one tunnel CA
with separate leaves; CA-private-key retention/issuance is X1 work.

`TestContract3RenderUnchanged` freezes the old two-hop entry and exit JSON shape
and compares JSON and derived YAML bytes after normalizing temporary material
paths and the metrics directory. Existing direct-forward JSON/YAML goldens also
remain unchanged. The production material path algorithm has not changed.

## Generated YAML examples

The following use example addresses and readable material paths. Replace each
`<digest>` with that half's material digest. These are separate configurations
on separate servers. Production uses absolute runtime paths. Each configuration
also contains `metrics: {addr: unix://<runtime>/metrics.sock}` and
`log: {level: warn, format: text}`; those common fields are omitted below.

### Two servers, one relay leg: entry → exit → target

Entry (`entry-rule`, listen 30001, TCP and UDP target `127.0.0.1:443` **on exit**):

```yaml
services:
  - name: fwd-entry-rule-30001-tcp
    addr: 0.0.0.0:30001
    handler: {type: tcp, chain: chain-entry-rule}
    listener: {type: tcp}
    forwarder:
      selector: {strategy: round, maxFails: 1, failTimeout: 5s}
      nodes: [{name: target-0, addr: '127.0.0.1:443'}]
  - name: fwd-entry-rule-30001-udp
    addr: 0.0.0.0:30001
    handler: {type: udp, chain: chain-entry-rule}
    listener: {type: udp}
    forwarder:
      selector: {strategy: round, maxFails: 1, failTimeout: 5s}
      nodes: [{name: target-0, addr: '127.0.0.1:443'}]
chains:
  - name: chain-entry-rule
    hops:
      - name: hop-0
        nodes:
          - name: relay-0
            addr: 203.0.113.30:22000
            connector: {type: relay}
            dialer:
              type: tls
              tls:
                certFile: tls/entry-rule/hop0-<digest>/cert.pem
                keyFile: tls/entry-rule/hop0-<digest>/key.pem
                caFile: tls/entry-rule/hop0-<digest>/ca.pem
                serverName: exit.tunnel.qui.internal
```

Exit (`exit-relay`):

```yaml
services:
  - name: relay-exit-relay-22000
    addr: 0.0.0.0:22000
    handler: {type: relay}
    listener:
      type: tls
      tls:
        certFile: tls/exit-relay/relay-<digest>/cert.pem
        keyFile: tls/exit-relay/relay-<digest>/key.pem
        caFile: tls/exit-relay/relay-<digest>/ca.pem
```

### Three servers, two relay legs: entry → middle → exit → target

The entry configuration above changes only its hop address to
`203.0.113.20:21000`, `serverName` to `mid.tunnel.qui.internal`, and that hop's
client leaf/CA files to the entry → middle material. Its forward target remains
`127.0.0.1:443`. The exit configuration stays as above, with material for the
middle → exit leg. The middle configuration is:

```yaml
services:
  - name: relay-mid-relay-21000
    addr: 0.0.0.0:21000
    handler: {type: relay, chain: chain-mid-relay}
    listener:
      type: tls
      tls:
        certFile: tls/mid-relay/relay-<digest>/cert.pem
        keyFile: tls/mid-relay/relay-<digest>/key.pem
        caFile: tls/mid-relay/relay-<digest>/ca.pem
chains:
  - name: chain-mid-relay
    hops:
      - name: hop-0
        nodes:
          - name: relay-0
            addr: 203.0.113.30:22000
            connector: {type: relay}
            dialer:
              type: tls
              tls:
                certFile: tls/mid-relay/hop0-<digest>/cert.pem
                keyFile: tls/mid-relay/hop0-<digest>/key.pem
                caFile: tls/mid-relay/hop0-<digest>/ca.pem
                serverName: exit.tunnel.qui.internal
```

The entry never receives the exit's address or client leaf in this model.
The listener is `tls` with a client CA, never GOST's `mtls` listener (which means
multiplexed TLS). Middle and exit listen over TCP even when carrying UDP traffic.

## Health, totals and UDP caveats

Middle services use the existing exact-child health check and contribute their
TCP listener to `HealthEndpoints`. There is no production UDP listener on a TLS
relay half; UDP socket ownership checks apply to UDP entry/direct listeners.
Health tests listener availability, not target reachability or tunnel handshake.
The existing `relay` handler filter excludes both middle and exit bytes from node
totals. Only entry/direct `fwd-*` counters count, with no user attribution.

UDP is framed through the relay protocol over TLS/TCP on each leg, then sent as
UDP from the exit to the target. TCP loss and head-of-line blocking can affect
latency. A relay restart drops TCP sessions and UDP associations; clients may
need to retry/recreate flows. Transparent preservation of existing TCP sessions
or UDP associations is not promised.

Source inspection of qui shows **no explicit UDP listener `ttl` or `keepAlive`**,
and no connector/handler keepalive metadata. Those defaults remain unchanged so
contract-3 YAML stays identical. Do not claim a measured idle lifetime from this.
Read-only flyx reference inspection found UDP listener
`metadata: {keepAlive: true, ttl: 30s}` in `forward_services.go`, and relay
connector/handler `nodelay` plus mux keepalive interval 15s / timeout 45s in
`tunnel_runtime.go`. These settings are not copied into qui. Their effect on
plain TLS relay (versus multiplexed transports), GOST 3.3.2 default UDP TTL,
idle expiry and reuse after failure require Linux measurement before choosing
new defaults. X0 echo probes use fresh sockets and do not measure long idle flows.

## Recovery and evidence

Expected: a dead exact child is detected by the existing supervisor (normally
the next 3-second tick), and the reconciler restores its retained successful
revision. Startup also reconstructs the reconciler from encrypted local storage
and calls Restore. No new panel publish is needed. Failed restores use the
existing backoff. Downstream restarts must not restart the entry; new TCP and UDP
flows must resume. Existing connections may be lost.

Measured locally on Windows:

- Contract validation, capability rejection, render reference checks, separate
  material halves, relay counter exclusion and health endpoint generation pass.
- Contract-3 render equality and existing direct-forward goldens pass.
- The gated runtime suite compiles and passes vet; `GOST_BINARY` is unset, so
  **no GOST runtime result is measured locally**.

## Remaining decisions

1. Keep GOST's current UDP defaults for X0; decide explicit TTL/keepalive only
   after the idle/recovery measurements above.
2. X1 must enforce three distinct roles globally, gate middle nodes at contract
   4, issue per-leg leaves, and publish exit → middle → entry with inverse rollback.
   X0 cannot enforce a distributed route from one node's state.
3. Runtime recovery acceptance is pending the Linux run. The test harness covers
   retained Agent state and real child supervision, not installation/service
   manager recovery or separate-host networking.
