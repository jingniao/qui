## Contract interpretations and behavior changes

- DELETE has no `updatedAt` request body in §5 or `api.ts`; concurrency tokens
  are required for PUT and rotation. No extra DELETE parameter was introduced.
- A pending-delete rule remains a referencing row and blocks tunnel deletion,
  as in the mock, until publication removes it. It also retains its claims.
- A tunnel update returns the §5 `Tunnel` shape. Its linked rules are updated
  transactionally and can be read through the existing filtered rule list.
- Published edits retain old listener claims as well as new ones. Never-published
  drafts can replace their claims on edit and release them on deletion.
- Two existing canvas test expectations were adjusted for D4/D5: disabled
  listeners reserve ports, and an implicit new listener requires a configured
  range. Canvas conflict response shapes and messages are otherwise retained.
- Draft saves validate node existence/deletion and data shape. GOST installation,
  contract capabilities and deployment readiness must be checked by X1b planning.

### Review corrections to X1a

- The shared `portOccupants` function now takes an inbound scope. Enabled
  inbound saves and explicit canvas listeners check enabled inbounds only;
  disabled inbound saves check claims only. Tunnel/rule claims always reserve,
  regardless of enabled state. Automatic allocation still skips every configured
  inbound, including disabled inbounds and every expanded range port.
- `ports/check` deliberately reports disabled inbounds as `usedBy` so editors
  can warn. A manual listener save may nevertheless reuse a disabled inbound's
  port. This distinction is documented beside the shared implementation.
- Canvas encrypted relays retain their legacy default when the target has no
  range: TLS 8443 / WireGuard 51820. A configured but exhausted range still
  fails. New tunnels, rules and `ports/allocate` keep `no_free_port` without a
  range/manual port. The two named canvas regression expectations were restored.

These corrections supersede X1a's description of changed canvas expectations.

### Delivered behavior and decisions

- Added the exact `PublishSelection`, `PublishPlan` and `PublishResult` JSON
  shapes and `/tunnels/plan` and `/tunnels/publish` endpoints. Planning is
  read-only and lists ordered servers, listeners, routes, create/update/remove
  changes, conflicts and dependency warnings. Publishing rebuilds that plan
  under the existing canvas mutation lock and captures draft versions.
- A selected tunnel includes its rules. A selected rule includes its tunnel;
  a dirty tunnel dependency also includes its rule dialers so topology edits
  and credential rotation cannot update a listener without its callers.
- Two-node tunnels require GOST contract 3 on all nodes; three-node tunnels
  require contract 4 on all nodes. Unavailable/pending cores, old Agents and
  receiving hops without a public IP or connect override are refused before
  materialization, with Chinese explanations.
- Reused the GOST relay input/hop builders. A receiving hop has one shared
  listener for all rules of its tunnel. Entries and middle listeners carry
  exactly one next hop; the final target remains on each entry rule. Linked
  targets retain D8 derivation, including loopback when exit equals destination.
  Direct rules choose GOST when present, otherwise the primary Xray/sing-box.
- Extended the existing sealed material with an independent second leg. Both
  sets are issued at save/rotation time, using the existing issuance/sealing
  code, with separate CAs and client/server leaves. Planning issues nothing;
  no private material enters API responses, plans or audit records.
- Extended unreleased migration 0129 with `tunnel_objects` and updated its
  pinned checksum. Ownership and stable generated IDs never depend on names.
  Inbound reads expose `managedBy: {kind,id,name}`; ordinary inbound PUT/DELETE
  refuse these objects with 409 `managed_by_tunnel`. Managed listeners are
  represented once by their claims in the shared port service.
- Materialization reconciles only the selected owners' inbounds in one SQLite
  transaction. Snapshots then use the existing `CanvasPublisher` pruning and
  deployment-batch machinery. The tunnel adapter waits for terminal receipts
  (up to the frontend's 300-second publication window). Exit precedes middle
  precedes entry; existing batch rollback reverses that order. Unchanged nodes
  have no revision and return `unchanged`.
- Only complete successful publication advances published markers. Failure
  restores the previous generated business objects and retains draft rows and
  all claims. Successful removal deletes pending rules before tunnels; old
  listener claims are released only after successful apply. Repeated unchanged
  publication creates neither revisions nor batches.
- Backup inventory and validation include ownership, object/owner references
  and matching claims. Current restore preserves ownership and sealed material;
  pre-0129 fixtures remain supported. Generated forwards and relay listeners
  remain excluded from subscriptions; relayed user endpoints remain N1.

API deviations from plan §5: **none**.
