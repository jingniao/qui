# v1.5.0 修复方案：让现有 Agent 能启用网页升级

> 状态：2026-11-10 编写，Owner 已批准；2026-11-11 实现并通过测试机验收（见[验收报告](v1.5.0-agent-web-upgrade-verification.md)）。实施中补充：qui-update 在“已是最新版本”时也执行启用，否则从 ≤1.4.7 升级后的第二次运行不会启用。起因见[阶段 1 验收报告](v1.5.0-agent-web-upgrade-verification.md)：普通安装的 Agent 从未进入受管模式，排队网页升级一律 409。本文只解决“怎样进入受管模式并且出错能退回”，不改签名、目录、切换、回滚等已有链路。

## 1. 现状（已核对源码）

| 事实 | 位置 |
| --- | --- |
| 只有带 `--supervise --initialize-agent-history` 启动一次，Agent 才建立受管状态（基线镜像、受管标记、任务日志、安装历史）；这个初始化写在长期运行的 `agenthost.Run` 里面，不是一次性命令 | `internal/agent/agenthost/host.go:83-111`、`cmd/agent/main.go:226-236` |
| 一旦受管状态里任何一个文件存在，普通启动（不带参数）就自动走受管模式 | `cmd/agent/main.go:322-328`、`agenthost/state.go:30` `Active` |
| 初始化前提：节点已登记，且至少正常运行过一次（存储下限由 `control.Run` 写入，`control.go:308`） | `host.go:55-61` |
| systemd 单元、OpenRC 脚本、install.sh、update.sh、node-install.sh **都没有调用初始化** | `deploy/` 全目录无匹配 |
| 初始化中途失败或断电会留下部分状态；之后普通启动按“已受管但状态不全”报 `ErrState` 退出，节点**一直起不来** | `host.go:111-114`、`state.go:28` |
| Agent 管理页只看 `panel_catalogue_supported` 就显示“升级”按钮；面板真正排队时看的是 `node_update_capabilities.agent_supported`，节点 API 没有暴露这个值 | `web/src/modules/system/components/NodeVersionPanel.vue:299-300`、`internal/panel/deployment/agent_updates.go` |
| 受管后，install.sh／qui-update 只替换引导程序 `/usr/local/bin/proxy-agent`，实际运行的镜像不变（文档已写明） | `docs/deployment.md:383` |

## 2. 方案选择

**选定：由 root 脚本在升级或安装成功之后显式初始化，失败自动退回普通模式。** 不采用“Agent 启动时自动初始化”，原因：

- qui-update 的 10 秒健康检查窗口内如果 Agent 自己初始化，随后更新失败回滚到 1.4.x 时，旧程序看到受管状态，会去运行 1.5.0 的镜像，**回滚失效**。改为在健康检查通过之后由脚本初始化，就不会碰到更新回滚。
- 保留源码原有的设计约定：“初始化是显式的”。

## 3. 改动清单

### 3.1 Agent（`cmd/agent`、`internal/agent/agenthost`）

1. **把初始化拆成一次性命令**：新增 `agenthost.Initialize(ctx, configPath, version)`，内容就是 `Run` 里现有的初始化分支（物化基线镜像 → 探测 → 写受管标记 → 建任务日志 → 建安装历史并写入基线），做完即返回。`Run` 删掉 `initialize` 参数，只负责已受管的启动。
2. **命令行**：`proxy-agent --config <文件> --initialize-agent-history` 成为一次性命令（与 `--enroll` 同样的写法：只接受这两个参数，成功打印一行后退出 0）。`--supervise --initialize-agent-history` 的组合不再接受。更新 `TestAgentFlagsAreExactlyTheSupportedSurface` 等 3 个命令行测试。
3. **防止半成品状态让节点起不来**：`Initialize` 第一步用排他方式创建 `identity/agent-supervision-init.pending`，全部完成并落盘后最后删除它。普通启动在判断 `Active` 之前先检查这个文件：如果它存在，说明初始化被中断，这时还没有任何受管 worker 运行过，可以安全地删掉第 1 节列出的 7 个受管路径和这个文件，写一条 WARN 日志，然后按普通模式启动。
   - 只有这个文件存在时才清理；已经完成初始化的节点（文件已删除）继续沿用“状态不全就拒绝启动”的原规则，不放宽防回退保护。
4. **单元测试**：初始化成功后普通启动进入受管模式；中途失败（例如注入探测失败）后普通启动回到普通模式；初始化已完成后不会再被清理；未登记或从未运行过的节点拒绝初始化并给出明确原因。

### 3.2 部署脚本（`deploy/linux`）

1. `service.sh` 新增函数 `agent_enable_web_upgrade`（在 systemd 与 OpenRC 上通用）：
   - 已受管（`/var/lib/proxy-agent/identity/agent-supervisor.enc` 存在且没有 `.pending` 文件）→ 直接返回“已启用”。
   - 停止服务 → 以 `umask 077` 执行 `runuser -u proxy-agent -- /usr/local/bin/proxy-agent --config /etc/proxy-agent/config.yaml --initialize-agent-history` → 启动服务 → 10 秒健康检查。
   - 任何一步失败：停止服务，把受管路径移到 `/var/lib/proxy-agent/web-upgrade-failed-<时间>/` 作为备份（不直接删除，便于排查），然后启动普通模式并再做一次健康检查。只打印警告“网页升级未启用，节点仍按普通模式运行”，**不让整个升级失败**。
2. `update.sh`：`--component agent` 健康检查通过、记为完成之后调用该函数。服务原本没在运行的就跳过，并提示下次怎样启用。
3. `node-install.sh`（新装）：登记并首次启动、健康检查通过后调用该函数（这时存储下限已写入）。
4. **已受管节点再跑 qui-update `--component agent`**：照常更新引导程序（受管模式下的监督进程就是它，修复也要靠它下发），但把结尾的提示改成“引导程序已更新到 X；节点实际运行的 Agent 版本由面板的 Agent 管理决定”，不再说“已更新到 X”误导人。
5. `deploy/linux/tests/` 补测试：启用成功、初始化失败后退回普通模式、已受管时跳过、服务没在运行时跳过。

### 3.3 面板与页面

1. 节点 API 增加只读字段 `agentUpdateSupported`（取自 `node_update_capabilities.agent_supported`）。
2. Agent 管理页的“升级”按钮改为看 `agentUpdateSupported`。不支持时按“隐藏不可用操作”的规则不显示按钮，改为提示“需在服务器上运行一次 `qui-update --component agent` 启用网页升级”（覆盖旧版本 Agent，以及已经是 1.5.0 但初始化失败的节点）。“全部升级”跳过这些节点。
3. 面板排队时对“不支持网页升级”返回单独的错误码 `agent_update_unsupported` 和明确的中文说明，不再混在通用的 `agent_update_conflict` 里。

### 3.4 文档

- `docs/deployment.md`、`docs/operations.md`：怎样启用网页升级、怎样确认（面板按钮出现）、失败备份放在哪里；**手动退出受管模式**的步骤（停服务 → 把受管路径移作备份 → 启动，回到引导程序版本；如果新版本已经提高了存储格式，旧引导程序会明确拒绝启动，这时只能装回足够新的版本）。
- `AGENTS.md` 第 23、29.2 节补一句启用方式。
- 发布说明的升级注意事项按实际行为改写。

## 4. 不做

- 不加 `--no-web-upgrade` 之类的开关；需要时可以按手动步骤退出受管模式。
- 不改签名、目录、下载、切换、健康检查、回滚这些已有链路。
- 不在 `qui` 菜单里加“退出受管模式”（以后需要再说）。

## 5. 验证

1. 本地：`go test ./cmd/agent ./internal/agent/agenthost ./internal/panel/...`（相关包），`bash scripts/quick-check.sh`，以及上述部署脚本测试。
2. 测试机重跑发布规划的阶段 1，在原来三个场景前先加两步：
   - **A. 启用路径**：Alpine/OpenRC 容器从 1.4.7 用 `qui-update --component agent` 升到 1.5.0，确认脚本打印“已启用”、面板 `agentUpdateSupported=true`、按钮出现；重启服务后仍是受管模式。
   - **B. 失败退回**：故意让初始化失败（例如把基线镜像目录预先占成一个普通文件），确认节点退回普通模式并保持在线，备份目录存在，按钮不出现。另外在初始化中途杀掉进程，确认留下的 `.pending` 让下次启动自动退回普通模式。
   - 然后跑原来的三个场景：成功升级到 1.5.1、文件损坏被拒、健康检查失败回滚。
3. systemd 主机（测试机本机）至少把启用路径 A 跑一遍，确认 `ProtectSystem=strict` 下受管镜像目录可写、可执行。
4. 之后接着发布规划的阶段 2–9 执行，不变。

## 6. 影响与估计

- 规模：Agent 约 150 行加测试，脚本约 120 行加测试，面板与页面约 40 行，没有迁移。
- 受管模式下每个节点多一个监督进程（约 10–20 MB 内存）。
- 生产升级时（另行请示），三台 Agent 用 qui-update 升到 1.5.0 后会自动启用网页升级；Alpine LXC 也要确认启用成功。
- 预计实现与审查 2–3 小时，测试机验收约 1.5 小时，然后回到发布规划的阶段 2。
