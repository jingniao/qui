**结论：通过（第二轮，2026-11-11 02:41–02:56 UTC）。** 第一轮（2026-11-10 18:36–18:43 UTC）因普通安装的 Agent 从未进入受管模式而阻塞；按[修复方案](v1.5.0-agent-supervision-plan.md)修复（提交 `e847eb0`、`5fca8a9`）后，在 Alpine/OpenRC 与 Debian/systemd 上重跑，启用、失败退回与三个规定场景全部符合预期。

唯一远程目标为本地测试机 `192.168.5.36`；未访问生产主机，未使用 `~/.qui-accept`。签名私钥只经管道写入测试机 0600 文件，签名结束由 `shred -u` 销毁，复查不存在；登记码同样用后销毁。报告不含私钥、登记码与会话。

## 1. 第一轮阻塞（摘要）

## 3. Alpine/OpenRC 结果

| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 起点 | 第一轮留下的旧构建 1.5.0，普通模式 | 在线，`agentUpdateSupported=false` |

| B1 初始化失败 | `releases/` 设为 0500 后运行 `qui-update` | 走“已是最新版本”分支调用启用；Agent 报 `mkdir …/agent-installed: permission denied`，自行清理，未留 pending；脚本打印“网页升级未启用…失败现场在 …/web-upgrade-failed-20261111T024545Z”，退出码 0；节点普通模式在线 |

| A 启用 | 再运行一次 `qui-update --component agent` | 受管标记、安装历史、基线镜像建立，无 pending；`agentUpdateSupported=true`；`rc-service proxy-agent restart` 后日志 `supervised Agent runtime started`，worker 为 `releases/agent-installed/proxy-agent-399e1d1a….bin --managed-worker` |

| 场景 2 文件损坏 | 把目录里 `28cba49f….bin` 中间一个字节取反（摘要变为 `97a9be22…`），排队 1.5.2 | `rejected`，代码 `download_failed`；节点仍 1.5.1 在线 |
| 场景 3 健康失败 | 排队 1.5.3（探针兼容、正常运行即退出 42 的静态程序） | `rolled_back`，代码 `rolled_back`，装回 1.5.1（摘要、序号一致）；节点在线 |

说明：

- 摘要校验在 Agent 下载候选（`updater.Downloader.FetchExpected`）时执行，失败统一报固定码 `download_failed`；协议没有单独的“摘要不符”码，属设计如此。
- 场景 2、3 期间各有一次控制连接断开 1–2 秒（`persistent store is locked by another process`）后自动重连，节点状态与修订不变。记为观察项，不影响结论。
- `/usr/local/bin/proxy-agent --version` 在受管后始终是引导程序版本 1.5.0；实际运行版本以面板 `agentVersion` 与 worker 镜像为准，与文档一致。

## 5. 结论与后续

- 启用路径、失败退回、中断清理、成功升级、损坏拒绝、健康失败回滚在 OpenRC 与 systemd 上均符合预期。
- 生产 ≤1.4.7 主机需要运行两次 `qui-update --component agent`：第一次由旧脚本升到 1.5.0，第二次启用网页升级（面板提示会一直显示到启用为止）。新装节点由 `node-install.sh` 自动启用（该函数调用与 qui-update 相同，本轮未单独实机执行 `node-install.sh`）。
- 测试机遗留：`/root/qui-alpine-accept/v150-release/` 下的构建、签名材料与证据；`/root/qui-sysd-accept/`；容器内失败备份目录 `web-upgrade-failed-20261111T024545Z`（空目录）。均不影响其他环境。
