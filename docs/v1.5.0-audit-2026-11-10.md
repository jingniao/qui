## 发现

优先级：P1 为发布前应先解决的阻断或主要功能失效；P2 为应在版本验收前修复的正确性问题。下列行号对应本报告的审计快照。

### A01 · P1 · GitHub Actions 工作流不是合法 YAML

位置：`.github/workflows/check.yml:217`、`:226`、`:243`。

三个多行 `run` 的头部被写成 `run: |\`。YAML 块标量头不允许该反斜杠；用仓库现有 `yaml` 包解析得到三个 `Block scalar header includes extra characters` 错误。GitHub 无法正常加载工作流，`check`、真实核心与 Release 签名流程都受影响。前端及 Go 包单测不会发现此问题。

### A02 · P1 · 外部规则刷新成功，真实节点策略却静默丢失规则

位置：`internal/platform/server/server.go:320`、`:324`；`internal/panel/policy/external_sources.go:200`；`internal/panel/policy/service.go:151`。

服务器创建 `policy.Repository` 时未传 `configurationVault`，只给 `SourceRefresher.Vault` 赋值。因此刷新能加密写入缓存，`lastStatus=ok`、条目数正常；生成节点策略调用 `Repository.SourceEntries` 时却返回 `vault unconfigured`。`Service.resolve` 又只在 `err == nil` 时合并，不传播该错误。只有外部来源的规则会被关闭，混合规则只剩手写条目，可能漏掉应阻断或分流的目标。

隔离复现输出：

```text
server_wiring_refresh: status=ok entries=1
server_wiring_read_cache_error: vault unconfigured
```

同一装配还没有赋值 `policy.Service.NodeCapabilities`，所以 `Service.Save` 中的关键字能力预检分支不会执行；快照/发布阶段的已有门禁不能替代保存时的门禁。

### A03 · P2 · 恢复后的通知状态没有从数据库删除，恢复通知每轮重发

位置：`internal/panel/notification/evaluator.go:101`、`:205`、`:309`；`internal/panel/notification/repository.go:392`。

评估器通过 `delete(next, key)` 结束离线、资源占用、流量告警；`SaveStates` 却只 upsert `next` 中的行，不删除缺失行。下一轮从数据库又读到 `active=true`，重新发恢复通知。工作循环每 60 秒运行，会持续产生恢复通知；之后再次出现异常时也沿用旧状态和冷却时间。

已复现：首次恢复事件数 1，保存后数据库仍为 active，再次评估正常节点又产生恢复事件 1。现有评估器单测在内存中传递状态，未覆盖这一持久化往返。

### A04 · P2 · 更换外部规则 URL/格式/行为后，旧缓存仍冒充新来源

位置：`internal/panel/policy/external_sources.go:98`、`:142`。

已有来源只按 ID 保留状态、计数、成功时间和缓存，既不读取也不比较旧 URL/format/behavior。Owner 修改来源后，页面仍显示成功；在新来源刷新前，节点会用旧列表，mihomo 则按新 URL 拉取，造成两端规则不一致。若新 URL 持续抓取失败，旧列表仍长期存在。

已复现：URL 已变为 `https://new.example.com/rules`，状态仍为 `ok`，`SourceEntries` 仍返回 `old.example.com`。现有 `TestSaveSourcesKeepsCacheForSameID` 甚至明确断言“改 URL 后保留旧成功状态和缓存”；这属于测试固化错误语义，不能以该测试通过为验收依据。

### A05 · P2 · 公网 IP 通知不遵守冷却，最后一个地址消失也不通知

位置：`internal/panel/notification/evaluator.go:232`、`:235`。

公网 IP 分支发送后从未将状态置为 active，每次变化都会命中 `!st.Active`，绕过默认 30 分钟冷却。同时 `currentVal != ""` 排除了“候选地址从非空变为空”的情况，遗漏规划要求的地址消失通知。

已复现：相隔一分钟的两次 IP 变化均发送通知，随后删除最后一个地址产生 0 条事件。

### A06 · P2 · TCP 缓冲三元组与最大值的契约没有在前端统一

位置：`web/src/modules/nodes/components/detail/serverTuningModel.ts:169`、`:213`、`:250`。

helper/心跳的 `tcp_rmem`、`tcp_wmem` 是完整三元组，例如 `4096 131072 8388608`，草稿与期望则只存最大值 `8388608`。`keyStatus` 直接比较字符串，正确应用也永久显示漂移；“纳入面板管理”又把外部完整三元组复制进只接受整数的草稿，确认提交时报参数越界。

两种行为都已在实际前端模型中复现。需要在比较和纳管时统一提取三元组的最大值，保留 helper 负责其余两项的现有边界。

### A07 · P2 · 只读参数仍可进入草稿、预设与提交

位置：`web/src/modules/nodes/components/detail/ServerTuning.vue:277`、`:280`；`serverTuningModel.ts:160`。

`availableKeys` 只检查 `present`，没有检查 Agent 已上报的 `writable`；状态函数也只识别“不存在”，不识别“存在但只读”。容器内只读参数仍可编辑、被预设填入，并通过提交过滤。实际 helper 写失败会回滚整份请求，破坏“只提交该环境可用参数”的要求。

已复现：`present=true,writable=false` 的键被标为 `default`；源代码中的提交集合仍包含该键。

### A08 · P2 · 动态算法列表与提交校验仍不一致

位置：`web/src/modules/nodes/components/detail/serverTuningModel.ts:185`、`:250`、`:263`；`ServerTuning.vue:111`。

下拉框按服务器能力生成，可列出合法的 bbr2/bbr3；提交却仍用旧静态 `field.choices` 校验，不含二者。已复现“服务器上报 bbr3 → 下拉可选 → 提交报参数越界”。

预设也只按 sysctl 键是否存在过滤，不检查预设中的 bbr/fq 是否为该机已可用或可加载算法。没有 bbr 的机器仍会被通用预设填入 bbr，最终 Agent 拒绝整份配置。

### A09 · P2 · 文件句柄展示读取了不存在的字段

位置：`web/src/modules/nodes/components/detail/ServerTuning.vue:269`；`web/src/modules/nodes/api.ts:164`；`proto/agent.proto:75`、`:98`。

实际协议为 `fd_limits`/JSON `fdLimits`，是 `ProcessLimit{name,soft,hard}` 列表，包含 Agent 和核心进程。前端却定义并读取 `agentLimits/agent_limits` 的 `fdCur/fdMax`，没有相应后端转换。新版 Agent 正常上报时页面仍显示“—”，也没有展示各核心限制，无法满足与 `/proc/<pid>/limits` 对照的验收项。

### A10 · P2 · “重启后保持”没有重启证据

位置：`web/src/modules/nodes/components/detail/ServerTuning.vue:306`。

该标签条件仅是“至少一项由面板管理且没有漂移”，没有记录/比较应用时与当前的 `bootId`。刚应用成功、从未重启的主机也会被标为“重启后保持”。这超出了当前数据能证明的结论；应区分当前一致与经过开机标识变化后仍一致。

### A11 · P2 · 超过 15 分钟的 CPU/内存持续阈值无法正常触发

位置：`internal/panel/notification/model.go:22`；`worker.go:82`；`evaluator.go:148`。

API 允许持续时间达到 1440 分钟，工作循环固定只取最近 15 分钟采样，评估器又要求 `len(samples) >= DurationMinutes`。配置为 30/60 分钟等合法值后，窗口永远凑不齐，持续高占用也不告警。此外采样时间戳在装配时被丢掉，跨缺测间隔的几个样本可能被当作连续窗口。这需要按真实时间窗口评估，而非只按样本数量。

### A12 · P2 · 新数据的备份校验未达到文档所称覆盖范围

位置：`internal/panel/system/backup/inspect.go:412` 附近；`AGENTS.md:1383`、`:1384`。

备份入口新增了地址和通知校验，但没有外部规则来源/密封缓存的校验入口，也没有 `validateTuningDismissals` 实现。全仓库检索该函数只有文档描述；`service_set_sources` 在备份包只出现于回退测试夹具。全库备份会携带这些表，但“表被带上”不等于“缓存能以归档 Vault 解密、结构和引用有效已校验”。本轮未制作损坏归档来复现接受结果，此项依据为校验代码路径缺失。

P7 文档还把实际的 `(node_id,key)`、`value` 和带宽上限 `100000` 写成 `(node_id,rule_key)`、`dismissed_value`、`1000000`，并声称不存在的校验函数已工作，应与实现一起修正。

- P7 Task 9 要求测试机重启、覆盖配置导致漂移、清除恢复、systemd 沙箱及 OpenRC 实测。当前文档没有足以对这些逐项复核的结果；“先前以 root 写 sysctl 的实验”不能替代这些验收。

- 本地没有 `v1.5.0` tag，未找到当前同一快照的 Linux 完整门禁与 GitHub check/cores 成功记录。本轮没有查询或修改生产，也未核实 GitHub Secret 是否已配置。
