## 1. 审计结论

**当前版本不满足发布条件。P1–P7 均已提交实现，但不能标记为“全部验收完成”。**

较前一份静态审计，本次增加了测试机上的全仓库检查、真实核心检查、实际 HTTP 权限测试、真实浏览器、完整加密归档检查、真实内核/helper 与双客户端端口跳跃验证。确认了原报告的主要缺陷，并新增 systemd 写路径缺失、调优错误不可见、证书异步结果串用、签名版本绑定不足和依赖安全基线问题。

最优先处理四项功能/流程阻断：

1. GitHub 工作流不是合法 YAML，CI 和 Release 无法按现状执行。
2. 外部规则缓存没有接入真实策略装配，页面刷新成功而目标仍走默认出口。
3. P7 的 systemd 单元没有开放新调优参数的写路径，实际采用推荐会失败。
4. 能力门禁放过禁用实体的新字段，旧 Agent 仍会因严格解码拒绝整份发布。

另外，测试机 Go 1.26.0 构建的安全扫描命中已知漏洞及调用路径，需在发行构建工具链和依赖层面消除命中，不能仅凭功能测试通过放行。扫描命中不等同于已经证明远程可利用。

## 5. 缺陷清单

P1：发布前优先处理的主要功能、安全基线或流程阻断。P2：在版本验收前应修复的正确性缺陷。依赖项以扫描覆盖与调用上下文解释，不作未验证的利用结论。

### A01 · P1 · CI/Release 工作流不是合法 YAML

位置：`.github/workflows/check.yml:217,226,243`。

三处 `run: |\` 含非法块标量头。仓库现有 YAML 解析器确认 3 个错误，基准版本为 0。GitHub 不能正常加载该工作流；本地 shell/Go 检查不检查工作流 YAML，所以本地门禁通过也无法抵销本项。

### A02 · P1 · 外部规则刷新成功，但未进入真实策略

位置：`internal/platform/server/server.go:320,324`；`internal/panel/policy/external_sources.go:200`；`internal/panel/policy/service.go:151`。

`policy.Repository` 没有配置 Vault，只有刷新器拥有 Vault。缓存写入成功，读取却返回 `vault unconfigured`，`resolve` 吞掉读取错误，导致规则被关闭或只保留手写条目。

除代码级复现外，本次从真实 HTTPS 抓取规划中的 OpenAI.list，接口返回 `ok`/34 条；另外用正确 Vault 解密确认其中确有 chatgpt.com 条目。创建 Block 策略成功，但真实 HTTP 模拟 `chatgpt.com` 返回 `matched=false`、`Direct`、`no matching policy`。这是漏阻断/漏分流，不能按“抓取成功”认定功能完成。

相同服务器装配还遗漏 `policy.Service.NodeCapabilities`，保存时的关键字能力预检永不执行；快照/发布的现有门禁仍有效，但不是保存门禁的替代品。

### A03 · P2 · 恢复通知状态未从数据库删除

位置：`internal/panel/notification/repository.go:392`，`evaluator.go:101,205,309`。

Evaluate 在恢复时删除内存状态；SaveStates 只 upsert，未删除数据库旧行。下次读出仍 active，再发送一次恢复。Linux 隔离库复现：`first=1, persisted_active=true, repeated_recovery=1`。影响离线、资源、流量规则及下一次异常的冷却计算。

### A04 · P2 · 改 URL/格式/行为仍沿用旧来源缓存

位置：`internal/panel/policy/external_sources.go:98,142`。

保存只按 ID 保留旧状态、时间、计数和缓存，没有比较来源身份。已复现新 URL 显示 `ok`，节点仍读出旧域名；mihomo 则从新 URL 拉取，形成客户端/节点不一致。现有测试明确认可了改 URL 后保留缓存，需修正测试语义。

### A05 · P2 · 公网 IP 通知绕过冷却并遗漏全量消失

位置：`internal/panel/notification/evaluator.go:232,235`。

公网 IP 分支没有将发送后的状态置为 active，连续变化每次都绕过 30 分钟冷却；条件又排除了空候选，最后一个地址消失不通知。Linux 复现：两次相隔一分钟的变化各产生 1 条，最后地址删除产生 0 条。

### A06 · P2 · TCP 缓冲三元组与单值契约不一致

位置：`web/src/modules/nodes/components/detail/serverTuningModel.ts:169,213,250`。

当前值为 `4096 131072 8388608`，期望为最大值 `8388608`。直接字符串比较导致正确应用也被标为漂移；外部纳管又复制完整三元组到只接受整数的草稿。模型复现及真实浏览器均确认。见证据截图的 tcp_rmem/tcp_wmem 行。

### A07 · P2 · 可用性过滤遗漏只读标志

位置：`ServerTuning.vue:277,280`，`serverTuningModel.ts:160`。

只按 present 过滤，忽略 writable。已上报 `present=true,writable=false` 的参数仍显示默认、输入可编辑、可进入提交；helper 一键应用按事务回滚，单个不可写参数会拖累整份请求。浏览器 fixture 的只读 rmem_max 行仍可编辑。

### A08 · P2 · 算法下拉、预设与提交校验不一致

位置：`serverTuningModel.ts:185,250,263`；`ServerTuning.vue:111`。

动态列表可展示服务器真实提供的 bbr2/bbr3，提交仍按旧静态 choices 拒绝。已复现 bbr3 可选却报越界。预设只按键存在过滤，不按算法可用/可加载过滤，没有 bbr/fq 的主机也会被填入该值。

### A09 · P2 · 文件句柄字段与协议不匹配

位置：`ServerTuning.vue:269`；`web/src/modules/nodes/api.ts:164`；`proto/agent.proto:75,98`。

真实契约为 `fdLimits[]`（name/soft/hard），前端读取不存在的 agentLimits.fdCur/fdMax。浏览器通过真实 API 收到 Agent/核心各 `524287/524287` 的 fixture，页面仍显示“—”；核心进程列表也未展示。

### A10 · P2 · 无重启证据却显示“重启后保持”

位置：`ServerTuning.vue:306`。

条件仅为 panel 项大于零且无 drift，没有保存和比较应用时/current boot ID。未重启的主机也会得到已验证重启保持的结论。需将当前一致与经过重启验证区分。

### A11 · P2 · 合法长持续窗口无法触发占用告警

位置：`internal/panel/notification/model.go:22`；`worker.go:82`；`evaluator.go:148`。

API 可设到 1440 分钟，worker 固定只取 15 分钟，evaluator 按样本数凑持续分钟数。30/60 分钟等合法配置无法满足；时间戳在适配层丢弃，缺测间隔也无法被识别。应验证真实连续时间，不能只计样本个数。

### A12 · P2 · 完整归档检查接受新表的非法数据

位置：`internal/panel/system/backup/inspect.go`；`AGENTS.md:1383,1384`。

本次已将上一份报告中的静态缺口提升为完整归档复现：

- 使用仓库 sourceFixture 创建有效基础库，写入无法由 Vault 打开的外部规则缓存，Create 后 Inspect 完整加密归档仍成功。
- 插入非白名单 `kernel.arbitrary_unknown` dismissal，完整归档检查仍成功。

两个针对“必须拒绝”的独立回归均失败。文档声称存在的 `validateTuningDismissals` 在源码中不存在。文档还把实际的 `(node_id,key)`/`value`/带宽上限 100000 写成 `(node_id,rule_key)`/`dismissed_value`/1000000。

### A13 · P2 · 签名有效不等于用户所选版本匹配

位置：`internal/panel/deployment/agent_releases.go:378` 附近；`NodeVersionPanel.vue:1346` 附近。

Import 核对签名、组件和架构，却不核对 manifest.version/sequence 与所选正式版。独立回归把有效签名 1.4.6/1004006 放在 1.5.0 的附件名下，Import(1.5.0) 成功返回旧版本，并按所选序号写目录。

界面找不到所选版本时又退回“同平台任意版本”，进一步隐藏了错误。实际 Agent 的签名和反重放边界未被绕过；后果可能是错误目标或目录不匹配导致更新失败，不能把此项描述为任意二进制执行。

### A14 · P1 · systemd 沙箱未随新白名单扩展

位置：`deploy/systemd/proxy-agent-tuning.service:27–34`。

`ReadOnlyPaths=/proc/sys` 下只开放旧参数，新六项没有 ReadWritePaths。真实实验使用不变 Helper 实现、独立网络命名空间和临时配置目录：

### A15 · P2 · 调优错误被记录但不在界面展示

### A19 · P1 · 禁用实体仍携带旧 Agent 不认识的新字段

位置：`pkg/contracts/desiredstate/port_hop_gate.go:14`、`keywords.go:18`；`internal/panel/proxy/snapshot.go`；`internal/panel/policy/service.go:165`；`internal/panel/deployment/repository.go:253`。

两个门禁只检查 enabled 项，而快照保留禁用入站/策略，Pending 又按原样 JSON 序列化。旧 Agent 的 DisallowUnknownFields 在处理 enabled 语义之前就拒绝新字段。

本次另行归档 v1.4.7 的实际类型，做当前/旧版本联测：

```text
disabled_hop_capability_error=<nil>
disabled_keyword_capability_error=<nil>
current_decode_disabled-hop=<nil>
current_decode_disabled-keyword=<nil>
v1.4.7_strict_decode_disabled-hop=json: unknown field "hop_port_start"
v1.4.7_strict_decode_disabled-keyword=json: unknown field "keywords"
```

因此不是简单的“禁用后不会渲染”：禁用对象会先使整份配置解码失败。先升级面板、后逐台升级 Agent 的过渡阶段，以及 Agent 回滚后，都可能阻塞后续发布。应按序列化字段门禁，或在旧 Agent 的快照中安全移除不支持字段/实体；三处门禁必须一致。当前 keywords/port-hop 单测明确期望禁用项放行，需补真实旧解码器联测来纠正这一盲点。
