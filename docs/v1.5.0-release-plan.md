## 3. 出问题时怎么办

| 情况 | 处理 |
| --- | --- |
| 小缺陷：只涉及一个模块、无迁移、改动几十行内、修复方式明确 | 派 Codex 修复并补一个回归测试，`bash scripts/quick-check.sh` 通过后继续，不另行请示 |
| 门禁失败 | 按 `docs/release-runbook.md` 4.2 节：只重跑失败的包一次；重跑通过且与本批改动无关记为偶发；再次失败按“小缺陷”修复后，对新提交重跑门禁 |
| 测试本身写错（脚本问题，不是产品问题） | 修正脚本重做该步骤，报告里如实记录 |
| **停下来报告 Owner**：需要迁移或大改、安全问题、Agent 网页升级的签名/回滚链路有缺陷、GitHub Secret `AGENT_SIGNING_KEY` 不存在、tag 推送后 Release 任务失败 | 停止后续阶段，不删除已推送的 tag，写清现象、证据与建议 |

## 6. 阶段 1：Agent 网页一键升级实机验收

目的：在测试机上走通“面板托管签名目录 → 网页排队 → Agent 校验、切换、健康检查”的链路。只测三种情况：成功升级、文件损坏被拒、健康检查失败回滚。

**环境（复用已有）：**

- 隔离面板：`/root/qui-alpine-accept/panel/`（配置、数据库、Owner 密码文件）。
- Alpine/OpenRC 容器：`/root/qui-alpine-accept/container.sh` 启停，节点已登记。
- 官方公钥已内置在当前代码里（`pkg/contracts/release/official.go`），与本地私钥配对，所以**面板与 Agent 都不需要配置 `release_keys`／`updates`**，走的就是默认目录路径。

**步骤：**

1. 用当前 HEAD 的树在测试机构建两份发布包：`VERSION=1.5.0` 与 `VERSION=1.5.1`（只在测试机本地，不发布）。
2. 面板换成 1.5.0 包里的 `proxy-panel` 二进制（同一配置与数据库），启动；容器内 `qui-update --component agent --version 1.5.0 --bundle … --sums … --yes`，确认面板显示 Agent 1.5.0 在线，能力里 `panel_catalogue_supported=true`。
3. 把本地私钥用管道写到测试机 0600 文件，用 `scripts/sign-agent-release.sh 1.5.1 <1.5.1 发布目录> <私钥文件>` 生成 `proxy-agent-1.5.1-linux-amd64.bin` 与 `.manifest.json`。
4. 按面板导入时的目录布局放入签名目录 `<面板数据目录>/releases/agent-catalogue/`：`proxy-agent/linux/amd64/1005001/manifest.json` 与 `artifacts/<sha256>.bin`（布局以 `internal/panel/deployment/agent_releases.go` 的 `Import` 为准）；再用 `POST /api/v1/releases`（Owner＋CSRF）登记这份签名清单。
5. **成功升级**：`POST /api/v1/agent-updates`（或页面“Agent 管理”的升级按钮）向该节点排队 1.5.1。期望：任务成功，面板显示 Agent 1.5.1 在线，容器内 `proxy-agent --version` 为 1.5.1。

7. **健康检查失败回滚**：准备 1.5.3，二进制换成一个启动后立即退出的小程序（静态编译，`go run ./cmd/release sign` 直接签名，序号 1005003），登记、排队。期望：Agent 切换后健康检查失败，自动回滚到 1.5.1 并保持在线，任务记为失败或已回滚。
8. 清理：删除测试机上的私钥副本（`shred -u`）；停止面板与容器；签名目录与测试版本留在 `/root/qui-alpine-accept/` 下不影响任何东西，不必删除。

**通过标准：** 第 5、6、7 步结果都符合期望。
