## 1. 规则集页面不能用关键字和外部来源，且编辑会清掉关键字

> **状态：已实现（2026-11-11，未提交）。** 共享组件 `web/src/modules/routing/components/ServiceSetEditor.vue`，两个页面都用它，旧副本删除；保存总是携带 `keywords` 与 `sources`；规则集列表显示外部来源数量与抓取状态、关键字计数。类型检查、构建与前端自检通过；浏览器走查未做。

> 来源：Owner 2026-11-11 反馈（「分流控制 → 规则集」创建对话框里看不到引入外部规则集的地方）。

### 现状

v1.5.0 的规则集关键字条目与外部来源（[v1.5.0 规划](v1.5.0-plan.md)第 9 项）只做进了「客户端策略 → 编辑配置 → 规则集」里的对话框（`web/src/modules/routing/pages/ClientPolicyPage.vue`，模板约 2135–2339 行，脚本约 4206–4400 行）。独立的「分流控制 → 规则集」页面（`web/src/modules/routing/pages/ServiceRulePage.vue`，路由 `/routing/services`）有自己的一份对话框副本，没有同步：

| 位置 | 关键字条目 | 外部来源 |
| --- | --- | --- |
| 客户端策略 → 编辑 → 规则集 → 创建／编辑 | 有 | 有（含刷新与抓取状态） |
| 分流控制 → 规则集 → 创建／编辑 | 无 | 无 |

更严重的是数据丢失：后端保存规则集时先 `DELETE FROM service_set_entries` 再按请求重写全部条目（`internal/panel/policy/repository.go` 的 `SaveService`），而 `ServiceRulePage.vue` 的表单只带 `domains`／`suffixes`／`cidrs`，不带 `keywords`。所以在客户端策略里加过关键字的规则集，**在规则集页面打开再保存，关键字会被全部清空，没有任何提示**。外部来源不受影响：请求不带 `sources` 字段时后端保留原值（`Sources *[]SourceInput`，`omitempty`）。

v1.5.0 浏览器走查只检查了客户端策略里的那份对话框，因此漏掉了这个页面（见 [v1.5.0 浏览器走查](v1.5.0-browser-walkthrough.md)）。

**临时规避（发布 1.5.1 前）：** 带关键字或外部来源的规则集只在「客户端策略 → 编辑 → 规则集」里编辑，不要在「分流控制 → 规则集」里保存。

### 方案

- 把客户端策略里完整的规则集对话框（名称、说明、启用、精确域名、后缀、**关键字**、IP/CIDR、**外部来源**的增删与「刷新」、抓取状态与失败原因、已保存引用、禁用提示、删除确认）抽成共享组件，例如 `web/src/modules/routing/components/ServiceSetEditor.vue`，两个页面都用它。去掉 `ServiceRulePage.vue` 里的旧副本，以后只有一份，不会再出现一边改了一边没改。
- 保存请求总是带完整的 `keywords` 与 `sources`（来源在编辑时回填），避免任何入口因漏带字段清空数据。
- 后端兜底不做：两个入口共用编辑组件且总是携带 keywords 与 sources。
- 规则集列表的「来源 / 版本」列显示外部来源数量与最近抓取状态（成功／失败／待抓取），对应 v1.5.0 规划第 9 项「页面为每个外部来源标明客户端可用／节点可用，显示最近抓取时间、条目数与失败原因」。列表的「匹配规模」把关键字数量也算进去。
- 后端不改接口；如审查认为有必要，可让 `SaveService` 在请求省略 `keywords`（JSON 中缺失而非空数组）时保留原关键字，作为对旧客户端的兜底。是否采用在实施时决定并写进说明书 §27.7。

### 验收

- 两个页面都能新建带关键字与外部来源的规则集；外部来源能刷新并显示状态。
- 回归：在客户端策略里建一个带关键字和外部来源的规则集，到规则集页面打开再保存，关键字、来源与其缓存都保留；反过来也一样。前端自检加断言：两个页面使用同一个编辑组件，保存载荷包含 `keywords` 与 `sources`。
- 浏览器走查覆盖「分流控制 → 规则集」页面本身（创建、编辑、刷新来源、列表状态列、最小字号 12px、无 `pageerror`）。

## 2. 受管 Agent 无法发布指定核心的入站（`apply_failed`）

> **状态：已实现（2026-11-11，未提交），待测试机受管节点实测。** 上层进程在启动 worker 前用已打开的发布历史证明并升级存储格式（`agenthost.raiseFormats`、`updater.(*History).CheckActivation`）；受管 worker 不再自行证明，发布前地板已升级即跳过（`control/inventory_formats.go`）；`Reconciler.Apply` 提前失败带固定码 `storage_preflight_failed`／`revision_store_failed` 并记 WARN 日志，面板页面加了中文标签。`ApplyResult` 协议没有原因字段，原因只进 Agent 日志，本版不改协议。单元测试只覆盖函数级（地板已升级跳过、未升级才检查、上层进程无操作与任务未空闲拒绝、提前失败带码），持锁下的真实复现与上层进程升级成功路径须在测试机实测。核心启动失败时保留 stderr 末尾的诊断本版不做，延后。

> 来源：Owner 2026-11-11 反馈「创建代理失败」，在 Owner 的面板＋Agent 合装主机 5.45.96.43（「德国 netcup」，Debian 13，面板与 Agent 均为 1.5.0）上实机诊断。

### 现象

Agent 于 2026-11-11 05:44 UTC 按「运行两次 `qui-update --component agent`」启用网页升级（受管模式）。此后在该节点新建 Hysteria2 入站（`core = sing-box`，ACME 证书）并发布，修订 13、15–19 全部 `apply_failed`，每次约 2 秒即失败并保持原配置；Agent 与面板日志都没有任何原因。草稿里的这个入站会被每次手动发布一起带上，所以之后新建的 VLESS 入站（`core` 为空）也一起失败。自动额度版本（修订 14、20）以已发布状态为基线、不含该入站，因此照常成功。同一节点在 2026-11-09 尚未进入受管模式时，Hysteria2 入站发布成功（修订 8–10）。

### 根因

1. `internal/agent/control/control.go` 的 `PrepareStorage`（约 369–386 行）只要发现任何入站的 `Core` 非空（启用与否都算），就调用 `agenthost.CheckMultiCoreActivation`。
2. 受管模式下它走到 `updater.CheckIdentityActivation`（`internal/agent/updater/identity_preflight.go`），后者经 `historyHandles` 对 `agent-release-history/.history.lock` 与 `identity/agent-release-checkpoint.enc.lock` 执行 `filelock.Try`（`internal/agent/updater/history.go` 约 159–162 行）。
3. 这两把锁由受管模式的上层进程（`/usr/local/bin/proxy-agent`）在 `agenthost/host.go` 约 81 行 `updater.OpenHistory` 打开后**长期持有**；实际执行配置的 worker 子进程拿不到锁，得到 `filelock.ErrBusy`（`persistent store is locked by another process`）。
4. `Reconciler.Apply`（`internal/agent/reconcile/reconcile.go` 约 224–227 行）对 `PrepareStorage` 的错误不设 `Code`、不写 `Message`，也不建修订目录；`control.go` 约 739–741 行把空码统一映射成 `apply_failed`，错误本身不进日志。

实机证据：用 v1.5.0 源码（`d823018` 之后无 Go 改动）编译只读诊断程序，以 `proxy-agent` 账号在该主机调用 `CheckMultiCoreActivation`，返回 `persistent store is locked by another process`；`/proc/locks` 显示两把锁的 FLOCK WRITE 属于上层进程 PID。用同一 sing-box 1.14.4、同一 UDP 36122 端口手动启动最小 Hysteria2 配置正常，排除端口、二进制、权限与证书。该节点的存储契约在 11-09 已升到多核心格式（Configuration 写 4、DesiredState 写 3、Spool 写 6、ReleaseHold 写 3），这次检查本是多余的。诊断程序已从主机删除，主机未做任何改动。

### 影响

- 所有受管 Agent：从 ≤1.4.7 运行两次 `qui-update` 启用网页升级的节点，以及 1.5.0 `node-install.sh` 新装（自动受管）的节点。只要草稿里有显式 `core` 的入站（sing-box 的 Hysteria2／TUIC、GOST 转发、显式写 `xray` 的入站），该节点所有手动发布都失败。
- **生产升级到 1.5.0 前必须先修复**：生产三台若有显式核心的入站，升级并启用网页升级后将无法再发布这些节点。
- v1.5.0 网页升级验收（[验收记录](v1.5.0-agent-web-upgrade-verification.md)）没有覆盖「受管模式下发布带显式核心的入站」。

**临时规避（发布 1.5.1 前）：** 受管节点不要新建或保留显式核心的入站；已卡住的节点删除从未发布成功的那个入站（仅禁用不够，检查会计入禁用入站）后再发布。需要 sing-box 协议的节点暂不启用网页升级。

### 方案

> 2026-11-11 复核补充：worker 启动时（`control.go` 约 319、337 行）在存储地板尚未升级时同样调用 `CheckCoreAccountingActivation`／`CheckMultiCoreActivation`，受管模式下也会撞锁，导致 worker 无法启动；而第 4 项的安装器只等存储基线文件出现，基线写出（约 308 行 `storage.Ensure`）与格式升级（约 341 行）之间若被停服务，受管 worker 就会在启动时失败。因此采用：**受管模式下由上层进程在启动 worker 之前，用它已打开的发布历史完成镜像兼容性证明并升级核心计量与多核心存储格式**；worker 在地板已升级时跳过检查（启动与发布前两处一致）。

- 修掉锁冲突：受管模式下由持有发布历史的上层进程完成镜像兼容性检查（经已有的监督通道交给 worker 结果），或 worker 复用上层已校验的结论；不得让 worker 再次 `filelock.Try` 上层长期持有的锁。另外，当存储契约已包含多核心写格式时直接跳过激活检查（`ActivateCoreInventoryFormats` 本就是无操作），作为最小兜底。实施时一并排查 worker 内其他打开发布历史的调用（例如 `control/core_installation.go` 的 `updater.OpenHistory`）以及 `CheckCoreAccountingActivation` 是否有同样问题。
- 补上诊断缺口：`Reconciler.Apply` 的早期错误（`PrepareStorage`、存储写入、vault 等）给出固定错误码（例如 `storage_preflight_failed`）与简短原因，写一条 WARN 日志并经 `ApplyResult` 回传面板显示；sing-box／Xray 启动失败时保留核心 stderr 的末尾若干行用于日志（不进面板、不含凭据）。

### 验收

- 回归测试：受管模式（上层持有发布历史锁）下，worker 应用带 `core = sing-box` 入站的修订成功；存储契约尚未升级与已升级两种初始状态都覆盖。
- 早期错误路径的单元测试断言错误码、WARN 日志与 `ApplyResult` 原因都存在。
- 实机：在 5.45.96.43 升级到 1.5.1 后，发布 Hysteria2（sing-box、ACME 证书、可选端口跳跃）与 VLESS 入站成功，客户端连通；另在一台新装（`node-install.sh` 自动受管）节点上重复一次。
- 把「受管 Agent 发布显式核心入站」加入网页升级验收清单。

## 3. 安装命令对话框去掉面板地址与端口输入

> **状态：已实现（2026-11-11，未提交），待随 1.5.1 发布。** quick-check（web＋text）通过。

> 来源：Owner 2026-11-11 反馈（新建服务器的「一键安装命令」对话框截图，圈出「面板地址」「面板 Web 端口」两个输入框）：去掉，统一使用后台设置的或默认的。

### 现状

「新建服务器」（`web/src/modules/nodes/components/ServerEnrollment.vue`）与「原位身份恢复」（`web/src/modules/nodes/components/NodeRecoveryPanel.vue`）的安装命令对话框各有可编辑的「面板地址」「面板 Web 端口」，默认值取「系统设置 → 节点安装连接地址」，未设置时取浏览器地址，在对话框里改只影响本次命令。版本页「添加内核」（`NodeVersionPanel.vue`）已经只读取默认值，没有输入框。

### 方案

- 去掉这两个对话框里的面板地址与面板 Web 端口输入框，命令一律用 `resolveInstallEndpoint()` 的结果：已保存的设置优先，逐项回落到浏览器地址与端口；Agent gRPC 地址与端口规则不变。「运行内核」选择保留。
- 对话框用一行只读文字显示命令实际使用的面板地址与端口及来源（系统设置／当前浏览器地址），并提示要改请到「系统设置 → 节点安装连接地址」。去掉「在此修改只影响本次命令，不写回设置」的说明。
- 同步说明书 §11.3、§27.14 与[安装指南](install-guide.md)里「对话框内可改、只影响本次命令」的描述。

### 验收

- 两个对话框都没有地址／端口输入框；保存了安装连接地址时命令使用保存值，未保存时使用浏览器地址与端口；改完系统设置后重新打开对话框即生效（同一页面会话内的缓存在保存设置时已清除）。
- 前端自检断言两个对话框不再有 `v-model` 绑定的面板地址／端口输入，三个对话框仍经 `resolveInstallEndpoint()` 取值。

## 4. 安装命令可选是否启用网页升级

> **状态：已实现（2026-11-11，未提交），待随 1.5.1 与第 2 项一起发布。** `node-install-test.sh` 54/54 与 quick-check（text＋web＋deploy）通过；实机验收未做。勾选框为共享组件 `web/src/modules/nodes/components/WebUpgradeOption.vue`。

> 来源：Owner 2026-11-11：在安装弹窗上加一个勾选框，勾选后以后可以直接在网页上更新 Agent，不需要再去服务器运行一次 `qui-update --component agent`；不勾选就还是原来的逻辑。

### 现状

1.5.0 的 `deploy/linux/node-install.sh` 在登记并启动 Agent 后总是调用 `agent_enable_web_upgrade`（`deploy/linux/service.sh`），新装节点一律进入受管模式，没有关闭的选项。之后要启用网页升级的已有节点在本机运行 `qui-update --component agent`（`update.sh` 同样调用 `agent_enable_web_upgrade`，无新版本可装时也会启用）。

### 方案

- `node-install.sh` 新增无参数开关 `--web-upgrade`：带上时安装完成后调用 `agent_enable_web_upgrade`（失败只提示、不让安装失败，与现在一致）；不带时不启用，并在结尾提示「网页升级未启用；需要时在本机运行 `qui-update --component agent`」。默认不启用，即不勾选＝原来需要手动 `qui-update` 的逻辑。
- 三个生成安装命令的弹窗（新建服务器、原位身份恢复、版本页「添加内核」）在运行内核选择旁加勾选框「启用网页升级」，说明「勾选后以后可直接在面板网页上升级 Agent，无需再到服务器运行 `qui-update --component agent`」；默认不勾选，勾选后命令追加 `--web-upgrade`。`installCommand()` 增加对应可选参数，只在勾选时输出。
- 同步说明书（当前状态里「新装由 `node-install.sh` 自动启用」、§23）、[安装指南](install-guide.md)、[部署](deployment.md) §4 与 `node-install.sh --help`。
- 注意与第 2 项的关系：第 2 项修复前，受管节点无法发布显式核心的入站，因此第 4 项必须与第 2 项一起发布。

### 1.5.0 新装没有真正启用网页升级（Owner 2026-11-11 实测）

Owner 用 1.5.0 `node-install.sh` 新装节点「111」（61.228.99.110，2026-11-11 06:20 UTC 登记）后，版本页仍显示「需在服务器上运行一次 qui-update --component agent 启用网页升级」；面板库里该节点 `node_update_capabilities.agent_supported = 0`。

根因是时序：受管初始化（`agenthost.Initialize`）要求存储基线 `identity/agent-storage-contract.enc` 已存在（否则报 `node must have a stored configuration baseline before initialization`），而这个文件连同 `configuration.key` 只在 Agent 第一次正常启动、走到 `control.go` 的 `storage.Ensure` 时才写出（之前还要打开并校验各核心二进制）。`node-install.sh` 在 `service_start proxy-agent` 后立即调用 `agent_enable_web_upgrade`，后者先停掉服务再初始化；在 1 核小机器上 Agent 来不及写出基线，初始化失败，`agent_web_upgrade_failed` 打印「网页升级未启用，节点仍按普通模式运行」后被 `|| true` 吞掉，安装照常显示成功。`qui-update` 先做 10 秒健康检查，那时基线早已存在，所以能成功。1.5.0 验收（[记录](v1.5.0-agent-web-upgrade-verification.md)）注明未实机执行 `node-install.sh`。（主机侧报错原文未取得：没有该主机的登录权限；失败现场应在其 `/var/lib/proxy-agent/web-upgrade-failed-<时间>/`。）

修复：`agent_enable_web_upgrade` 在停服务前，等待服务保持运行且 `identity/agent-storage-contract.enc` 出现（有上限，例如 60 秒；超时按现有失败路径提示，不让安装失败），`node-install.sh` 与 `qui-update` 共用。部署测试覆盖「基线尚未出现时等待、出现后才停服务初始化」与超时路径。已装好的 1.5.0 节点在本机运行一次 `qui-update --component agent` 即可启用。

**状态：已修复（2026-11-11，未提交）。** `agent_enable_web_upgrade` 停服务前最多等 60 秒基线文件（`QUI_WEB_UPGRADE_WAIT` 仅供测试覆盖），超时或服务停止时不改动任何东西；本地 Linux 测试机上 `agent-web-upgrade-test.sh` PASS（新增基线延迟出现、始终不出现、等待中服务停止三个场景）、`node-install-test.sh` 54/54、`update-test.sh` 28/28。实机新装验收未做。

### 验收

- `deploy/linux/tests/node-install-test.sh`：带 `--web-upgrade` 时调用启用流程，不带时不调用并输出提示；未知参数仍拒绝。
- 前端自检：三个弹窗都有该勾选框且默认不勾选；`installCommand()` 只在勾选时输出 `--web-upgrade`。
- 实机：勾选安装一台节点，面板 Agent 管理页直接出现「升级」按钮；不勾选安装一台，不出现，运行一次 `qui-update --component agent` 后出现。

## 5. Windows 上国旗只显示国家代码

> **状态：已实现（2026-11-11，未提交），待随 1.5.1 发布。** quick-check 通过，构建产物含 `TwemojiCountryFlags-*.woff2`（sha256 `9f04f144…54e3b8`，78292 字节）；在 Windows 本机浏览器用最小页面对比确认：不加字体显示「DE」「HK」「US」，加字体显示国旗，中文与英文字形不变。面板页面本身的浏览器走查未做。

> 来源：Owner 2026-11-11 截图：服务器卡片名称前显示「DE」「HK」而不是国旗。

### 原因

`web/src/modules/nodes/nodeMeta.ts` 的 `countryCodeToFlag` 输出区域指示符号组成的国旗表情（服务器卡片、节点列表、版本页、服务器概览都用它）。Windows 的 Segoe UI Emoji 不含国旗字形，浏览器只能显示两个字母；macOS、iOS、Android 有原生国旗，所以只在 Windows 上出现。

### 方案

- 自托管 Twemoji 国旗字体：取 `country-flag-emoji-polyfill` 0.1.10 发布包里的 `dist/TwemojiCountryFlags.woff2`（约 78 KB），放进 `web/src/styles/fonts/`，同目录放许可说明（代码 MIT，国旗图案 Twemoji CC-BY 4.0，须署名）。不引入该包的 JS，也不从 CDN 加载。
- `web/src/styles/main.css` 增加 `@font-face`，`font-family: "Twemoji Country Flags"`，`unicode-range` 只含国旗相关码位（U+1F1E6-1F1FF、U+1F3F4、U+E0062-E007F），`font-display: swap`；在 `web/tailwind.config.js` 的 `sans` 字体栈最前面加入该字体。因 `unicode-range` 限定，其他文字仍用原系统字体，浏览器只在页面出现国旗字符时下载该文件。面板 CSP 的 `font-src 'self'` 已允许，无需改后端。
- [设计规范](design-system.md)第 3 节「使用本机系统字体，无需下载字体文件」补充这一例外。

### 验收

- Windows Chrome／Edge 的服务器卡片、节点列表、版本页与服务器概览显示国旗图案；未知地区仍显示 🌐；其他文字字体不变。
- 构建产物包含该 woff2，前端自检断言 `@font-face` 的 `unicode-range` 与字体栈首项存在。

## 7. 监控图表 CPU 与网速大多为空

> **状态：已实现（2026-11-11，未提交）。** quick-check（text、web、deploy、go、real-core）通过；新增 `TestShortIntervalHeartbeatsReuseCPUAndNICRatesWithoutResettingBaseline`、`TestNICRatesUseElapsedClockAndCounterResetIsUnknown`、`TestMetricSampleKeepsMeasuredRatesWithinMinute`。实机验证未做。

> 来源：Owner 2026-11-11 截图（服务器详情 → 监控）：CPU、接收／发送速率只有零散的点，并提示「需要新版 Agent 上报」，而 Agent 已是 1.5.0；内存、磁盘是连续曲线。

### 根因

线上三台节点最近 60 分钟的 `node_metric_samples`：CPU 与网速约 75% 的分钟为 NULL（44/60、46/60、41/60），内存、负载 0 个 NULL。

- Agent：`internal/agent/control/control.go` 的控制循环每处理一条面板消息（TCP 探测命令／结果、设备门控续期等，经 `continue` 回到循环开头）都会立即再发一次心跳。`internal/agent/capability/metrics.go` 的 `Sampler.Heartbeat` 用「本次与上次调用」的差值算 CPU，`host_metrics.go` 的 `interfaceRates` 同样算网卡速率；两次调用间隔不足 1 秒时不填这两项，同时把基准重置为本次读数。于是紧挨着的第二次心跳没有 CPU 与网速。
- 面板：`internal/panel/node/metrics.go` 每分钟只保留最后一条心跳，`ON CONFLICT … DO UPDATE` 整行覆盖，后到的空值盖掉同一分钟里先到的有效值。
- 页面：当前值同样取最近一次心跳，所以常显示「—」，且误报「需要新版 Agent 上报」。

### 方案

- Agent：`Sampler` 只在与基准相隔足够长（至少 1 秒）时计算 CPU 与网卡速率并推进基准；间隔过短的调用沿用上一次算出的值，不清空、不重置基准。
- 面板：分钟采样的速率型字段（CPU 百分比、收发速率）在同一分钟内改为「新值非空才覆盖」，其余字段保持「最后一条为准」。这样现有 1.5.0 Agent 不升级也能得到连续曲线。
- 页面：当前值为空时，若该指标在所选范围内有历史测量，显示最近一个历史值或「—」，不再提示「需要新版 Agent 上报」；只有 Agent 确实不支持该指标（能力缺失）时才提示升级。

### 验收

- Agent 单元测试：间隔不足 1 秒的连续两次 `Heartbeat()` 都带 CPU 与网卡速率，且基准不被短间隔调用重置。
- 面板测试：同一分钟先写有效 CPU、后写空 CPU，保存结果仍为有效值；其他字段以最后一条为准。
- 实机：升级面板后（不升级 Agent），1 小时视图里 CPU 与网速 NULL 分钟显著减少；升级 Agent 后接近 0。

## 9. 节点列表把从未生效的入站显示为「已生效」

> **状态：已实现（2026-11-11，未提交）。** 新增只读接口 `GET /api/v1/nodes/{id}/inbound-states`（Owner／Viewer），草稿取 `SnapshotIntent`、运行侧取 `PublishedWithIntent`，比较排除用户凭据、WireGuard 对端与无用户时的自动停用；结果码中文名合并为 `web/src/modules/system/revisionResult.ts` 一份。`TestInboundStates` 10 个用例通过；浏览器与实机未验。

> 来源：Owner 2026-11-11 截图（节点配置 → 节点列表）：「德国 netcup · hysteria2-36122」明明没有生效，却显示「已生效」。

### 原因

`web/src/modules/proxy/pages/ProxyNodeListPage.vue` 的 `loadServerPublishStates` 取的是**整台服务器**最近一条修订（`deploymentAPI.nodeRevisions(id, 1, 1)`），再经 `publishProgress.ts` 的 `serverPublishState` 显示，服务器上每个入站都套用同一个标签。5.45.96.43 上最近一条是自动额度版本修订 20（成功），所以 Hysteria2 与 VLESS 都显示「已生效」；实际上这两个入站从未成功发布（修订 13、15–19 均 `apply_failed`，修订 20 以已发布状态为基线，不含它们，见第 2 项）。后端目前没有「单个入站是否已生效」的数据。

同一行另有两处误导：「真实状态」列显示的「在线」是服务器在线，不代表该入站在运行；Hysteria2 的「协议与传输」显示 `tcp + tls`，而它实际走 UDP/QUIC。

### 方案

- 后端为自建入站给出只读的发布状态（入站列表与详情各带一个字段，例如 `publishState`）：把草稿入站与该服务器**当前已确认运行的修订**（Agent 上报的 current revision 对应的已发布状态）比较，取值
  - `effective`：运行修订里有该入站，且其运行配置与草稿一致（比较口径复用发布模块已有的「运行配置是否变化」比较，忽略修订号，用户凭据按集合比较或不参与，避免自动额度版本造成误报）；
  - `modified`：运行修订里有，但草稿已修改未发布；
  - `pending`：最新修订包含该入站且正在等待服务器确认；
  - `unpublished`：运行修订里没有（新建未发布、或发布失败已回滚）；若该服务器最近一次包含它的发布失败，另带失败码（如 `apply_failed`）。
  禁用入站按启用意图判断。只读计算，不新增表与迁移。
- 节点列表与卡片视图按入站显示：已生效（绿）／有未发布修改（黄）／发布中（蓝）／未生效（红，悬停或副文字给出最近失败原因）。服务器级的发布进度只用于服务器视图，不再套到每个入站上。
- 「真实状态」：入站未生效时不显示「在线」，改显示「未生效」；只有入站已生效时才显示服务器在线状态与延迟。
- 「协议与传输」：Hysteria2／TUIC 显示 `udp + quic`（或「QUIC」），不再沿用 TCP 传输字段的默认值。

### 验收

- 后端测试：新建未发布、发布成功、成功后再修改、发布失败回滚、自动额度版本成功（不含该入站）五种情况的 `publishState` 正确；自动额度版本不把未发布入站算作已生效。
- 前端自检：节点列表按入站的 `publishState` 渲染标签，不再用服务器最近修订给每个入站贴标签。
- 实机：5.45.96.43 上第 2 项修复前，Hysteria2 显示「未生效（apply_failed）」；修复并发布成功后显示「已生效」。
