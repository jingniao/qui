# v1.5.1 规划

> **状态：规划，尚未实施。** 当前行为以[项目说明书](../AGENTS.md)与源码为准。v1.5.1 定位为 v1.5.0 的补丁版，无迁移；建议在生产升级前发布，让生产直接升到 1.5.1。

## 1. 规则集页面不能用关键字和外部来源，且编辑会清掉关键字

> 来源：Owner 2026-11-11 反馈（「分流控制 → 规则集」创建对话框里看不到引入外部规则集的地方）。

### 现状

v1.5.0 的规则集关键字条目与外部来源（[v1.5.0 规划](v1.5.0-plan.md)第 9 项）只做进了「客户端策略 → 编辑配置 → 规则集」里的对话框（`web/src/modules/routing/pages/ClientPolicyPage.vue`，模板约 2135–2339 行，脚本约 4206–4400 行）。独立的「分流控制 → 规则集」页面（`web/src/modules/routing/pages/ServiceRulePage.vue`，路由 `/routing/services`）有自己的一份对话框副本，没有同步：

| 位置 | 关键字条目 | 外部来源 |
| --- | --- | --- |
| 客户端策略 → 编辑 → 规则集 → 创建／编辑 | 有 | 有（含刷新与抓取状态） |
| 分流控制 → 规则集 → 创建／编辑 | 无 | 无 |

更严重的是数据丢失：后端保存规则集时先 `DELETE FROM service_set_entries` 再按请求重写全部条目（`internal/panel/policy/repository.go` 的 `SaveService`），而 `ServiceRulePage.vue` 的表单只带 `domains`／`suffixes`／`cidrs`，不带 `keywords`。所以在客户端策略里加过关键字的规则集，**在规则集页面打开再保存，关键字会被全部清空，没有任何提示**。外部来源不受影响：请求不带 `sources` 字段时后端保留原值（`Sources *[]SourceInput`，`omitempty`）。

v1.5.0 浏览器走查只检查了客户端策略里的那份对话框，因此漏掉了这个页面（见 [v1.5.0 浏览器走查](v1.5.0-browser-walkthrough.md)）。

**临时规避（发布 1.5.1 前）：** 带关键字或外部来源的规则集只在「客户端策略 → 编辑 → 规则集」里编辑，不要在「分流控制 → 规则集」里保存。

### 方案

- 把客户端策略里完整的规则集对话框（名称、说明、启用、精确域名、后缀、**关键字**、IP/CIDR、**外部来源**的增删与「刷新」、抓取状态与失败原因、已保存引用、禁用提示、删除确认）抽成共享组件，例如 `web/src/modules/routing/components/ServiceSetEditor.vue`，两个页面都用它。去掉 `ServiceRulePage.vue` 里的旧副本，以后只有一份，不会再出现一边改了一边没改。
- 保存请求总是带完整的 `keywords` 与 `sources`（来源在编辑时回填），避免任何入口因漏带字段清空数据。
- 规则集列表的「来源 / 版本」列显示外部来源数量与最近抓取状态（成功／失败／待抓取），对应 v1.5.0 规划第 9 项「页面为每个外部来源标明客户端可用／节点可用，显示最近抓取时间、条目数与失败原因」。列表的「匹配规模」把关键字数量也算进去。
- 后端不改接口；如审查认为有必要，可让 `SaveService` 在请求省略 `keywords`（JSON 中缺失而非空数组）时保留原关键字，作为对旧客户端的兜底。是否采用在实施时决定并写进说明书 §27.7。

### 验收

- 两个页面都能新建带关键字与外部来源的规则集；外部来源能刷新并显示状态。
- 回归：在客户端策略里建一个带关键字和外部来源的规则集，到规则集页面打开再保存，关键字、来源与其缓存都保留；反过来也一样。前端自检加断言：两个页面使用同一个编辑组件，保存载荷包含 `keywords` 与 `sources`。
- 浏览器走查覆盖「分流控制 → 规则集」页面本身（创建、编辑、刷新来源、列表状态列、最小字号 12px、无 `pageerror`）。

## 发布

- 无迁移；纯前端改动可走短门禁，若后端兜底一并修改则走完整门禁（`scripts/gate-scope.sh` 自动判定）。
- 发布说明写明 1.5.0 的数据丢失风险与规避方法，以及「从 ≤1.4.7 升级 Agent 仍需运行两次 `qui-update --component agent`」。
