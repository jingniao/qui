# v1.5.2 规划

> **状态：规划，尚未实施。** 当前行为以[项目说明书](../AGENTS.md)与源码为准。v1.5.2 定位为 v1.5.1 的补丁版。

## 1. 监控页面反复显示「正在读取历史指标…」，图表短暂变空

> 来源：Owner 2026-11-11 截图（qui.lluu.de「德国 netcup」→ 监控，1H）：页面时常出现「正在读取历史指标…」，同时 7 张卡片全部变成「— · 暂无历史测量」，过一会儿才恢复。

### 现状与根因

`web/src/modules/nodes/components/ServerMetricsGrid.vue` 有三个触发重新读取 `GET /api/v1/nodes/{id}/metrics` 的来源：每 60 秒的定时器、`watch(() => [props.node.id, props.hours], …)`，以及窗口事件 `proxy-node-status`。

- **事件太频繁，且不区分节点。** 面板在每条 Agent 心跳、Agent 更新结果、健康检查结果到达时都发布 SSE `node_status`（`internal/panel/node/control.go` 中 `c.Notify(id)`，心跳每台约 15 秒一次），`web/src/app/events.ts` 把它转成不带节点 ID 的 `proxy-node-status`。监控卡片收到任何节点的事件都重新读取历史指标；3 台节点约每分钟 12 次，每次都把 `loading` 置真，显示「正在读取历史指标…」。
- **图表被清空。** `NodeDetailPage.vue` 也监听 `proxy-node-status` 并重新读取节点，传给监控卡片的 `node` 换成新对象。监控卡片的 `watch` 源是返回新数组的函数 `() => [props.node.id, props.hours]`，Vue 用 `Object.is` 比较新旧返回值，每次都算「已变化」，回调执行 `points.value = []` 后再读取，于是请求返回前全部卡片显示「暂无历史测量」。节点 ID 与时间范围其实都没有变。

### 方案

- `watch` 改为分别比较两个值（`watch([() => props.node.id, () => props.hours], …)`），只有节点或时间范围真的变化时才清空并重新读取。
- 后台刷新（定时器与状态事件）保留现有数据直到新数据返回，不清空，也不显示「正在读取历史指标…」；该提示只用于首次读取与切换节点或时间范围。刷新失败时保留旧图并提示，不清空。
- 历史指标为每分钟采样，心跳事件不应触发读取：去掉对 `proxy-node-status` 的监听，或只在本节点状态变化（例如由离线转为在线）时读取，且与定时器合并为每 60 秒最多一次。
- 顺带检查同样监听 `proxy-node-status` 的其他页面（`NodeDetailPage.vue`、`ProxyNodeListPage.vue`、`OutboundGroupPage.vue`、`ProxyChainListPage.vue`）是否也有「每次心跳全量重读」的问题，需要时按节点 ID 过滤或节流；SSE 事件本身已带 `nodeId`，前端转发时可以保留它。

### 验收

- 前端自检覆盖：节点对象替换但 ID 与范围不变时不清空数据、不显示读取提示；切换范围时清空并显示提示；刷新失败保留旧数据。
- 浏览器走查：在 3 台在线节点的面板上停留监控页 5 分钟，「正在读取历史指标…」只在首次进入与切换范围时出现，图表不再闪空；读取请求约每分钟 1 次（开发者工具网络面板计数）。

## 2. 「版本与更新」页国旗仍显示字母

> 来源：v1.5.1 发布后在 qui.lluu.de 复核，见 [v1.5.1 规划](v1.5.1-plan.md)第 5 项与[发布说明](release-notes-1.5.1.md)「已知限制」。

`NodeVersionPanel.vue` 列表与卡片两处国旗方块带 `font-mono`，等宽字体栈没有国旗字体，Windows 上仍显示「DE」「HK」。方案：在 `web/tailwind.config` 的 `mono` 栈首加入 `"Twemoji Country Flags"`（`unicode-range` 只覆盖国旗码位，不影响其他字符）。验收：Windows 浏览器打开「版本与更新」页显示国旗，等宽数字与英文字形不变。

## 3. 「网络质量与延迟」图表与上方机器监控图表样式不一致

> 来源：Owner 2026-11-11 截图（「德国 netcup」→ 监控，12H）：上方 7 张机器监控卡片是 v1.5.1 的 Chart.js 样式，下方延迟图字体、线条、图例、坐标轴都不一样。v1.5.1 [发布说明](release-notes-1.5.1.md)「已知限制」已记「延迟图未改为 Chart.js 风格」。

### 现状与根因

`web/src/modules/nodes/components/LatencyChart.vue` 仍是手绘 SVG（`viewBox="0 0 800 270"`，`class="w-full"`），没有用 v1.5.1 的 `MetricLineChart.vue`：

- **字号随宽度放大。** 坐标轴文字是 SVG 内的 `text-xs font-mono`（12 个 viewBox 单位），整张图按容器宽度等比缩放，宽屏下约放大 2 倍以上，纵轴「1500」与横轴时间变成很大的等宽字，违反[设计规范](design-system.md)的字号表（辅助信息 12px），也与上方卡片的 12px 无衬线坐标轴不一致。线宽（1.8）同样被放大。
- **横轴只有一个刻度。** `times` 调用 `hourTicks(start, end, timezone, selectedHours)`，把「所选小时数」当作刻度间隔：12H 每 12 小时一个刻度，所以只显示「09:00」；24H、7D 同样只剩一到两个。
- **图例、配色与布局不同。** 图例在下方、方块标记，上方卡片是顶部圆点；丢包用整高红色竖线；没有面积填充规则与悬停读数卡片的统一样式；时间范围切换用另一套按钮（1H/6H/12H/24H/7D/全不选），与机器监控右上角的分段控件样式不同，且两处范围已共用 `monitoringHours`，出现两套控件。

### 方案

- 延迟图改用 `MetricLineChart.vue`（Chart.js，按需加载），与机器监控共用坐标轴、网格、字体、图例（顶部圆点）、悬停读数与 12px 字号；多目标为多条线，颜色沿用目标颜色（电信／移动／联通）。
- 横轴刻度交给 Chart.js 按宽度自动生成，与上方卡片同一套时间格式（`formatXTick`）；纵轴为毫秒，与上方一样自动取整。
- 丢包改为同图的第二纵轴（丢包率 %，柱状或阶梯线），或在悬停读数中列出，不再画整高竖线；「延迟／丢包／平滑峰值」开关保留，切换只改变数据集。
- 时间范围只保留一套控件：机器监控右上角的分段控件同时控制延迟图（两者已共用 `monitoringHours`），延迟区去掉重复的 1H–7D 按钮，「全不选」「检测目标」保留在延迟卡片内。
- 三个目标卡片（平均延迟 · 丢包率 · 抖动）保持，字号与上方卡片的标题行、数值行一致。

### 验收

- 前端自检：12H／24H／7D 的横轴刻度数量大于 1；丢包数据映射到第二纵轴或悬停读数；平滑峰值开关只改变显示数据、不改目标卡片统计。
- 浏览器走查（1280px 与 1920px 宽）：延迟图坐标轴文字为 12px、与上方卡片同一字体；图例在顶部；只有一套时间范围控件；切换范围时两部分同步；无 `pageerror`。

> 第 4–6 项来自 2026-11-11 在 qui.lluu.de「德国 netcup」的全协议实测：16 个测试入站（Xray 与 sing-box 各自支持的全部协议），修订 24–26，测完已删除。Owner 同日决定纳入本版。

## 4. sing-box TCP 入站让 Agent 每 30 秒记一条 WARN

### 现状与根因

节点上有 sing-box 的 TCP 入站时，Agent 每 30 秒记一条 `telemetry observations rejected during parsing attribution or submission`（实测 6 个 sing-box TCP 入站时每次 48–209 条），同时抬高上报给面板的未归属观测计数（`CollectorLossStatus.RejectedObservations`）。删掉这些入站后约 1.5 分钟停止；测试前该节点的 sing-box 只有 UDP 的 Hysteria2，一条也没有。

- sing-box 的监听健康检查（`internal/agent/core/singbox/adapter.go` 的 `configurationHealth`）对每个 TCP 入站拨号后立即关闭，监督进程每 3 秒巡检一次。
- sing-box 访问日志解析（`internal/agent/collector/singbox.go`）收到 `inbound connection from <地址>` 就建一条挂起记录，等 `inbound connection to <目标>` 来补全。健康检查的连接没有目标，挂起 2 分钟后被清理，`!entry.done` 时调用 `failed()`，计为 rejected。
- Xray 的解析（`writer.go`）对「没有目标且来自回环地址」的行已经豁免（`loopbackSource`，注释写明 Agent 自己的 TCP 健康检查不是观测），sing-box 没有对应处理。

### 方案

- 挂起记录保存来源地址；清理时若记录从未拿到目标，且来源是回环地址，直接丢弃，不计 rejected。规则与 Xray 一致：来自非回环地址、没有目标的连接（例如外部握手失败）仍计为未归属。
- 不改健康检查频率，也不改 rejected 的其他判定。

### 验收

- 单元测试：回环来源、只有 `inbound connection from` 的连接 2 分钟后不计 rejected；非回环来源的同类连接仍计 1 次；有目标的连接按原逻辑发出记录。
- 测试机实测：建若干 sing-box TCP 入站并发布，10 分钟内 Agent 日志没有该 WARN；用真实客户端访问时访问记录照常生成。

## 5. Reality 握手目标：去掉 `www.microsoft.com:443` 预设并补充提示

### 现状与根因

官方 Xray 26.3.27 用 `www.microsoft.com:443` 当 Reality 握手目标时连接失败，sing-box 和 Xray 两种客户端都连不上。在 5.45.96.43 上独立运行官方 Xray 服务端与客户端（不经过 qui）同样失败，换成其他目标立即正常；sing-box 服务端用这个目标正常。编辑器「常用目标」下拉的**第一个预设就是它**，Xray 用户很容易直接选中。

其余 5 个预设在同一台机器上用官方 Xray 实测（Reality TCP+Vision 与 Reality gRPC 各一次，每次两个 HTTPS 请求）全部通过：`www.apple.com`、`www.amd.com`、`www.nvidia.com`、`dl.google.com`、`www.cloudflare.com`。

### 方案

- **已改（2026-11-11，未发布）：** `serverSettingsModel.ts` 的 `REALITY_HANDSHAKE_PRESETS` 去掉 `www.microsoft.com:443`；`node-editor-selftest.mjs` 同步；[安装指南](install-guide.md)的示例改为 `www.amd.com:443`。quick-check（text＋web）通过。
- 握手目标说明补一句：「部分站点只适用于 sing-box，Xray 连接会失败；不确定时从常用目标中选择」。
- 已经用 `www.microsoft.com` 的现有 Xray Reality 入站不自动修改。是否在编辑器里对「Xray + 该目标」给出警告，待实现时定；不做阻止保存，因为原因在上游、不在 qui。

### 验收

- 前端自检：预设列表不含 `www.microsoft.com:443`，每个预设与它派生的 SNI 仍是合法组合。
- 浏览器走查：Reality 入站编辑器的常用目标下拉与说明文字按上述显示。

## 6. HTTP／SOCKS5／Shadowsocks 入站可以选 WebSocket、gRPC，但发布失败或客户端连不上

### 现状与根因

协议选 HTTP 时，编辑器的「传输」下拉仍提供 TCP、WebSocket、gRPC（`serverSettingsModel.ts` 的 `transportChoices` 对所有协议都给这三项）。后端 `desiredstate`（`protocol.go`）只校验传输值本身，不看协议，所以面板能保存。之后：

- **sing-box**：渲染（`internal/agent/core/singbox/render.go`）对 VLESS、Trojan 以外的协议带传输直接报错「sing-box transport requires VLESS or Trojan」，发布失败并回滚。
- **Xray**：渲染（`internal/agent/core/xray/protocols.go` 的 `stream`）照常生成走 WebSocket／gRPC 的 HTTP 或 SOCKS5 监听；但 URI 订阅导出 `http://`、`socks5://` 时不带传输方式（`internal/panel/subscription/format/uri/uri.go`），客户端按明文连接，连不上。Shadowsocks 的 URI 同样没有传输字段。

### 方案

- WebSocket、gRPC 只对 VLESS 与 Trojan 开放（xhttp 仍只限 VLESS）；HTTP、SOCKS5、Shadowsocks 只有 TCP。编辑器按「隐藏不可用选项」规则不显示其他传输。
- 面板保存、`SnapshotIntent` 与发布前三处用同一条规则拒绝（与现有能力门禁同一位置），错误给中文说明。
- 已保存的不合法组合：读取时编辑器显示「（现有值）」并要求改为 TCP 才能保存；发布前校验拒绝，不会再下发到节点。发版前查生产库里有没有这样的入站，有的话在发布说明里写明处理方法。

### 验收

- 后端测试：HTTP、SOCKS5、Shadowsocks 携带 `ws`／`grpc`／`xhttp` 时保存与发布均返回 400；VLESS、Trojan 不受影响。
- 前端自检：协议为 HTTP、SOCKS5、Shadowsocks 时传输选项只有 TCP。
