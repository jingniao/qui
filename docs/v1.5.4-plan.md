## 1. 部署结果丢失时，按心跳确认修订

### 现状

v1.5.3 修好了「新修订的数据先到、应用结果丢失」这一条路径，但应用结果仍只存在 Agent 当前会话的内存里（`internal/agent/control/control.go` 的 `results`），会话在发出结果前断开（网络抖动、面板重启）结果就丢了。面板只靠 `ApplyResult` 把 `deployment_targets` 从 `pending` 改成 `success`；心跳里的 `current_revision`／`successful_revision` 只做格式校验（`internal/panel/node/control.go`），不参与确认。`pending` 只在删除节点时才会被标为失败，所以结果一旦丢失，节点会一直「发布中」，后续发布被 `deployment_conflict` 拒绝。

### 方案

- 面板收到心跳时，若该节点有 `pending` 的修订，且心跳报告 `successful_revision` 等于它、核心健康，则按成功确认（与 `ApplyResult` 成功走同一条路径：更新运行状态、推进订阅快照、排部署后对账），并记一条 INFO 日志「按心跳确认修订」。
- 心跳报告的成功修订比 `pending` 的更新或不同，不做推断，保持原样。
- 不替代 `ApplyResult`：失败、回滚与原因码仍只来自 `ApplyResult`。

### 验收

- 单元测试：`pending` 修订＋心跳 `successful_revision` 相同 → 确认为成功；不同 → 不变；已是 `success`／`failed` → 不变。
- 测试机：在 Agent 发出结果前切断连接（或用测试钩子丢弃结果），重连后的第一次心跳把修订确认为成功，之后可以正常发布。

## 2. 访问记录批次被拒时也隔离

### 现状

流量批次被面板连续拒绝 3 次会被隔离、冷却后重试（`telemetryQueue.RejectTraffic`），访问记录批次没有这套机制：v1.5.2 卡住期间，访问记录批次每 30 秒被拒一次、控制连接每 30 秒断一次，没有上限（[1.5.3 发布说明](release-notes-1.5.3.md)「修复」）。

### 方案

- Agent 的访问记录队列加与流量相同的拒绝计数与隔离（连续 3 次 `FailedPrecondition` → 隔离、保留在磁盘、冷却 1 小时或 Agent 重启后重试），日志「access batch quarantined after repeated rejection」。
- 本地 spool 表结构变化走 spool 自己的迁移；隔离的访问记录不参与容量淘汰的优先删除（与流量批次一致，第 21 节）。

### 验收

- 单元测试：访问记录批次被拒 3 次后隔离，后续批次继续发送；冷却后重试；被接受后从队列删除。
- 控制会话测试：被拒批次不再导致无限断开重连。

## 3. 面板记录批次被拒的原因

### 现状

面板拒收流量或访问记录批次时只给 Agent 返回 `traffic batch rejected`／`access batch rejected`，不写日志，具体原因（修订未确认、身份冲突、时间在未来等，`internal/panel/access/traffic_service.go` 的各个阶段）丢失。v1.5.2 的死锁靠读代码和查数据库才定位。

### 方案

- 面板在拒收时记一条 WARN：节点 ID、批次 ID、阶段（`trafficStageError` 已有的阶段码或固定原因）、涉及的修订号；同一节点同一原因每分钟最多一条，避免刷屏。不记录用户名、域名等内容。
- 可选：在节点详情「事件」里显示最近一次拒收原因。

### 验收

- 单元测试：各拒收分支产生带固定原因的日志；限流生效。

## 5. 节点侧完整的国内域名名单

### 现状

节点「国内」集合只用 `geolocation-cn`（约 5400 个域名）加国内 IP 段。geosite `cn` 有约 11 万条，超过单个外部来源 2 万条的解析上限（`MaxSourceEntries`），展开进期望状态也会接近 2 MiB；所以 `www.qq.com` 这类只在 geosite `cn` 里的域名在节点侧拦不到（[1.5.3 发布说明](release-notes-1.5.3.md)「第 8 项阻断」）。另外，15000 条的策略让 sing-box 启动约 30 秒，规则越多、每次发布中断越久。

### 方案：核心原生规则集文件（Owner 2026-11-12 选定方案 A，纳入本版）

曾考虑的另两种：B 提高解析上限（配置与启动时间继续变大，不采用）；C 维持现状只写说明（不采用）。

- **来源类型**：规则集的外部来源增加「节点原生」格式：sing-box 用 `.srs`，Xray 用 geosite／geoip 数据文件里的一个标签（例如 `geosite:cn`）。地址仍只允许 HTTPS，前缀白名单先只放 MetaCubeX meta-rules-dat（sing-box 用 `sing` 分支的 `geo/geosite/*.srs`、`geo/geoip/*.srs`，Xray 用 `release` 分支的 `geosite.dat`／`geoip.dat`）。`service_set_sources.format` 的 CHECK 只允许 yaml／text／mrs，需要**新增迁移 0143** 扩展取值，备份校验（`validateServiceSetSources`）与回退夹具同步。
- **期望状态**：策略不再把这类来源展开成条目，而是带上规则集引用（名称、类型 domain／ipcidr、核心对应的文件地址）；`desiredstate` 新增字段只做加法，旧 Agent 不认识就由能力位挡住。
- **Agent**：新增逐核能力位 `native_rule_sets_supported`（`CoreCapability` 下一个空闲字段，`Capabilities` 单核标量同步）。Agent 自己下载文件到 `runtime/<core>/rulesets/`（0700／0600），限制大小（建议 32 MiB）与超时，下载后用核心原生校验（sing-box `rule-set` 能被 `check` 接受、Xray `run -test`）确认可用才切换；下载失败沿用上一份已校验的文件，从未下载成功则该修订按普通失败回滚并报固定错误码。文件按地址与内容摘要命名，旧文件在切换成功后清理。核心不自行联网下载（sing-box 不用 remote `rule_set`），以便离线、校验与回滚都由 Agent 掌握。
- **刷新**：文件内容每天变化，没有厂商摘要；Agent 按来源的刷新间隔（默认 1 天）在后台重新下载，内容变化时只重载使用它的核心，与配置发布无关；面板在节点详情显示每个规则集文件的版本时间与最近一次下载结果。是否需要「重载核心」这一新的固定操作，实施前在 Agent 白名单（第 23 节）里定稿。
- **内置「国内」集合**：迁移 0143 为 `service-cn` 追加 geosite `cn` 与 geoip `cn` 的节点原生来源；面板对上报 `native_rule_sets_supported` 的节点用原生来源，对旧节点继续用现有 yaml 展开，「屏蔽回国」策略本身不变。其他内置集合是否改用原生来源，实施时按条目数决定（超过数千条的优先）。
- **客户端**：订阅里不输出节点原生来源（客户端已有 mrs 版本），客户端预设不变。

### 验收

- 迁移与备份：0143 在全新库与已有自定义来源的库上都能升级；备份校验接受新格式；旧归档仍合法。
- 真实核：Xray 与 sing-box 用 geosite `cn`＋geoip `cn` 启用「屏蔽回国」后，`www.qq.com`、`www.baidu.com`、`114.114.114.114` 在节点侧被阻断，`www.google.com` 不受影响；与展开方式相比，期望状态体积和核心启动时间明显下降（记录数字）。
- 失败路径：下载失败沿用旧文件；首次下载失败时修订回滚并给固定错误码；旧 Agent 在保存、快照与发布前三处被能力位挡住。
- 实机：在测试机或 Owner 自己的面板上发布一次，确认发布期间不再出现 v1.5.2 那样约 30 秒的核心启动。

## 10. 用户找不到门户登录入口（Owner 2026-11-12 报告）

### 现状

Owner 在后台为用户设置了账号与门户密码，用户仍「无法登录」。代码路径本身正常（`TestPortal*` 覆盖了「新建用户 → `PUT /api/v1/users/{id}/login` → `POST /api/v1/portal/auth/login`」），问题在入口：

- 终端用户只能在 `/portal/login` 登录；打开面板地址进入的是管理员登录页 `/login`，用户的账号密码在那里只会得到「用户名或密码错误」（管理员与用户认证隔离，第 6.3 节）。
- 面板里没有任何地方给出 `/portal/login`：管理员登录页没有入口，用户详情「用户门户登录」区块不显示门户地址，订阅链接也不附带。
- 「新建用户」抽屉没有门户登录设置，用户名提示写着「用于身份凭据登录」；新用户默认不允许登录、没有密码，须另到用户详情勾选「允许登录用户门户」并设置密码。

### 方案

- 管理员登录页加「代理用户请前往用户门户登录」链接到 `/portal/login`，门户登录页加返回管理员登录的小字链接；两处都不提示账号是否存在。
- 用户详情「用户门户登录」区块显示门户地址（按当前访问面板的地址拼出 `…/portal/login`）并可复制，旁边给出「登录门户 + 订阅链接」一并复制的按钮，便于一次发给用户。
- 「新建用户」抽屉增加可选的「允许登录用户门户」与初始密码（勾选时必填、两次输入一致）：创建成功后调用既有 `PUT /api/v1/users/{id}/login`；第二步失败时用户已创建，抽屉提示「用户已创建，门户登录未设置：<原因>」并转到该用户详情，不重复创建。用户名提示改为「代理凭据与用户门户登录使用的名称」。
- 门户登录页区分「请求过多，请 15 分钟后再试」（429，第 29.1 节登录限制）与凭据错误，凭据错误仍用统一文案。

### 验收

- 浏览器走查：从面板地址能找到门户入口；新建用户时勾选门户登录，立即能在 `/portal/login` 登录；未勾选的用户登录失败，提示不泄露账号是否存在。
- 前端自测覆盖新建抽屉两步保存的成功与第二步失败路径。

## 11. 用户门户页面完善（Owner 2026-11-12 要求）

### 现状

门户（`web/src/portal/`）仍是 v1.4 的最小实现，五个分区共用一个约 115 行的页面：

- 概览：到期只显示时间，不显示剩余天数；不显示下次流量重置日期（用户有每月／每 30 天的重置周期，第 9.1 节，门户接口目前不返回）；状态异常时只有一句原因。
- 订阅：格式只显示内部 ID（`uri`、`base64`、`sing-box`、`clash` 等），不说明对应哪个客户端，也没有导入步骤；二维码点击后显示在列表下方。
- 节点：只有名称、地区与在线状态，不显示该节点给本人开放的协议（`GET /api/v1/portal/nodes` 不返回）。
- 流量：每个时间桶一行文字加色条，字节一律按 GiB 保留 3 位小数，与后台已改用的 Chart.js 图表不一致。
- 账号：只有修改密码，不显示本次登录的到期时间（会话接口已返回 `expiresAt`）。
- 布局：顶栏只写「我的账号」，窄屏下导航按钮换行；五个分区的页头说明都重复「一个账户一条订阅，可在多台设备上使用」。

### 方案

- **概览**：账号状态、流量（进度条，已用／剩余／额度，单位自动换算）、到期（日期与剩余天数，7 天内提示）、下次流量重置日期；状态为禁用、到期或超额时写明原因并提示联系管理员；增加默认格式订阅链接的「复制」快捷入口。
- **订阅**：每种格式显示面向用户的名称与一句适用客户端说明（例如「mihomo／Clash Meta」「sing-box」「通用链接，适用于 v2rayN 等」），系统默认格式置顶；二维码在弹窗中显示；附简短的导入步骤。一键导入协议仍待核实（第 10.3 节），本版不做。
- **节点**：显示每个节点对本人开放的协议，离线节点排在后面。
- **流量**：改用与后台一致的 Chart.js 柱状图（上传、下载堆叠），单位自动换算，显示所选范围的合计。
- **账号**：显示用户名、显示名与本次登录到期时间；修改密码时提示与后台一致的密码规则。
- **布局**：顶栏显示用户的显示名；窄屏导航改为可横向滚动的一行；字号遵循[设计规范](design-system.md)第 3 节；去掉重复的页头说明。Owner 的只读预览（`/portal-preview`）使用同一套页面。
- **接口（只做加法）**：`GET /api/v1/portal/me` 增加 `trafficResetCycle` 与 `nextTrafficResetAt`（与用户详情同一计算）；`GET /api/v1/portal/nodes` 的每项增加 `protocols`，取自与订阅相同的授权与过滤管线，只含本人可用的端点。只读预览的快照同步这些字段。

### 验收

- 浏览器走查 375、823、1280px 三种宽度，覆盖正常、即将到期、超额、禁用四种账号状态。
- `web/scripts/portal-selftest.mjs` 更新；新增字段补接口测试（重置日期与用户详情一致；节点协议与本人订阅端点一致，不含未授权入站）；门户与管理员会话隔离的现有测试保持通过。

## 12. Clash 客户端无法导入订阅（Owner 2026-11-12 报告）

### 已核对（2026-11-12）

- **配置本身**：全部内置预设（含三个「屏蔽回国」预设）与带地区组、精确端点、空组策略的模板，都由真实核测试 `TestMihomoAcceptsTheProfiles` 用 mihomo 1.19.33 执行 `mihomo -t` 通过（v1.5.3 的门禁与 2026-11-12 的门禁）。这只证明该版本 mihomo 能解析，不证明各图形客户端（其内置 mihomo 版本可能更旧）能导入。
- **传输**：qui.lluu.de 经 Cloudflare 提供公网证书（Google Trust Services），用 Clash Verge、mihomo、Clash Meta for Android 的 User-Agent 请求订阅地址都直接到达面板（无效 Token 得到面板自己的 403 JSON），没有被 Cloudflare 质询拦截。
- **生产面板**：证书由私有 CA 签发，v1.4.1 时已记录 Clash Verge 与 v2rayN 报「self-signed certificate in certificate chain」无法导入，Owner 当时决定延后（[1.4.1 发布说明](release-notes-1.4.1.md)）；生产仍是该证书时，任何客户端都无法通过 HTTPS 导入。
- **格式命名**：订阅格式 `clash` 实际是 mihomo（Clash Meta）配置，带 VLESS、Hysteria2、`rule-providers` 的 `mrs` 格式等，旧版 Clash（Clash for Windows、ClashX 的 Premium 核心）无法加载，旧版要用 `clash-legacy`；但页面只显示内部 ID，用户容易选错。
- **不带格式的链接**：已验证的 User-Agent 匹配表为空（第 10.3 节），不带 `?format=` 的链接总是返回系统默认格式，默认若不是 `clash`，Clash 客户端拿到的是 URI／Base64 列表而不是 YAML。
- **面板规则集地址**：`/sub/{token}/rules/{id}` 的绝对地址按请求本身拼出（`r.TLS` 为空则用 `http`，主机取 `Host`）；面板在终止 TLS 的反向代理后面时，配置里会写成 `http://` 地址。只影响引用面板规则集的模板，三个「屏蔽回国」预设的规则集来自 jsDelivr，不受影响。

### 待确认

失败时使用的客户端与版本、所用的订阅链接（哪个格式）与客户端报错原文，以及是哪台面板。实施前先用 Owner 的实际配置复现，确定根因后再定下面方案的取舍。

### 方案（按复现结果取舍）

- **复现与客户端矩阵**：用 Owner 的实际订阅（去除凭据）在 Clash Verge Rev、Clash Meta for Android 与 mihomo 的当前版本和较旧版本上导入；真实核测试增加一个较旧的 mihomo 版本，配置中需要较新 mihomo 才支持的字段（如 `mrs`、xhttp、端口跳跃）按格式能力省略或警告。
- **格式名称**：用户详情、门户与订阅预览把 `clash` 显示为「mihomo（Clash Meta／Clash Verge）」、`clash-legacy` 显示为「Clash（旧版 Premium 核心）」，并写明各自适用的客户端（与第 11 项的订阅页一起做）。
- **按客户端自动选择格式**：在真实客户端上核实 User-Agent 后写入匹配表（mihomo、Clash Verge、Clash Meta for Android 等），使不带格式的链接对这些客户端也返回 mihomo 配置；系统设置里的「按 User-Agent 识别」默认值与说明同步。
- **反向代理后的地址**：面板规则集地址优先使用系统设置「节点安装连接地址」里的面板地址与端口（第 27.14 节），未设置时才按请求拼出；或只在请求来自可信代理时采用 `X-Forwarded-Proto`／`X-Forwarded-Host`。
- **生产证书**：若根因是生产的私有 CA，按 v1.4.1 记录的选项处理：给面板配域名并用已实现的 Cloudflare DNS-01 申请公网证书（第 27.16 节，推荐），或在客户端信任面板 CA。这一条只涉及部署，不需要改代码。

### 验收

- Owner 报告的客户端用同一条订阅链接导入成功，节点与分流规则可用；记录客户端名称与版本。
- 新增或调整的格式名称、User-Agent 匹配与规则集地址各有单元测试；真实核测试在两个 mihomo 版本上都通过。
