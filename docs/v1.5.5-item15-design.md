# qui v1.5.5 第 15 项实施设计

## 1. 范围、依据与方案选择

本文件是实施提案，不表示功能已实现或生产已验证。整项 15a–15f 进入 1.5.5；15a 已完成，删除被中转出站引用的入站返回 409 `inbound_has_relay_outbound`。默认新建独立入口，复用为高级选项；无限画布保留。常用操作为「添加中转 → 选择入口及可选中间服务器 → 创建并发布」，一次确认。不可用操作隐藏，进行中防重、当前值及只读展示例外。

依据：`docs/v1.5.5-plan.md` 第 15 节；`AGENTS.md` 10.3、12、14、16、26.9、27.12、27.13。计划中较早的“默认方式待决定”已被“已确认”覆盖。生产方案及端口问题仅引用计划记录，本任务未连接生产。

建议扩展现有 CanvasLayout、规划与部署批次，不另建一套中转执行器。另两种方式的取舍：只用 linked 规则可转送现有目标入口，但不能表达独立用户入口与入口默认出站；另建线路实体及发布器会复制共享依赖、端口及回滚逻辑。两者均不作为本提案主路径。新增接口和结构均在下文标为拟新增。

## 2. 现状：布局、对象归属与发布

`internal/panel/proxy/canvas_repository.go` 的 `CanvasScheme` 对应 `canvas_schemes`，保存 layout_json、updated_at、published_at、published_batch_id；`SaveCanvasScheme` 保存草稿，`DeleteCanvasScheme` 只删画布，运行对象保留。并发使用 updatedAt。

`canvas.go`：`CanvasLayout{Instances,Connections}`；`CanvasInstance` 有 instanceId/ref/x/y/role、listenPort/targetPort、relayPortMode/relayPort。ref 为 server/inbound/outbound/import 加 ID；role 为 entry/relay/exit。`CanvasConnection` 有 id/source/target/type、tunnelId、tunnelProtocol/tunnelPort、supportTcp/supportUdp、旧转发字段。布局严格解码，不能随意塞未知 JSON。服务器执行通过 `canvas_tunnels.go` 的 `saveInlineTunnels`、`resolveCanvasLayout` 将连接持久化或解析为共享 tunnelId；客户端执行维持内嵌合同。

`canvas_tunnels` 保存端点引用、连接参数、稳定分配端口及版本；`canvas_tunnel_objects` 按对象 ID 唯一归属隧道，`CanvasTunnelObject` 与 `objectOwner/ownCanvasObject` 位于 `canvas_tunnel_objects.go`；名字只用于展示与历史识别。`canvas_tunnel_publications` 保存待清理发布关联，不能只看当前草稿判定资源无用。0124 的一次性认领与 0131 `ReconcileCanvasForwards` 不应重新运行名称猜测。

`canvas_publish.go` 的 `canvasBuildPlan/canvasBuildPlanInternal` 生成 `canvasPlan`：edges、chains、entries、节点顺序和归属。`tls` 通道实际为 Trojan/TLS，wireguard 按能力检查；新画布不新增旧 port_forward/GOST 连接。`canvas_ensure.go` 的 `canvasEnsure` 生成目标节点 `InternalRelay=true, SubscriptionVisible=false` 内部入站、源节点配套出站，多边路径生成代理链。内部监听默认 direct，不等于用户入口的最终路径。

现有绑定实际已支持：`canvas_publish.go` 只将 ref=inbound 且 role=entry 的实例加入 `canvasEntry`；`canvasEnsure` 将其 DefaultOutbound 改为配套出站 ID、`chain:<id>` 或最终外部出站。ref=server 的 entry 只表示服务器，不生成用户入站。因此计划记录的生产方案虽有通道，普通入站仍 direct。现有移除连线可能在 `canvasEnsure` 把失去路径的入口改 direct；本项受管入口必须改为显式恢复或阻止，不能继承此行为。

`canvas_plan.go` 的 `PlanCanvasScheme` 复用 build、归属差异、监听冲突与引用检查；`canvas_ports.go` 的 `canvasAllocatePorts` 复用 `portOccupants/allocatePorts`。现有内部监听有历史默认端口兼容分支，新用户入口不使用该分支。

`canvas_publish_apply.go` 的 `PublishCanvasScheme` 顺序为 build → canvasApplyPlan → canvasSnapshots → Deploy.PublishCanvas → markTunnelPublication。`canvasApplyPlan` 的 canvasUndo 只覆盖 ensure 失败；陈旧资源删除失败返回 warnings。不能声称它已覆盖快照失败、批次创建失败或异步 Agent 失败后的全部数据库恢复。`canvasSnapshots` 复用 `RelaySnapshots/SnapshotIntent`、按目标先于源排序；部署包 `batches.go` 的 `queueRollback/RollbackBatch` 负责运行修订回滚。

## 3. 15b：用户入口绑定及迁移 0146

### 3.1 布局与入口对象

拟在 `canvas.go` 的 CanvasInstance 添加可选 `entryBinding`，仅 server execution 的 entry 可用：`{mode:create|reuse, inboundId?, protocol?, core?, portMode:auto|manual, port?, groupIds:[]}`。create 保持 server ref，生成后的 ID 在服务端归属表记录；reuse 指定同服务器的具体普通用户入站。不得绑定 internalRelay、已删除或不支持的入站。旧 inbound entry 读出为待确认的历史复用，不能凭当前出站推断原值。

扩展 `canvasPlan/canvasEntry`，使计划包含待建用户入口、端口、协议、分组差异与目标路由；`canvasEnsure` 在依赖对象就绪后创建用户入口，再接默认出站。入口 `InternalRelay=false`、订阅可见，名称建议「A → B」，多跳为「A → M → B」；名称不做身份键，重复名字按既有校验明确报错。端口从入口服务器 node_meta 范围经 allocatePorts 分配，纳入同次计划全部监听占用；无范围或耗尽返回 no_free_port，不退到 8443。预览仅建议端口，执行重新校验并固定实际端口。

复用 `SaveInbound` 的协议设置和凭据生成路径，不复制出口凭据或用户密码。入口默认协议沿用出口入站，须通过 `ValidateInboundCore` 与 TCP/UDP 能力校验；不同核心时提议明确的同类可用协议并显示转换结果。没有同类协议则阻止并要求选择，禁止任意选协议。TLS、Reality、WireGuard 等必要参数仍走既有生成/校验；同类协议映射表和可自动完成的协议范围待 Owner 确认。

### 3.2 0146 表结构提案

迁移文件拟名 `0146_canvas_entry_bindings`，实际目录及序号实施前核对，避免与其他项迁移冲突。新增：

- `canvas_entry_bindings`：id TEXT PK、scheme_id TEXT 可空、instance_id TEXT、inbound_id TEXT NOT NULL UNIQUE、mode TEXT CHECK(create/reuse)、original_default_outbound TEXT（reuse 必填，create 为空）、applied_default_outbound TEXT、state TEXT、updated_at TEXT；方案有效时 UNIQUE(scheme_id,instance_id)。scheme_id 删除置空保留运行归属；inbound_id 外键禁止误删受管入口。
- `canvas_entry_publications`：operation_id TEXT PK、binding_id TEXT、batch_id TEXT 可空、action TEXT CHECK(publish/remove)、status TEXT、before_json TEXT、after_json TEXT、created_at/updated_at TEXT。before/after 为严格类型的入口、分组及生成对象恢复材料；含密封数据时复用 vault，接口不返回秘密。用于重启后关联批次和补偿，不允许仅靠进程内 undo。

新入口归属于方案绑定，不塞进语义为“隧道所有”的 canvas_tunnel_objects；通道对象仍由 tunnelId 归属。仅删除画布后绑定保留，scheme_id=NULL，成为可追踪遗留入口。原出站在首次真正接管前事务写入，后续发布不覆盖；原出站字符串保留 direct/block/普通 ID/chain:ID 的既有编码。恢复前同时校验目标存在、启用、节点适用与无环。禁止将失效引用通过外键级联丢失。

### 3.3 分组、授权与订阅

发布请求拟加 `entryGroups:{mode:exit_groups|explicit|none,groupIds?:[]}`，建议默认 exit_groups，但尚未成为 Owner 决策。预览展开出口入站当前所在且用途合格的分组；执行重查成员和版本，变化则要求刷新确认。不自动授权全部用户，不添加显式服务器成员代替用户入站。复用入口默认保留其现有分组，新增分组须明确列出。绑定 groupIds 与请求解析结果应同一版本，禁止两处相互覆盖。

`LineGroupPage.vue` 已以具体入站授权；新入口通过 node_group_inbounds 加入目标组，沿用自动凭据发布与 SnapshotIntent 的 AccessReader。客户端订阅取新入口的成功运行配置、A 的连接地址/端口和按该入站授权的用户凭据，显示「A → B」；不能取 B 的用户凭据或把内部监听暴露为订阅节点。应在所有必要节点确认成功后才激活新增成员及入口订阅；若组关系提前写入供快照生成，订阅读取必须按待发布状态过滤，避免中途暴露。

`node_relays.go` 的 `CreateNodeRelay/NodeRelayRules` 与 GET/POST `/nodes/{id}/relays` 属于另一条 linked 模式：规则入口监听将流量转送目标用户入站，凭据属于被授权的目标入站。`relaySnapshot/saveRelaySnapshot` 写 `tunnel_rules.published_snapshot`，只能成功发布后推进。新画布用户入口是终止认证再代理，不创建重复 linked 规则，不伪造 published_snapshot；若用户在新入口上另建 linked 规则，目标仍为新入口 ID，沿用其授权和 published_snapshot。订阅链路名称展示可加只读路径元数据，不能更换订阅身份键。

## 4. 三步完成接口与失败语义

拟新增 Owner+CSRF `POST /api/v1/relay-schemes/quick/plan`（只读）与 `POST /api/v1/relay-schemes/quick`（实际创建）。输入 `{requestId,entryNodeId,middleNodeIds:[],exitInboundId,entryGroups,entryProtocol?}`；确认请求附预览版本令牌。允许跳数沿用现有代理链限制，不引入无限跳。入口在 B 入站卡片触发时预填 exitInboundId，在 A 服务器触发时预填 entryNodeId，缺失项在同一选择面板补齐。

拟新增 `canvas_quick.go` 构建普通 CanvasLayout，先统一做引用、环路、协议及端口规划；将 PlanCanvasScheme 的内部规划抽为接收内存 CanvasScheme 的共用函数，使预览不保存临时方案。执行通过 SaveCanvasScheme 及 PublishCanvasScheme 共用内部服务，不在 HTTP handler 串调用 HTTP，不在持锁函数内再次获取 canvasMu。接口返回 `{schemeId,operationId,batchId,nodes,warnings}`，批次尚未确认返回 202；前端只显示发布中，成功轮询后显示用户可用条件。

一次确认列出新增入口、协议转换、全部通道、分组授权及受影响现有用户。requestId 应持久唯一（可在 entry_publications 加 UNIQUE request_id），重复请求返回同一操作，避免网络重试重复建入口。

预检失败无业务写入；物化/快照/批次创建失败恢复本次数据库变更并保留原始及补偿错误。批次开始后由现有 deployment 批次反向回滚运行修订；新操作记录等待终态后恢复生成对象和分组，草稿保留可重试。rollback_failed 保留操作及归属，阻止下一次冲突发布并显示逐节点原因。进程崩溃由持久操作记录恢复关联状态，不推断成功。不能直接复用现有“旧对象删失败仅 warning”来宣布撤除成功。

`ProxyNodeListPage.vue` 当前把 internalRelay 映射为普通卡片，需在普通入站映射前过滤；`LineGroupPage.vue` 的 allAvailableNodes 在候选层即过滤 internalRelay，而不仅保存时拒绝。内部对象仍可在方案详情及遗留视图读取。

## 6. 15d：停用并移除与仅删除画布

拟新增 `POST /canvas-schemes/{id}/remove-plan` 和 `/remove`，输入 updatedAt 与可选 `restoreTargets:{bindingId:defaultOutbound}`。扩展 CanvasPlanResult：入口删除/恢复、分组移除、保留共享对象及引用者、受影响节点与发布顺序。复用 canvasBuildPlan、canvasStaleObjects、canvasCheckReferences、canvasListenerConflicts 和 canvasReferrers；撤除模式不能简单使用空布局触发现有 direct 分支。

执行先处理用户入口：create 禁用/移除订阅成员并发布入口停止；reuse 恢复原默认出站并发布确认。再按消费者到提供者移除代理链、配套出站、内部监听，节点按入口→中间→出口确认，避免尚有用户流量时先切断接收端。数据库外键删除顺序同样链→出站→监听；逻辑撤除和最终物理删除分阶段，保留回滚所需材料及端口声明直到确认。

共享资源按 tunnelSchemes、其他方案发布关联、canvasReferrers 与策略引用共同保护；保留并列出引用者，不按名称整批清理。复用入口当前出站已被外部改动、原出站缺失/禁用/有环时返回 409，要求 Owner 明确恢复目标或先处理引用，不默认 direct。指定 direct 必须是 Owner 的显式选择。分阶段用同一 operation 串联现有批次，失败按阶段恢复运行及数据库，成功前不删方案与归属证据。

原 DELETE 保持“仅删除画布”的次级语义，文案明确保留入口、分组和运行资源；0146 的归属记录转为 detached。前端无可撤除对象时隐藏主按钮。涉及 canvas_handler.go、canvas_publish_apply.go、canvas_tunnel_lifecycle.go、canvas_objects.go、拟新增 canvas_remove.go 及 RelayCanvasPage.vue；迁移复用 0146 操作记录。

## 7. 15e、15f：遗留资源与分项状态

`canvas_tunnel_objects.go` 的 LegacyCanvasObjects 与 `/canvas-tunnels/legacy-objects`、显式 adopt 是已有基础，但“没有归属的历史名字”不足以覆盖“归属存在、方案已删”的对象。拟新增 GET `/relay-schemes/legacy-resources`，按通道/绑定汇总当前归属、历史发布、内部监听、出站、链、引用者、运行修订、可清理原因；结合 orphan binding、无当前方案但仍有发布关联的 tunnel 和未认领旧对象。名字只提供线索，未知归属标待核实，不自动认领。清理复用 remove-plan/remove 的同一服务，生产清理另行授权。

切片 10 实现 GET `/canvas-schemes/{id}/status`，投影 `{draft,batch,nodes,entries,subscription,probe}`，沿用现有画布 Owner 读取权限（Viewer 返回 403）。draft 比较 updatedAt 与 publishedAt，未发布为有修改；batch 通过部署模块现有 Batch 读取接口取得批次及各节点结果；nodes 独立比较运行修订与批次期望修订；entries 读取持久绑定及入站当前路由，不将绑定状态当作 Agent 确认。subscription 逐条检查入口存在、启用、订阅可见、至少一个启用的 subscription/mixed 分组、客户端连接地址及批次成功。管理员总体条件不等同每个用户均有权限，也不表示真实连通。

probe 只关联已保存 TCP 探测命令中可精确匹配入口 IP 与端口的最近结果，并展示探测来源节点、时间与结果；这些结果仅说明入口 TCP 可达性，不验证认证或整条中转路径。域名入口没有可靠的历史解析关联时显示未探测。入站 reachability 未持久化，不能作为历史结果；查询不主动探测、不写库、不缓存推断结果，不新增迁移。单节点发布没有批次 ID 时批次保持为空，订阅条件明确提示批次尚未成功。

RelayCanvasPage.vue 的方案详情分别显示上述六项；发布返回仅提示请求已提交。批次 deploying/rolling_back 时每 3 秒轮询，终态停止，切换方案与离开页面取消旧轮询；读取失败显式显示错误，可手动刷新。客户端执行方案保持原订阅发布语义。

### 切片 9 实施边界（2026-11-14）

新增 Owner 只读 `GET /api/v1/relay-schemes/legacy-resources`，返回 `detached`、`orphanTunnels`、`unowned`。前两类按保存的通道端点引用与入口绑定构造连通组，列入口、服务器、模式、原出站／当前出站、通道对象、外部引用者和操作阻止原因。无归属对象复用既有历史对象筛选及显式 adopt，标记「归属待核实」。查询共用抽取的只读 helper，不触发 `ReconcileCanvasTunnels`，不按名称认领或清理。当前方案布局引用的通道不进入遗留组；其他方案仅保留历史 publication 关联时仍列为引用者并阻止完整撤除。

新增 Owner＋CSRF＋审计的 `POST /api/v1/relay-schemes/legacy-resources/reattach`，输入 `{bindingIds?,tunnelIds?,name}`，成功返回 201 `{schemeId}`。所选资源须连通；非连通返回 400，端点缺失、入口同时匹配入站与服务器端点、多绑定匹配同端点、实例 ID 重复、分叉／汇合或环路等无法还原情况返回 409，`error.reasons` 逐条说明。仅使用持久引用还原布局，不从名字或当前出站猜测缺失连线。

重新挂接在同一事务创建 server 草稿、重设 detached 绑定归属并保留原 instance_id、mode、original/applied 默认出站；已有 `published_version` 的通道补入新方案的 publication 关联，以便后续草稿删边后撤除规划仍能识别对象。新方案 `publishedAt` 保持为空，不将历史关联表示为新方案已发布。不修改入站、出站、链、分组或运行配置，不生成 Revision、不调用部署。遗留视图展示归属与引用证据；运行修订和订阅可用性继续由切片 10 的方案状态接口展示，不根据挂接结果推断。

前端仅在资源非空时显示「遗留资源（N）」，N 为 detached 连通组、orphanTunnels 连通组及 unowned 对象的总数。不可操作按钮隐藏并显示原因；「重新挂接为方案」选中新草稿，「完整撤除」先挂接再打开既有 CanvasRemoveDialog，仍须完成影响预览、恢复目标选择及改动确认。不新增撤除执行器，不改变 canvas_remove 的执行语义，不新增迁移；未连接生产或执行生产清理。

## 8. 兼容、备份与能力边界

旧方案缺 entryBinding 时显示「通道已部署，用户入口未绑定」或「历史入口，恢复目标未登记」，不得自动修改原有入站。Owner 可显式新建入口升级；复用旧入口须预览当前路由并指定可核实恢复目标。0146 不自动猜原出站。客户端执行方案拒绝新绑定字段，保持 client_published_layout 语义。

## 10. 风险、待核实与需要 Owner 决定的点

主要风险：复用入口改变现有用户出口；组关系提前写入导致订阅越过发布确认；批次运行回滚与数据库草稿不一致；共享通道被误删；断电发生在物化和批次关联之间；撤除中端口过早释放。以上通过明确预览、持久操作、版本校验和确认后清理处理，禁止静默转 direct。

待核实：现有发布器在进程重启与备份恢复时的回调接点；组自动凭据发布如何避免与方案批次抢占节点；全部协议默认材料能否自动生成；订阅成功快照的具体字段扩展位置。上述接点未完成逐行追踪，实施切片开始前必须补足，不能据本文直接宣称已有完整事务保障。

需要 Owner 决定的点：

1. 新建入口是否默认加入出口入站所在且用途合格的节点分组？提案默认 exit_groups；也支持显式选择或不入组。
2. 入口协议是否默认沿用出口协议？入口核心不支持时，同类协议的具体映射和自动选择顺序是什么？无同类协议时提案要求手动选择。
3. 旧方案已有用户入口、却没有原出站记录时，是否统一要求 Owner 显式登记恢复目标后才能接管和撤除？
4. 停用并移除独立入口时，是否删除该入口后来人工加入的其他分组关系及人工修改过的配置，还是遇到这些变更就阻止并要求处理？
5. 仅删除画布后，遗留视图是否允许重新挂接方案与完整撤除两种操作？提案保留归属证据，不自动清理。
6. 撤除跨节点分阶段发布是否接受短暂中断？提案先停止/恢复用户入口，再清理通道，不承诺保持既有会话。

### Owner 决定（2026-11-13）与审查结论

1. 新建入口默认加入出口入站所在且用途合格的节点分组（exit_groups），也可显式选择或不入组。
2. 入口协议由用户自行选择：快速创建对话框只列入口服务器核心支持的协议（不支持的隐藏），预选出口入站的协议（入口支持时），用户可改；不做自动映射。
3. 旧方案已有入口、无原出站记录时，须 Owner 显式登记恢复目标后才能接管或撤除，不默认 direct。
4. 停用并移除独立入口时，若该入口后来被人工加入其他分组或人工改过配置，先阻止并列出这些变更，由 Owner 确认后再继续。
5. 仅删除画布后，遗留视图同时提供「重新挂接方案」与「完整撤除」。
6. 撤除接受短暂中断：先停止或恢复用户入口，再清理通道，不保持既有会话。

审查结论：只新增 `canvas_entry_bindings`（迁移 0146）；不新增 `canvas_entry_publications` 持久操作表，回滚与状态沿用现有部署批次记录，快速创建的幂等用绑定表上的 request_id 唯一约束实现。若实施中证明必须有独立操作记录，再提出。

## 13. 切片 6 后端：快速创建

新增 Owner＋CSRF 的 `POST /api/v1/relay-schemes/quick/plan` 与 `POST /api/v1/relay-schemes/quick`。输入为 `{requestId,entryNodeId,middleNodeIds:[],exitInboundId,entryProtocol,entryCore?,entryGroups:{mode,groupIds?}}`，拒绝未知字段；入口协议必填，分组模式未指定时采用 `exit_groups`。预览复用内存规划，返回原有 `CanvasPlanResult`，包含 entries、servers、conflicts、warnings；规划失败时 `ok=false`，不写库。

执行构建普通服务器画布：入口 server＋create 绑定、可选中间 server、出口 inbound，方案名为「入口服务器 → 出口服务器」。连线采用新建代理中转的 `proxy_chain`＋`tls`，TCP 开、UDP 关，避免只支持 TCP 的出口被默认 UDP 拒绝；未指定固定端口，复用既有端口分配与链跳数校验。用户入口自动分配端口，无可用端口时规划失败。

执行返回 202 `{schemeId,publication,warnings}`，publication 含真实入口、批次 ID 及节点发布状态；202 表示请求已提交，运行结果仍由批次状态确认。幂等复用 `canvas_entry_bindings.request_id` 唯一约束，在物化后、提交部署前写入；同一 canvasMu 覆盖查找、规划、保存与发布，不重复加锁。重复请求返回原方案、原入口和当前批次节点状态，不再次发布；绑定记录独立于画布布局，编辑草稿不丢失请求标识。已删除方案或未完成发布关联的请求明确报错，不新建第二个方案。

仅快速创建将物化 undo 保留至部署接收：物化、快照或批次创建失败时逆序恢复对象与分组，删除本次方案和本次新建连线，保留原始错误；补偿失败时保留方案供检查，并附补偿错误。部署返回错误和批次 ID 时读取批次状态：仍为 draft 则删除未启动批次并恢复本次创建；已启动则保留方案及对象，失败交给部署批次回滚，返回警告或当前节点失败状态。不增加迁移、独立操作表或崩溃恢复执行器；普通画布发布的补偿边界不变。

## 14. 切片 8 后端：停用并移除

新增 Owner＋CSRF 的 `POST /api/v1/canvas-schemes/{id}/remove-plan` 与 `/remove`，严格接受 `{updatedAt,restoreTargets?,acknowledgeChanges?}`。预览只读，返回 `ok`、`entries`、`objects`、`nodes` 与 `changeDetectionRule`；执行重读规划，版本过期返回 409，未确认改动或恢复目标不可用返回 409 `canvas_remove_conflict`，`error.details` 携带影响预览。

现有绑定只保存 applied 默认出站，没有完整配置及初始分组快照。因此 create 入口列出所有当前分组，默认出站变化单独展示；完整配置基线缺失也要求 `acknowledgeChanges=true`，并返回当前协议、核心、监听地址与端口，不把可编辑草稿当成创建时证据。外部引用阻止入口删除，确认参数不能绕过。reuse 恢复原出站，原值缺失、失效、禁用、节点不适用或成环时须显式提供目标；旧布局未绑定入口的请求键在预览中为 `legacy:<instanceId>`，不推断 direct。

通道按当前草稿、历史发布关联、对象归属与引用关系规划；其他方案、策略、linked 规则及普通对象使用的资源保留，保护沿依赖传播。发布顺序为先停止 create 入口或恢复 reuse 路由并等待确认，再按入口→中间→出口停用可删除通道并等待确认，最后删除分组成员、入口、绑定、通道对象与方案。失败沿用数据库 undo 与部署批次／单节点回滚，保留方案及原始错误。
