## 2. 当前数据与引用链

### 2.1 来源已经有可推导的类型

`internal/panel/subscription/importer/store.go` 的 `Source.Kind`、`sourceKind()` 已区分 `content` 与 `url`，没有独立 SQL 类型列。判定依据是 `subscription_sources.url_encrypted` 解密后的明文：空串为粘贴来源，非空为 URL。`Store.Save()` 接收互斥的 `Input.Content` / `Input.URL`；粘贴内容解析后保存节点，并密封空 URL。`Store.Refresh()` 对空 URL 返回 `ErrContentSource`，不执行抓取。

特别注意：当前 `sourceKind()` 在解密失败时返回 url。0147 转换不能使用该返回值作迁移判定；必须直接解密并返回原始错误，避免把损坏的粘贴来源错误认定为机场。不能使用名称、节点数、抓取时间或状态猜类型。旧接口还允许同一来源被重新提交内容/URL，实施时需明确阻止已有稳定节点来源在普通保存中切换类型，避免绕开引用转换。

前端 `web/src/modules/proxy/importApi.ts` 的 `importSourceKind()`、`proxySourceType()`、`airportSources()`、`loadImports()` 已消费该类型，把 content 映射为 manual、url 映射为 subscription。这不代表逐节点编辑和分组包装已经解决。

### 2.2 加密缓存结构

`migrations/0116_subscription_sources.sql` 建立：

| 表 | 当前关键字段与意义 |
| --- | --- |
| subscription_sources | id、name、url_encrypted、interval_seconds、last_fetch_at、last_status、last_error、created_at、updated_at；0133 加 last_success_at、latest_result_json |
| imported_proxies | id、source_id、name、protocol、payload_encrypted、fetched_at；source_id 删除级联 |
| user_source_grants | 历史来源授权；当前实际访问由节点分组授权决定 |

`Store.replace()` 先删除来源缓存，再把每个 `proxy.Proxy` 序列化为 JSON，整条使用配置 Vault.Seal() 密封。明文 name/protocol 是检索元数据，真实协议、连接地址、端口、TLS、传输与凭据等在密封 Proxy 内；没有保存可直接编辑的原始分享链接正文。当前行 ID 为 `sourceID + "-" + id.Hash(JSON)`，名称也参与哈希。`seen[pid]` 按完整内容去重。

`Store.Items()` 解密缓存，返回 id/sourceId/proxyKey/name/protocol/server/port，proxyKey 当前为 `name|protocol`；不返回凭据。`Store.Proxies()` 在分组授权 SQL 筛选后解密，覆盖 `Origin{Source:"import:"+sourceID, Ref:行ID, Labels:授权分组标签}`。因此只改明文 name 或只改密封 Name 都会造成两份名称不一致。

## 3. 稳定身份与来源区分

### 3.1 方案比较与建议

建议复用 `imported_proxies.id` 为 content 的稳定业务 ID：新节点使用项目 `internal/platform/id.New()`，在成功分析、正式入库时逐条生成；改名永不重算 ID。旧 content 行在 0147 中各生成一个新 ID，并记录旧行到新行映射。url 行继续使用原内容哈希。

替代方案一是在密封 Proxy 内增加 ID：需要同时维护明文检索键和密封 ID，且现有备份严格解码受影响，不利于授权 SQL。替代方案二是永久独立身份映射表：需要维护缓存替换、删除与映射生命周期，增加双重身份。两者都可以实现，本设计建议让缓存行本身成为 content 的持久节点实体，仅保留迁移映射作为迁移证据，不参与日常名称解析。

旧 content 内容哈希 ID 原地冻结也能成为稳定身份，并可省去画布 ref 重写；代价是新旧 ID 生成语义不同且要清楚声明永久不再 replace。本文选择显式转换方案是为了统一 content 身份生成和留下可审计映射，这是设计建议，非 Owner 既定决定。

### 3.2 新引用协议

- 分组 content：`proxy_key = "id:" + imported_proxies.id`；url：仍为空或 `name|protocol`。
- 客户端策略 content：`@endpoint:import:<sourceID>:id:<nodeID>`；url：继续 `@endpoint:import:<sourceID>:<name|protocol>`。
- 画布 content：`import:<nodeID>`，沿用现有语法，迁移只替换 ID；url ref 不变。
- `Origin` 建议新增运行期 `ImportKind`（content/url），必须标记 `json:"-"`，由 `Store.Proxies()` 在读取后设置；EndpointRef 仅在 content 分支使用 `Origin.Ref`。当前 URL 内容 ID 对完整 Proxy JSON 做哈希，新增字段即使为空也可能改变旧序列化字节，故该字段不得进入加密缓存 JSON 或哈希输入；验收须确认 URL 序列化字节与哈希 ID 完全不变。

不能仅看到 `id:` 前缀就猜来源类型：旧 URL 节点名也可能以它开头；分组匹配先按来源类型分派，旧规则语法以完整结构（包括 `|protocol`）解析。新 ID 使用 id.New() 的不含冒号/竖线字符集，满足现有画布 token 约束。

content 禁止再走删除全部缓存后重算 ID 的普通 replace 路径。新粘贴批次创建独立内部来源与多条节点，逐条管理；对已有来源重贴整批内容、切换为 URL 的旧写路径应明确拒绝并指向新增节点操作，不能静默替换身份。是否继续支持批次替换见 Owner 决策项。

## 4. 0147 一次性转换与授权不变量

### 4.1 SQL 与 Go 分工

建议 `migrations/0147_imported_proxy_identity.sql` 只做结构变更：创建单行一次性标记表 `import_identity_reconcile`（done 初始 0）和迁移映射表 `import_identity_map`（source_id、old_proxy_id、old_proxy_key、new_proxy_id），并为 imported_proxies 增加整数 revision（初始 1）。映射表仅记录不含凭据的身份材料，不被正常解析器用于兼容名称查找；其生命周期与归档校验一并管理。

来源类型仍由密封 URL 判定，不强加 SQL 默认类型。SQL 已能读取行 name/protocol/id，但无法可靠判定来源类型或验证密封名称，故核心转换必须在 Vault 可用后由 Go 执行。建议新函数 `Store.ReconcileImportedIdentities(ctx)`，并提供事务内版本供恢复协调器调用。模块间通过 platform/server 注入事务协作函数，避免 importer 引入 rules/proxy 后形成循环依赖。

沿用 `proxy/tunnels_migration.go:Repository.ReconcileCanvasForwards()` 的模式：事务内读取 done；已完成直接返回；节点、引用、映射、报告和 done 同一提交。不能先写 done 再转换，也不能因某来源失败而宣称全库完成。

### 4.2 转换步骤

1. 在接受 HTTP 编辑、订阅读取或后台刷新前执行。读取来源并逐一解密；错误直接中止，包含原始原因的服务端日志只记录必要 ID，不记录 URL/凭据。
2. 对全部 content 条目读取明文元数据并解密验证 Proxy；要求两份名称/协议一致。为每行分配新 ID，建立 `(source,old row ID) -> new ID` 和 `(source,name|protocol) -> 新 ID 集合`。保留连接参数、凭据、状态和时间，迁移不抓取、不发布。
3. content 的旧整源分组成员展开为该来源**所有已存缓存行**的显式 ID 成员；旧非空键展开为所有匹配行。合并重复成员，不迁移 url 成员。来源 failed 时也保留缓存的成员范围，不能用 usable=0 把成员清空，以免损失后续可恢复范围。
4. 扫描 `client_policy_profiles.template_json` 中全部活动/未启用配置及禁用组/规则，扫描 `system_settings.client_rules` 活动快照；将 content 精确成员改为新 ID 成员。旧一键多匹配要在原位置展开并去重，保持成员顺序。活动配置和活动快照须保持一致，不遗漏独立 revision。建议同事务推进被改模板 revision、活动快照 revision，确保旧浏览器草稿得到冲突响应，具体依照 profiles 现有并发实现。
5. content 的 `@source:<sourceID>` 建议展开为当时来源的全部显式 ID 端点，仍由用户授权管线过滤。url 的 `@source` 完全不动。此举冻结原粘贴来源范围，是否采用列为 Owner 决策，不应偷偷扩大到全来源模板重写。
6. 对 `canvas_schemes.layout_json` 和 `client_published_layout` 解码成 CanvasLayout，仅将实例的 `import:<old row ID>` 改为对应新 ID；不改 instanceId、连线、路径、执行方式、运行资源或连接参数。更新时间/并发戳，使并发旧草稿不能覆盖转换。显示缓存按新数据投影；不得字符串全局替换任意 JSON。
7. 写回新行 ID 与映射，核对下面的不变量，最后写 done=1 并提交。中途错误全事务回滚；重启重试不会留下半套引用或第二套节点。

### 4.3 授权一致性必须按集合检查

以旧行 ID 映射到新行 ID 后比较每个 `(group,source)` 的可达缓存节点集合；再比较每用户经启用/可见/用途、协议及来源状态过滤后的最终端点集合与分组标签集合。所有 url 行、引用及其集合保持不变。迁移不改 user_node_group_grants、组 enabled/purpose/subscription_visible，不从显式服务器推导授权，也不从 user_source_grants 复活授权。

客户端模板比较的是显式成员和来源成员的原始端点集合；画布比较的是实例对应端点与已发布链的跳点集合。显示名和存储 ID 变化不能导致授权增加、丢失或从整链变成部分链。订阅汇总现有名称去重另外核对，不能仅以授权 SQL 一致冒充所有格式输出一致。

对无缓存的整源成员，展开为空会冻结为空，不授权以后新导入的节点。对悬空旧键、悬空画布 ref，不能把它改成整个来源、第一条节点或 direct。建议输出明确对象清单并阻止完成转换，交由 Owner 决定保留显式失效引用的表达或清理；实现不得删除后继续。该异常策略须先确认，尤其草稿当前允许 unresolved import。

`SaveGroup()` 当前 imports 数量上限为 200；展开后可能超限。禁止截断。建议服务端/API/前端按实际产品容量统一调整校验并验证请求体大小，或设计支持存量大集合保存的明确规则；具体上限由 Owner 决定，不在迁移中塞入隐藏上限。

### 4.4 启动与恢复入口

`internal/platform/server/server.go` 已调用 ReconcileCanvasForwards，应在 Vault 初始化、schema 升级后，以及后台任务和路由服务开放前接入 0147。恢复的候选库与进程内事务都要使用同一转换逻辑。

`internal/platform/recovery/database.go` 在候选库打开后调用旧画布转换，但之后还会从冻结当前库附加并复制权威数据；**不能只在该早期位置加一次转换就结束**。须在 sources、group imports、profiles、canvas 草稿/快照的最终权威数据全部落位后、验证与切换候选库前运行，标记必须与这套最终数据同源。精确插入顺序实施前待核实。

`importer/recovery.go:PrepareRestoreTx()` 明确保留冻结当前来源与授权权威数据；`node/group_recovery.go` 也复制当前导入成员。旧归档恢复时不可拿归档 done=1 跳过从旧当前库复制来的未转换引用；同样不可拿当前 done=1 跳过归档独有的旧画布。应先统一最终数据与映射，再提交一个与最终候选内容一致的完成标记；发现旧当前画布混配时明确报错，不能按相同显示名猜目标。

## 5. 改名接口与显示传播

建议 Owner-only、沿用 Require/CSRF 的 `PUT /api/v1/imported-proxies/{id}/name`，请求 `{name, expectedRevision}`；响应完整无凭据节点元数据与新 revision。节点不存在 404，url 节点 409 `import_node_readonly`，输入错误 400，重名 409 `import_node_name_conflict`，过期编辑 409 `stale_import_node`，存储失败 500。revision 建议通过 0147 增加 imported_proxies 的整数 revision，初始为 1；若最终选择使用密文摘要并发令牌，应明确替代，不拿 fetched_at 充当改名版本。

建议 name 去掉首尾空白，1–200 UTF-8 字节，拒绝控制字符和换行，失败返回字段错误并保留输入。该长度沿用来源现有 200 字节约束作为提案，并非现有节点名称已按此限制。旧合法长名称不得在迁移中裁剪；新改名提交按新边界校验。名称可含 `|`、冒号等普通字符，稳定引用不再依赖它们。

同来源建议禁止完全相同的名称（跨协议也拒绝），无需通过给名称追加数字实现暗中改名。跨来源同名和与自建入站同名还会触发 Registry.Collect() 去重，见 §8 与 Owner 决策。

事务内按 id、content 类型、revision 校验，解密 Proxy，只改 `Proxy.Name`，重新密封，同时更新明文 name 和 revision，保留 ID、source_id、protocol、fetched_at、凭据及连接参数。持有与 Save/Refresh 相同写入互斥约束，实际提交以事务和版本检查为准。审计只记录节点 ID 与动作，日志保留原始错误，不输出凭据。不能调用 replace() 或来源 update 冒充节点改名。

`Store.Items()`、`Store.Proxies()` 是节点名的权威读取点；列表、分组、候选读取当前名，画布按稳定 ref 解析当前元数据，不把实例快照旧 name 作为权威。已发布客户端链的内部 `chain-<scheme>-<instance>` 标识保留其依赖用途，用户可见标题应明确投影当前节点名，不能直接改内部链标识破坏 DialerProxy。

改名保持显式成员身份和授权；关键词策略本来按名称做 NFKC/大小写筛选（membership.go 的 matchesKeywords），真改名可能改变关键词命中，必须在保存响应/界面展示实际影响。不能承诺“改名后所有策略组成员集合不变”；显式 ID 引用不变与关键词筛选结果变化应分别说明。

## 6. 单节点删除与影响确认

16f 实施口径（2026-11-14）：Owner 使用 `GET /api/v1/imported-proxies/{id}/deletion-preview` 查询 `{node,groups,clientPolicies,canvases,lastInSource}`；`DELETE /api/v1/imported-proxies/{id}` 提交 `{expectedRevision,removeReferences}`，沿用管理员 CSRF。删除事务内重新查询当前引用，节点修订过期返回 409 `stale`。URL 节点返回 409 `import_delete_unsupported`；草稿或已发布客户端画布引用返回 409 `import_in_use_by_canvas`，要求先修改并发布方案；精确分组或客户端策略引用未确认时返回 409 `import_referenced`。确认后同事务移除 `id:<id>` 分组成员及客户端策略中的精确端点成员、排除项，复用策略保存校验与修订更新；策略组删空校验失败则返回 409 并列组名，全部回滚。节点分组按现有规则允许保留为空。只删除指定节点，最后一条删除时同时清理隐藏空来源，操作日志为「删除导入节点」。此处按本次 Owner 请求采用节点修订与服务端事务内重查，不新增下文早期建议的确认 ID 或影响摘要字段。

建议增加 `GET /api/v1/imported-proxies/{id}/deletion-preview` 和 `DELETE /api/v1/imported-proxies/{id}`；后者提交 confirmNodeId、expectedRevision、impactDigest。预览列节点名与类型、各分组/授权用户影响、全部保存客户端配置的精确成员与动态关键词/来源匹配、草稿画布实例、已发布客户端链、同来源剩余节点数。预览只读，不返回凭据。确认时事务内重新计算影响摘要，不一致返回 409，用户重新审阅；不能拿客户端列出的引用作为实际删除范围。

建议有分组或精确策略引用时，经一次明确确认原子移除对应 ID 成员并删除该行；不改同来源其他行、不删来源、不删除 URL 节点。最后一条节点删除后可保留隐藏空来源，避免无意级联清理旧对象；是否自动清空空来源由 Owner 决定。

已发布客户端链仍引用该节点时建议阻止删除，列方案名称与跳点，要求先修改并发布链；草稿画布引用建议阻止并提供定位。另一可选策略是确认后使相关完整链失效并显式保留失效实例，不能把链余下跳点拼成直连。两种产品行为待 Owner 决定，实施不能先选择破坏性批量删除方案。动态模板无持久 ID 成员可删，只报告节点消失后的空组/emptyPolicy 影响。

需要跨 importer/node/rules/proxy 的事务协作，通过应用协调器收集引用并执行；复用各模块现有解码和校验，不在 handler 中写分散 SQL。审计只记录节点与引用对象 ID。影响计算失败、引用变化或事务失败均返回明确错误，不显示删除成功。

## 8. 备份、恢复与导出兼容

`internal/panel/system/backup/imports.go:validateImports()` 已校验 0116 存在性、URL 解密、密封 Proxy 严格字段解码、0133 结果及时间一致性。0147 需版本分支校验：新 revision、标记/映射结构、ID 唯一性、content 引用目标/source 归属、明文与密封名称/协议一致；旧归档没有 0147 仍合法，迁移后再作新规则校验。不能改用要求旧归档立即包含新字段的验证器。

由于建议增加 revision，`importer/recovery.go` 的 `INSERT INTO imported_proxies SELECT *` 必须改为按归档版本显式列复制；旧库缺列时显式写初始 revision=1，不能出现新旧列数不符。0147 rewind 同时移除 revision 列、标记表和映射表，并接入实际最新版本回退链。标记和映射要进入备份清单、验证和恢复权威来源选择；涉及 `backup/inventory.go`、backup 版本回退链、platform/recovery，具体归档结构持有文件实施前待核实。`AGENTS.md` §26.9、§31 在实施阶段须同步登记，本文任务不修改它们。

便携备份恢复和进程内恢复分别验证：0147 前归档、含完整 0147 的归档、旧当前库叠加新归档、新当前库叠加旧归档、重复恢复。恢复不能重新给已稳定节点发 ID，不能重新抓 URL、恢复已撤销的来源授权或自动发布 Agent。降级到不识别 0147 的旧程序必须沿项目既有匹配数据库恢复规则，不承诺旧二进制能理解新引用。

名称输出要逐格式检查，不能假定只改 Proxy.Name 就全部完成：

1. `subscription/source/source.go:Registry.Collect()` 在规则展开之前按 endpoint.Name 全局去重，首个保留、后续丢弃并警告。改名跨来源撞名可能使本节点或其他节点消失，即使授权行完全没变。候选也复用授权订阅管线，可能同时消失。需决定拒绝冲突或采用显式消歧方案，不能静默接受后声称引用都有效。
2. URI/Base64 与 Clash 系列应沿现有导出器传递新名称，并验证规则组引用使用同一输出名；协议过滤与原警告不变。
3. `subscription/format/singbox/singbox.go:renderOutbound()` 当前 tag 使用 Origin.Node.Name、Origin.Ref、Protocol，WireGuard 分支也基于 Origin，而非 Proxy.Name。需要为 content 节点引入使用新名称的有范围分支，并同步所有 tag 引用、DialerProxy/链依赖；url 与自建节点输出保持原口径。禁止全面重命名所有格式 tag 作为顺手修正。
4. 客户端链当前输出内部链名；改名应不破坏 chain 依赖。是否要求链克隆出站也展示新名，及其具体格式，见 Owner 决策。真实客户端对 tag 改名后的手工选择状态是否保留待核实，不声称自动保留。

## 10. 风险、待核实与需要 Owner 决定的点

### 10.1 已识别风险

- 并行改动可能改变迁移头、恢复列及画布字段，实施前须重新读取；0147 不得被其他条目占用，不能覆盖未提交文件。
- 旧键一对多、整源展开超 200 条、失效来源缓存和悬空画布都可能使简单替换漏授权或错误指向。
- 真改名影响名称去重与关键词，不只是引用稳定问题；需要明确展示实际订阅影响。
- 恢复会合并归档和当前权威数据，单一 done 标记若脱离最终数据复制顺序会错误跳过转换。
- 新字段导致旧 `SELECT *` 恢复复制失败；迁移、备份、rewind 链应同步排期。
- sing-box 和链的内部标识不能直接批量改成显示名；不同客户端对名称变化的选择状态行为待真机核实。

### 10.2 待核实

- 最终恢复协调器中各 PrepareRestoreTx 的调用顺序、标记/映射的权威来源及最终候选校验时点；不得仅凭当前 database.go 早期 reconcile 位置落实现。
- client_policy_profiles.ui_metadata_json 是否保存节点 ref 或节点名缓存；需要按真实 schema 逐字段检查，禁止任意字符串替换。
- 画布实例显示元数据、各前端本地草稿是否缓存旧 ref，以及迁移后 revision 冲突提示路径。
- 内容批量替换的实际调用方，以及是否存在来源类型切换的已发布调用方式；需要明确拒绝行为和错误提示。
- 当前工作区 0144–0146 的最终文件/迁移校验/rewind 链位置；本文只预留 0147，不修改这些文件。

### 10.3 需要 Owner 决定的点

1. 改名遇到跨来源或自建节点同名时，选择拒绝并列出冲突，还是允许保存并明确接受现有订阅去重后节点可能消失；若要求自动消歧，需要另行确定输出命名规则。同来源建议跨协议也禁止同名，名称建议限制为 1–200 UTF-8 字节，请确认。
2. 旧粘贴来源的 `@source:<id>` 客户端策略成员是否一并冻结为当时的逐节点 ID 成员；已有空来源整源授权是否接受转换为空集合，并要求后来导入的节点重新显式入组。
3. 旧整源展开超过当前 200 条成员上限时，采用什么可见、可维护的容量规则；不得截断已有授权。
4. 遇到悬空旧成员、悬空画布 ref 或无法核实的历史同键数据时，是否阻止迁移并交人工处理，还是保留明确的失效引用并完成其余转换；无论选择哪种，都不自动绑定其他节点。
5. 删除被画布引用的节点时，是先阻止并要求修改/发布方案，还是允许确认后使相关完整链失效；是否允许确认时同时移除分组与客户端策略的精确成员，以及最后一条删除后是否清理隐藏空来源。
6. 是否取消既有 content 来源的整批替换和 content/URL 类型切换入口；若保留整批替换，需要另定新增、保留、删除节点的显式差异确认规则，不能按名称猜稳定身份。
7. sing-box 普通 content 出站建议使用真实新名称；客户端链的克隆出站是否也要求显示新名称，以及采用什么显示形式以保持链内部引用一致。

## Owner 决定（2026-11-13）

两类导入的区分已确认（见计划第 16 节表格）：本项只作用于单独导入（`Kind=content`），导入订阅连接（`Kind=url`）完全保持现状。第 10 节七点按建议执行：

1. 改名与任何已存在节点（单独导入、机场订阅、自建）重名时拒绝保存并列出冲突；名称 1–200 UTF-8 字节；同一来源内跨协议也不允许重名。
2. 单独导入来源的 `@source:<id>` 客户端策略成员在转换时冻结为当时的逐节点 ID 成员；空来源转为空集合。
3. 分组导入成员上限由 200 提到 1000，转换不截断已有授权。
4. 转换遇到悬空的旧成员或画布引用：保留为明确的失效引用并完成其余转换，写入迁移报告；不阻止升级，不自动绑定其他节点。
5. 删除被画布引用的节点先阻止，要求先修改并发布方案；确认删除时可同时移除分组与客户端策略中指向它的精确成员；最后一个节点删除后清理隐藏的空来源。
6. 取消单独导入来源的整批替换与改为订阅地址的入口（订阅连接也不能改为粘贴内容）；粘贴总是新增节点。
7. sing-box 客户端链的克隆出站也使用新名称，沿用现有后缀写法。
