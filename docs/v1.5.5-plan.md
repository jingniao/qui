## 1. 导入的 Clash（mihomo）配置解析不出境外域名

### 现象（Owner 2026-11-12 实测）

mihomo 客户端（TUN，fake-ip，GLOBAL 模式）导入订阅后，直接访问 IP 正常（`110.242.69.202:443`），境外域名全部失败：

```text
[TCP] dial GLOBAL 198.18.0.1:49904 --> www.nodeseek.com:443 error: dns resolve failed: couldn't find ip
[TCP] dial GLOBAL 198.18.0.1:49917 --> accounts.google.com:443 error: dns resolve failed: couldn't find ip
[TCP] dial GLOBAL 198.18.0.1:49930 --> qui.lluu.de:443 error: dns resolve failed: couldn't find ip
```

### 根因（待用 Owner 实际订阅确认）

三个「屏蔽回国」预设（`internal/panel/subscription/rules/presets.go` 的 `metaPreset`）写出的 DNS 段是：

```yaml
dns:
  enable: true
  enhanced-mode: fake-ip
  nameserver: [https://doh.pub/dns-query, https://dns.alidns.com/dns-query]
  fallback:   [https://dns.cloudflare.com/dns-query, https://dns.google/dns-query]
```

模板模型（`rules.DNS`）和导出器（`format/clash` 的 `dnsSection`）只能表达 `enable`／`enhanced-mode`／`nameserver`／`fallback` 四项，没有 `fallback-filter`、`default-nameserver`、`proxy-server-nameserver`、`nameserver-policy`、`fake-ip-filter`。

mihomo 设置了 `fallback` 却没有写 `fallback-filter` 时，按默认的 `geoip: true, geoip-code: CN` 处理：国内 DoH 返回的地址只要不在中国，就改用 fallback 的结果。fallback 用的 Cloudflare／Google DoH 默认直连，在国内被阻断或很不稳定，所以**所有解析到境外 IP 的域名都解析失败**，国内域名和纯 IP 不受影响，与日志一致。凡是要在本地解析的流量都会碰到这个问题：GLOBAL／规则选中 DIRECT 的连接、节点地址是域名（`connectHost`）时对节点服务器本身的解析、不带 `no-resolve` 的 IP 规则。

经典分流、基础代理、分流+去广告、白名单这几个预设默认不启用 DNS（不输出 `dns:`），由客户端自己的 DNS 设置负责，不受本问题影响。

### 方案

- `rules.DNS` 增加可选字段：`defaultNameservers`（只允许 IP，用来解析 DoH 主机名）、`proxyServerNameservers`（解析节点服务器域名）、`fakeIpFilter`（域名或通配，例如 `*.lan`、`+.local`、时间同步域名）、`fallbackFilter{geoip,geoipCode,ipcidr[],domain[]}`。导出器只为 mihomo（`clash`）输出这些字段，legacy Clash 照旧；模板校验与保存、预览共用 `validateDNS`。旧模板缺这些字段时按空值读取，输出不变。
- 修改三个「屏蔽回国」预设的 DNS：nameserver 只用国内 DoH，**去掉 fallback**（fake-ip 下走代理的域名由节点在远端解析，不需要本地 fallback），加 `default-nameserver: [223.5.5.5, 119.29.29.29]`、`proxy-server-nameserver` 用国内 DoH、常用 `fake-ip-filter`。
- 校验与提示：启用 DNS 且有 fallback、但 fallback 不走代理（mihomo 的 `#<策略组>` 后缀）也没写 `fallback-filter` 时，保存不拒绝，但在编辑器与订阅预览给出中文警告，说明境外域名可能解析失败。
- 已保存的配置不自动改写（Owner 可能有意为之）：编辑器 DNS 区块提供「套用推荐 DNS」按钮；发布说明写明用了「屏蔽回国」预设的配置需要手动套用一次并重新启用。
- 编辑器 DNS 区块（`web/src/modules/routing/pages/ClientPolicyPage.vue`）补上述字段。

### 验收

- 单元测试：新字段的校验（非 IP 的 default-nameserver、非法 filter 拒绝）、mihomo 输出包含新字段、legacy 输出不含、旧模板输出逐字节不变；三个预设的 DNS 段改为新值。
- 实机：Owner 用 mihomo（TUN＋fake-ip）重新导入订阅，规则与 GLOBAL 模式下 www.nodeseek.com、accounts.google.com、qui.lluu.de 均可访问；节点用域名连接地址时同样可用；国内域名仍按预设处理（屏蔽回国）。

### 已确认（Owner 2026-11-12）

- Owner 当前启用的客户端配置来自「屏蔽回国」预设，根因成立。
- 预设的 fallback 直接去掉，不提供「fallback 走代理」的替代选项。

## 2. 服务器列表页放一会儿就全部显示「离线」

### 现象（Owner 2026-11-12）

「服务器 → 服务器列表」页面在后台放一段时间后，所有服务器都显示「离线」，网速与「已运行」变成「–」，节点其实在线；刷新页面即恢复。

### 根因

`web/src/modules/nodes/pages/NodeListPage.vue` 只在打开页面和筛选条件变化时调用 `load()` 读一次节点列表，此后从不刷新节点数据；而页面时钟 `now` 每 5 秒更新一次，`serverStatus()`（`components/serverListModel.ts`）用「当前时间 − 读取时的 `lastHeartbeat`」判断，超过 45 秒就判为离线。所以与是否在后台无关：页面停留 45 秒以上不操作就会全部变「离线」，后台更容易遇到。

面板在每次心跳都会经 SSE 发 `node_status`（`internal/panel/node/control.go`，前端转为窗口事件 `proxy-node-status`），节点详情、出口组、版本页等都监听了它，唯独服务器列表没有。节点详情另有 15 秒定时刷新与切回前台时刷新（`visibilitychange`）。

### 方案

- 服务器列表监听 `proxy-node-status`，用现有 `throttleTrailing`（5 秒）静默刷新**节点列表本身**（`nodeAPI.list`），不显示加载状态、不清空页面、不重读每台服务器的元数据与今日流量（那些是每台一个请求）；刷新失败保留上次数据。
- 页面切回前台（`visibilitychange` 变为 visible）时立即静默刷新一次；另加 30 秒兜底定时刷新，仅在页面可见时执行，防止 SSE 断开期间状态过期。
- 静默刷新与完整 `load()` 共用 `generation`，筛选或翻页触发的完整读取优先，旧的静默结果丢弃。
- 本月整机流量、本月代理流量等补充数据仍随完整读取与「刷新」按钮更新，不随心跳刷新。

### 验收

- 页面停留 2 分钟以上（前台与后台各一次），在线节点保持「在线」，网速与已运行时间持续更新；关掉一台 Agent 后约 45 秒内显示离线，恢复后自动回到在线。
- 浏览器网络面板中，静默刷新只请求节点列表，不重复请求每台服务器的元数据与流量。
- 前端类型检查、构建与自测通过。

## 3. 服务器卡片可拖动排序

### 需求（Owner 2026-11-12）

「服务器 → 服务器列表」的卡片位置可由 Owner 自己拖动调整。

### 现状

节点列表按 `created_at,id` 排序（`internal/panel/node/repository.go`），页面不能调整顺序。前端没有拖拽依赖，客户端策略页与中转画布用的是浏览器原生拖拽（`draggable`／`dragstart`）。

### 方案

- **顺序保存在面板**：`system_settings` 新键 `server_order`（`{ids:[...],revision,updatedAt,updatedBy}`，无迁移，随整库快照备份恢复），所有管理员与 Viewer 看到同一顺序，换浏览器不丢。接口 `GET /api/v1/system/server-order`（Owner／Viewer）、`PUT`（Owner＋CSRF，体 `{ids,expectedRevision}`，未知字段拒绝，ID 须为存在的未删除节点且不重复，最多 1000 个；revision 不匹配 409 `settings_conflict`；记操作日志「调整服务器顺序」）。
- 页面按保存的顺序排列：列表里有、保存里没有的服务器（新加的）按原 `created_at` 顺序排在最后；保存里有、但已删除的 ID 忽略，下次保存时清掉。卡片与列表两种视图用同一顺序。
- 拖动：仅 Owner；卡片用原生拖拽（不加依赖），拖动时显示插入位置，松手立即保存，失败恢复原顺序并提示。有搜索、状态、分组等筛选，或不在第一页时禁用拖动并提示「清除筛选后可调整顺序」，避免只对部分服务器排序造成歧义。按钮、链接区域不触发拖动，点击卡片进入详情的行为不变。
- 「上移／下移」：手机浏览器不支持原生拖拽，卡片与列表行另加「上移」「下移」两个小按钮（仅 Owner，桌面也显示），每点一次与相邻服务器交换并立即保存；第一个不显示「上移」、最后一个不显示「下移」；与拖动相同，有筛选或不在第一页时隐藏（按「隐藏不可用操作」的规则，不置灰）。连续快速点击时合并为一次保存，保存失败恢复原顺序并提示。
- 本项只影响服务器列表页；总览、选择器等其他地方的服务器顺序不变（如需统一另行确认）。

### 验收

- 拖动后刷新页面、换浏览器、Viewer 登录看到同一顺序；新增服务器出现在最后；删除服务器后顺序仍正确。
- 手机宽度下用「上移」「下移」调整顺序，结果与拖动一致；首尾按钮按规则隐藏。
- 有筛选时不能拖动；两个窗口同时保存时后保存的一方得到冲突提示并重新读取。
- 后端单元测试覆盖校验（未知、重复、已删除 ID）、revision 冲突与未变化不推进 revision；前端类型检查、构建与自测通过；1280／1920px 与手机宽度走查。

### 已确认（Owner 2026-11-12）

- 顺序保存在面板，所有人看到同一顺序。
- 增加「上移」「下移」按钮，供手机浏览器使用。

## 4. 服务器列表的筛选改为「服务器分组」（编辑弹窗里填标签）

### 需求（Owner 2026-11-12）

服务器列表工具栏的「全部节点分组」改为「服务器分组」：Owner 在服务器的编辑弹窗里给服务器输入标签，按标签筛选服务器。

### 现状

该下拉列出的是**订阅节点组**（`node_groups`，决定用户订阅与授权，见说明书第 10 节），按组成员筛选服务器（`NodeListPage.vue` 的 `group`），与「服务器怎么归类」不是一回事；只有 Owner 能看到。编辑弹窗（`components/ServerQuickEdit.vue`）保存的是节点元数据 `node_meta`（名称、地区、备注、续费等，`internal/panel/node/meta.go`），没有标签。

- **订阅节点组不受影响**：仍在「节点配置 → 节点分组」管理，授权与订阅逻辑不变；只是服务器列表不再按它筛选。
- 与第 3 项（拖动排序）的关系：按标签筛选时禁用拖动，与其他筛选一致。

### 验收

- 给服务器加、改、删标签后刷新仍在；Viewer 可见可筛选不可改；旧版本保存元数据不会清掉标签。
- 筛选「未分组」与某个标签结果正确，地址栏可分享；搜索可按标签命中。

- 一台服务器可以有多个标签。
- 只做筛选，卡片不按分组分段显示。

## 5. 服务器卡片「编辑」点击后弹窗出现慢

### 现象（Owner 2026-11-12）

服务器列表点击卡片按钮后，弹窗要等一会儿才出现。

### 根因

「编辑」（`components/ServerQuickEdit.vue` 的 `openEditDrawer`）先**等两个请求都返回**（`nodeAPI.get` 读最新节点、`loadNodeMeta` 读元数据）才把弹窗打开，期间页面没有任何反馈；到海外面板的往返越慢，等得越久。弹窗动画本身只有约 0.25 秒（`styles/main.css` 的 `ios-modal`），不是原因。「删除」先开弹窗再读预览，不慢；「安装」对已登记服务器只弹提示，对待登记服务器要先请求重新签发注册码（写操作，必须等），按钮也没有加载状态。

### 方案

- 「编辑」点击后**立即打开弹窗**，先用列表里已有的节点数据与页面已缓存的元数据（`getNodeMeta`）填表；后台再读最新节点与元数据，返回后只覆盖用户尚未改动的字段（改过的字段保留），读取期间弹窗顶部显示「正在读取最新信息」、保存按钮禁用；读取失败显示错误并保留缓存值（仍可保存），服务器已被删除则关闭弹窗并提示。
- 保存逻辑不变（保存时仍会再读一次最新数据再合并）。
- 「安装」对待登记服务器：点击后按钮立即显示加载状态并防止重复点击，直到注册码返回再弹出安装命令。
- 第 4 项的标签输入加入同一弹窗，随本项一起实现。

### 验收

- 在限速网络（浏览器开发者工具 Slow 4G）下，点击「编辑」弹窗立即出现，最新数据随后填入；读取中改过的字段不被覆盖。
- 「安装」点击后立即有加载反馈，不能重复提交。
- 前端类型检查、构建与自测通过。

### 已确认（Owner 2026-11-12）

- 慢的是「编辑」按钮。

## 6. 外部导入的 Reality 节点进不了 Clash 订阅，且警告不说是哪个节点

### 现象（Owner 2026-11-12）

用 admin 的授权预览 Clash（mihomo）订阅：导入来源已授权、已被读取，但其中的节点不在输出里，预览只给两条笼统警告：

```text
source · import:fFWETOjriP3TxyjmRm-q6ErAAiYB5_tIeh53wNuA6gU：Only supported valid entries are imported; unsupported options and entries are omitted.
format · clash：Endpoint omitted: client format cannot represent its security or transport settings; use a compatible URI client
```

### 根因

`internal/panel/subscription/proxy/client_settings.go` 的 `ClientFormatSupportsSettings` 只放行 v1.4 实测过的两种 Reality 组合给 mihomo：Reality＋TCP＋`flow=xtls-rprx-vision`，以及 Reality＋xhttp（`mode=auto` 且 ALPN 恰为 `[h2]`）；而且两者都要求**没有 SpiderX**。常见分享链接因此被整条省略：

- 3x-ui 等面板生成的 Reality 链接几乎都带 `spx=%2F`（导入器 `importer/parse.go` 原样存为 `SpiderX`）；mihomo 与 sing-box 本就没有对应字段，SpiderX 只影响 Xray 客户端的伪装爬取，不影响连接。
- Reality＋TCP 不带 Vision、Reality＋gRPC 在 mihomo 中可用，但未实测所以不输出。
- Reality＋xhttp 的分享链接通常不写 `alpn`，ALPN 为空即被省略。

警告由 `format/clash/clash.go` 统一给出，不含节点名与具体原因，Owner 无从判断。

### 方案

- **警告具体到节点和原因**：省略时写「节点「<名称>」：<原因>」，原因用固定中文文本，例如「Clash 不支持 Reality 的 spx 参数」「Reality 未使用 Vision」「Reality＋gRPC 暂不支持」「xhttp 未声明 h2 ALPN」「xhttp 模式不是 auto」。同一原因多个节点合并为一条并列出名称（最多 10 个，其余写「等 N 个」）；sing-box 与 legacy Clash 同样改。只给 Owner 预览，订阅正文不变；不含 UUID、密码、公钥等凭据。
- **放宽 mihomo 输出（逐项先在测试机用真实 mihomo 连真实 Xray 服务端验证，通过的才放开）**：
  1. 忽略 SpiderX：mihomo 与 sing-box 输出时直接不写它（URI/Base64 仍保留 `spx`）。
  2. Reality＋TCP 无 flow：mihomo 输出 `reality-opts` 且不写 `flow`。
  3. Reality＋gRPC：mihomo 输出 `network: grpc` 与 `grpc-opts.grpc-service-name`。
  4. Reality＋xhttp 的 ALPN 为空：按 mihomo 默认 ALPN 输出（验证其默认能与服务端协商成功），其余模式（packet-up/stream-up/stream-one）按验证结果决定。
  未通过验证的组合保持省略，并用上面的具体原因提示。
- 自建入站走同一函数，放宽同样作用于自建 Reality 入站的 mihomo 输出；说明书第 10.3 节与[协议矩阵](protocol-support-matrix.md)的「mihomo 仅输出已测……」同步修改。

### 验收

- 单元测试：每种被省略组合给出对应具体原因与节点名；放开的组合输出正确 YAML（SpiderX 不出现、无 flow 不写 flow、gRPC 字段正确）；URI/Base64 输出不变；未放开组合仍省略。
- 实机：测试机 192.168.5.36 上真实 mihomo 分别连接 Reality TCP（有／无 Vision、带 spx）、Reality gRPC、Reality xhttp（ALPN 空／h2；mode 为 auto 与 stream-one）服务端，记录每项结果；Owner 用 mihomo 重新导入订阅，被导入的节点出现且可连通。

### 已确认（Owner 2026-11-12）

Owner 被省略的链接是 VLESS＋Reality＋xhttp：`type=xhttp`、`mode=stream-one`、`fp=chrome`，带 `pbk`／`sid`／`sni`，**无 `alpn`、无 `flow`、无 `spx`**（凭据与地址不入文档）。它同时命中两条省略规则：xhttp 模式不是 auto、ALPN 为空。因此放宽清单第 4 条优先：先验证 mihomo 对 Reality＋xhttp 的 `mode: stream-one` 与 ALPN 为空（用 mihomo 默认 ALPN）能否连通 Xray 服务端，通过即放开；packet-up／stream-up 同批验证。第 1–3 条（SpiderX、无 Vision、gRPC）照常验证，不阻塞本条。

## 7. 外部导入对常见分享链接过严，整条拒收

### 现象（2026-11-12 代码核查）

导入器（`internal/panel/subscription/importer/parse.go`）对 URI 只认 16 个查询参数（security、sni、peer、servername、alpn、type、path、serviceName、flow、encryption、pbk、sid、spx、fp、host、mode），**出现任何其他参数整条拒收**；对 Clash YAML 用 `KnownFields` 严格解码，出现未列字段同样整条拒收。用常见链接在本机实测 `importer.Analyze`：

| 链接特征 | 结果 |
| --- | --- |
| VLESS／Trojan 带 `headerType=none`（v2rayN、3x-ui 常见，含义就是默认值） | 拒收 `unsupported_transport`（query.headertype） |
| Trojan 带 `allowInsecure=0`、Hysteria2 带 `insecure=0`（明确「不跳过验证」） | 拒收 |
| VLESS／Trojan＋WebSocket 带 `host=`（CDN 用法几乎必带） | 拒收 `invalid_protocol_combination`（query.host）；模型里也没有 WS Host |
| Hysteria2 带 `obfs=salamander&obfs-password=` | 拒收；模型无 obfs |
| Hysteria2 带 `mport=`（端口跳跃） | 拒收（自建入站能输出跳跃，导入却不收） |
| TUIC 带 `congestion_control`／`udp_relay_mode`（几乎所有 TUIC 链接都有） | 拒收；模型其实有这两个字段 |
| Reality 带 `spx=%2F` | 接收，但 Clash／sing-box 输出省略（第 6 项） |
| 不带上述参数的 Hysteria2、SS（AEAD）、Reality＋Vision | 正常 |
| SS 带 `plugin=`、VMess、WireGuard | 拒收（本就不支持，合理） |

Clash YAML 导入同理：`ws-opts.headers`、Hysteria2 的 `obfs`／`ports`／`up`／`down`、TUIC 的 `congestion-controller`／`udp-relay-mode`、以及 `tfo`、`packet-encoding`、`ip-version`、`smux` 等常见字段都会使整条被拒。

### 方案

- **默认值与无害参数忽略而非拒收**：`headerType=none`（非 none 仍拒收）、`allowInsecure=0`／`insecure=0`／`allow_insecure=0`（为 1 仍按现行规则拒收 `insecure_tls`）、`ed`（WS early data，并入 path 处理或忽略待定）、TUIC 的 `disable_sni=0`。Clash YAML 中只影响本地行为的 `tfo`、`ip-version`、`packet-encoding`、`udp-over-tcp: false` 等忽略。忽略的参数在刷新结果里计一条固定说明（不含值）。
- **补齐模型并导入／导出**（各格式能表达的才输出，不能表达的按现有方式省略并给具体原因）：
  1. WS Host：`Transport.Host`；URI `host=`，mihomo `ws-opts.headers.Host`，sing-box `transport.headers.Host`。
  2. TUIC：URI 的 `congestion_control`、`udp_relay_mode`、`alpn` 映射到已有 `QUIC` 字段。
  3. Hysteria2 端口跳跃：URI `mport`、YAML `ports`／`hop-interval` 映射到已有 `QUIC.HopPorts`／`HopInterval`。
  4. Hysteria2 obfs（salamander）：`QUIC.Obfs`、`QUIC.ObfsPassword`；URI `obfs`／`obfs-password`，mihomo `obfs`／`obfs-password`，sing-box `obfs{type,password}`。obfs 密码按凭据对待：加密缓存、预览与日志不显示。
  5. Hysteria2 `up`／`down`（YAML）映射到已有 `QUIC.UpMbps`／`DownMbps`。
- 仍拒收：`insecure=1`、`plugin`、VMess、WireGuard 导入、xhttp `extra` 等现有明确不支持项，刷新结果的原因码不变。
- 说明书第 10.3 节外部导入段落与[协议矩阵](protocol-support-matrix.md)同步。

### 验收

- 上表每类链接各一条单元测试：接收的字段正确进入模型，并在 URI／mihomo／sing-box 三种输出中出现（能表达时）；`insecure=1`、`plugin`、未知参数仍拒收且原因码不变；旧缓存条目（无新字段）读出与输出逐字节不变。
- 加密备份校验接受新字段，旧归档仍合法。
- 实机：带 obfs 与端口跳跃的 Hysteria2、带 congestion_control 的 TUIC、WS＋Host 的 VLESS 各导入一条，在 Clash Verge Rev 中可连通（测试机自建对应服务端）。

### 已确认（Owner 2026-11-12）

- Hysteria2 混淆（salamander）纳入本项：导入（URI 与 Clash YAML）并在 URI／mihomo／sing-box 中输出，混淆密码按凭据对待（加密缓存，预览、日志与刷新诊断不显示）。

## 8. Clash 输出：自签名证书的 VLESS／Trojan／HTTP 未固定证书；经中转的 Hysteria2 仍带跳跃端口

### 现象（2026-11-12 代码核查）

1. 自建 TLS 入站选「面板自签」时，已发布状态带 `TrustedCAPEM`，订阅模型里是 `TLS.PinnedCA`。mihomo 导出（`format/clash/clash.go` 的 `convert`）只对 Hysteria2／TUIC 调用 `pin()` 写 `fingerprint`，**VLESS、Trojan、HTTP、SOCKS5 的 TLS 不写**，客户端用公网 CA 校验自签证书必然失败，节点看似在订阅里却连不上。URI／Base64 对这些协议同样无法携带固定证书，但只省略了 Hysteria2／TUIC。
2. 中转端点（`source/published/relays.go` 的 `RelayEndpoint`）只把地址与端口换成入口，**保留了目标 Hysteria2 的 `HopPorts`**；mihomo／sing-box／URI 会让客户端去入口服务器的跳跃端口段，而入口上并没有这些端口的转发。

### 方案

- mihomo：凡 `TLS.PinnedCA` 非空的 TLS 端点（VLESS、Trojan、HTTP、SOCKS5）都写 `fingerprint`（与 Hysteria2 同一 `certificateFingerprint`）。
- URI／Base64：`PinnedCA` 非空的 VLESS／Trojan／HTTP／SOCKS5 TLS 端点与 Hysteria2／TUIC 一样省略，并在预览给出具体原因「自签名证书无法写入链接，请改用 Clash 或 sing-box 订阅」；sing-box 已写 `tls.certificate`，核对四种协议都覆盖。
- 中转端点清空 `HopPorts`／`HopInterval`，只用规则端口；预览不需要提示。

### 验收

- 单元测试：自签名 VLESS／Trojan／HTTP 的 mihomo 输出含正确 `fingerprint`；URI 省略并给原因；sing-box 含证书；中转后的 Hysteria2 在三种格式中都没有跳跃端口。
- 实机：测试机自签名 VLESS-TLS 与 Trojan 入站，Clash Verge Rev 导入后可连通。

## 11. 「版本与更新」：没有发布过配置的节点也能直接网页升级（Agent 与代理核心）

### 现象（Owner 2026-11-12 截图）

## 14. 客户端策略地区组：成员不可见、添加无反馈与节点删除能力不完整

### 现象（Owner 2026-11-13）

- 地区分组点击「添加节点来源」中的「＋ @all 全部」「＋ 直连」看起来没有反应。
- 实际订阅配置中有直连 `DIRECT`，地区组编辑区却没有显示，也找不到删除入口。
- 下方候选节点可以勾选，但不能据此判断组内已有成员，也无法通过取消勾选删除已加入节点。Owner 要求先核实删除能力，避免只补显示后仍然不能删除。

### 根因与已核实的代码行为

- **显示缺失**：`web/src/modules/routing/pages/ClientPolicyPage.vue` 的用途组和其他分组会遍历 `getGroupMembers()` 展示成员及删除按钮；地区组分支只显示固定的「客户端运行时决定」卡片、添加来源与候选列表，没有展示已配置成员。因此 `@all`、`DIRECT`、显式端点均可存在于数据中而不显示。
- **添加缺少反馈**：两个按钮均绑定 `addGroupMemberDirect()`。成员不存在时写入 `group.proxies` 并标记修改，但地区组没有对应的成员显示；成员已存在时直接结束，无「已添加」提示。代码可以解释点击后无可见变化；尚未在浏览器现场确认是否另有遮挡或点击事件未触发的问题，不能直接认定按钮完全不可点击。
- **候选选择与成员状态分离**：复选框绑定临时数组 `selectedEndpoints`；「添加所选端点」只执行添加，不回填已有成员，取消勾选不执行删除；刷新候选会清空临时选择。
- **保存与输出仍保留真实成员**：`routing/api.ts` 的 `toConfig()`／`fromConfig()` 在模板 `members` 与编辑器 `proxies` 之间转换；保存时提交完整模板，`internal/panel/subscription/rules/profiles.go` 覆盖存储该模板。地区组的显示遗漏不影响这些成员保存或进入订阅。
- **地区关键词不排除直连**：`rules/expand.go` 仅对代理节点应用包含／排除关键词，显式 `DIRECT` 和其他策略组引用不受该过滤影响。授权或关键词过滤后没有可用成员时，还可能按空组策略生成 `DIRECT`。Owner 当前输出中的直连究竟来自显式成员还是空组处理，尚需读取实际组配置与解析结果确认。

### 删除能力核查结论

| 对象 | 当前能力与限制 |
| --- | --- |
| 显式 `DIRECT`、显式 `@endpoint:<ref>`、`@all` 等已配置成员 | 已有通用 `removeGroupMember()`：按成员索引移除，使用 `formatGroupMembers()` 重新序列化并标记修改；地区组缺少调用该函数的界面入口。保存链路支持成员移除，无需独立删除接口。 |
| 从 `@all` 等来源动态展开的某个节点 | 没有按端点精确排除的机制。仅删除相同节点的显式成员后，它仍可能由 `@all` 或其他来源进入订阅；不能把「移除显式成员」显示为「该节点已从组中删除」。 |
| 最后一个已配置成员 | 删除函数可在本地移除，但后端要求每组 1–256 个成员，空列表保存会失败。空组策略处理的是展开后无可用成员，不能绕过该保存校验。 |
| 空组处理产生的 `DIRECT` | 属于解析结果，不是可直接删除的显式成员；删除显式 `DIRECT` 后，若仍无可用节点且空组策略为直连，输出仍会出现 `DIRECT`。 |

以上为源码链路核查结论，尚未执行删除、保存、重新打开与客户端更新订阅的实测。

### 方案与实现边界

- 地区组展示完整的**已配置成员**，包括 `@all`、直连、显式端点和已有的其他来源／策略组引用；每项提供可见的移除入口，复用现有删除与序列化逻辑。此处删除只影响该策略组成员关系，不删除服务器、入站、导入节点或用户授权。
- 添加来源后立即显示新增成员；已存在的来源明确标注「已添加」，不再无反馈。候选列表明确为待添加选择，不能让取消勾选看起来像删除组内节点；无选择时给出明确状态。
- 将已配置成员、按所选用户授权展开的实际节点、客户端运行时选择分开展示；解析结果显示节点来自哪些成员来源，直连标明「显式配置」或「无可用成员时使用」，避免把解析结果当作可直接删除的配置成员。
- **动态节点删除必须单独处理**：目标是能从地区组中精确排除某个动态展开节点，并在保存、重新打开、刷新来源及客户端更新订阅后持续生效；不能只删除一条显式引用却保留同节点的其他来源。具体排除字段、端点稳定标识、作用范围及旧模板／备份兼容方案待设计确认；现有名称关键词排除不能冒充精确节点删除能力。
- 删除最后一个配置成员时，页面明确提示至少保留一个成员，沿用现有后端校验，不静默添加 `DIRECT`、`@all` 或更改空组策略。显式直连与空组直连分别配置、分别提示，不自动替 Owner 改变流量行为。
- 实施前核对实际组数据中的 `DIRECT` 来源，并在浏览器确认按钮事件是否触发；若存在额外点击问题，按证据修复。

### 验收（待实施时按 Owner 授权执行）

- 打开已有地区组即可看见真实成员，包括原有 `DIRECT`、`@all` 与显式端点；添加立即可见，重复添加有明确状态，删除入口在桌面与手机宽度均可操作。
- 分别移除显式 `DIRECT`、显式端点和 `@all`：保存后重新打开仍已移除；作为当前订阅模板时，客户端更新订阅后的结果与配置和空组策略一致；非当前模板的编辑不影响正在使用的订阅。
- 同一节点同时来自显式端点与 `@all`（或其他来源）时，移除显式成员后仍存在的原因能看见；实现动态精确排除后，该节点从所有适用来源展开的结果中消失，其他节点不受影响，来源刷新后不重新出现。
- 删除最后一个成员时清楚提示保存限制，不出现页面假成功或静默补回成员；无可用节点时分别验证 `direct` 与 `reject`，明确区分显式直连和空组处理生成的直连。
- 候选复选框的选择、添加、取消选择与成员删除语义清楚；不得把清空临时选择当作删除成功。解析结果随配置变更失效并可重新读取。
- 动态精确排除的持久化、授权边界、旧模板与备份兼容按确认后的设计验收；前端类型检查、构建及相关自测，涉及后端合同或迁移时补相应最窄检查与发布门禁。当前文档登记不执行测试。

### 撤除与遗留资源管理

- 主操作为「停用并移除方案」，先生成影响预览：涉及的用户入口、分组、入站、出站、代理链、共享资源、目标服务器与需要发布的配置。未经确认不执行撤除。
- 独立新增的入口在撤除时清理其专用资源和对应分组成员；复用入口须按可核实的原出口恢复，并预览恢复目标与用户影响。原出口资料缺失、目标失效或存在其他引用时明确阻止或要求 Owner 指定处理方式，不静默改为 `direct`。
- 共享资源有其他方案或代理对象引用时保留，并列出引用者。沿用既有发布、确认及失败回滚流程；失败保留未撤除资源和可重试状态，不提前显示已删除或已清理。
- 「仅删除画布」作为次级操作，明确说明保留运行资源、不会撤除代理路径，并提示将进入无画布引用资源的管理范围。
- 遗留资源视图按通道展示内部监听、配套出站、历史归属与当前引用。清理前检查共享和业务引用；按依赖顺序解除出站再撤除监听，并执行必要的配置发布。未完成 Agent 确认前不显示运行资源已撤除。
- 普通节点页遇到受管内部资源时，展示具体阻塞对象、关联方案和处理入口，不能继续只报通用服务器错误。API 返回可辨识的引用冲突及关联对象，服务端日志保留原始原因。

### 验收（实施时按 Owner 授权执行）

- 无限画布保留拖拽、连接、平移、缩放及多跳编排；选中用户入口、服务器、连线时可清楚辨识角色、协议与流量方向。
- 复现只有服务器通道、未绑定入口的方案，明确显示待完善，无法冒充用户可用节点；绑定并部署确认后，节点列表与分组中出现对应入口，页面与实际订阅路径一致。
- 独立新增方式保留原直连入口；复用方式保留原入口身份与地址，并明确改变出口。分组成员数量、授权、订阅和跨页面定位正确；内部监听不进入用户成员选择器。

- 用本轮旧方案遗留的同类数据验证监听／出站引用可追踪、单独删除能给出关联原因、整组清理依赖顺序正确。生产遗留资源的实际清理需 Owner 另行授权，本规划不执行清理。
- 1280／1920px 与手机宽度走查状态和交互；相关前端、后端及真实核验证在实施阶段另行取得 Owner 授权后执行。本次仅登记规划，不新增或运行测试。

## 16. 单独导入节点支持直接改名，去掉单节点的「整个来源」包装

### 需求（Owner 本轮提出，待实施）

- 单独导入的节点应能直接修改节点名称，保存后节点列表、分组成员、画布资源库、客户端策略候选及订阅输出一致显示新名称。
- 单独导入的节点按单个节点管理，不再为每个节点展示一层来源组，不要求先编辑来源才能管理节点。
- Owner 截图中的「新加坡 公司 aws（整个来源）」「v6only-xhttp（整个来源）」应显示为具体导入节点，展示真实名称、协议、端口和连接地址；不继续以「整源」及协议／端口为空的方式呈现。
- 本项中的「不需要划分成组」按去掉单独导入节点的来源包装登记；现有用于用户订阅授权的节点分组继续保留，单独导入节点可以作为具体节点加入这些分组。若 Owner 要求连用户授权分组也取消，需另行明确授权方式与范围。

### 已核实的代码行为

- `ProxyNodeListPage.vue` 的 `openEditNode()` 对导入节点统一引导编辑来源，提示「更改会影响该来源的全部节点」，没有独立的节点名称编辑入口。
- `subscription/importer/handler.go` 提供来源的创建／修改／删除／刷新及导入节点列表查询，没有针对单个导入节点名称的修改接口。来源名称与其包含节点的名称分别存在，修改来源名称不等于修改节点名称。
- `LineGroupPage.vue` 的 `allAvailableNodes` 对全部导入来源都生成 `proxyKey:''` 的「整个来源」候选，没有将粘贴内容的单独导入与 URL 订阅来源区分展示。单独导入因此也被显示成来源组。
- 导入成员键及部分解析结果使用 `name|protocol` 标识来源内节点。直接改动原始节点名可能影响分组成员、客户端策略、画布等引用；实施前需沿调用链核实持久引用与订阅命名规则，不能仅改页面文字或换键后让已有成员失效。

### 方案与边界

- 在单独导入节点的卡片／列表及详情提供「修改名称」，直接编辑当前节点的显示名称，不要求重新粘贴分享链接，不改变协议、服务器、端口或凭据。保存失败展示明确原因并保留编辑内容，不显示改名成功。
- 名称在服务端持久保存，换浏览器、刷新页面与备份恢复后仍保留；以稳定的节点身份关联显示名称与既有引用，不能用页面临时状态代替。具体字段、接口及是否需要迁移在实施设计时确认。
- 粘贴导入一条或多条节点时，每个节点分别作为管理对象展示，可独立改名和删除。用户不必额外建立一个来源组；如底层仍需来源记录承载加密内容与解析结果，将其作为内部实现，不在日常节点管理中暴露为必经的分组层级。
- 节点分组的候选与已选成员按具体节点显示，来源类型标记「单独导入」，展示真实协议、端口与地址，允许移出单个节点。URL 订阅仍按机场来源管理，可保留「整个来源」与单节点选择；本项不改变 URL 来源的批量订阅语义。
- 处理已发布数据中的旧「整个来源」成员：核对其中实际包含的节点、授权和其他引用后转换或解析为具体成员，保留当前有效接入范围；不能只隐藏旧行导致授权丢失，也不能自动授权来源外节点。需要兼容的旧成员和接口必须在实施前说明。
- 单节点删除只影响该节点及明确列出的引用；批量粘贴产生多个节点时，不能因为删除其中一个节点而删除同来源的其他节点。有关引用需要先提示影响、交由 Owner 确认。
- 不自动改名 URL 订阅来源内的全部节点，不绕过既有授权，不把节点显示名称作为新的唯一业务身份。本项与第 14 项客户端策略成员展示、第 15 项画布及分组联动保持一致。

### 验收（实施时按 Owner 授权执行）

- 单独导入后直接修改名称，保存、刷新、重新登录后仍为新名称；节点列表、节点分组、画布、客户端策略候选与有权用户的订阅一致。
- 改名后节点协议、地址、端口、凭据和授权不变；既有分组成员、画布实例与客户端策略引用仍指向同一节点，不变成失效成员、不重复生成节点。
- 按截图场景，两个单独导入节点在分组内显示真实协议与端口，不再显示「整个来源」「整源」及由来源包装造成的空字段；URL 订阅来源的原有显示和操作保持。

- 保存失败、引用冲突等原因可见，不静默回退原名；相关检查在实施阶段另行获得 Owner 授权后执行。本次仅加入规划，不新增或运行测试。

## 17. 出站可单独指定源 IP（同一服务器的不同入站走不同出口 IP）

### 需求（Owner 2026-11-13）

一台服务器绑定多个 IP 时，希望不同入站从不同的 IP 出网，例如入站 A 从 IP1 出、入站 B 从 IP2 出。目前只能按整台服务器设置一个出口 IP，新建服务器与新建入站时都不能指定。

### 现状（2026-11-13 代码核查）

- 出口 IP 只有服务器级设置：`desiredstate.Network`（`pkg/contracts/desiredstate/network.go`）的 `outbound_source_ip`／`outbound_interface`（核心出站源 IP／网卡）和 `host_source_ipv4/ipv6`（服务器强制出站），在「节点详情 → 节点设置」里填写（`ServerSettings.vue`），见说明书第 13.1 节。登记接口只收名称与 `connectHost`。
- 渲染时把同一个值写进**全部**拨号出站：Xray `applyOutboundSource`（`internal/agent/core/xray/network.go`）给每个非 blackhole 出站写 `sendThrough` 与 `sockopt.interface`；sing-box 同名函数（`internal/agent/core/singbox/network.go`）给每个可拨号出站与出站 WireGuard 端点写 `inet4/inet6_bind_address` 与 `bind_interface`。
- `desiredstate.Outbound`（`state.go`）没有源地址字段。Direct 本身就是一个出站资源（`protocol: direct`），入站的 `default_outbound` 和分流规则的「指定出站」都能指向具体出站。
- `desiredstate.Decode` 用 `DisallowUnknownFields`，旧 Agent 收到带新字段的状态会整条拒绝，所以必须加能力位门禁。
- 服务器强制出站（nft SNAT）只豁免**一个**地址：`hostnet.Desired` 的 `exempt_ipv4`／`exempt_ipv6` 各一个，取自服务器级核心出站源 IP（`internal/agent/reconcile/hostnetwork.go` 的 `exemptAddress`）。如果只给出站加字段而不改这里，同时开启强制出站时，出站单独指定的源 IP 会被 SNAT 改写成强制出站地址。
- helper 可能比 Agent 旧：helper 单元执行的是 `/usr/local/bin/proxy-agent --apply-host-network`（`deploy/systemd/proxy-agent-host-network.service`，OpenRC 的 `host-network-watch` 同理），网页升级不替换这个文件，源码注释也写明回应请求的可能仍是升级前安装的程序（`internal/agent/hostnet/hostnet.go` 文件协议说明）。`hostnet.ReadDesired` 严格解码、拒收未知字段，所以请求文件不能直接改格式或无条件加字段，否则旧 helper 拒收整个请求，强制出站与开机重放都会失败。现有能力位 `port_hop_supported` 只检查 helper 单元文件是否存在（`hostnet.HelperInstalled`），不能说明 helper 的版本。

### 内核能力（2026-11-13 核对）

- Xray：每个出站都有 `sendThrough` 和 `streamSettings.sockopt.interface`，路由可以按 `inboundTag` 选出站。
- sing-box：每个出站的拨号字段里都有 `inet4_bind_address`、`inet6_bind_address`、`bind_interface`，路由可以按 `inbound` 选出站；`selector`／`urltest` 组本身不接受拨号字段，组里每个成员可以各自绑定。
- 内核能力足够，缺的是 qui 的模型、渲染与界面。

### 方案

- **契约**：`desiredstate.Outbound` 加两个可选字段 `source_ip`、`source_interface`（`omitempty`，未填时序列化结果与现在逐字节相同），校验复用 `Network.Validate` 的规则：单播地址、Linux 网卡名语法。Block 出站不允许填写。
- **优先级**：出站自己的值 > 服务器级「核心出站源 IP／网卡」> 不绑定。两项分别继承，例如出站只填 IP 时，网卡仍沿用服务器级设置。
- **渲染**：两个核心的 `applyOutboundSource` 改为逐个出站取有效值；地址族策略（Xray `ForceIPv4/6`、sing-box `domain_resolver.strategy`）按该出站自己的源地址决定。出口组成员与代理链本节点这一跳都用各自出站的值，sing-box 组本身仍不写拨号字段。已知限制保持不变：目标是另一地址族的字面量 IP 时连接失败。
- **强制出站豁免（兼容方案）**：
  - 原字段 `exempt_ipv4`／`exempt_ipv6` 含义不变，仍写服务器级核心出站源 IP。
  - 新增可选字段 `extra_exempt_ipv4`／`extra_exempt_ipv6`（地址列表，`omitempty`，每族上限待定，例如 16），新 helper 把它们与原字段合并成 nft 的 `saddr != { … }` 集合，校验沿用单播地址规则。
  - 只在真正需要时写新字段：某地址族开了服务器强制出站，且有启用出站的 `source_ip` 属于该族、既不同于服务器级核心出站源 IP 也不同于强制出站地址。出站源 IP 等于强制出站地址时，SNAT 改写成同一地址，无须豁免。其余情况请求文件与现在逐字节相同，新旧 helper、Agent 升级与回滚、开机重放都不受影响。
  - helper 能力：新 helper 在 `status.json` 回执里写功能标记（例如 `"features":["extra_exempt"]`，旧 Agent 读回执用宽松解码，可以忽略）；Agent 新增 `Capabilities.host_source_extra_exempt_supported`（字段 32，仅主机级标量，与 `port_hop_supported` 同一写法），只在最近一次回执带该标记时上报为真。helper 尚未运行过时，Agent 写一次内容不变的请求触发它以取得回执，不另加命令。
  - 面板只拦截上面那种组合：节点没上报该能力时，保存、`SnapshotIntent` 与发布前三处拒绝（`host_source_exempt_unsupported`，中文提示「请在节点上运行一次 `qui-update --component agent` 更新主机网络 helper」）。只给出站指定源 IP、不开强制出站，或源 IP 与强制出站地址相同，都不需要新 helper。
  - Agent 降级：把 Agent 降到 1.5.5 以前前，须先清除这种组合（与「降级到 1.3 以下前先移除 GOST」同一写法），写入运维手册。否则旧 helper 开机重放会拒收带新字段的请求文件，直到旧 Agent 重写请求。
  - 退路（不采用，记录备查）：不改 helper，面板直接拒绝「开着强制出站，又给出站指定了不同源 IP」的组合。改动更小，但两个功能暂时不能同时使用。
- **能力位门禁**：新增 `Capabilities.outbound_source_supported`（字段 31）与 `CoreCapability.outbound_source_supported`（字段 16），Xray 与 sing-box 上报为真，GOST 为假（不渲染用户出站）。面板在保存、`SnapshotIntent` 与发布前（`validateStateCoresTx`）三处一致拒绝旧 Agent（`outbound_source_unsupported`，中文提示先升级 Agent）。
- **面板存储**：两个值放进出站的密封设置或新列，实施时决定；如需新列则用迁移 0145（0144 已留给第 4 项）。备份校验覆盖。
- **编辑器**：出站编辑器（`OutboundListPage.vue`）的高级选项加「出站源 IP」「出站网卡」。源 IP 提供下拉，候选为该服务器心跳上报的地址列表（`publicAddresses`），也允许手填（私网地址、未上报的地址）；留空显示「沿用服务器设置：<值或不绑定>」。
- **用法**：每个出口 IP 建一个 Direct 出站并填写源 IP，入站的默认出站选对应的 Direct 出站，或用分流规则「指定出站」。节点详情的出站网络区块列出单独指定了源 IP 的出站。
- **不做**：按入站直接填出口 IP（入站与出站解耦，见说明书第 3.4 节，统一经出站表达）；新建服务器时填写出口 IP（登记时 Agent 尚未上报地址，仍在节点设置里改）。

### 验收

- 单元测试：字段校验（非法地址、非法网卡名、Block 出站带字段拒绝）；两个核心的渲染器分别覆盖出站自带值、继承服务器级值、都不填（输出与现在逐字节相同）、出口组成员与代理链；强制出站豁免：需要时新字段包含全部相关出站源 IP，不需要时请求文件与现在逐字节相同；旧 helper 读取不含新字段的新请求文件成功；新 helper 读取旧请求文件成功；回执功能标记缺失时 Agent 不上报能力位、面板三处拒绝该组合；旧 Agent 在保存、快照、发布三处都被拒绝；旧状态、修订与备份可读。部署脚本测试（`deploy/linux/tests/host-network-test.sh`）覆盖新旧请求文件。
- 实机：在一台有两个公网 IP 的服务器上建两个 Direct 出站，分别绑定两个 IP，两个入站各指向一个，客户端分别访问 IP 查询站点，看到的出口 IP 与配置一致；同时开启服务器强制出站时结果不变（`nft list table inet proxy_agent_source` 可见豁免集合）；网页升级过、helper 仍为旧版的节点上，该组合被面板拒绝并给出更新提示，运行一次 `qui-update --component agent` 后可以保存发布；写一个服务器上不存在的源 IP，应用失败并自动回滚，原配置继续服务。

### 待确认

- 「从哪个 IP 进就从哪个 IP 出」：Xray 官方文档出站页（<https://xtls.github.io/config/outbound.html>，2026-11-13 查阅）写明 `sendThrough` 有两个特殊值：`origin`「将使用本机被连接的 IP 发出请求」，`srcip`「将使用入站时的源 IP 发出请求」；同页说明 UDP 因无连接、Xray 无法得知原目标 IP，这一功能对 UDP 不生效。文档没有写最低版本，须在节点实际安装的 Xray 版本上核实。sing-box 文档没有对应值，只能绑定固定地址。如果 Owner 需要，可作为仅 Xray、仅 TCP 的选项另行评估；本项先只做显式指定源 IP。
- 新字段 `extra_exempt_ipv4/6` 每族上限取值，以及 helper 从未运行过时触发首次回执的具体方式，实施设计时确定。
