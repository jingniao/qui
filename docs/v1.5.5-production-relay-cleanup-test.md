## 3. 根因

### 3.1 美国 shlii.io 自 #63 起全部校验失败

美国 shlii.io 的修订：#62（16:57，方案发布 测试中转-shlii-CC）成功；#63–65（17:06–17:08，`auto: user amdin updated`）、#67、#71（「未命名方案 1」发布）全部 `validation_failed`。

用修订差异接口比较 #63 与 #62（只读、密钥已掩码），唯一变化是：Owner 授权 amdin 后，amdin 的 shadowsocks 凭据被加入两个 shadowsocks 入站，这两个入站因此从「无用户 → 渲染为停用」变成「启用」：

- 「测试-直连-SS」:35001，设置 `method=chacha20-ietf-poly1305`，正常；
- 方案入口「美国 shlii.io → 美国 CC」:35004，设置为空对象，渲染器使用默认加密方法。

Shadowsocks 空方法合法：Xray 的 `method` 与 sing-box 的 `cipher` 均默认使用 `chacha20-ietf-poly1305`。R1 的空方法拒绝在发布前撤销，因为它破坏了合法内部中转入站：发布提交 8aa92ab 的本地 Linux 门禁（真实核部分）中 `TestRealThreeAgentChainBatchTCPUDPAndReverseReset` 与 `TestRealSingboxThreeAgentChainBatchTCPUDPAndReverseReset` 均报 `入站「C internal Shadowsocks」（）：Shadowsocks 入站必须指定加密方法`。本轮未重跑 Linux 实核门禁。画布／快速中转新建入口和内部监听仍显式填写默认方法。

shlii 自 #63 起 `validation_failed` 的真实原因仍未知。#63 相比 #62 仅为两个 Shadowsocks 入站加入 amdin 凭据并启用，同时使方案入口的中转出站（Trojan TLS → 美国 CC:35003）首次可达并进入渲染。需要 Agent 的具体消息，或读取 38.244.50.17 上 2026-11-14 17:06 UTC 前后的 `journalctl -u proxy-agent`。

### 3.2 失败批次回滚造成两台节点不一致

「未命名方案 1」两次发布（#66/#67、#70/#71）都是先成功应用美国 CC，再在美国 shlii.io 校验失败，于是批次把美国 CC 回滚到 #61。修订列表仍显示 #66、#70「成功」，但方案状态页显示美国 CC「运行 #61」。结果：

- 美国 CC 运行中的配置只有 trojan:35003 内部监听（测试中转-shlii-CC），**没有** trojan:35004（未命名方案 1）和 vless:35000（「美国 CC · vless-37119 中转方案 (草稿)」）；
- 美国 shlii.io 的草稿里却有三条启用的中转出站，分别拨向 CC 的 35003、35004、35000。

### 3.3 由此挡住所有删除

隧道发布和画布撤除都要给美国 shlii.io 下发一份「当前草稿」。下发前的依赖检查（`deployment.validateBatchDependencies`）逐条检查草稿里启用的中转出站，要求目标节点**正在运行**对应的内部监听；35004、35000 两条找不到，返回 `internal_inbound_unavailable`，整批在开始前中止。所以：

- 第 8 步隧道发布：v1.5.5 把这个错误改写成「发布中止，未下发」，两台都「已跳过」；
- 第 10 步画布撤除：阶段一给美国 shlii.io 停入口时同样被挡。挡住它的是**另外两条遗留通道**的出站，不是本方案自己的出站；
- 即使依赖检查放行，美国 shlii.io 仍会因 3.1 的空方法入站校验失败。
