## A. 必须修复（安全与写错数据）

### A1. root helper 写 status.json 可被面板账号劫持（提权）

**位置**：`deploy/linux/panel-update-request.sh` 的 `write_status`。

**问题**：该函数以 root 运行，在面板账号拥有的 `/var/lib/proxy-panel/panel-update/` 里 `mktemp` 出临时文件，随后**按路径**执行 `>` 写入、`chown`、`chmod`、`mv`。目录属于 `proxy-panel` 且没有粘滞位，面板账号可以在 `mktemp` 与写入之间删掉临时文件、换成指向任意文件的符号链接。bash 的 `>` 和不带 `-h` 的 `chown` 都会跟随链接，结果是 root 截断并改写目标文件，再把它的属主改成 `proxy-panel`（例如 `/etc/shadow`）。面板自己就能写 `request.json` 触发 helper，所以攻击者只要控制了面板进程，就能稳定地反复尝试。

**方案**：
- 临时文件改在 root 专用目录（`/var/lib/proxycontrol-install/`，root 0700）里创建、写入、`chown`、`chmod`，最后一步 `mv` 到面板目录。`rename` 遇到目标是符号链接时会替换链接本身，不会跟随。
- 写入前确认两个目录在同一文件系统（`stat -c %d` 相同），不同就拒绝执行并写 journal，避免 `mv` 退化成按路径复制。
- 所有 `chown` 改用 `chown -h`，作为第二道保护。
- 同时排查 helper 与 `update.sh` 里其他「root 在面板可写目录中按路径写文件」的地方，按同一规则处理，至少包括 `copy_database_atomic` 写 `backups/*.partial`。

**验收**：`deploy/linux/tests/panel-update-helper-test.sh` 增加用例：在 `mktemp` 之后、写入之前插入钩子，把临时路径换成指向测试文件的符号链接，要求目标文件内容与属主都不变、`status.json` 仍正确写出。

### A2. root 更新器信任面板可写配置里的数据库路径

**位置**：`deploy/linux/update.sh` 的 `database_path`，以及调用它的 `backup_database`、`database_differs`、`restore_database`。

**问题**：`/etc/proxy-panel/config.yaml` 属于 `proxy-panel`，面板的 systemd 单元也允许写 `/etc/proxy-panel`（`ReadWritePaths`）。更新器以 root 读取其中的 `database:`，只要求绝对路径、普通文件、不是符号链接：
- 备份时把该文件复制到面板可读的备份目录（报告指出的越权读取）；
- 面板更新失败回滚时，`restore_database` 对该路径执行 `rm -f <路径>-wal <路径>-shm`，再把备份 `mv` 覆盖到该路径（报告漏掉的越权删除与覆写）。

触发前提是面板进程已被控制，但这正是更新器与面板分权要防的情况。

**方案**：
- 首次安装和每次面板更新时，由 root 把实际数据库路径写进安装记录（root 0700 的 `/var/lib/proxycontrol-install/`）。之后备份、比较、回滚都只用记录里的路径；配置里的值与记录不一致时拒绝更新，并提示 Owner 在 shell 里确认。
- 无论来源是什么，路径必须在 `/var/lib/proxy-panel/` 下（先 `realpath -e` 再比较前缀），文件属主必须是面板账号。
- 旧安装没有这条记录时，第一次 `qui-update` 自动读一次配置，按上述规则校验通过就写入记录并继续，不需要 Owner 手动确认；不通过就拒绝更新并说明原因（Owner 2026-11-14 确认）。
- 复制源文件改用面板账号读取（`setpriv --reuid`／`runuser -u proxy-panel -- cat`），root 只负责写到目标位置。

**验收**：`deploy/linux/tests/update-test.sh` 覆盖：配置指向 `/var/lib/proxy-panel` 以外的文件、指向属主不是面板账号的文件、配置与记录不一致，三种情况都拒绝且不读、不删、不写目标；正常路径的更新、回滚与 `--database` 降级行为不变。说明书第 30.1 节补一句：数据库路径以安装记录为准。

### A3. 服务器快捷编辑保存时切换目标会写错服务器

**位置**：`web/src/modules/nodes/components/ServerQuickEdit.vue` 的 `saveEdit`。

**问题**：保存时先按 A 读取最新节点与元数据，`await` 之后再读 `editTarget.value.id` 和 `editForm`。保存期间弹窗可以关闭（`FormDrawer.handleClose` 不看 loading 状态），如果此时打开 B，后面的 `nodeAPI.save` 和 `saveNodeMeta` 会以 B 的 ID 写入 A 的出站网络字段、A 的元数据与表单内容。

**方案**：
- 进入 `saveEdit` 时把目标 ID 与表单深拷贝成局部快照，后续所有请求只用快照。
- 保存期间禁止关闭弹窗、禁止打开另一台：`FormDrawer` 在 `loading` 为真时忽略关闭；`openEditDrawer` 遇到 `editingSaving` 为真时直接返回。
- 出站网络四项仍按审计建议处理：只回传本弹窗编辑的字段。前提是 `PUT /nodes/{id}` 省略这几项时保留原值；实施时先核对后端，不满足就继续回传从同一 ID 读到的值。

**验收**：在 `web/scripts/` 中新增或扩展自测：模拟保存未完成时切换到 B，要求所有请求的 ID 都是 A，B 不收到任何写请求。

### A4. Go 工具链升级到 1.26.11

GO-2026-6859 是 HTTP/1 使用 `MaxBytesReader` 时并发读请求体与写响应头导致的崩溃。项目使用了相关 API，当前处理路径没有发现并发条件，但升级成本很低：
- `go.mod` 改为 `go 1.26.11`；`.github/workflows/` 中硬编码的 `go1.26.10` 校验（约第 268 行）同步修改；本地测试机 192.168.5.36 更新工具链。
- 顺带把 `golang.org/x/net` 升到 0.62.0、`golang.org/x/crypto` 升到当前版本；项目不使用受影响的包，升级只为消除扫描命中。
- 用 `govulncheck` 重新扫描，结果写进发布说明。

## B. 应修复（发布一致性与权限）

### B1. 隧道发布等待中断后，面板与节点状态不一致

**位置**：`internal/panel/deployment/tunnels_publish.go` 的 `PublishTunnels`、`internal/panel/proxy/tunnels_publish.go` 发布收尾段。

**问题**：发布先改写生成对象，再持久创建部署批次，然后用**请求上下文**（加 300 秒超时）轮询批次。浏览器断开或超时后，等待返回错误，`restore()` 把生成对象恢复成旧状态，草稿、版本与订阅快照都不推进；但批次仍在后台执行，节点可能已经应用新修订。结果是数据库里的监听、端口声明与订阅快照和节点实际运行的配置不一致，删除场景下订阅还会继续包含已经失效的端点。

**方案**：
- 等待改用 `context.WithoutCancel(ctx)`：浏览器断开不再中止收尾，300 秒上限保留。
- 把「批次终态 → 推进版本与快照，或恢复对象」抽成一个按批次 ID 执行的收尾函数，并在批次表记录该批次属于隧道发布、收尾是否已完成。
- 超时而批次仍在执行时**不恢复**，接口返回「发布仍在进行」。后台在批次进入终态时调用同一个收尾函数，面板重启后也扫描未完成收尾的隧道批次并补做。
- 需要新列记录收尾状态时新增迁移（预计 0149）。实施前先确认能否复用现有部署批次的字段，能复用就不加迁移。

**验收**：单元测试覆盖「请求取消后批次成功」「超时后批次失败」「收尾前面板重启」三种情况，最终草稿、端口声明与订阅快照都与批次结果一致；页面在发布仍在进行时显示进行中，不显示失败。

### B2. 画布更新生成出站时丢失源 IP／网卡

**位置**：`internal/panel/proxy/canvas_ensure.go` 中两处手写 `OutboundInput{...}`（更新与失败补偿）。

**问题**：v1.5.5 给出站加了 `SourceIP`／`SourceInterface`，这两处没有带上。Owner 给画布生成的出站设置了源 IP 或网卡后，画布下次发布会把它清空，失败补偿也恢复不回来。

**方案**：在 proxy 包里加 `outboundInputOf(Outbound) OutboundInput`，完整复制全部可写字段，并对照 `inboundInputOf` 的写法。更新时以它为基础，只覆盖画布负责的字段（名称、目标入站、协议、TCP/UDP、失败策略、启用）；补偿直接用它还原原对象。

**验收**：单元测试：生成出站带源 IP／网卡时重新发布保留原值，发布失败时补偿恢复全部字段。另加一个测试，用反射比较 `Outbound` 与 `OutboundInput` 的同名字段都被复制，防止以后新增字段又漏掉。

### B3. 原生规则集刷新先覆盖文件、后校验配置

**位置**：`internal/agent/rulesets/rulesets.go` 的下载与 `os.Rename`、`internal/agent/reconcile/reconcile.go` 的 `PrepareRuleSets` 到 `Validate` 段。

**问题**：缓存文件按 URL 命名，下载只检查文件头的前 3 个字节就覆盖旧文件，核心的原生校验在之后才执行。上游发布了文件头正常但内容损坏的文件时：
- 新修订校验失败，并被记为该修订的**永久失败**，即使原因只是这次下载的文件，之后重试同一修订也不会重新尝试；
- 旧文件已经被替换，正在运行的核心不受影响（内容已加载到内存），但只要核心重启（崩溃恢复、Agent 重启、后续发布），使用同一文件的旧修订也无法启动。

「回滚到历史修订时使用更新后的规则内容」是说明书第 17 节写明的设计（新内容在下一次应用时生效），不改。

**方案**（不改文件命名，改动最小）：
- 下载成功时先把旧文件改名为 `<名称>.prev` 再换上新文件，并在本次 `Apply` 里记下替换了哪些文件。
- 本次应用在渲染、校验、切换或健康检查任一步失败时，把这些 `.prev` 换回原名；成功后删除 `.prev`。`Cleanup` 同时清理残留的 `.prev`。
- 本次应用替换过规则集文件时，校验失败不记永久失败（与 `retainedRevision` 同样处理），下次重试会重新下载。

按内容摘要命名、随修订保存（报告的建议）需要改 `Render` 路径、`Keep` 与 `Cleanup` 的修订绑定，代价明显更大，本版不做。

**验收**：`rulesets` 与 `reconcile` 的单元测试：提供文件头正确但会导致校验失败的新文件，要求原文件恢复、修订失败不被记为永久、下一次重试会重新下载；成功路径下不留 `.prev`。

### B4. 规则集下载阻塞 Agent 控制循环与心跳

**位置**：`internal/agent/control/control.go`，`apply` 在接收消息的同一循环里同步执行；心跳也在这个循环里发送。

**问题**：首次下载 `geoip.dat`（约 20 MiB）或下载链路慢时，单个文件最长 3 分钟，期间不发心跳。面板 45 秒收不到心跳就把节点判为离线，可能连带影响发布状态。核心重启和健康检查同样在这个循环里，但通常只有几秒。

**方案**（先实测再决定是否改代码，Owner 2026-11-14 确认）：
1. 先实测：在测试机上用限速代理让下载持续约 90 秒，记录面板上节点状态与发布状态的变化。
2. 实测确实出现离线或发布异常，再修改：把 `PrepareRuleSets` 移到收到 `ApplyCommand` 之后、进入 `apply` 之前的独立 goroutine，下载期间循环照常发心跳；下载完成后再把应用排回循环。必须保持 v1.5.3 的顺序约束（应用结果先于新修订的流量与访问记录），新增一个时序测试锁住这一点。
3. 实测没有可见影响时，只在说明书第 17 节写明首次下载期间节点可能短暂显示离线，本项不改代码。

### B5. 新装 helper 第一次配置时不上报额外豁免能力

**位置**：`internal/agent/hostnet/hostnet.go` 的 `RunHelper`、`internal/agent/control/tuning.go` 的 `hostSourceExtraExemptSupported`。

**问题**：能力取决于 `status.json` 里有没有 `features`，而 helper 只有在执行过一份 desired 之后才写 `status.json`。新装节点第一次直接配置「单出站源 IP＋整机强制出站」时，面板以 `host_source_exempt_unsupported` 拒绝，并错误地提示升级 Agent。说明书第 23 节和运维手册把这一点记为待核实。

**方案**：没有 desired 文件时，`RunHelper` 也写一份 `status.json`：`ID` 为空，`OK` 为真，带当前 `Features`。安装器在安装或升级 helper 后启动一次 oneshot 单元，确保新装节点马上有这份回执。Agent 核对清除请求是否完成时按 ID 匹配，空 ID 不会被误认为某个请求的结果，实施时再核对一遍。

**验收**：`hostnet` 单元测试：没有 desired 时写出带 features、空 ID 的状态；Agent 据此上报能力，且不会把它当成任何请求的结果。`host-network` 部署测试覆盖首次安装后立刻存在回执。说明书第 23 节与运维手册删去对应的「待核实」。

### B6. 外部规则源修改后，旧抓取结果仍可回写

**位置**：`internal/panel/policy/external_sources.go` 的 `Refresh`。

**问题**：先读出来源的 URL、格式与行为，再联网抓取（最长 15 秒），回写时只按 ID 匹配。Owner 在抓取期间修改了 URL，旧响应仍会写进新来源的缓存与状态，并可能触发策略变化。

**方案**：三条 `UPDATE` 都加上 `AND url=? AND format=? AND behavior=?`（取开始时读到的值）。影响 0 行就丢弃结果，也不调用 `OnChange`。

**验收**：单元测试在抓取函数中途修改来源 URL，要求缓存、状态与计数都不被旧结果覆盖，也不触发变化回调。

### B7. 管理员登录、改密的并发窗口

**位置**：`internal/panel/auth/service.go` 的 `Login`、`ChangePassword`，`repository_sqlite.go` 的 `CreateSession`、`ChangePassword`。

**问题**：密码校验（哈希计算较慢）与写入之间没有条件约束。用旧密码的登录请求如果正好卡在改密之前完成校验，会在改密删除全部会话**之后**再创建新会话，旧密码因此仍留下一个有效会话；两个并发改密也可能互相覆盖。

**方案**：沿用门户的写法。`CreateSession` 改为 `INSERT ... SELECT ... FROM admins WHERE id=? AND password_hash=? AND status='active'`，传入校验时用的哈希，影响 0 行时返回凭据错误；`ChangePassword` 加 `AND password_hash=?`（取校验时的旧哈希），影响 0 行返回冲突。Owner 重置他人密码不需要旧密码，仍无条件写入，但同一事务里删除会话的行为不变。

**验收**：单元测试：校验通过后、建会话前插入改密，要求登录失败且不留会话；两个改密并发时只有一个成功。

### B8. SSE 事件不按角色过滤

**位置**：`internal/platform/events/events.go` 的 `Handler`。

**问题**：所有已登录管理员共用同一个事件出口。Viewer 能收到 `system.alert` 里的 `user_access`（用户名、用户 ID、原因）以及证书发布失败等 Owner 事件，与说明书第 6.2 节和通知接口给 Viewer 的范围不一致。没有凭据外泄。

**方案**：`Handler` 在请求开始时取得会话角色。对 Viewer 只放行节点状态、发布状态、总览统计，以及与通知接口相同的 4 类监控通知；其他 `system.alert` 不发送。15 秒的重新认证时同步刷新角色，Owner 降为 Viewer 时立即按 Viewer 过滤。

**验收**：单元测试分别以 Owner 和 Viewer 订阅，发布 `user_access` 与 `node_status`，Viewer 只收到后者。
