# v1.6.1 规划：以 v1.6.0 为最低版本精简代码

状态：已随 v1.6.1 发布（2026-11-18，tag → `306d393`，见[发布说明](release-notes-1.6.1.md)）。Owner 于 2026-11-17 决定把代码精简放进 v1.6.1，并同意以 v1.6.0 为最低升级来源。

## 1. 决定

| 项目 | 决定 |
| --- | --- |
| 面板升级来源 | 只接受 v1.6.0 或更新版本的数据库（完整记录 0001–0152）。更旧的数据库启动时报 `ErrPredatesBaseline`，`--check-database` 报 `outdated`，须先升到 v1.6.0 并启动一次 |
| 备份归档 | 只接受 v1.6.0 及以后的归档；旧归档在校验迁移时拒绝 |
| 迁移文件 | 0001–0152 合并为 `migrations/0152_baseline.sql`；旧文件名与校验和留在 `internal/platform/db/legacy.go` 供识别已升级的数据库，旧记录原样保留 |
| 一次性转换 | 0124 画布隧道认领、0131 画布转发转换、0147 导入身份转换、0150 残留清理的代码删除；0153 删除它们的标记与报告表（任一标记未完成时 0153 失败、数据库不变） |
| Agent | 本版不改 Agent 能力位门禁与单核心回退（见第 4 节） |

生产核实（2026-11-17，只读）：面板 1.6.0、迁移头 0152；0124／0131／0147／0150 的完成标记均为 1，0131 转换数量 0，迁移报告为空，`canvas_tunnel_objects` 为空。12 台节点在线，9 台 Agent 为 1.6.0，台湾 wap、日本 zouter、香港 阿里云*1 为 1.5.8。

## 2. 基线的生成与核对

基线由当时的 0001–0152 在空库上依次执行后导出：表、内置数据行、索引、视图、触发器按此顺序写出，内置数据里的生成时间改回 `strftime('now')`，四个一次性标记写为已完成（新库没有要转换的数据）。导出后在空库执行基线、再导出，与原导出逐字节一致，外键检查为空。

`internal/platform/db/migration_state.go` 统一判定 Migrate、`--check-database` 与备份校验：记录了全部 152 条旧迁移且校验和一致视为已在基线；只记录一部分为过旧；校验和不一致为外来或被改动的数据库。

## 3. 删除范围

- 迁移：152 个 SQL 文件及其逐个迁移测试（`migrations/*_test.go` 只留证书与身份恢复两项按最终表结构的检查和新的校验和测试）。
- 备份与恢复：约 40 处「归档是否已应用某迁移」的判断与旧结构分支（旧核心更新表结构、0128 前无 GOST 材料列、0143 前无原生来源列等），以及只为构造旧归档的测试与 rewind 辅助函数。
- 一次性转换：`ReconcileCanvasTunnels`、`ReconcileCanvasForwards`、`ReconcileRelayCleanup`、`ReconcileImportedIdentities` 及恢复时的导入身份重映射；隧道发布不再保留「首次无修改发布沿用旧物化形态」。
- 接口：`GET /api/v1/canvas-tunnels/legacy-objects`、`POST /api/v1/canvas-tunnels/{id}/adopt`、`POST /api/v1/canvas-tunnels/{id}/rotate-credentials`、`GET /api/v1/tunnels/migration-report`（前端未使用）。
- 策略模拟（Owner 2026-11-17 追加）：删除「分流控制 → 策略模拟」页面与菜单、节点策略页的入口、`POST /api/v1/policies/simulate`、面板端模拟实现与 `pkg/contracts/policy` 中只为模拟存在的匹配函数（`Matches`、`ScopeMatches`、`ValidateRequest`、`Simulate`）、前端客户端策略模拟运算及对应错误文案；节点策略的保存校验、展开与下发不变。
- Agent 签名发布目录（Owner 2026-11-17 追加）：「任务记录」页不再列出签名发布目录，删除手工登记接口 `POST /api/v1/releases`。面板只保留最新导入的 Agent 版本：升级对话框与 `GET /api/v1/agent-releases` 只给 GitHub 最新正式版，导入只接受它；导入成功后及面板启动时删除旧版本的清单与归档文件，以及没有任何升级任务引用的旧目录行（有任务引用的行保留供任务历史显示版本，未完成任务所需的文件保留）。Agent 本机的失败自动回滚不受影响。生产面板当前保存了 18 个版本、约 353 MB。
- Agent 降级（Owner 2026-11-17 追加）：`qui-update` 在目标版本（`--version` 或 GitHub 最新发布）低于已安装 Agent 时，于下载与停止服务前拒绝；组合主机省略 `--component` 时同样拒绝，只回退面板须加 `--component panel`；已安装版本读不出时不拒绝。失败提示不再给 Agent 的降级命令。删除只为降级存在的「目标 installer 不支持 v2 安装记录」检查，以及文档中「降级 Agent 到 1.3 以下前先移除 GOST」「降级旧 helper 前清除额外豁免」两条说明。升级失败时自动恢复原 Agent（Agent 本机与 `qui-update` 快照）不变；直接运行旧归档里的 `install.sh` 不经过此检查。
- 备份清单计数去掉 `relayCleanupReconcile`、`importIdentityMap`、`canvasForwardReconcile`、`tunnelMigrationReport`。

## 4. 不在本版

- Agent 能力位门禁（扩展策略、原生规则集、按出站源地址、域名关键字、证书文件、多核心等）与旧单核心上报的回退。生产 Agent 均已支持这些能力，但去掉门禁需要在握手时拒绝旧 Agent，且被拒绝的 Agent 无法再经网页升级；收益约几百行，留待生产 Agent 全部到 1.6.x 后单独评估。
- 旧画布 port_forward／GOST 连接的只读保留与删除路径，以及中转路径的合并。

## 5. 升级注意

1. 生产面板与数据库已在 1.6.0，可直接升到 1.6.1。0153 只删除标记表，不改业务数据。
2. 升级前照常保留更新器备份。降级回 1.6.0 时数据库已有 0153，需用更新前备份（与其他带迁移的版本相同）。
3. 1.6.0 之前做的备份在 1.6.1 上无法恢复；升级后先做一份新的加密备份并校验。
4. 那 3 台 1.5.8 的 Agent 不受本版影响，可照常连接与网页升级。

## 6. 验证

- 备份：用 v1.4 之前生成的真实旧归档（`internal/platform/server/testdata/prerefactor_backup.pcb`）确认恢复被拒绝。
- 发布前按发布流程跑本地完整门禁与 GitHub `check`（含 `migrations/**` 改动，须完整门禁）。
